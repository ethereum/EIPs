## Abstract

This EIP modifies the 'eth' p2p protocol to support the block-level dependency proofs of [EIP-8288](./eip-8288.md). It adds two new messages, `GetDependencyProofs` (0x19) and `DependencyProofs` (0x1a), enabling peers to request and serve proofs for synchronization.

## Motivation

[EIP-8288](./eip-8288.md) requires every block to carry a dependency proof, currently a recursive STARK, that proves the validity of all dependencies declared by its transactions. The proof is not part of the block header or the block body. The header carries only a 32-byte commitment to it, `dependency_proof_hash`, and the proof itself travels in the `ExecutionPayload`.

Because the proof is in neither the header nor the body, `GetBlockBodies` cannot serve it, and the Engine API payload body methods reach only the local consensus layer. A node that validates a block by re-execution must verify its proof, so a syncing node needs a way to obtain proofs from peers. This EIP adds that wire protocol support.

## Specification

### Block Header

[EIP-8288](./eip-8288.md) appends two fields to the block header. In `BlockHeaders` messages they are encoded after the last header field of the preceding fork:

```
block-header = [
    ...
    dependency-proof-hash: B_32,
    block-deps-hash: B_32,
]
```

The `dependency-proof-hash` field contains `keccak256(dependency-proof)` and the `block-deps-hash` field contains `get_deps_hash(dependencies(block))`. These fields MUST be present in headers after EIP-8288 activation and absent for earlier blocks.

### Dependency Proof Encoding

A dependency proof is transmitted as the serialized proof byte string defined in [EIP-8288](./eip-8288.md):

```
dependency-proof: B
```

A block without dependencies has an empty `dependency-proof`.

### New Protocol Messages

#### GetDependencyProofs (0x19)

```
[request-id: P, [blockhash₁: B_32, blockhash₂: B_32, ...]]
```

Request dependency proofs for the given block hashes. The number of proofs that can be requested in a single message is subject to implementation-defined limits.

Proofs are only available for blocks after [EIP-8288](./eip-8288.md) activation and within the retention period defined therein. Requests for unavailable proofs return empty entries.

#### DependencyProofs (0x1a)

```
[request-id: P, [dependency-proof₁, dependency-proof₂, ...]]
```

Response to `GetDependencyProofs`. Each element corresponds to a block hash from the request, in order. The RLP empty string (`0x80`) is returned for blocks where the proof is unavailable.

A block without dependencies has an empty proof, which also encodes as `0x80`. The receiver tells the two cases apart by the block header: `dependency-proof-hash` equals `keccak256` of the empty byte string only for a block without dependencies.

The recommended soft limit for `DependencyProofs` responses is 2 MiB.

### Validation

When a dependency proof is received, clients MUST validate it by computing `keccak256(dependency-proof)` and comparing against the `dependency-proof-hash` in the corresponding block header. An empty entry for a block whose `dependency-proof-hash` is not the hash of the empty byte string does not match, but it signals that the proof is unavailable, not that it is invalid. Clients MUST NOT treat such an entry as an invalid response and SHOULD request the proof from another peer. A non-empty entry that does not match the header is invalid. Verifying the proof against `block-deps-hash` is part of block validation under [EIP-8288](./eip-8288.md) and is not required at the wire protocol level.

## Rationale

### Separate Messages vs. Block Body Extension

Proofs are transmitted via dedicated messages rather than extending block bodies because:

1. **Size**: A dependency proof is hundreds of kilobytes. Block bodies already grow with the gas limit, and keeping the proof out of them keeps `BlockBodies` responses and the RLP block size independent of proof size.
2. **Optional retrieval**: A node that trusts finality for a block does not need its proof. It can sync headers and bodies for finalized blocks without downloading proofs.
3. **Retention policy**: Proofs may be pruned per [EIP-8288](./eip-8288.md), while block bodies are retained longer.

This follows the same split as block access lists, which are also served by their own messages rather than through block bodies.

### Message IDs

`eth/74` extends `eth/73` of [EIP-8408](./eip-8408.md), which keeps the `GetCells` (0x14) and `Cells` (0x15) message IDs. Message IDs 0x19 and 0x1a leave 0x16 through 0x18 to other messages proposed to activate at the same fork.

### Response Size Limit

The 2 MiB soft limit is consistent with other eth protocol responses (blocks, receipts, headers) and accommodates several proofs per response. Responses containing a single proof that exceeds 2 MiB are still valid, as the soft limit governs when to stop appending additional items, not the maximum size of an individual item.

## Backwards Compatibility

This EIP changes the eth protocol and requires rolling out a new version, `eth/74`, which activates with [EIP-8288](./eip-8288.md). Other messages proposed for the same fork share this version rather than each introducing one, and the message IDs here are chosen not to overlap with them. Supporting multiple protocol versions is standard practice. Rolling out `eth/74` does not break older clients, as they can continue using earlier versions.

This EIP requires the hard fork that activates [EIP-8288](./eip-8288.md) for the header field extension. The new messages are only meaningful for blocks after that fork.

## Security Considerations

### Validation Cost

Validating a received proof against the header requires one keccak256 over a few hundred kilobytes, which is negligible. Verifying the proof against `block-deps-hash` is more expensive and is governed by the block validity rules of [EIP-8288](./eip-8288.md), not by this protocol.

### Amplification

A `GetDependencyProofs` request can trigger responses much larger than the request, since each requested hash can return a proof of hundreds of kilobytes. Implementations SHOULD apply rate limiting and respect the soft response size limit to prevent amplification attacks.

### Unavailable Data

Clients MUST handle empty responses gracefully. A peer returning empty entries for available blocks may be misbehaving but could also have pruned the data legitimately.
