## Abstract

Introduce a new instruction that allows smart contracts to create (and update) delegation accounts that match [EIP-7702](./eip-7702.md)'s design. These accounts can be used similarly to [ERC-1167](./eip-1167.md) clones, with significant advantages. The instruction may also append a caller-supplied byte string after the designator, so that each account can carry its own configuration in code. Code written this way resolves as an ordinary EIP-7702 delegation; the trailing data is visible to code introspection but invisible to the delegation resolver.

## Motivation

Many on-chain applications involve creating multiple instances of the same code at different locations. Account abstraction solutions depend heavily on this pattern to deploy smart account instances.

These applications often rely on clones, or proxies, to reduce deployment costs. Clones, such as those described in ERC-1167, are minimal pieces of code that contain the target address directly in the bytecode. That makes them extremely lightweight but prevents any form of reconfiguration (upgradability). Upgradeable proxies differ from clones in that they read the implementation's address from storage. This makes them more versatile but also more expensive to use.

a critical  downsides: calldata must be copied to memory before performing the delegate call.

EIP-7702 introduces a new type of object with the expected behavior: the delegation indicator. These objects are designed to be instantiated at EOA addresses, but the same behavior can be reused to implement clones at the protocol level. Using delegation indicators for this use case provides upgradeability without the need for storage lookups, provided the contract calling `SETDELEGATE` allows it.

Studies by the Geth team (see "Not all state is equal" from EthCC[9]) have shown that 97.1% of the ~50 million contracts deployed correspond to code that has been deployed more than once, and that 28.6% of the unique bytecodes are tiny (under 1 KiB). Clones and proxies probably account for a large fraction of these contracts. Having a technical solution to use delegation indicators for these contracts would positively impact both the users (through reduced interaction cost) and the network's sustainability (through reduced state growth).

The use cases for this new deployment method include the "traditional" family of smart contract accounts used by wallets such as Safe, [ERC-4337](./eip-4337.md)-compliant smart accounts (that need upgradeability to stay up to date with new versions of the entrypoint), and all the new deployments implicitly required by proposals such as [EIP-8141](./eip-8141.md) in our path toward quantum-resistant accounts.

### Account Abstraction

Smart accounts (contracts that are "owned" by one or multiple keys and are intended to replace EOAs) are often deployed using clones or proxies that point to a singleton implementation. This forces a choice between an upgradeable or a non-upgradeable design. Both designs come with downsides. Non-upgradeable designs can leave you stranded with buggy (or limited) account code. Upgradeable designs incur costs associated with fetching the implementation address from storage.

The `SETDELEGATE` instruction would enable new factories to implement an upgradeable design without the added cost of the lookup. Factories could also deploy non-upgradeable variants, or even selectively disable the upgradeability of some accounts. Both the upgrade mechanism and the selective locking would be handled at the factory level, which removes the burden of implementing the upgrade logic in the account itself.

Additionally, using EIP-7702 delegations instead of clones/proxies moves the call redirection logic from userspace to the protocol. This means fewer EVM operations and thus reduced gas consumption for every operation that calls these contracts. This includes the verification of signatures and the execution of user operations, but also transfers of assets that include a callback, such as [ERC-721](./eip-721.md) and [ERC-1155](./eip-1155.md) tokens.

### Scalability

Clone and proxy contracts are present in large numbers in the blockchain state. OpenZeppelin's [ERC-1967](./eip-1967.md) proxies are ~708 bytes. Using EIP-7702 delegations that are only 23 bytes would significantly reduce blockchain state usage.

Additionally, clone and proxy contracts handle call redirection in userspace, which incurs execution cost. Using EIP-7702 delegations moves the redirection to the protocol level, reducing the gas cost of all operations targeting these accounts. This means more gas/blockspace is available for the actual execution of the contracts.

### Per-account configuration

A delegation alone makes every account of a given type byte-for-byte identical. Anything that distinguishes one account from another, such as an owner set or a public key, must then live in a per-account satellite contract or a storage slot, which reintroduces the lookup that the delegation removed.

The trailing data segment closes that gap. Per-instance configuration rides in the account's own code, is readable by the delegated code through
`EXTCODECOPY(ADDRESS)` against an account that is already warm, and is available on the account's first call without a separate state object. One audited implementation can then serve an unbounded population of accounts, each contributing only its designator and its own configuration bytes to the state.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)
and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

A new instruction (`SETDELEGATE`) is added at `0xf6`. It takes four stack operands and produces one:

```
SETDELEGATE
  stack input (top first):  salt, target, data_offset, data_len
  stack output:             location
```

### Behavior

Executing this instruction does the following:

1. Deduct `EMPTY_ACCOUNT_COST` gas.
2. Halt if the current frame is in `static-mode`.
3. Pop `salt`, `target`, `data_offset`, and `data_len` from the operand stack.
4. Halt if `data_len` is greater than `MAX_DATA_LEN`
5. Charge gas for memory expansion gas for the region `[data_offset, data_offset + data_len)` as for any memory read
6. Charge gas for code data costs of `DATA_WORD_COST * ceil(data_len / 32)`.
7. Calculate `location` as `keccak256(DESIGNATOR ++ address ++ salt)[12:]`.
8. Add `location` to `accessed_addresses`, as defined in [EIP-2929](./eip-2929.md).
9. Halt if the code at `location` is not empty and does not start with b`DESIGNATOR`.
10. Add `EMPTY_ACCOUNT_COST - BASE_COST` gas to the global refund counter if `location` exists in the trie.
11. Set the code of `location` to either `DESIGNATOR ++ target ++ data` or empty, matching the delegation process defined in EIP-7702,
    - `data` is `memory[data_offset : data_offset + data_len]`
    - If `data_len` is 0, the code written is exactly `DESIGNATOR ++ target`.
    - Similarly to EIP-7702, if `target` is `0x0` (regardless of `data_len`), do not write the designation. Instead, clear the code at `location` and reset the `location`'s code hash to the empty hash `0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`.
12. If the nonce of the account at `location` is 0, increment it to 1
13. push `location` onto the stack

In step 11, `target` MUST be exactly 20 bytes. If the value retrieved from the stack is smaller than 20 bytes, it MUST be left-padded (big-endian notation) with zeros. If it is larger than 20 bytes, the highest-order bytes MUST be trimmed. The code placed at `location` MUST be exactly 23 + data_len bytes long.

The write is not conditioned on the previous contents of `location` beyond the step 9 check: a designator MAY be replaced by a designator with a different target, different trailing data, or both. Code that is not a designator is never overwritten.

Note: The delegation is effective immediately upon completion of the operation. Calls to the address starting from the very next operation will execute the newly delegated code.

The delegation indicators created by the `SETDELEGATE` opcode are the same objects as those created using EIP-7702. Therefore, all behavioral specifics documented in EIP-7702 (`CODESIZE`, `CODECOPY`, targeting precompiles, and chaining delegation indicators) also apply here. Any future EIP that modifies the behavior of EIP-7702 delegation indicators should also apply to those created using `SETDELEGATE`. They are not contracts and cannot be deleted using `SELFDESTRUCT`, even if `SELFDESTRUCT` occurs in the same transaction that created the account at `location`. Destruction of delegations SHOULD only be possible by the same caller (that created them) performing a new `SETDELEGATE` call with the same salt and a zero target.

Step 12 ensures that an account created using `SETDELEGATE` never returns to an empty state (as forbidden by [EIP-7523](./eip-7523.md)). Even if the balance is zero, no state was ever set, and the code is removed by a `SETDELEGATE` operation with a zero target, the nonce being at least one guarantees the account is not considered empty.

Delegated code reads its account's trailing data from `code[23:]` using `EXTCODECOPY(ADDRESS, …)` with length `EXTCODESIZE(ADDRESS) - 23`. It MUST use the `EXTCODE*` family against `ADDRESS` rather than `CODESIZE` and `CODECOPY`: during delegated execution the plain `CODE*` instructions observe the executing target's own code, so they see neither the designator nor the trailing data.

### Parameters

The first three parameters are the same ones used in EIP-7702.

| Constant             | Value    |
| -------------------- | -------- |
| `DESIGNATOR`         | 0xef0100 |
| `EMPTY_ACCOUNT_COST` | 25000    |
| `BASE_COST`          | 12500    |
| `DATA_WORD_COST`     | 3        |
| `MAX_DATA_LEN`       | 65516    |

## Rationale

### Gas Cost

The execution of the `SETDELEGATE` instruction involves fewer moving pieces than what EIP-7702 gas costs account for:

- There is no signature recovery.
- There is no dedicated calldata that must be accounted for beyond what is already paid at the transaction level.
- There is no nonce update (aside from the initial set to 1 in step 9).

Therefore, the cost of executing this instruction could be lower than that of EIP-7702. The values from EIP-7702 are reused here for simplicity. They are lower than the costs of `CREATE` or `CREATE2` operations, making this instruction competitive for the intended use cases.

### Address Derivation

The `location` is derived from `keccak256(DESIGNATOR ++ address ++ salt)`, using the caller's address and a caller-chosen salt. This mirrors the deterministic addressing of `CREATE2` while using a distinct pre-image length (55 bytes) to avoid collisions with existing address derivation schemes (see Backwards Compatibility).

`DATA_WORD_COST` prices the trailing bytes as persistent state, so that storing configuration in code is never cheaper than the state it occupies.
`MAX_DATA_LEN` bounds the trailing payload against state-bloat griefing and should be reconciled with the deployed code size regime of the target chain.

### Excluding `target` and `data` from the address preimage

The location derives from the executing account and `salt` only, not from `target` or `data`. A caller that wants the address to commit to a particular configuration folds that value into the salt, for example `salt = keccak256(pubkey)`. Because the address does not otherwise depend on the target or the data, the same account can be given a different target, different trailing data, or both, at the same address. That is what makes stable-address reconfiguration possible, such as rotating a stored key or repointing to a new implementation without changing the account's identity.

Including the target or the data in the preimage would make the address a commitment to the exact configuration, but would force any reconfiguration to change the address, defeating a stable account identity. Callers who want configuration-bound addresses retain that option through the salt.

### Target and data layout

`target` is taken from the stack the way every other address operand is, keeping the low 20 bytes and discarding anything above them. Halting on a non-zero high word was considered, on the grounds that a dirty word is never intended, but it would make `SETDELEGATE` the only instruction that treats a stack address more strictly than `CALL` and its siblings do, and callers already assemble addresses knowing the convention.

The data follows the target immediately, with no padding between them. Reserving space for a wider target was also considered and rejected: it would cost 12 bytes of state in every account carrying data, to hold a value that is zero in all of them, hedging a change that may never come.

Because a designator with no trailing data remains exactly 23 bytes, it stays byte-for-byte identical to one written by an EIP-7702 authorization.

### Refusing to overwrite non-designator code

Step 9 halts when `location` already holds code that does not begin with `DESIGNATOR`. The check draws the line between the two things a caller might be doing. Replacing a designator is reconfiguration, and is the point of the instruction. Replacing anything else means the caller has landed on an account that is not one of its delegations, and there is no case in which continuing is what the caller wanted.

Nothing in the address derivation makes that situation impossible. `location` derives from the executing account and a caller-chosen salt, so a factory computing a salt from untrusted input can be steered onto an address that already holds ordinary contract code, and an address can receive code by other means before the factory reaches it. Without the check, `SETDELEGATE` would silently convert that account into a delegation, discarding its code while leaving its balance, nonce, and storage in place. Halting keeps the instruction unable to destroy anything a caller did not create as a designator, at the cost of one comparison that a correct factory never triggers.

The check also costs rotation nothing, because it admits designator-to-designator writes. Requiring `location` to be *empty* would be the restrictive alternative, and it is the one this EIP rejects, for the reasons in the next section.

### Replacing an existing designator

A designator may be replaced by another one, and reconfiguration depends on it. Since the address is independent of the data, re-executing `SETDELEGATE` from the same account with the same salt and new trailing data replaces the stored configuration at the same address. If the write were gated on emptiness, an account could be configured exactly once and could never rotate its key without changing identity.

Authority is bounded by who can execute the instruction, since `location` derives from the executing account's address. No account can rewrite another account's designator.

Immutability is therefore a userspace policy rather than a protocol guarantee, as it already is for the factories that deploy clones and proxies. A factory that wants write-once behavior checks that `EXTCODESIZE(location)` is zero before calling `SETDELEGATE`; delegated code that wants controlled rotation gates any subsequent `SETDELEGATE` behind its own signature check and nonce. Leaving the policy in userspace keeps the instruction minimal and avoids needing two opcodes for write-once and rotatable accounts.

### Keys in the account

The motivating application for trailing data is a post-quantum account authenticator.

[EIP-8141](./eip-8141.md) lets an account define its own signature scheme. The account address is stated explicitly in the transaction rather than derived from a public key, so the key need not be recovered from a signature and need not travel on the wire. This inverts the economics of signature schemes with large public keys: the key can live in the account, and only the signature is transmitted per transaction.

Trailing data is the natural place to put that key. A single verification contract is deployed once, and each account is a delegation to it carrying its own public key after the designator:

```
account code:  0xef0100     ++ AUTH ++ pubkey
               └ designator ┘└  20  ┘└ per-account public key ┘
```

The shared verifier, executing in the account's context, reads the key from `code[23:]` and verifies against it. Every account delegating to that verifier is distinguished only by its trailing key, with no per-account contract deployed and no storage slot initialized. This is cheaper than either alternative, a per-account satellite contract or a cold `SLOAD` on every verification, and the key is available on the account's first use.

The sizes involved make the case concrete. An ML-DSA public key of 1312 to 2592 bytes, depending on parameter set, is stored once as trailing data while each transaction carries only the signature. For a scheme whose signatures are smaller still, the per-transaction footprint of a post-quantum account approaches that of an ECDSA account today: the large object is paid for once at setup and lives in code rather than on the wire.

## Backwards Compatibility

### Address Collision

The derivation of `location` is designed not to conflict with contracts created using the `CREATE` or `CREATE2` opcodes. In particular, the pre-images used to hash the produced address have different lengths, preventing any collision.

Contracts deployed using `CREATE2` have an address derived from an 85-byte pre-image, as opposed to 55 bytes for `SETDELEGATE`. This difference alone eliminates the risk of pre-image collision.

Contracts deployed using `CREATE` have an address derived from `RLP([address, nonce])`. For this pre-image to have a length of 55 bytes (matching `SETDELEGATE`), the `nonce` would need to be 32 bytes long. In that case, the RLP encoding would be `0xf694<address>a0<nonce>`, which does not start with the `0xef0100` designator used by `SETDELEGATE`. A smaller nonce could lead to a pre-image starting with `0xef`, but then the pre-image would be shorter than 55 bytes. Even in that case, the pre-image would start with `0xef94` (where `0x94` encodes the 20-byte `address` object), which still differs from the `SETDELEGATE` pre-image prefix.

## Reference Implementation

Two assembly contracts demonstrate the write and read halves of the account model described above. Both are written for the Good Ethereum Assembler and assemble to runtime bytecode. `SETDELEGATE` and the EIP-8141 instructions they use have no assigned opcodes, so those are emitted as raw bytes with placeholder values; the output documents intent and is executable only on an EVM extended to recognize them.

[`ImmutableSetDelegateFactory.eas`](../assets/eip-7819/ImmutableSetDelegateFactory.eas) is the write side. Given an ML-DSA public key as calldata, it computes `salt = keccak256(pubkey)` and executes `SETDELEGATE(salt, AUTH, dataOffset, dataLen)`, so the created account's code is `DESIGNATOR ++ AUTH ++ pubkey` at `keccak256(DESIGNATOR ++ factory ++ salt)[12:]`. Deriving the salt from the key makes the key the source of the address: one key yields one address, computable off-chain before the account exists. The factory also shows how a caller enforces immutability in userspace, deriving `location` itself and refusing to proceed unless `EXTCODESIZE(location)` is zero, so it can never re-point an account it already created.

[`MLDSAAuth.eas`](../assets/eip-7819/MLDSAAuth.eas) is the read side, and is the delegation target such accounts point at. Running in the account's context, it recovers the account's own public key from `code[23:]` using `EXTCODECOPY(ADDRESS)`, selects an ML-DSA parameter set from the key length, and verifies a signature over the frame hash via a hypothetical set of precompiles. It is the worked example of the self-read rule in the Specification: the plain `CODE*` instructions would return this verifier's own bytecode, so only the `EXTCODE*` family against `ADDRESS` reaches the designator and the trailing data.

Together they cover the round trip this EIP introduces, and demonstrate that trailing data is reachable by the delegated code while remaining invisible to delegation resolution.

## Security Considerations

### Delegator Upgrades and Deletion

Reusing EIP-7702 behavior, including clearing the code when the target is `0x0`, enables the ability to upgrade or even remove the created delegation indicator. This process is controlled (and can be restricted) by the factory contract that calls `SETDELEGATE`. Some factories will add checks that prevent re-executing `SETDELEGATE` with a salt that was already used, making the created delegation indicator immutable. Others may allow access-restricted upgrades but prevent deletion. In any case, guarantees about the lifecycle of delegation indicators created using `SETDELEGATE` are provided by the contracts that call it, not by the protocol itself.

Assuming immutability without such a guard is a security error.

### Delegator Chaining

As documented in EIP-7702, designation chains or loops are not resolved. This means that, unlike clones, chaining is an issue. However, this is something developers are accustomed to, as chaining proxies can result in unexpected behaviors, including infinite delegation loops.

Factories may want to protect against this risk by verifying that the `target` does not itself contain a delegation indicator.

### Front-Running Initialization

Unlike EIP-7702 signatures, which can be included in any transaction and can thus lead to initialization front-running if the implementation doesn't verify the authenticity of the initialization parameters, `SETDELEGATE` is executed by a smart contract that can perform the initialization logic atomically, immediately after the delegation is created. This process is well understood by developers who already initialize clones and proxies just after creation.

### Multiple Delegation Changes Within a Single Transaction

If a contract performs multiple `SETDELEGATE` operations with the same salt but different targets within the same transaction, while also making calls to the corresponding address, this would result in—within a single transaction without reverts—an address that has multiple different code values associated with it, two or more of which are executed. This includes the delegation being removed or reset any number of times during the transaction.

This behavior is already possible with more traditional upgradeable contracts, where the implementation target changes as a result of modifying a specific storage slot.

### Trailing data is public

Trailing data is account code and is world-readable. Secrets such as private keys or seeds MUST NOT be stored in it. Public keys are appropriate.

The address does not authenticate the trailing data. Any party able to execute
`SETDELEGATE` from the creating account can change it. Binding a configuration to an address is the caller's responsibility, through the salt; authorizing changes to trailing data is the delegated code's responsibility.

### State growth

`DATA_WORD_COST` and `MAX_DATA_LEN` bound the cost and size of trailing data so that it cannot be used to grow state more cheaply than ordinary state growth.

### Static mode

`SETDELEGATE` modifies state and MUST fail inside a static call, consistent with
`CREATE` and `SSTORE`.
