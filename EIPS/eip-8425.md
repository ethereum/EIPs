## Abstract

Before the freeze, owners can migrate to quantum-resistant wallet code at the same address through [EIP-8298](./eip-8298.md). The freeze rejects transactions carrying protocol-validated secp256k1 signatures and removes the `ecRecover` precompile. An owner who missed migration can install successor code at the same address with a hash-based zero-knowledge proof of the wallet seed.

## Motivation

A practical quantum break of secp256k1 could expose unmigrated accounts. Specifying a response in advance lets clients and wallets implement, test and audit it before an emergency, reducing coordination under time pressure. Whether to activate this response, when to do so, or whether to choose another course remains a separate decision.

## Specification

### Parameters

| Parameter | Value | Meaning |
| --- | --- | --- |
| `QUANTUM_FREEZE_TIME` | TBD | Activation timestamp (Unix seconds) |
| `RECOVER` | `0x07` | Recovery frame mode |
| `SEED_PROOF_GAS` | 2000000 | Execution gas per proof verification attempt |

The network may schedule the timestamp in advance or coordinate an earlier one in an emergency. Nodes must agree on it before activation.

### Freeze

For blocks with `block.timestamp >= QUANTUM_FREEZE_TIME`, reject before execution any transaction containing a protocol-validated secp256k1 ECDSA signature. This applies to transactions with a secp256k1 sender signature (including [EIP-7702](./eip-7702.md) transactions) and to [EIP-8141](./eip-8141.md) transactions whose `signatures` list contains a `SECP256K1` entry. Existing delegations remain callable.

Remove the `ecRecover` precompile at `0x0000000000000000000000000000000000000001` and its automatic [EIP-2929](./eip-2929.md) prewarming. Preserve the account state. Ordinary account and gas rules apply to all call types. Successful calls to the empty code return empty data. A successful `CALL` transfers forwarded value, and a revert rolls back that transfer.

### Mnemonic recovery

The wallet locally derives the 64-byte [BIP-39](https://github.com/bitcoin/bips/blob/0d99ffd39fdaf75209c43b1f8ec3fbbc23f10814/bip-0039.mediawiki) seed using PBKDF2-HMAC-SHA512 (2048 iterations). Use the mnemonic as the password and `"mnemonic" + passphrase` as the salt, normalizing each string to NFKD before encoding it in UTF-8. The default passphrase is empty. A backup of the seed bytes grants the same authority.

#### Submission and execution

From the freeze timestamp, an EIP-8141 transaction may include `RECOVER` only as its last frame, outside any atomic batch, with an explicit 20-byte target, zero flags and zero value. Its data is exactly 222,760 bytes, comprising a 92-byte header with a big-endian uint64 nonce followed by the proof.

```text
be8(nonce) || source || code_hash || tag || proof
```

Violating these constraints invalidates the transaction. A sponsor may approve payment in an earlier frame and pays ordinary frame-data charges. The target needs neither a signature nor ETH.

Charge and warm the target at frame entry under EIP-8141. Record each charged target or source access in the block-level access list even if the frame later reverts. Dispatch directly even for a delegated target. Use live account state after any earlier frame or batch rollback.

Use EIP-8298's definition of a system contract and its `SETCODEFROM` rules for source eligibility, adoption costs and code-hash recording.

1. Require prior payment approval and the target's current nonce to equal `nonce`. Its own code must be empty or exactly `0xef0100` followed by a 20-byte address. An absent target has nonce zero and empty code. Reject precompiles, system contracts and targets created by contract creation in this transaction.
2. Charge for source access and validation, then warm the source. Require an eligible source whose current `codeHash` equals `code_hash`.
3. Charge `SEED_PROOF_GAS` before decoding the proof or reconstructing the journal. Verify the [proof](#proof-system) against the [expected journal](#proof-statement).
4. Charge the remaining current-account and write costs. Charge EIP-8141 account-creation state gas if the target has zero nonce, zero balance and empty code. Install the authorized code hash and record the change. Preserve target nonce, balance and storage. Return success with empty logs, without executing wallet code.

A failed execution check reverts the frame. Insufficient gas causes an exceptional halt. EIP-8141 frame charging and rollback apply, including rollback of address warmth.

#### Proof statement

Use [BIP-32](https://github.com/bitcoin/bips/blob/0d99ffd39fdaf75209c43b1f8ec3fbbc23f10814/bip-0032.mediawiki) private derivation along `m/44'/60'/a'/c/i`, with unsigned `a, i < 2**31` and `c` equal to 0 or 1. Use compressed SEC1 public keys for non-hardened steps. Reject an invalid master key or child at the specified index. For the resulting secp256k1 point `(x, y)`, derive `account = keccak256(be32(x) || be32(y))[12:]`.

`beN` encodes an unsigned integer in exactly `N` big-endian bytes. Addresses are 20 bytes, hashes are 32 bytes, and the domain string is ASCII. The guest reads the 168-byte witness with `a` encoded before hardening.

```text
witness = seed || be4(a) || be4(c) || be4(i) || be32(chain_id) || be8(nonce) || source || code_hash
intent  = "EIP-8425/recover/v1" || be32(chain_id) || account || be8(nonce) || source || code_hash
tag     = HMAC-SHA-256(key=seed, message=intent)
public_input_hash = keccak256(intent || tag)
journal = account || tag || public_input_hash
```

Only the 84-byte journal is public output. The verifier reconstructs it using the current chain ID, the frame target as `account`, and the header fields, including the supplied `tag`.

#### Proof system

The frame carries a native RISC Zero zkVM 3.1.0 succinct STARK for the [recovery guest](../assets/eip-8425/zk/guest/src/main.rs). The [verifier](../assets/eip-8425/zk/host/src/lib.rs) with its [locked dependencies](../assets/eip-8425/zk/host/Cargo.lock) defines transcript verification for these parameters.

| Parameter | Value |
| --- | --- |
| Guest image ID | `b226389c8a52e7ed9f679f2960a03b863e288eb20220f3854929e6015642573d` |
| Inner recursion control root | `e6feef13db7aed4a731c7b0852de1f5c89b137726073f625d05333184d3a551d` |
| Allowed outer control IDs | [Outer control ID list](../assets/eip-8425/zk/allowed-control-ids.hex) |
| Proof system and recursion circuit | `RISC0_STARK:v1__` and `RECURSION:rev1v1` |
| Hash suite and base field | Poseidon2 over Baby Bear, `p = 15 * 2**27 + 1` |
| Trace length, FRI expansion and queries | `2**18`, 4 and 50 |

1. Decode exactly 55,667 little-endian uint32 words (222,668 bytes). Require every word to be below `p` and raw word 32 to equal 18 (zero-based).
2. Compute the receipt claim digest below for a successful halt with no unresolved assumptions. Convert words 0–31 from Montgomery form. Words 0–15 must match the inner root's eight little-endian uint32 words, each followed by zero. Words 16–31 must match the claim digest's sixteen little-endian uint16 limbs.
3. Verify the complete STARK transcript with the pinned recursion circuit and hash suite. Require its reconstructed code Merkle root to be an allowed outer control ID. Reject any failure or trailing data.

For `ReceiptClaim::ok(image_id, journal)`, let `H` be SHA-256 and `Z` be 32 zero bytes. To compute `T(label, children, words)`, hash the concatenation of `H(ASCII(label))`, the 32-byte child digests in order, the words as little-endian uint32s and the child count as a little-endian uint16. Use raw digest bytes throughout.

```text
post   = T("risc0.SystemState",  [Z],                         [0])
output = T("risc0.Output",       [H(journal), Z],             [])
claim  = T("risc0.ReceiptClaim", [Z, image_id, post, output], [0, 0])
```

The list contains one 32-byte outer control ID per line. Hex-decode the 27 lines and concatenate them in file order. The SHA-256 digest of these 864 bytes is `c4f876ad6fbc09316f20dee62e51b33bb98097489b2194738987dd50cc1a5c56`.

## Rationale

The freeze covers EIP-8141 signers because wallets and sponsors can authorize actions from `SIGPARAM` independently of the transaction sender.

Starting from the seed supports all BIP-39 word lists and passphrases with one circuit. The journal binds the request. Authorizing a new request under the same seed requires a fresh HMAC even after the first proof becomes public.

RISC Zero's hash-based STARK targets post-quantum soundness and seed privacy through zero knowledge, and requires no trusted setup. Rust lets implementers iterate on the guest during drafting. This specification fixes the proof system and its parameters. Changes before activation should be justified by independent cryptographic audits or cross-client benchmarks.

At the [EIP-7904](./eip-7904.md) benchmark target of 100 million gas per second, `SEED_PROOF_GAS` (2,000,000 gas) corresponds to 20 ms per verification. On an Apple M2 Max, the reference verifier (Rust 1.96.0, release build) checked the public test proof 101 times serially in one process after 10 warm-up checks. With the inputs in memory, the median was 11.66 ms (95th percentile 11.97 ms, maximum 12.31 ms).

This estimate assumes serial verification. Clients can use idle CPU cores to verify proofs from different transactions in parallel because the verifier reads only the public request and proof. Eligibility checks, gas charges and state updates still follow transaction order.

EIP-8141 counts each frame-data byte as four floor tokens at 16 gas each. Recovery data contributes exactly 14,256,640 gas. Both the full floor and intrinsic gas plus declared execution limits must fit the 16,777,216 execution-gas cap. State gas is budgeted separately.

## Backwards Compatibility

Activation requires a hard fork, quantum-resistant transaction submission and wallet support. Transactions signed before the freeze face the same checks at inclusion. Contracts relying on `ecRecover` must handle empty return data.

## Security Considerations

### Recovery authority

Anyone with the seed can recover a delegated account even after wallet key rotation. Installing regular code ends seed recovery, including when a compromised signer migrates first. Owners with only a raw private key or an unsupported derivation path must migrate before the freeze.

The [recovery proof](#proof-statement) uses the canonical [BIP-44](https://github.com/bitcoin/bips/blob/0d99ffd39fdaf75209c43b1f8ec3fbbc23f10814/bip-0044.mediawiki) hierarchy for Ethereum (`m/44'/60'/a'/c/i`). Paths outside this hierarchy include the legacy Ledger path used with MyEtherWallet (`m/44'/60'/0'/i`) and the three-level path accepted by Trezor firmware (`m/44'/60'/a'`). Further research into wallet usage and community discussion should inform which additional paths, if any, to support.

The recovered wallet uses the source's runtime code and the target's existing storage. Since installation is the last frame and executes no wallet code, any later initializer must authenticate the owner against a key or commitment already bound to the code or target storage. Letting the first caller set the owner exposes the account to takeover.

For example, to recover an EOA `A` with empty storage, the owner generates an ML-DSA key pair and deploys wallet code with the hash of the new public key `pk` embedded in its runtime code. The owner's seed proof authorizes the source address and code hash. A sponsor submits `RECOVER` to install that code at `A`.

- Owner key fixed in code. From the first operation after recovery, the wallet checks `keccak256(pk)` against the embedded hash and verifies the signature under `pk` over the operation, chain ID, `A` and a replay nonce. This wallet needs no initializer.
- Owner key in storage. The wallet keeps spending disabled until a one-time `initialize(pk, sig)` call succeeds at `A` in a later transaction. Anyone can relay the call. The wallet checks `keccak256(pk)` against the embedded hash and verifies `sig` under `pk` over an initialization message binding the chain ID and `A`. It then stores `pk` as the initial owner key and enables spending.

A hardware wallet may lack an on-device prover. If it supports pre-freeze migration, the seed can stay on-device. Importing the seed into a separate prover, even offline, exposes every derived account to that host. Keep secrets out of logs, crash dumps and automatic backups. Give the sponsor only the public request and proof.

The proof leaves the sender and payer unbound so an owner can change sponsors. A copied recovery frame can install the same authorized code first. If the original transaction is also included, its recovery reverts before proof verification and its payer still pays at least the calldata floor. For a zero-value `VERIFY` + `RECOVER` transaction, the floor is 14,269,590 gas before sponsor data and signature charges. Private submission can reduce this exposure.

### Cryptographic assumptions

Any seed deriving the 160-bit address satisfies the proof. Generic quantum preimage search costs about `2**80` evaluations in the idealized query model. The mnemonic and passphrase may have less entropy. The public tag permits testing a candidate seed without its path.

The backend's 50-query FRI profile has a conjectured 97-bit security target. A quantum knowledge-soundness bound for the full protocol remains open. The guest, recursion verifier, Fiat-Shamir and FRI assumptions and zero-knowledge implementation require independent review. The gas charge is provisional pending cross-client benchmarks.

### Availability of recovery software

Before mainnet activation, multiple independent operators should each retain and publish a complete copy of the offline build archive and its SHA-256 manifest. Include the guest and verifier sources, their lockfiles and vendored dependencies, the base image, the pinned toolchains and build tools, offline build instructions, and the guest ELF. Verify that an independent offline rebuild from this archive reproduces both the published ELF SHA-256 digest and the specified guest image ID.

### Other authorization paths

The freeze preserves the [EIP-7951](./eip-7951.md) `P256VERIFY` precompile where active and the EIP-8141 `P256` rules. P-256 alone remains vulnerable to quantum forgery. A wallet can require both a P-256 signature and an independent ML-DSA signature for the same operation.

Users may be unable to withdraw assets if the only withdrawal path relies on `ecRecover`.

Empty return data leaves the caller's output memory unchanged. Contracts that check only call success or read output without validating its length may therefore still accept unauthorized calls. Removing the precompile does not protect contracts that implement ECDSA verification independently.
