## Abstract

This EIP introduces `SETCODEFROM`, an EVM instruction that sets the current account's code hash to the code hash of a source account with existing deployed code. The change takes effect when the account's outermost execution frame ends successfully, and the new code is visible to code execution from then on. An account that already holds regular deployed code can adopt only from its own code.

## Motivation

This EIP has two primary use cases.

First, it improves code reuse and deployment economics. Deploying many contracts with identical runtime code is expensive, especially when contract deployment is repriced more closely to state growth, for example under [EIP-8037](./eip-8037.md). Initcode can initialize per-instance storage and then adopt shared deployed code, without paying code-deposit gas for identical runtime code. A contract whose own code contains `SETCODEFROM` can also adopt a new shared implementation later.

Second, it provides an account migration path for disabling ECDSA-based EOA transaction authority. Migration code can store account-specific wallet state, including post-quantum (PQ) wallet state, then adopt regular wallet code. After that update, account control is through the installed wallet code rather than ECDSA transaction origination. This is because the account now has regular deployed code, not an [EIP-7702](./eip-7702.md) delegation indicator, so ECDSA-authenticated transactions remain invalid under [EIP-3607](./eip-3607.md). [EIP-7702](./eip-7702.md) authorization processing can no longer redelegate the account because the authority code check only accepts empty code or an existing delegation indicator. The account can still upgrade through upgrade logic in the installed code, for example by executing `SETCODEFROM` again from that code or by using other methods. Protocol-level ECDSA transaction origination remains permanently disabled.

`SETCODEFROM` provides the code-adoption step for both cases after any per-instance state has been initialized.

## Specification

### Parameters

The opcode is defined as follows:

| Parameter                | Value |
| ------------------------ | ----- |
| `SETCODEFROM_OPCODE`     | `0xA7` |

### `SETCODEFROM`

`SETCODEFROM(source)` takes one stack item. The low 160 bits of the stack item are interpreted as `source`.

Before execution:

```text
[..., source]
```

After execution:

```text
[..., success]
```

`success` is `1` if `source` is a valid source account, and `0` otherwise.

The instruction is address-based: its input is `source` address, not a raw code hash. It reads `source.codeHash` from a live account in consensus state.

For this instruction, the current account is the current execution-environment address, meaning the account returned by `ADDRESS` and whose storage is affected by `SSTORE`. If the executing code was loaded from another account, including through [EIP-7702](./eip-7702.md) delegated execution, `SETCODEFROM` updates the execution-environment account, not the code source account.

An *active frame* of an account is an execution frame whose current account is that account, from the moment the frame is entered until it ends: the frame of a transaction, `CALL` or `STATICCALL` that targets the account, a frame entered from one of its frames by `DELEGATECALL` or `CALLCODE`, and the creation frame of the account while it is being created. Frames are nested, so among the active frames of an account one was entered before all the others: the account's *outermost active frame*.

A source account is valid for `SETCODEFROM` if all of the following are true:

- The source account exists in the state.
- `source.codeHash != EMPTYCODEHASH`, where `EMPTYCODEHASH = 0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`.
- `source.code` is valid regular deployed code under the active fork, i.e. it does not start with `0xEF`, which is reserved by [EIP-3541](./eip-3541.md) and used by [EIP-7702](./eip-7702.md) delegation indicators.
- The source account was not created in the current transaction. An account counts as created in the current transaction exactly when [EIP-6780](./eip-6780.md) would let `SELFDESTRUCT` delete it. This restriction applies to the source only: the current account may itself have been created in the current transaction, including during its own initcode.

If executed in a static context, `SETCODEFROM` causes an exceptional halt.

If the current account is a system contract, `SETCODEFROM` causes an exceptional halt. A system contract is an account that the protocol calls from `SYSTEM_ADDRESS` (`0xfffffffffffffffffffffffffffffffffffffffe`) during block processing; the [EIP-6110](./eip-6110.md) deposit contract, whose logs are read but which is never called, is not one.

If the current account's code is neither empty nor an [EIP-7702](./eip-7702.md) delegation indicator, and the code executing in the current frame is not that code, `SETCODEFROM` causes an exceptional halt. The comparison is between code hashes: the hash of the code loaded for the frame and the current account's `codeHash`. They differ in a frame entered by `DELEGATECALL` or `CALLCODE` into different code. The address the code was loaded from is irrelevant: a frame entered by `DELEGATECALL` or `CALLCODE` into an account that holds identical code, or into an account delegated to the current account by an EIP-7702 delegation indicator, executes the current account's code. An account that holds regular deployed code therefore adopts only from its own code, and not from a library, a module or a proxy implementation that it runs. The condition does not restrict initcode, nor code executing for an account whose code is a delegation indicator.

These halts happen before `SETCODEFROM_SOURCE_GAS` is charged, so `source` is not accessed.

If `source` is not a valid source account, `SETCODEFROM` pushes `0` and makes no state change.

If `source` is a valid source account, `SETCODEFROM` records `source.codeHash` as the *pending code hash* of the current account, replacing any pending code hash recorded for it earlier, and pushes `1`. Recording does not change the current account's `codeHash`: the pending code hash is written as specified in [Deferred Effect](#deferred-effect). Validity and the recorded hash are determined when the instruction executes. Subsequent changes to `source` must not affect the pending code hash or the `codeHash` written from it, and must not affect the availability of the bytecode referenced by that code hash. `source` is validated and read by its `codeHash`; a code hash pending for `source` itself is not taken into account. This also holds when `source` is the current account: recording the code hash that the current account still holds replaces a pending code hash, and nothing is then written.

Pending code hashes follow normal EVM revert semantics. If a frame reverts or halts exceptionally, the recordings made in it and in the frames it entered are discarded, and each account has again the pending code hash, if any, that it had when the frame was entered. A code hash that has been written reverts like any other state change.

### Deferred Effect

When the outermost active frame of an account ends successfully, i.e. without reverting and without an exceptional halt, and a code hash is pending for the account, the account's `codeHash` is set to the pending code hash and the pending code hash is cleared. This write is part of the frame's completion: it takes effect before execution returns to the frame's caller or, when the frame has no calling frame, before the transaction is processed further. It charges no gas and cannot fail. If the pending code hash equals the account's `codeHash`, the write changes nothing. A frame that ends by `SELFDESTRUCT` ends successfully, so a pending code hash is written; the deletion of the account under [EIP-6780](./eip-6780.md), if any, happens at the end of the transaction as usual. Each frame of an [EIP-8141](./eip-8141.md) frame transaction has no calling frame, so a code hash written at its end is used by the frames that follow.

An active frame of the account that is not its outermost one does not write when it ends. A pending code hash therefore exists only while the account has an active frame, and this instruction never changes the code of an account while one of its frames is active.

Until the write, the account's code is unchanged for every observer. `EXTCODESIZE`, `EXTCODEHASH` and `EXTCODECOPY` of the account, calls that target it, and the validation of the account as a `source` all use the `codeHash` the account still holds. No instruction returns a pending code hash; the gas cost of `SETCODEFROM` reveals only whether the code hash of a given `source` is the pending one. Every frame keeps executing the code that was loaded for it, and `CODESIZE` and `CODECOPY` refer to that code. After the write, the new code hash is used by later code executing operations, including later calls to the same account in the same transaction, subject to normal revert semantics.

### Contract Creation

`SETCODEFROM` is permitted during initcode execution, both in a contract-creation transaction and during `CREATE` and `CREATE2`. It behaves as specified above: the current account is the account being created, whose code is empty, and the creation frame is its outermost active frame. A frame that the initcode enters by `DELEGATECALL` or `CALLCODE`, and a call back into the account being created, are active frames of that account that are not its outermost one, so they do not write when they end. `CODESIZE` and `CODECOPY` in the creation frame continue to refer to the initcode being executed. Until the creation completes, `EXTCODESIZE`, `EXTCODEHASH` and `EXTCODECOPY` of the account being created report empty code and calls that target it execute no code, as for any account under construction.

When initcode execution completes successfully, contract creation installs code as follows:

- If no code hash is pending for the created account, the initcode's return data is validated, charged code-deposit gas, and installed as the account's code.
- Otherwise the created account has adopted code through `SETCODEFROM`. The pending code hash is written: the created account's `codeHash` is set to it and it is cleared. The initcode's return data is treated as empty for contract-creation completion and is not validated, hashed, installed, or charged code-deposit gas. No code-deposit cost is charged as part of this creation for the adopted code.

Whether a code hash is pending is determined before the return data is examined.

In the second case, the code the creation deploys is the code behind the pending code hash when initcode execution completes, i.e. the code of the last successful `SETCODEFROM` of the creation that was not reverted. Clients that report a creation's deployed code, for example in execution traces or `eth_call` results, report that code. As for every creation, a successful `CREATE` or `CREATE2` still leaves the caller's return data buffer empty ([EIP-211](./eip-211.md)).

The account-creation costs of the creation itself are unchanged. In particular, if creation adds a new account leaf, the normal account-creation state-gas charge still applies. If the destination account already exists, no account-creation state-gas is charged, as usual.

When creation completes with code adopted through `SETCODEFROM`, no code-deposit state gas or code-deposit execution gas is charged for the adopted code. The adoption only updates the created account's `codeHash` to reference code that already exists.

Failure handling is unchanged: if the creation frame reverts or halts exceptionally, the pending code hash is discarded with every state change made in that frame.

### ECDSA Transaction Origination

After an adoption installs regular deployed code on an account, i.e. once its pending code hash has been written, the account is controlled through that code. If the account held an [EIP-7702](./eip-7702.md) delegation indicator, the adopted code replaces it. The account has nonempty regular code, so an ECDSA-authenticated transaction whose recovered sender is that account is invalid under [EIP-3607](./eip-3607.md). It also disables [EIP-7702](./eip-7702.md) redelegation, because EIP-7702 authorization processing accepts only empty code or an existing valid delegation indicator for the authority account. From then on, only the adopted code itself can adopt again for the account.

### Gas Costs

The following gas parameters are used:

- `SOURCE_ACCOUNT_ACCESS_COST` is `COLD_ACCOUNT_ACCESS` if `source` is cold, otherwise `WARM_ACCESS`
- `SETCODEFROM_SOURCE_GAS` is `SOURCE_ACCOUNT_ACCESS_COST + WARM_ACCESS`
- `SETCODEFROM_CURRENT_ACCESS_GAS` is `WARM_ACCESS`
- `SETCODEFROM_WRITE_GAS` is `ACCOUNT_WRITE`
- `SETCODEFROM_STATE_GAS` is `0`

`SETCODEFROM` charges `SETCODEFROM_SOURCE_GAS` in execution gas for each execution attempt. This covers the source lookup and validation:

- carrying the `source` address = `0`, charged by ordinary calldata or deployed-code costs
- loading the source account leaf = `SOURCE_ACCOUNT_ACCESS_COST`
- validating source code = `WARM_ACCESS`, a fixed charge covering the additional code-store access required when deployed bytecode must be inspected

Once `SETCODEFROM_SOURCE_GAS` is charged, `source` is added to `accessed_addresses` ([EIP-2929](./eip-2929.md)) whether or not it is valid. Validation reads `source`'s own code and never resolves an [EIP-7702](./eip-7702.md) delegation, so the delegation target of a delegated `source` is not accessed, charged or warmed.

If `source` is valid, the instruction charges `SETCODEFROM_CURRENT_ACCESS_GAS` before comparing `source.codeHash` with the current account's pending code hash if one is recorded, and with its `codeHash` otherwise:

- accessing the already warm current account leaf = `WARM_ACCESS`

If the two code hashes differ, the instruction charges `SETCODEFROM_WRITE_GAS`. Its write component follows [EIP-8038](./eip-8038.md):

- updating the current account's code hash when the pending code hash is written = `ACCOUNT_WRITE`

`SETCODEFROM_WRITE_GAS` is charged when the instruction executes. Writing the pending code hash charges nothing, and the charge is not returned when the pending code hash is replaced or discarded.

An invalid source charges neither `SETCODEFROM_CURRENT_ACCESS_GAS` nor `SETCODEFROM_WRITE_GAS`. A valid source with the same code hash charges `SETCODEFROM_CURRENT_ACCESS_GAS` but not `SETCODEFROM_WRITE_GAS`. Under the current EIP-8038 parameters, `ACCOUNT_WRITE` is `9000`, `COLD_ACCOUNT_ACCESS` is `3000`, and `WARM_ACCESS` is `100`. The resulting execution-gas costs are:

| Result                                 | Cold source | Warm source |
| -------------------------------------- | ----------: | ----------: |
| Invalid source                         |      `3100` |       `200` |
| Valid source with unchanged code hash  |      `3200` |       `300` |
| Pending code hash is set or replaced   |     `12200` |      `9300` |

Under [EIP-8037](./eip-8037.md), `SETCODEFROM_STATE_GAS` is `0`. `SETCODEFROM` performs no code-deposit operation. An adoption only updates the current account leaf to reference the `codeHash => code` mapping of the source's code, which is already in the state or was deposited earlier in the same block. The gas cost is not affected by source code size.

This also applies when `SETCODEFROM` executes in initcode. The enclosing contract creation may independently incur the normal state-gas charge for creating a new account leaf, but adopting code through `SETCODEFROM` incurs no code-deposit state gas and no code-deposit execution gas. In particular, neither cost depends on the size of the adopted code.

### Block-Level Access Lists

For block-level access lists (BALs) as defined by [EIP-7928](./eip-7928.md), this EIP extends `CodeChange` with an optional trailing element, `new_code_hash`. A code hash change made by writing a pending code hash is recorded as that hash, never as bytecode:

```python
# CodeChange: [block_access_index, new_code]             code installed by contract creation or EIP-7702
#          or [block_access_index, b"", new_code_hash]   code adopted by SETCODEFROM
CodeChange = [BlockAccessIndex, Bytecode, Optional[Hash32]]
```

If an account's code hash at the end of a transaction differs from its code hash at the start of that transaction, and the final value was set by writing a pending code hash, the change must be recorded as `[block_access_index, b"", code_hash]`. Every other code change keeps the two-element form. A BAL that records a code change in any other way is invalid. A pending code hash that is discarded, a write that does not change the code hash, and a code hash that is written and later written back to its value at the start of the transaction record no code change.

The bytecode behind `new_code_hash` is in the pre-block state or in the `new_code` of a `code_changes` entry with a lower block access index; no entry refers to bytecode recorded at the same or a higher index.

`SETCODEFROM` accesses `source` once `SETCODEFROM_SOURCE_GAS` has been charged, whether or not `source` is valid. From then on `source` must be included in the BAL, with empty change lists if it has no other changes. If the instruction halts before that charge, or the charge fails, `source` is not accessed and must not be included. In [EIP-7928](./eip-7928.md)'s gas validation before state access, the pre-state validation cost of `SETCODEFROM` is `SETCODEFROM_SOURCE_GAS`.

### Public Mempool

These rules apply only to public mempool validation and do not affect consensus.

An EOA's ECDSA-signed transactions stay valid while its code is empty or an [EIP-7702](./eip-7702.md) delegation indicator. Once it adopts regular code, [EIP-3607](./eip-3607.md) makes them invalid, including those already pending, so nodes should evict them when processing a new block and reject new ones. This retires the account's key, not the account: the account keeps transacting as the sender of [EIP-8141](./eip-8141.md) frame transactions that its code approves, which the public mempool accepts under EIP-8141's rules and the ones below, and keeps acting when other transactions call it. An EOA adopts code only by running EIP-7702 delegated code, so an adoption invalidates no more pending transactions than delegated code already can, and EIP-7702's recommendation of one pending transaction per delegated EOA applies as is.

[ERC-7562](./eip-7562.md) validation of user operations should block `SETCODEFROM`, as it blocks `SELFDESTRUCT`: executed during validation, it changes code that the validation of other pending operations can depend on.

For EIP-8141 frame transactions:

- `SETCODEFROM` should be banned during validation-prefix execution.
- A contract reached through `CALL*` or `EXTCODE*` during the validation prefix whose code contains a `SETCODEFROM` instruction, excluding `PUSH` data and other immediates, should be treated like an account with an [EIP-7702](./eip-7702.md) delegation indicator, i.e. as having mutable code. The regular code stored at the sender's address, running as the resolved target of a validation-prefix frame, is not treated as mutable merely because it contains `SETCODEFROM`; executing the instruction there is still covered by the first rule.
- A contract whose code contains no `SETCODEFROM` instruction cannot change its code, whichever code it reaches through `DELEGATECALL` or `CALLCODE`, and is not treated as mutable on that ground. Code that it reaches this way during the validation prefix is itself subject to the previous rule. Proxy-based accounts therefore need no additional rule.

## Rationale

Using an address rather than a raw code hash avoids depending on client-local code database contents, which may differ across nodes. A newly synced node may have a smaller local code database than a long-running node because it may not keep historical or unreferenced bytecode entries. For this reason, this EIP makes `SETCODEFROM` copy the code hash from a live source account, so the adopted code hash is confirmed by current consensus state. A valid source cannot be deleted, but it can replace its own code hash later in the same block; the bytecode it deposited at creation must then still be persisted for the accounts that adopted it.

`SETCODEFROM` requires that the source account exists, even though a nonexistent account has no code and is already excluded by the `EMPTYCODEHASH` condition in a state model where a nonexistent account reads as an empty account. Implementations that represent a nonexistent account's code hash as zero rather than as `EMPTYCODEHASH` would otherwise accept such an account as a valid source and install a code hash with no code behind it. Stating existence separately removes that reading.

A `SETCODEFROM` code change records a code hash instead of bytecode because the bytecode already exists, in the pre-block state or in the `code_changes` entry of the creation that deposited it; repeating it would price BAL bytes far below any other operation (see Security Considerations). The change still needs an entry, because consumers that read an account's code at a block access index, such as parallel executors or nodes that apply the BAL without executing, would otherwise see the old code. The hash is a separate element of `CodeChange` because a 32-byte `new_code` value is indistinguishable from 32 bytes of runtime code, and keeping it inside `CodeChange` leaves each account with one list of code changes. With no bytecode fallback, an entry's form identifies its origin, two elements for creation or an [EIP-7702](./eip-7702.md) delegation and three for adoption, and its size is fixed, so a byte-floor scheme such as [EIP-8279](./eip-8279.md) can meter the instruction when it executes.

A source created in the current transaction is rejected because its code is transient: under [EIP-6780](./eip-6780.md) the account can be deleted before the transaction ends, and it can replace its own code hash with `SETCODEFROM`. Either way an adopter keeps a code hash whose bytecode is in neither the pre-block state nor the BAL, which records end-of-transaction values only and nothing for a deleted account. The gap is transitive, since a pre-existing account can adopt from the created source, be adopted from in turn, and then adopt something else, so checking the immediate source is not enough. Rejecting created sources is: every adopted code hash was then held, at the start of the adopting transaction, by an account not created in it, so its bytecode is in the pre-block state, in the `new_code` of an earlier creation, or was itself adopted earlier, to which the same argument applies. The cost is that a template cannot be adopted in the transaction that deploys it.

The instruction is self-only during deployed-code execution to keep authority local to the account whose code is executing. It does not allow the executing code to update any other account's code hash.

An account that holds regular deployed code adopts only from its own code. Since [EIP-6780](./eip-6780.md), regular code does not change after the transaction that deploys it, and code that a contract runs through `DELEGATECALL` or `CALLCODE` can no longer remove or replace the contract's code. Libraries, modules, proxy implementations and governance payloads are run with the caller's storage and balance on that basis, and checks that run after such a call, registries of reviewed addresses and mempool rules that treat helper code as immutable rely on it. If delegated code could adopt for its caller, a contract's code would be only as stable as everything the contract ever delegates to, and an implementation that can be made to run chosen code in its own context could have its code replaced for every proxy that uses it. [EIP-6913](./eip-6913.md) specified this restriction for its `SETCODE` instruction, in a stricter form that also covers initcode, so that code which does not contain the instruction can be assumed immutable. The same holds here: an account whose regular code contains no `SETCODEFROM` instruction never changes its code. The restriction does not apply to an EOA, whose only code is the code it is delegated to and whose delegate may reach its logic through `DELEGATECALL`, nor to an account under construction, which has no code of its own yet. Its cost is that proxies, clones and other contracts cannot adopt through the code they delegate to: a contract that is meant to adopt later must contain the instruction in its own code. The refusal is an exceptional halt before any charge, which is what `0xA7` does in such a frame before this EIP.

The adopted code hash is written when the account's outermost active frame ends, not when the instruction executes, so that an account never presents code that its frames are not executing. Contracts identify other accounts by their code, for example a router that lets every clone of a pair template move the tokens that users approved to the router. With an immediate update, a frame could adopt such code, keep executing its own code, and call the router while presenting the adopted code; adopting its previous code back before returning would leave no code change in the state or in the block access list. [EIP-7702](./eip-7702.md) keeps `EXTCODEHASH` from following delegations for the same reason: an account must not be able to temporarily masquerade as having a particular code hash. The write waits for the account's outermost active frame, and not only for the frame that executes the instruction, because a frame entered by `DELEGATECALL` or by a re-entrant call returns into another frame of the same account that still executes the old code. Deferring the write to the end of the transaction instead would keep later calls in the same transaction, and later frames of an [EIP-8141](./eip-8141.md) frame transaction, on the old code. A recording replaces an earlier one, as every state write replaces the previous value, and the write gas is judged against the pending code hash, so that repeating an adoption is not charged as a second write.

Allowing `SETCODEFROM` during initcode keeps one code-installation rule for creation: creation installs either the bytes returned by initcode or the code hash adopted during it, never both. Whether a code hash is pending for the created account at the end of initcode execution decides which, so the two paths cannot interleave. Contract creation is not the first operation whose outcome is decided by state changes made inside the creation frame: under [EIP-6780](./eip-6780.md), `SELFDESTRUCT` executed in the transaction that created an account deletes that account after creation completes, discarding the code that creation installed.

Initcode support makes per-instance initialization atomic on every creation path. Initcode writes per-instance storage, adopts shared code with `SETCODEFROM`, and returns no data. A contract-creation transaction with a nil `to` field therefore initializes and adopts in one transaction, and a factory does not need to deploy an initializer runtime and call back into it.

For example, the instruction can be used in the following patterns.

An account migration function can store account-specific wallet state, then adopt a shared wallet implementation:

```
SSTORE(pq_pubkey_slot, userPubkey)
SSTORE(recovery_slot, recoveryConfig)
if SETCODEFROM(PQ_WALLET_TEMPLATE) == 0: REVERT()
STOP
```

An [ERC-20](./eip-20.md) clone factory can deploy a tiny initializer with `CREATE2`, then call it to initialize token metadata and ownership before adopting a shared token implementation:

```
SSTORE(name_slot, "MyToken")
SSTORE(symbol_slot, "MYT")
SSTORE(owner_slot, msg.sender)
if SETCODEFROM(ERC20_TEMPLATE) == 0: REVERT()
STOP
```

## Backwards Compatibility

This EIP requires a hard fork to implement because it introduces a new instruction which did not exist previously. Before this EIP, `0xA7` causes an exceptional halt. After it, for an account that holds regular deployed code, `0xA7` still causes an exceptional halt in every frame that executes code other than the account's own, so libraries, modules and implementations that such an account runs through `DELEGATECALL` or `CALLCODE`, including code deployed after this EIP, cannot change its code. The behavior of an already deployed contract therefore changes only if its own code executes `0xA7`. A scan of the code left by contract creations on Ethereum mainnet up to block 26,430,999 (104,313,762 creations, 3,031,417 distinct codes) found two codes in which the instruction would execute without halting, and both halt exceptionally on the next instruction for every input, as they halt on `0xA7` before this EIP. The scan follows each code from its first instruction through fall-through and through every jump destination that the code pushes as a constant, under the instructions assigned at the time of writing. A further analysis of the 6,650 codes in which `0xA7` follows a jump destination that no such jump reaches found no jump that a caller can direct there and after which the frame ends successfully; it did not finish for one of these codes.

This EIP also alters the [EIP-7928](./eip-7928.md) BAL encoding by adding an optional `new_code_hash` element to `CodeChange`. A client implementing only EIP-7928 will reject blocks that use it, and vice versa.

The `0xEF` source restriction also excludes three contracts whose code starts with `0xEF`. These contracts were deployed on Ethereum mainnet after [EIP-3541](./eip-3541.md)'s state survey but before its activation. Because `0xEF` is an undefined instruction that causes an exceptional halt, none of them provides executable source code. Excluding these contracts therefore has no negative effect on practical code reuse.

## Security Considerations

`SETCODEFROM` can change the code used by later executions of an account. Contracts that expose this instruction must restrict access to trusted control paths, because a successful call can permanently change account behavior if the transaction does not revert. A path restricted to calls from the account itself is still reachable by code that the account runs through `DELEGATECALL` or `CALLCODE`, which can call the account with the account as caller.

`SETCODEFROM` copies whatever code hash the source holds when it executes, and a valid source can replace its own code hash, including between the time an adoption is authorized and the time it executes. An adoption authorized in advance, by a signature, a proposal or any other commitment, should therefore name the expected code hash and not only a source address, and the adopting code should compare `EXTCODEHASH(source)` with that hash immediately before `SETCODEFROM`, with no intervening external calls, so that a source whose code has changed in the meantime is rejected rather than adopted.

When `SETCODEFROM` executes several times for an account before its outermost active frame ends, the last recording that is not reverted is the one written, and the result of an earlier instruction says nothing about later ones. Code that adopts should execute `SETCODEFROM` after any call that could lead to another recording for the same account, including calls into code that can call the account back.

`SETCODEFROM` changes account-code identity semantics. Code executing with an account's authority can replace the code identity visible to later execution and code-inspection with regular code from another account. Because the new code hash is written only when the account's outermost active frame ends, an account does not present one code while its frames execute another: its code identity changes between its frames, not during them.

Like [EIP-6913](./eip-6913.md), this EIP forbids code replacement when the executing code differs from the account's code, but only for accounts that hold regular deployed code: code that a contract runs through `DELEGATECALL` or `CALLCODE` cannot replace the contract's code. An EOA has no such protection. The code it is delegated to, and any code which that code runs through `DELEGATECALL` or `CALLCODE`, can adopt for the EOA, and the adoption cannot be undone. A module, session key or guardian that can make the delegate run code of its choice in the account's context can therefore retire the key and install code of its choice. Wallets must treat any such module as upgrade-authorized code, restrict delegatecall targets accordingly, and require explicit authorization before execution. A pending code hash cannot be read, so a wallet cannot learn, after a module returns, what the module recorded; it can only test a guessed code hash through the gas cost of `SETCODEFROM`. Reverting the frame that ran the module discards whatever the module recorded.

An [EIP-7702](./eip-7702.md) delegation executes its target's current code, so delegating to an account whose code can reach `SETCODEFROM` trusts every code that account may adopt. This now includes EOAs. A delegation to an EOA used to execute nothing, since an EOA's code is empty or a delegation indicator, which delegations do not follow. Once the EOA adopts code, every account delegated to it executes that code. The deferred effect protects only the adopting account's own frames: a frame of an account delegated to it keeps executing the code it was loaded with, while later calls to that delegated account execute the adopted code.

The source restriction requires valid regular deployed code under the active fork, e.g. code that does not use the `0xEF` prefix reserved by [EIP-3541](./eip-3541.md) and used by [EIP-7702](./eip-7702.md) delegation indicators. It also excludes empty code. Precompiles are excluded without a separate condition: a precompile has no deployed code in state, so its address either does not exist in the state or has `EMPTYCODEHASH`. This prevents `SETCODEFROM` from bypassing deployed-code validity rules or treating precompile behavior as deployed code.

Protocol-level ECDSA transaction origination is disabled once the account has regular deployed code, meaning code that is not an [EIP-7702](./eip-7702.md) delegation indicator. Contracts that verify ECDSA signatures directly through `ecRecover` may still recover that address. This affects signature-based authorization such as `permit`. A companion `ecRecover` change, such as [EIP-8151](./eip-8151.md), can reject recovered addresses whose account code is regular deployed code rather than an [EIP-7702](./eip-7702.md) delegation indicator, and return empty output with `success = 1`, as for a failed recovery.

An EOA that adopts regular code retires its key and cannot undo the adoption: it can no longer originate ECDSA transactions, [EIP-7702](./eip-7702.md) can no longer redelegate it, and no instruction returns it to empty code. The adopted code is then the only way for the account to act; with [EIP-8151](./eip-8151.md), `ecRecover` no longer returns its address either, so code that authorizes through `ecRecover` against the account's own address fails permanently, and a fallback to the account's own key when no other key is set locks the account out at adoption. If authorization depends entirely on uninitialized state and no separately authenticated initialization path exists, the account may become unusable. Initialization should therefore be completed in the adopting transaction; initialization left open to anyone can be front-run.

Adoption also changes how the account receives: a plain ETH transfer sent by `CALL`, or a token transfer with a receiver hook, now executes the adopted code and fails where the code rejects it or lacks the hook. This EIP does not require [EIP-8141](./eip-8141.md). On a chain without it, [EIP-3607](./eip-3607.md) leaves the account unable to originate transactions, so the account acts only when called. Adopted code that offers no relay path of its own, for example through an [ERC-4337](./eip-4337.md) entry point, is then stranded. If the chain later adds EIP-8141, the account can act again only if the adopted code supports EIP-8141 validation and approval. The EVM gives the code no reliable way to learn which EIPs are active on the chain.

Implementations must keep pending code hashes apart from account code hashes and journal them with the other state changes of a frame, so that a revert restores them. Re-entrant calls into an account before its pending code hash is written execute the code the account still holds; calls after the write execute the adopted code. Code that adopts and then needs the adopted code to run, for example to initialize it, must write the storage that the adopted code expects before adopting, or have the account called again after its outermost active frame has ended, for example by the caller or in a later frame of the transaction.

An account under construction can be called before its initcode returns, for example through a callback from a contract that the initcode calls. Such a call executes no code, as for any account under construction, also after a successful `SETCODEFROM` in the same initcode: the adopted code runs only once the creation has completed, against the storage that the initcode wrote.

Recording adopted bytecode in the BAL would let one `SETCODEFROM`, at `9300` gas for a warm source, add up to the maximum code size to the BAL, below one gas per byte, where the [EIP-7928](./eip-7928.md) `bal_items` bound assumes small items. An adoption instead adds a 32-byte hash, and because a source created in the current transaction is invalid, the hash always resolves, so no adoption adds bytecode.

Mempool rules that assume deployed code is immutable must account for `SETCODEFROM`; see [Public Mempool](#public-mempool).
