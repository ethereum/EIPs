## Abstract

This proposal defines a minimal keystore authority layer for abstract accounts. An on-chain **Keystore** maps each account to a set of **actors**; each actor is bound to an **authenticator** contract that verifies a signature and returns the actor's identity (`actorId`). Authorizations are established and rotated through a single signed mechanism (`createAccount`, `applySignedAccountChanges`) and committed to a deterministic CREATE2 address, so the same account resolves to the same address and authority on every chain.

The Keystore exposes a single authentication primitive, `authenticateActor`, that a host transaction type authenticates against over its own digest. The base layer reserves scope bits for compatible extensions without requiring policy enforcement, account locking, keyed transaction nonces, or nonce-free transaction modes.

## Motivation

Account abstraction systems need a portable answer to a narrow question: which actors may authorize an account, and which authenticator proves each actor's identity? Binding this authority model to one transaction format or a broad set of account-management features makes otherwise compatible accounts harder to support across chains.

This proposal specifies the smaller common core: actors, authenticators, signed configuration changes, deterministic addresses, and a stable scope word. A chain or transaction type can implement only this layer and still interoperate with accounts and wallets that support compatible extensions.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

The Keystore contract is the canonical ABI surface. The layouts and digests below are normative. Exact storage-slot derivation and typed-data typehash strings remain to be specified before this proposal advances beyond Draft.

### Authority Model

An account authorizes a set of **actors** through the Keystore contract at a fixed address. An actor is identified by a 32-byte `actorId` and is bound to an **authenticator**, a contract implementing `IAuthenticator.authenticate(hash, data) -> actorId`. The authenticator *authenticates* by returning the `actorId` it recovered from the signature; the actor's **scope** then *authorizes* what that actor may do.

Because the authenticator returns the `actorId` rather than accepting it, the Keystore needs no per-algorithm logic and stays crypto-agile. An account adopts a new signature scheme by authorizing a new actor pointing at a new authenticator, with no migration or address change.

Any contract implementing `IAuthenticator` MAY be permissionlessly registered as an actor's authenticator. Which authenticators a chain accepts on its transaction path is that chain's own acceptance rule; a registered authenticator is always usable within EVM execution.

### Storage Layout

Each actor occupies a single `actor_config` slot, packed `authenticator(20) ‖ expiry(6) ‖ scope(2) ‖ reserved(4)`, where `expiry` is a `uint48` Unix timestamp in seconds (`0` = no expiry) and `scope` is a `uint16` grants bitmask (`0x0000` = unrestricted, the admin predicate). An actor is exactly this one slot, with no per-actor side state; revocation deletes the slot. The self-actor (`actorId == bytes32(uint256(uint160(account)))`) is held inline in a packed account-state slot. Validity is decided by a single `actor_config` SLOAD.

### Actor Scope

`scope` is a `uint16` bitmask of **grants**, read fail-closed: a context is authorized only when `scope == 0x00` (admin) or the corresponding grant bit is set; unknown bits grant nothing. All future scope bits MUST be pure grants.

| Bit | Value | Name | Context |
|-----|-------|------|---------|
| 0 | `0x01` | SENDER | May originate transactions |
| 1 | `0x02` | (reserved) | Reserved for compatible extensions |
| 2 | `0x04` | (reserved) | Reserved for compatible extensions |
| 3 | `0x08` | SELF_PAYER | Authorizes paying the account's own gas |
| 4 | `0x10` | SPONSOR_PAYER | Authorizes paying gas for a different account |
| 5–15 | | (spare) | Reserved for future pure grants |

The reserved bit values (`0x02`, `0x04`) are unused by this proposal. Extensions MAY assign them additional grant semantics. Reserving them here ensures that the same `scope` word remains portable between the base layer and those extensions.

### Actor Expiry and Epoch

An actor is **live** at `now` iff `expiry == 0 || now <= expiry`, checked at inclusion; the protocol never walks authorizer lineage. Initial actors are always non-expiring; `expiry` is set only by a later configuration change and SHOULD be applied only to non-admin actors.

Signed configuration-change batches carry a channel and sequence for replay protection and ordering. The **local** channel packs `local_epoch(high 32) ‖ local_sequence(low 32)`; `IncrementLocalEpoch` bumps `local_epoch` and resets `local_sequence`, invalidating every unlanded local signature at the prior epoch without revoking live actors. The **multichain** channel (`chain_id 0`) is a plain monotonic counter for synchronizing actor state across chains.

### Account Creation, Import, and Address Derivation

`createAccount(userSalt, bytecode, initialActors)` deploys an account and registers its `initialActors`, each `[actorId, authenticator, scope]`. `importAccount(account, chainId, initialActors, signature)` registers an already-deployed account whose [ERC-1271](./eip-1271.md) check validates a typed ([EIP-712](./eip-712.md)-style) `ActorInitialization` digest binding the account, `chainId`, and the initial actors, all with `expiry = 0`.

Addresses are derived with CREATE2 over `userSalt`, `bytecode`, and a commitment to the sorted `initialActors`:

```text
initial_actors MUST be sorted by actorId (strictly ascending); reject otherwise
leaf_i        = keccak256(actorId_i || authenticator_i || scope_i)
actors_commit = keccak256(leaf_0 || leaf_1 || ... || leaf_n)
salt          = keccak256(user_salt || actors_commit)
address       = CREATE2(keystore_address, salt, keccak256(deployment_code))
```

Fixed-width leaves make the commitment canonical and linear in the actor count; the required strictly ascending `actorId` ordering rejects duplicates. `computeAddress` MUST apply the same validation as `createAccount`, so a predicted address always corresponds to an acceptable actor set.

### Config Change Format

`applySignedAccountChanges(account, changes)` is the single signed entry point for authority changes. A batch is authorized by one **admin** signature (`scope == 0x00`) over the batch digest; anyone MAY relay it. Each change is one of:

| `change_type` | Name | Payload |
|---------------|------|---------|
| `0` | `AuthorizeActor` | `abi.encode(bytes32 actorId, ActorConfig config)` to upsert an actor's `authenticator`, `expiry`, and `scope` |
| `1` | `RevokeActor` | `abi.encode(bytes32 actorId)` to delete the actor |
| `2` | `IncrementLocalEpoch` | Empty payload to cancel unlanded local signatures |

The batch digest is a typed struct hash binding `account`, the resolved `chainId` (`0` for multichain, otherwise `block.chainid`), the sequence word, and the ordered changes. `AuthorizeActor` stores `scope` verbatim and validates only timeless structure, including the admin signer and zero reserved bytes. Grant semantics are checked at the point of use.

### Signature Verification

The Keystore exposes one primitive, `authenticateActor(account, hash, auth) -> (actorId, scope)`, where `auth = authenticator(20) ‖ data`. It routes to the authenticator, validates the returned `actorId` against `actor_config` and the inline self-actor rule for the native secp256k1 path, enforces `expiry`, and returns the resolved `(actorId, scope)`. Because authority lives in a flat slot and the accepted authenticator set can be small, `authenticateActor` MAY run as native code and be exposed as a precompile, producing results identical to EVM execution.

### Host Transaction Type

This layer is authority only; it does not define a transaction. A **host transaction type** binds it in by:

1. **Authenticating**: for each party it needs to authorize, such as an originator, gas payer, or administrator, compute a digest over its own signed contents and call `authenticateActor(account, digest, auth)`, then check the returned `scope` against that context, fail-closed:
   - originate the transaction: `scope == 0x00 || (scope & SENDER) != 0`;
   - pay the account's own gas: `scope == 0x00 || (scope & SELF_PAYER) != 0`;
   - pay another account's gas: `scope == 0x00 || (scope & SPONSOR_PAYER) != 0`;
   - admin action: `scope == 0x00`.
2. **Applying configuration changes**: a host type MAY carry `createAccount` or `applySignedAccountChanges` and apply them through the Keystore as part of its flow, so an account can be created or rotated in the same transaction that uses it.

The digest, wire format, gas accounting, and non-configuration replay protection are entirely the host type's concern; this layer prescribes only the `authenticateActor` call and the `scope` check.

### Interfaces

```solidity
pragma solidity ^0.8.0;

interface IKeystore {
    struct ChangeSequences {
        uint64 multichain;
        uint32 localEpoch;
        uint32 localSequence;
    }

    struct ActorConfig {
        address authenticator;
        uint48 expiry;
        uint16 scope;
    }

    struct InitialActor {
        bytes32 actorId;
        address authenticator;
        uint16 scope;
    }

    enum AccountChangeChannel { Local, Multichain }
    enum ChangeType { AuthorizeActor, RevokeActor, IncrementLocalEpoch }

    struct AccountChange {
        ChangeType changeType;
        bytes payload;
    }

    struct SignedAccountChanges {
        AccountChangeChannel channel;
        uint64 sequence;
        AccountChange[] changes;
        bytes signature;
    }

    event ActorAuthorized(address indexed account, bytes32 indexed actorId, bytes actorData);
    event ActorRevoked(address indexed account, bytes32 indexed actorId);
    event AccountCreated(address indexed account, bytes32 userSalt, bytes32 codeHash);
    event AccountImported(address indexed account);
    event LocalEpochIncremented(address indexed account, uint32 localEpoch);

    function createAccount(bytes32 userSalt, bytes calldata bytecode, InitialActor[] calldata initialActors) external returns (address);
    function computeAddress(bytes32 userSalt, bytes calldata bytecode, InitialActor[] calldata initialActors) external view returns (address);
    function importAccount(address account, uint256 chainId, InitialActor[] calldata initialActors, bytes calldata signature) external;
    function applySignedAccountChanges(address account, SignedAccountChanges calldata changes) external;
    function authenticateActor(address account, bytes32 hash, bytes calldata auth) external view returns (bytes32 actorId, uint16 scope);
    function getActorConfig(address account, bytes32 actorId) external view returns (ActorConfig memory);
    function getChangeSequences(address account) external view returns (ChangeSequences memory);
}

interface IAuthenticator {
    function authenticate(bytes32 hash, bytes calldata data) external view returns (bytes32 actorId);
}
```

## Rationale

### Why a Minimal Keystore

Not every chain wants policy execution, account locking, or transaction nonce extensions. Specifying the actor and authenticator core on its own gives those chains a small, auditable surface: one `actor_config` slot per actor, one authentication primitive, and one signed configuration-change path.

### Why Reserve Extension Bits

The value of a keystore is that an account works everywhere. Keeping a stable scope word and reserving extension bits allows an account to retain the same address and authority wherever the same initial actors are supported. A host transaction type can assign additional fail-closed grant semantics without changing the base actor representation.

### Why the Epoch

`IncrementLocalEpoch` cancels outstanding unlanded local signatures without revoking live actors, giving a cheap way to invalidate everything signed but not yet applied without enumerating or touching each actor.

## Backwards Compatibility

The authority layer is additive. The Keystore is an ordinary contract deployable at a deterministic CREATE2 address on any chain, usable through the EVM even where no transaction type integrates it natively. Existing externally owned accounts and contracts are unaffected until they register actors.

This revision narrows the earlier Draft EIP-8130 specification to its portable authority core. Implementations of the earlier draft's transaction type and extended features need to follow a companion host-transaction specification.

## Reference Implementation

The interfaces in the specification define the required contract surface. A complete reference implementation is under development.

## Security Considerations

**Authentication surface**: For authenticators that are pure functions of `(hash, data)` and the resolved `actor_config`, the only invalidator of a prior successful authentication is an `actor_config` change. A chain that admits arbitrary authenticators on its transaction path widens this surface and MUST bound it with its own acceptance rule, such as an allowlist, static-purity proof, or traced revalidation.

**Actor identifier binding**: The Keystore checks that an authenticator's returned `actorId` maps back to that authenticator in `actor_config`, preventing a malicious authenticator from claiming another authenticator's actors.

**Implicit externally owned account scoping**: The implicit secp256k1 self-actor rule applies only on the native `ecrecover` path or a designated K1 authenticator while the default externally owned account actor remains active. A generic authenticator MUST NOT satisfy the implicit branch even if it returns `bytes32(uint256(uint160(account)))`.

**Epoch cancellation**: `IncrementLocalEpoch` cancels unlanded local signatures without revoking live actors. Retiring a landed authorization requires an explicit `RevokeActor`. Because the epoch does not walk lineage, an actor from an applied batch survives epoch increments.

**Front-running of account creation**: `initialActors` are committed to the CREATE2 salt, so an attacker cannot deploy the counterfactual address with a different actor set.

**Admin expiry**: A sole expiring admin can make an account and its cross-chain reconstruction unusable. Admin actors SHOULD be non-expiring, with `expiry` reserved for restricted actors.
