## Abstract

[EIP-7732](./eip-7732.md) propagates the execution payload as a single message on the `execution_payload` gossipsub topic. This EIP replaces it with a Waggle topic of the same name. Waggle is a libp2p publish-subscribe protocol for objects that peers reconstruct from pieces. The payload envelope is split into chunks, which peers push to each other, announce and request until each of them can reconstruct the envelope.

The builder commits to the chunk set in its execution bid with a descriptor. The descriptor gives the chunking scheme, the count and size of the chunks, and their Merkle root. A peer can verify each chunk independently with an inclusion proof against the bid in the corresponding beacon block.

This EIP defines one scheme. The plain scheme splits the envelope into 16 KiB chunks. The last chunk may be shorter. A peer needs every chunk to reconstruct the envelope.

The bid also commits to the root of the whole envelope. Consensus checks that root and fixes only the descriptor's fields and types. Client releases can add schemes that fit the bid and network messages without a fork.

## Motivation

The gas-limit growth that [EIP-7732](./eip-7732.md) enables implies larger payloads leading to increased latency. If Payload Timeliness Committee (PTC) members do not receive the payload within the attestation deadline, an otherwise valid payload is considered missed.

The existing `execution_payload` gossipsub topic scales poorly as payloads grow. Two effects dominate:

1. Once a peer has received a large message, it is hard to cancel in-flight duplicates, so the same bytes arrive several times and consume bandwidth that could carry new data.
2. A peer must download the full message before it can forward any of it, so each hop adds a full transfer, leading to increased latency proportional to message size multiplied by hop count.

Both effects are mitigated when the message is chunked. Large duplicates are impossible with chunk granularity, and a peer can forward each chunk as soon as it arrives, so hops overlap instead of serializing.

Gossipsub, however, routes each chunk as an independent message. A peer can tell its mesh peers about the chunks it holds only one message at a time, through control messages such as `IDONTWANT` and `IHAVE`, and recovers a missing chunk through heartbeat-driven `IHAVE`/`IWANT` gossip. Waggle makes the payload the unit of dissemination instead: peers exchange bitmaps of the chunks they hold, push new chunks to peers that lack them, and request missing chunks directly.

### Parameters

| Constant | Value |
| --- | --- |
| `MAX_PAYLOAD_CHUNK_SIZE` | `2**18` (262,144 bytes) |
| `MAX_EXECUTION_PAYLOAD_CHUNKS` | `2**11` (2,048) |
| `CHUNK_INCLUSION_PROOF_DEPTH` | `ceillog2(MAX_EXECUTION_PAYLOAD_CHUNKS)` (11) |
| `CHUNKING_SCHEME_PLAIN` | `ChunkingScheme(0)` |
| `PLAIN_CHUNK_SIZE` | `2**14` (16,384 bytes) |

The first three constants are the limits of the message format, within which every chunking scheme works: up to 2,048 chunks of up to 256 KiB each. The number of indices fixes the depth of a chunk's inclusion proof at 11. Changing these limits changes the `PayloadChunk` and `ChunkMetadata` messages. `PLAIN_CHUNK_SIZE` belongs to the one scheme this EIP defines.

`MAX_PAYLOAD_SIZE`, the networking limit on an uncompressed gossip message, bounds the serialized envelope. At that limit the plain scheme uses `MAX_PAYLOAD_SIZE // PLAIN_CHUNK_SIZE` (640) chunks. The index space holds more than three times as many.

The format also has room for a scheme with a fixed count of 64 at every envelope size. Even at the size limit, one sixty-fourth of the envelope fits in a chunk.

### Custom types

| Name | SSZ equivalent | Description |
| --- | --- | --- |
| `ChunkIndex` | `uint16` | Index of a chunk within its set, `0` through `chunk_count - 1` |
| `Chunk` | `ByteList[MAX_PAYLOAD_CHUNK_SIZE]` | One piece of the chunked envelope. In the plain scheme, this is a contiguous slice of the serialized `ExecutionPayloadEnvelope`. |
| `ChunkingScheme` | `uint8` | Identifies how the envelope is split into chunks and reconstructed |

### Commitment

The execution bid commits to the whole envelope and to the chunks used to disseminate it.

```python
class PayloadChunksDescriptor(Container):
    scheme: ChunkingScheme
    chunk_count: uint64
    chunk_size: uint64
    chunks_root: Root


class ExecutionPayloadBid(ProgressiveContainer):
    ...
    envelope_root: Root  # [New in this EIP]
    payload_chunks: PayloadChunksDescriptor  # [New in this EIP]
    ...
```

`envelope_root` and `payload_chunks` are new active fields of the progressive container. They follow the existing fields, which keep their indices.

Consensus checks `envelope_root` against `hash_tree_root(envelope)` (see Envelope verification). Only networking uses `payload_chunks`, to verify the chunks as they arrive.

A forwarding node reads the following fields from the descriptor.

- `scheme` identifies how the builder derives the chunks and how a receiver reconstructs the envelope.
- `chunk_count` is the number of chunks.
- `chunk_size` is the length in bytes of every chunk except the last. The last chunk is at most this long. A scheme can require it to be full.
- `chunks_root` is the SSZ `hash_tree_root` of a `Vector[Bytes32, MAX_EXECUTION_PAYLOAD_CHUNKS]`. Its first `chunk_count` entries hold the SHA-256 hashes of the chunks in index order. Its remaining entries are zero.

The chunks carry any other information the scheme needs, so the root commits to it.

The Chunking section defines how `compute_payload_chunks_descriptor` derives the descriptor for `CHUNKING_SCHEME_PLAIN`.

Consensus fixes only the descriptor's fields and their types. Which schemes a node implements, the values each scheme allows and the limits of the message format are networking rules.

Assigning a scheme identifier fixes the scheme's rules: the values its descriptors may hold and how its chunks are derived and reassembled. A changed rule requires a new identifier, so all nodes that implement an identifier apply the same rules.

Changing the format's limits requires a new version of the messages and their topic.

A descriptor is valid for a node if the node implements the scheme and the values satisfy both the format's limits and the scheme's rules.

```python
def is_known_chunking_scheme(scheme: ChunkingScheme) -> bool:
    return scheme == CHUNKING_SCHEME_PLAIN


def compute_plain_chunk_count(length: uint64) -> uint64:
    return (length + PLAIN_CHUNK_SIZE - 1) // PLAIN_CHUNK_SIZE


def is_valid_payload_chunks_descriptor(descriptor: PayloadChunksDescriptor) -> bool:
    if not is_known_chunking_scheme(descriptor.scheme):
        return False
    if not (
        0 < descriptor.chunk_count <= MAX_EXECUTION_PAYLOAD_CHUNKS
        and 0 < descriptor.chunk_size <= MAX_PAYLOAD_CHUNK_SIZE
    ):
        return False
    # CHUNKING_SCHEME_PLAIN
    return (
        descriptor.chunk_size == PLAIN_CHUNK_SIZE
        and descriptor.chunk_count <= compute_plain_chunk_count(MAX_PAYLOAD_SIZE)
    )
```

A node cannot use an invalid descriptor to disseminate a bid's payload (see Payload state).

A proposer SHOULD NOT select a bid with an invalid descriptor or a scheme it does not implement. This also applies to bids received outside gossip.

On the `execution_payload_bid` topic, add the following checks to the [EIP-7732](./eip-7732.md) validations. Apply them in order before checking the bid's signature. Here `bid = signed_execution_payload_bid.message`.

- _[IGNORE]_ The node implements the bid's chunking scheme: `is_known_chunking_scheme(bid.payload_chunks.scheme)`.
- _[REJECT]_ The descriptor is valid: `is_valid_payload_chunks_descriptor(bid.payload_chunks)`.

The two fields add 81 bytes to the Gloas bid. The networking limit on a `SignedExecutionPayloadBid`, `MAX_SIGNED_EXECUTION_PAYLOAD_BID_SIZE`, becomes `Uint64(197013)`.

### Envelope

Chunking is applied to the envelope:

```python
class ExecutionPayloadEnvelope(ProgressiveContainer(active_fields=[1, 1, 1, 0, 1])):
    payload: ExecutionPayload
    execution_requests: ExecutionRequests
    builder_index: BuilderIndex
    # [Modified in this EIP] removed `beacon_block_root`, whose field is inactive
    parent_beacon_block_root: Root
```

`beacon_block_root` is removed. The envelope is a progressive container, so its field becomes inactive, and the other fields keep their positions: `parent_beacon_block_root` is merkleized at field index 4, as before. This only concerns the `hash_tree_root` of the envelope. With `beacon_block_root` removed, the builder can compute `envelope_root` before the block exists. Inactive fields are not serialized, so the serialized envelope, and with it the chunks, consists of the four remaining fields.

Where [EIP-7732](./eip-7732.md) reads the beacon block root from the envelope, it is passed alongside the envelope instead.

`SignedExecutionPayloadEnvelope` is removed, and the builder does not sign the envelope. The bid in the validated beacon block authenticates the envelope through `envelope_root`. The builder signs the bid, or, for a self-build, the proposer signs the block.

### Chunking

The builder MUST derive the chunks and the descriptor according to the chosen scheme. In the functions below, `hash` is SHA-256.

Under `CHUNKING_SCHEME_PLAIN`, every chunk but the last is `PLAIN_CHUNK_SIZE` bytes long. The last chunk holds the remaining bytes and is nonempty. The plain scheme adds no padding.

```python
def compute_payload_chunks(
    envelope: ExecutionPayloadEnvelope,
    scheme: ChunkingScheme,
) -> List[Chunk, MAX_EXECUTION_PAYLOAD_CHUNKS]:
    assert is_known_chunking_scheme(scheme)
    # CHUNKING_SCHEME_PLAIN
    data = serialize(envelope)
    assert len(data) <= MAX_PAYLOAD_SIZE
    chunks = []
    for i in range(compute_plain_chunk_count(len(data))):
        start = i * PLAIN_CHUNK_SIZE
        chunks.append(Chunk(data[start:start + PLAIN_CHUNK_SIZE]))
    return chunks


def compute_payload_chunks_descriptor(
    envelope: ExecutionPayloadEnvelope,
    scheme: ChunkingScheme,
) -> PayloadChunksDescriptor:
    chunks = compute_payload_chunks(envelope, scheme)
    leaves = [hash(chunk) for chunk in chunks]
    leaves += [Bytes32()] * (MAX_EXECUTION_PAYLOAD_CHUNKS - len(leaves))
    return PayloadChunksDescriptor(
        scheme=scheme,
        chunk_count=len(chunks),
        chunk_size=PLAIN_CHUNK_SIZE,
        chunks_root=hash_tree_root(Vector[Bytes32, MAX_EXECUTION_PAYLOAD_CHUNKS](leaves)),
    )
```

Before signing the bid, the builder constructs the envelope, chooses the scheme, and sets `bid.payload_chunks` to `compute_payload_chunks_descriptor(envelope, scheme)` and `bid.envelope_root` to `hash_tree_root(envelope)`. For a self-build, the proposer does the same before signing the block.

Each chunk is disseminated in a `PayloadChunk`, along with its index and its inclusion proof:

```python
class PayloadChunk():
    index: ChunkIndex
    chunk: Chunk
    chunk_inclusion_proof: Vector[Bytes32, CHUNK_INCLUSION_PROOF_DEPTH]
```

`chunk_inclusion_proof` is the SSZ Merkle branch for leaf `index` in the vector. The leaf is `hash(chunk)`, the SHA-256 hash of the chunk's exact bytes.

The builder sets unused leaves to zero. When checking an individual chunk, a receiver checks the index against `chunk_count`. It does not check the unused leaves.

```python
def verify_payload_chunk_inclusion_proof(
    payload_chunk: PayloadChunk,
    descriptor: PayloadChunksDescriptor,
) -> bool:
    return is_valid_merkle_branch(
        leaf=hash(payload_chunk.chunk),
        branch=payload_chunk.chunk_inclusion_proof,
        depth=CHUNK_INCLUSION_PROOF_DEPTH,
        index=payload_chunk.index,
        root=descriptor.chunks_root,
    )
```

`is_valid_chunk_length` checks a chunk's length against the rules for its scheme.

```python
def is_valid_chunk_length(
    descriptor: PayloadChunksDescriptor,
    index: ChunkIndex,
    length: uint64,
) -> bool:
    if index + 1 < descriptor.chunk_count:
        return length == descriptor.chunk_size
    return 0 < length <= descriptor.chunk_size
```

Under the plain scheme, receivers concatenate chunks `0` through `chunk_count - 1` in order and deserialize the result. They use every byte because each leaf hashes the exact bytes of its chunk.

### Envelope verification

The envelope is verified against the commitment in the bid instead of a signature, and the beacon block root is passed alongside it:

```python
def verify_execution_payload_envelope(
    state: BeaconState,

    execution_engine: ExecutionEngine,

    payload = envelope.payload
    bid = state.latest_execution_payload_bid

    # [Modified in this EIP]
    # Verify the commitment instead of the signature and the beacon block root
    assert hash_tree_root(envelope) == bid.envelope_root

    # [Unchanged from EIP-7732] The remaining checks, from the
    # `parent_beacon_block_root` check onwards
    ...


def on_execution_payload_envelope(
    store: Store,
    # [New in this EIP]
    beacon_block_root: Root,
    # [Modified in this EIP] The envelope is not signed
    envelope: ExecutionPayloadEnvelope,
) -> None:
    # The corresponding beacon block root needs to be known
    assert beacon_block_root in store.block_states

    # Check if blob data is available
    # If not, this payload MAY be queued and subsequently considered when blob data becomes available
    assert is_data_available(beacon_block_root)

    state = store.block_states[beacon_block_root]

    # Verify the execution payload envelope
    verify_execution_payload_envelope(state, envelope, EXECUTION_ENGINE)

    # Add execution payload envelope to the store
    store.payloads[beacon_block_root] = envelope
```

`state` is the post-state of the beacon block. Processing the block authenticated its bid through the builder's signature on the bid or, for a self-build, the proposer's signature on the block.

Checking `envelope_root` therefore authenticates the envelope and binds it to the block. Fork choice makes the same check for every chunking scheme and for an envelope obtained by request.

### Networking

This EIP removes the `execution_payload` gossipsub topic. Nodes MUST NOT subscribe to it or publish on it under the fork digests of the fork that activates this EIP and of later forks. Execution payloads are instead disseminated over Waggle, on the Waggle topic `execution_payload`.

#### Waggle

Waggle is the libp2p publish-subscribe protocol for objects that peers reconstruct incrementally from pieces, with the protocol ID `/waggle/1.0`. Nodes MUST implement it as specified by libp2p, and this EIP assumes familiarity with that specification. Each Waggle message is about one object, and carries its `objectID` and, optionally, `piecesMetadata` and `pieces`. Waggle leaves the meaning of these fields to the application, and neither validates nor forwards messages itself. The following sections define them for execution payloads, along with how nodes validate and disseminate them.

#### Topic

The topic ID is the UTF-8 encoding of `/eth2/{fork_digest}/execution_payload/ssz_snappy`, with `fork_digest` formatted as in gossipsub topic names. Nodes subscribe to and unsubscribe from the topic of each fork digest as they do for gossipsub topics around fork transitions.

The payload of a beacon block is disseminated on the topic of the fork digest of the block's epoch.

#### Messages

Each message on the topic is about the execution payload of one beacon block, and carries the following:

| Waggle field | Content |
| --- | --- |
| `objectID` | The `hash_tree_root` of the `BeaconBlock` whose bid commits to the payload |
| `piecesMetadata` | If present, a `ChunkMetadata`, SSZ serialized |
| `pieces` | If present, a single `PayloadChunk`, SSZ serialized and compressed with Snappy block compression |

```python
class ChunkMetadata():
    slot: Slot
    have: Bitlist[MAX_EXECUTION_PAYLOAD_CHUNKS]
    request: Bitlist[MAX_EXECUTION_PAYLOAD_CHUNKS]
```

`slot` is the slot of the beacon block. `have` marks the chunks the sender holds, all of which it validated, and `request` the chunks the sender asks the receiver to send. Each bitmap has one bit per chunk. Its length is `chunk_count` from the block's descriptor.

Each chunk is compressed on its own, and the commitment covers the uncompressed chunks. Let `max_chunk_length` be the length of the largest valid `PayloadChunk`, whose chunk is `MAX_PAYLOAD_CHUNK_SIZE` bytes long, and `max_compressed_len` the worst-case length of Snappy compression, as defined for gossipsub. Nodes MUST NOT send messages on the topic that exceed the following limits, and MUST treat messages that exceed them as malformed:

- The encoded Waggle message, including its framing, is at most `max_compressed_len(max_chunk_length) + 1024` bytes long, which leaves room for `objectID`, `piecesMetadata` and the framing. Nodes MUST set the maximum message size of Waggle for the topic to this limit.
- The uncompressed length in the Snappy header of `pieces` is at most `max_chunk_length`. Nodes MUST check it before decompressing `pieces`.
- `pieces` is at most `max_compressed_len(n)` bytes long, where `n` is the uncompressed length in its Snappy header.

#### Payload state

A node tracks the payload of a beacon block from the moment it validates the block until `MAXIMUM_GOSSIP_CLOCK_DISPARITY` after the end of the slot following the block's slot. This is the payload's tracking window; afterwards the node MAY discard its state.

A node does not track a payload if the descriptor in the block's bid is invalid or the node does not implement its scheme.

With a valid descriptor (`is_valid_payload_chunks_descriptor`), a node MUST track the payload of each block that passes the `beacon_block` gossip validation.

With a valid descriptor, a node SHOULD track the payload of any other valid block, for example one obtained through a lookup.

For each tracked payload, a node keeps:

- the valid chunks it holds, verified against the descriptor in the block's bid;
- per peer, the chunks the peer is known to hold: those it announced in `have`, sent to the node, or received from the node;
- per peer, whether it is known to track the payload, which is the case once it sent `ChunkMetadata` about it, including `ChunkMetadata` remembered from before the node tracked the payload, as described in the Untracked payloads section.

Once the builder observes a beacon block containing its bid, it tracks the payload of the block with all chunks valid, and disseminates them as described in the Dissemination section.

A node processes chunks of a tracked payload as follows.

1. Once the node holds all `chunk_count` chunks, reconstruct the envelope as described in the Chunking section. If reconstruction or deserialization fails, follow the failure procedure below.
2. If the block has yet to be imported, keep the envelope until import completes. The envelope checks need the block's post-state. Waiting for the import is not a failure.
3. Apply the `execution_payload` gossip checks of [EIP-7732](./eip-7732.md). Use the block's root in place of `envelope.beacon_block_root`. Omit the duplicate envelope check and replace the signature check with `hash_tree_root(envelope) == bid.envelope_root`. If a check fails, follow the failure procedure below.
4. When the envelope passes the checks, record `seen.execution_payloads[payload.block_hash] = payload` and call `on_execution_payload_envelope` with the root of the block and the envelope.

If reconstruction fails or the reconstructed envelope fails its checks, treat any envelope produced by the reconstruction as invalid and handle the failure as follows.

1. Remember the failure for the payload's tracking window. Make no further reconstruction attempt for this payload.
2. Do not penalize peers for this failure.
3. If the node still needs the envelope, obtain it with `ExecutionPayloadEnvelopesByRoot`.

An envelope obtained by request also waits for the block's post-state. Apply the checks in step 3 to it, omitting the gossip filter on finalized slots.

When a requested envelope passes those checks, record `seen.execution_payloads[payload.block_hash] = payload` and call `on_execution_payload_envelope` with the root of the block and the envelope.

If the block turns out to be invalid, discard its envelope whether reconstructed or obtained by request.

A member of the Payload Timeliness Committee sets `payload_present` according to when the envelope passed the checks, whether it was reconstructed or obtained by request, rather than when it saw a `SignedExecutionPayloadEnvelope` referencing the block.

`seen.execution_payload_envelopes`, which only the `execution_payload` gossip validation used, is removed.

#### Validation

There is no gossipsub validation on Waggle topics. Instead, a node checks each message it receives as follows. _[IGNORE]_ means the node drops the message. _[REJECT]_ means the node drops the message and SHOULD penalize the sender. Nothing from a dropped message is used or forwarded, with two exceptions. `ChunkMetadata` about a payload the node does not track is remembered as described in the Untracked payloads section. And a `PayloadChunk` that passes the checks on chunks below MAY be used and forwarded even if the message is dropped for its `ChunkMetadata`: the inclusion proof makes the chunk valid whoever sent it, and whatever else the message carries.

- _[REJECT]_ The message is well-formed: it is within the size limits above, `objectID` is 32 bytes long, and `piecesMetadata`, if present, deserializes.
- _[IGNORE]_ The node tracks the payload of the block with root `objectID`. Otherwise, the message is handled as described in the Untracked payloads section.
- _[IGNORE]_ The message arrived on the topic of the fork digest of the block's epoch.
- _[REJECT]_ If `pieces` is present, its Snappy header declares an uncompressed length of at most `chunk_size + 358` bytes, and `pieces` decompresses and deserializes. Here `chunk_size` comes from the tracked payload's descriptor, and 358 bytes account for the other fields of a `PayloadChunk`. The node checks the declared length before decompressing `pieces`.

For a message about the payload of a tracked beacon block `block`, let `descriptor = block.body.signed_execution_payload_bid.message.payload_chunks`. Apply the following checks if the message carries a `PayloadChunk` `chunk`.

- _[REJECT]_ `chunk.index` is less than `descriptor.chunk_count`.
- _[REJECT]_ The chunk's length fits the descriptor, as checked by `is_valid_chunk_length(descriptor, chunk.index, len(chunk.chunk))`.
- _[REJECT]_ The sender has not sent the node a chunk with index `chunk.index` of this payload before.
- _[REJECT]_ The inclusion proof is valid as verified by `verify_payload_chunk_inclusion_proof(chunk, descriptor)`. A node that already holds the chunk at `chunk.index` MAY compare the chunks instead.

For a message about the payload of a tracked beacon block `block`, with `descriptor` as above, carrying the `ChunkMetadata` `metadata`:

- _[REJECT]_ `metadata.slot` equals `block.slot`.
- _[REJECT]_ `len(metadata.have)` and `len(metadata.request)` equal `descriptor.chunk_count`.
- _[REJECT]_ `metadata.have` includes every chunk the sender announced in earlier `ChunkMetadata` about this payload.
- _[REJECT]_ `metadata.request` includes none of the chunks the sender announced in `have`, or sent to the node.

##### Untracked payloads

Messages about a payload the node does not track are dropped, and their chunks are not buffered.

- **A validated block with an invalid descriptor or a scheme the node does not implement.** Discard remembered `ChunkMetadata` about the payload. Ignore further `ChunkMetadata` about it without penalizing the senders.

  The node has sent no `ChunkMetadata` about this payload, so a chunk is unexpected. Apply the Chunks case below.

  Obtain the envelope with `ExecutionPayloadEnvelopesByRoot`. The node MAY ask peers that announced the payload.

  The `ChunkMetadata` case below applies to blocks the node has not validated. The Chunks case also applies after a payload's tracking window.
- **`ChunkMetadata`.** Peers often track a payload before the node has validated its block.

  If `slot` is the current or the previous slot (within `MAXIMUM_GOSSIP_CLOCK_DISPARITY` allowance), the node SHOULD remember the sender's latest `ChunkMetadata` about the payload, ignoring its `request`.

  What it remembers MUST be bounded, for example to a few untracked payloads per peer.

  If the block remains unknown for a while, the node SHOULD look it up by root from the peers that announced the payload.

  Nodes SHOULD deduplicate and rate-limit the block lookups they make for remembered payloads.

  Once the node tracks the payload, each sender whose `slot` equals the block's slot and whose `have` has `chunk_count` bits is known to track it and to hold the chunks in its `have`. Discard other remembered `ChunkMetadata`.
- **Chunks.** Peers only send chunks to nodes that sent `ChunkMetadata` about the payload, so a chunk is unexpected unless the node stopped tracking the payload while it was in transit. The node SHOULD NOT penalize the sender if it stopped tracking the payload recently, for example during the slot after its tracking window, and MAY slightly penalize it otherwise.

#### Dissemination

The following parameters tune the dissemination. They are not part of consensus, and nodes MAY use different values, though they SHOULD NOT use a lower `PUSH_PEERS`, nor a different `MAX_REQUESTS_PER_PEER`, as it also limits the requests a peer has to serve.

| Name | Recommended value | Description |
| --- | --- | --- |
| `PUSH_PEERS` | `2` | Number of peers each valid chunk is pushed to |
| `PUSH_PHASE` | `250` milliseconds | Time after the first chunk of a payload arrives during which a node pushes its chunks |
| `ANNOUNCE_INTERVAL` | `50` milliseconds | Time for which announcements of a payload can be held back to coalesce them |
| `MAX_REQUESTS_PER_PEER` | `1` | Maximum number of chunks requested from a peer at a time, beyond which the peer need not serve requests |
| `REQUEST_DELAY` | `100` milliseconds | Time after a node starts tracking a payload before it requests missing chunks |
| `REQUEST_TIMEOUT` | `500` milliseconds | Time after which a requested chunk can be requested again, not counting the time to send it |
| `REQUEST_TIMEOUT_PER_BYTE` | `16` microseconds | Time added to `REQUEST_TIMEOUT` for every byte of the chunk |
| `MAX_UNANSWERED_REQUESTS` | `1` | Number of requests a peer can leave unanswered before it is not sent requests anymore |

A node disseminates the chunks of the payloads it tracks to its peers on the topic:

- **Push.** When a chunk becomes valid, the node SHOULD send it right away to `PUSH_PEERS` peers that are known to track the payload and not known to hold the chunk, preferring those with the fewest pending messages. It MAY send it to more. If there are fewer such peers, it SHOULD push to further ones as they start to track the payload, until it pushed the chunk to `PUSH_PEERS` peers. It MAY limit how many chunks of a payload it pushes to one peer, and push the rest to peers that start to track the payload later. `PUSH_PHASE` after the first chunk of a payload became valid, the node stops pushing its chunks; they are then only announced and served on request. `PUSH_PHASE` does not apply to the builder.
- **Announce.** The node MUST send its `ChunkMetadata` to each peer when it starts tracking the payload, even if it holds no chunk yet, and whenever its `have` changed since it last told that peer. It MAY coalesce the announcements of chunks that become valid within `ANNOUNCE_INTERVAL`, but SHOULD NOT hold back the first announcement of a payload, nor the one of its last chunk, after which peers stop sending chunks. When a peer sends its first `ChunkMetadata` about a payload, the node MUST send its own again, as the peer dropped earlier messages if it did not track the payload yet.
- **Request.** The node SHOULD request the chunks it lacks from peers that announced them, through `request`, with at most `MAX_REQUESTS_PER_PEER` requests outstanding per peer. A chunk not received within `REQUEST_TIMEOUT`, plus `REQUEST_TIMEOUT_PER_BYTE` for every byte of the chunk, SHOULD be requested again, possibly from another peer. The node SHOULD prefer peers that answered its requests, and MAY stop requesting from a peer that left `MAX_UNANSWERED_REQUESTS` requests unanswered, until the peer sends it chunks it lacked. A node SHOULD NOT send requests within `REQUEST_DELAY` after it starts tracking the payload.
- **Serve.** The node MUST send requested chunks it holds right away, unless it pushed them to the requester before. It is not required to serve more than `MAX_REQUESTS_PER_PEER` requests of a peer at a time: while it has yet to finish sending that many requested chunks to a peer, it MAY ignore further requests of that peer.

To avoid being penalized, a node MUST NOT send a peer a chunk of a payload the peer sent no `ChunkMetadata` about, MUST NOT send a peer a chunk it sent the peer before, MUST NOT request a chunk from a peer it announced or sent that chunk to, and MUST NOT remove a chunk from `have` once announced.

#### Request/response

`ExecutionPayloadEnvelopesByRange` and `ExecutionPayloadEnvelopesByRoot` gain a version 2 for the envelopes of this EIP, with the protocol IDs `/eth2/beacon_chain/req/execution_payload_envelopes_by_range/2/` and `/eth2/beacon_chain/req/execution_payload_envelopes_by_root/2/`. Each response chunk carries an envelope along with the root of its beacon block:

```python
class ExecutionPayloadEnvelopeWithRoot():
    beacon_block_root: Root
    envelope: ExecutionPayloadEnvelope
```

Otherwise, version 2 is identical to version 1, with `beacon_block_root` in place of `signed_execution_payload_envelope.message.beacon_block_root`: `ExecutionPayloadEnvelopesByRoot` requests envelopes by it, and it determines the fork digest context of each response chunk. A node passes a received envelope to `on_execution_payload_envelope` along with its `beacon_block_root`, whose commitment check rejects an envelope paired with the root of a block whose bid does not commit to it.

Version 2 only serves the envelopes of the fork that activates this EIP and later forks, as it carries no signatures. Version 1 remains for the envelopes of earlier forks, which are authenticated by their signatures, and only serves those. A node requests envelopes with the version that serves the fork of the requested slots or blocks, and responds only with the envelopes that the version of the request serves.

### Open questions and future considerations

- The networking scheme could be extended by erasure coding the chunks, so that a receiver can reconstruct the envelope from a subset of chunks. This introduces additional complexity and may lead to higher bandwidth usage. However, it may mitigate "coupon collector" problems, where a receiver missing a small number of chunks may wait a long time to receive them. Such an extension would be a second `ChunkingScheme`. Waggle does not require pieces to be slices of the object, so it can carry erasure-coded chunks as well.
- In future it might be considered to introduce a `bal_chunks` topic following the same broadcasting scheme for Block Access List (BAL, [EIP-7928](./eip-7928.md)) messages, which are currently part of the execution payload. This would allow BAL message propagation to start sooner than the rest of the payload.

## Rationale

**Why a Merkle commitment.** Alternatives such as KZG place proof generation on the builder's critical path. A Merkle tree over chunks is cheap enough to build at bid time, and one root over the chunks makes each chunk self-verifying against the commitment in the validated beacon block.

**Why the envelope omits `beacon_block_root`.** Under [EIP-7732](./eip-7732.md) the builder constructs the envelope after observing that its bid was included, and can therefore embed the beacon block root. Under this EIP the builder must commit to the chunks when it produces the bid — before the block exists — so the root cannot be part of the committed bytes. Instead, the beacon block root identifies the payload on the network: it is the Waggle object ID under which the chunks are disseminated, and receivers verify the chunks against the descriptor of the bid in the block with that root.

**Why the bid commits to the envelope's root as well.** Networking needs the shape of the chunk set and a way to verify each chunk on arrival. Consensus needs to authenticate the whole envelope, however the node obtained it. Checking `hash_tree_root(envelope)` uses existing SSZ code and keeps the chunking scheme out of the state transition. The builder already has the envelope at bid time. Its root costs 32 bytes in the bid.

A proposed change to Gloas would bind the revealed execution payload to the bid by committing to the payload's root. Committing to the whole envelope works independently of that proposal. If Gloas adopts the payload root, that root and the bid's other commitments would bind every field of the envelope and could replace `envelope_root`.

_Recomputing the chunk commitment in consensus._ Checking an envelope by recomputing its chunk root would make chunking part of the state transition. Every consensus client would have to implement each scheme and its codec before a builder could use it. Adding a scheme would require a fork.

_Relying on the bid's `block_hash`._ The bid already commits to the payload's block hash and the root of its execution requests. To verify the block hash itself, the consensus layer would have to compute the execution block header's hash. Otherwise only the execution engine would check the payload's contents, when it received the payload. With `envelope_root` the consensus layer can check the envelope itself, as it does for other objects it receives.

**Why a chunking descriptor in the bid.** The block root commits to the descriptor's fields and types, so changing its layout requires a fork. Consensus does not check the values of those fields. The bid already needs to change for this EIP. Including the fields that forwarding nodes need lets later schemes use the same bid layout.

The count bounds the index, gives the length of `have` and `request`, and tells a node when it has the complete set. The chunk size lets a node check the length of a chunk before using it and bound memory for the set. The chunks can carry scheme-specific information under the root, such as coding parameters or the boundary between two parts of the data. SEACAST, a broadcast protocol for Ethereum's large objects, likewise commits to its chunks through a descriptor of the chunk set.

A scheme can fix the count or the size, or allow either to vary by payload. It can add parity chunks for erasure coding or put the block access list first. All schemes use the same Merkle tree, hash and proof depth because these are part of the message format.

_Carrying the descriptor's values in each chunk._ Putting the values under the root would keep the chunk commitment in the bid to a single root. With the values in the bid, a node knows the shape of the set as soon as it sees the block. The bid topic and the proposer can also pass over a scheme the network has yet to implement. With the values in the chunks, the scheme would come to light only after the block, as a slot without a payload.

_An SSZ `List`._ A `List` would commit to the count again in its root and add a level to every proof. The descriptor already commits to the count. A fixed-size `Vector` gives every proof the same depth and lets clients derive roots and branches with existing SSZ code.

**Why the plain scheme fixes the chunk size.** One of the authors simulated segmented payload broadcast over gossipsub. Latency depended on chunk size more than on count. At 1 MiB it reached its floor at about 16 KiB per chunk. At every payload size tested, 16 KiB chunks gave lower latency than 32 KiB chunks. A fixed chunk size also performed better than a fixed count.

More chunks mean more overhead. The index, SSZ offset, inclusion proof and object ID total 390 bytes per message before metadata, framing and compression. That is about 2.4 percent of a 16 KiB chunk.

There are no Waggle measurements for the schemes discussed here. The dissemination parameters were chosen for a fixed count of 64. A 1 MiB envelope gives 64 plain chunks of 16 KiB each. Larger envelopes give more chunks.

_A fixed count._ A count of 64 would give chunks of about 1.6 KiB at 100 KiB, 16 KiB at 1 MiB and 160 KiB at the size limit. All three sizes fit the format. The plain scheme uses a fixed size because of the latency results above.

**Why a scheme identifier.** One byte per bid identifies how to derive chunks, how to reconstruct the envelope and which descriptor values are valid. Builders can choose a scheme per payload, for example a code below a given size and plain chunks above it. Tying the scheme to the fork version would allow only one scheme per fork and put every change on the fork schedule.

A scheme that fits the bid and message formats can be deployed in client releases because consensus checks the envelope against `envelope_root` and never the scheme. Nodes need to implement a scheme before builders use it. A node that cannot reassemble the envelope can still request it, but may receive it late or never. A Payload Timeliness Committee member that misses the deadline votes the payload absent. Builders have an incentive to wait for nodes to upgrade.

The bid topic forwards only the highest bid. At nodes that accept a new scheme, a high bid using it can suppress lower bids, leaving an unupgraded proposer with fewer bids. A node that does not implement a scheme ignores its bids and does not track its payloads. This avoids penalizing upgraded peers during a rollout.

**Why unpadded `ByteList` chunks.** SSZ has no outer length prefix, so padding bytes would deserialize as envelope data; hashing each chunk's exact bytes commits its true length instead. Pinning the split and merkleization to SSZ lets two clients derive identical roots with existing code.

**Why Waggle.** Besides making the payload the unit of dissemination, as described in the Motivation, Waggle lets all chunks of a payload share one object ID, so each chunk carries only its index and inclusion proof, rather than the commitment, slot and block root. Each Waggle topic uses its own streams, so payload chunks do not queue behind messages on gossipsub topics, nor delay them. Waggle also leaves peer scoring to the application, so penalties follow the validity rules of this EIP.

**Why chunks are only pushed to peers that track the payload.** Nodes validate a beacon block at different times, and a node cannot verify a chunk before it knows the bid of the block. A node that received chunks earlier would have to buffer them unverified, with bounds on the buffer and penalties for chunks of blocks that never arrive, or drop them and fetch them again. Instead, a node announces that it tracks a payload, and peers push chunks to it from then on. A node thus keeps no chunks of payloads it does not track, only the latest `ChunkMetadata` of the peers that announced them, and verifies every chunk on receipt. Keeping that `ChunkMetadata` lets the node push to these peers as soon as it tracks the payload, rather than once they sent it again. The cost is the delay until the announcement of a node reaches its peers.

**Why pushing is limited per peer and in time.** A node that holds every chunk of a payload would otherwise send all of them to the first `PUSH_PEERS` peers to track it, and none to its other peers. A limit per peer spreads the chunks, and peers request the ones not pushed to them. After `PUSH_PHASE`, most peers have already requested the chunks they lack, so pushing them would send them twice. The builder is exempt, as it holds every chunk before any of its peers tracks the payload: pushing each chunk as its peers start to track the payload is how it disseminates the payload.

**Why serving is limited per peer.** A node that had to serve every request right away could be made to queue a whole payload for each peer that requests all of its chunks at once, whether or not that peer requested them from others as well. Honest nodes keep at most `MAX_REQUESTS_PER_PEER` requests outstanding per peer, so a node can ignore the requests beyond that without slowing them down, which bounds what it has queued for a peer.

**Why payloads are tracked for the slot after their own.** A node that does not get a payload during its slot needs it in the next slot at the latest, to import a block built on it. Tracking payloads for that slot lets such a node still get the payload over Waggle, from the peers that hold it. Otherwise it would have to request the envelope from a peer, which it would only do by then as well.

## Backwards Compatibility

The `execution_payload` gossipsub topic is removed, nodes must support Waggle, and the bid gains two fields, so this change is not backwards compatible and requires a fork.

## Security Considerations

Chunks carry no individual signatures. Their authenticity derives entirely from `chunks_root` in the bid of a validated beacon block. For a self-build, the proposer's signature on the block authenticates the bid. Otherwise the builder signs the bid. A node verifies chunks only against the commitment in the bid of a beacon block it has validated, and only forwards valid chunks, so unsigned chunk spam is filtered at the first hop.

The `slot` in `ChunkMetadata` is covered by neither the bid signature nor the inclusion proof. For a tracked payload, a divergent `slot` is rejected. Before that, `slot` only decides whether a node remembers the `ChunkMetadata` about a payload it does not track, so a peer can make a node look up the blocks of made-up payloads of the current and the previous slot. The bound on what a node remembers limits this, together with the deduplication and rate limit on these lookups (see Untracked payloads), and nothing else is kept about payloads a node does not track. A remembered `have` holds at most `MAX_EXECUTION_PAYLOAD_CHUNKS` bits. The `have` a node remembers is, like any `have`, a claim of the peer about itself: it only decides which chunks the node pushes to that peer and requests from it.

Per-index equivocation is not possible: two distinct chunks that both verify at the same index against the same `chunks_root` would imply a collision in the Merkle tree, so at most one chunk per index can propagate for a given payload.

The `chunk.index` bound against `chunk_count` matters because `is_valid_merkle_branch` reads only the low `CHUNK_INCLUSION_PROOF_DEPTH` bits of the index. Without the bound, the same chunk could propagate again at a larger index with the same low bits.

A node checks the descriptor against the format's limits and the scheme's rules before tracking the payload. It also checks the length of each chunk against the descriptor. A bid can therefore make the node carry at most `chunk_count` chunks of at most `chunk_size` bytes each. For plain chunks the total is at most `MAX_PAYLOAD_SIZE` bytes.

The index and length checks are REJECTs. The object ID identifies the block, so both peers check against the same descriptor.

A node ignores a bid for a scheme it does not implement. The node cannot tell whether the identifier denotes a new scheme or no scheme at all. Rejecting the bid would penalize peers that upgraded first. A builder can use a high bid under a new scheme to suppress lower bids at nodes that accept it. This can leave an unupgraded proposer with fewer bids, and the builder pays only if its bid is included.

Waggle does not interpret requests, so it cannot bound them. As a node sends a peer each chunk at most once, a peer can make it upload at most one copy of each payload.

Nodes check message size limits before parsing. A node decompresses chunks only for a payload it tracks, after checking the declared length against the descriptor. These checks bound both the encoded and the decompressed message size.

Valid chunks do not imply a valid envelope, which is still fully validated after reconstruction by `verify_execution_payload_envelope`. The commitment check compares the envelope's root with `envelope_root`. This also covers envelopes obtained by request, which carry no inclusion proofs.

A builder can commit to chunks that reassemble into a different envelope from the one committed by `envelope_root`. Each node may verify and forward the entire set before discovering the mismatch, up to `MAX_PAYLOAD_SIZE` bytes of plain chunks. The node treats the reassembled envelope as invalid, does not count it as received and does not penalize its peers. It can still request the envelope that matches `envelope_root`.
