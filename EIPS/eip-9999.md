## Abstract

This EIP adds `payload_request_chain_root` to `BeaconState`: a running
commitment that binds execution payloads to the beacon blocks that committed to
them.

For each payload, both layers independently derive the same commitment over the
inputs of `engine_newPayload`. The consensus layer derives it from the
`ExecutionPayloadBid`, beacon state, and the execution requests carried in the
following beacon block; the execution layer derives it from the block it holds.

Each per-payload commitment is folded into the value standing after the previous
one, so the root at any block commits to every payload between that block and
the point the chain was anchored — the fork boundary, or the weak subjectivity
checkpoint a consensus client started from. A divergence anywhere in that range
changes every value after it, which is what lets a single equality settle the
whole range rather than one block. The consensus layer supplies its value as a
parameter to `engine_newPayload`, and the execution layer answers whether it
matches the chain it has accumulated.

A consensus client can therefore perform range sync without downloading
execution payload envelopes: it checks nothing per block, and settles the entire
range in one comparison once its execution client has the blocks. Verification
is deferred rather than skipped, and it is not delegated — the consensus layer
still performs the check itself, once, at the end.

The chain advances once per execution block. Slots whose payload is never
revealed produce no execution block and contribute nothing to it.

## Motivation

Before [EIP-7732](./eip-7732.md), a consensus client performing range sync had
to download every execution payload, because payloads were embedded in beacon
blocks. EIP-7732 moved them into separately gossiped
`ExecutionPayloadEnvelope` objects, and in doing so removed the consensus
layer's remaining data dependencies on them: execution requests now arrive in
the following beacon block as `parent_execution_requests`, and withdrawals are
computed from beacon state.

What survives is not a data dependency but a *verification* duty. The consensus
layer must still establish that the payload the execution layer executed is the
payload the beacon chain committed to. Today that is a list of field equalities
in `verify_execution_payload_envelope`, and every one of them needs the payload
in hand. A syncing consensus client must therefore either download every
envelope it will never otherwise use, or leave the range unverified.

The gap is narrow and precisely bounded. The bid's fields are already validated
against beacon state during block processing, and the payload's fields are
already validated by the execution layer. Only the **cross-layer equality** is
missing. This EIP supplies exactly that, and nothing else.

The verification is *deferred*, not delegated. The consensus layer still
performs the check itself; it performs it once at the end of a range rather than
once per block. Execution validity remains delegated to the execution layer
exactly as before.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in RFC 2119 and RFC 8174.

### Design constraint

The commitment MUST be computable by **both** layers from data each already
independently holds. A field the consensus layer cannot compute may enter only
as an opaque root, and an opaque root binds identity, never content. Any field
the consensus layer must *police* therefore appears in plaintext.

### Containers

```python
class ExecutionPayloadCommitment(ProgressiveContainer):
    ACTIVE_FIELDS = active_fields(width=7)

    parent_hash: Hash32
    prev_randao: Bytes32
    gas_limit: Uint64
    timestamp: Uint64
    block_hash: Hash32
    withdrawals: Withdrawals
    slot_number: Uint64
```

```python
class NewPayloadRequestCommitment(ProgressiveContainer):
    ACTIVE_FIELDS = active_fields(width=4)

    execution_payload: ExecutionPayloadCommitment
    versioned_hashes: VersionedHashes
    parent_beacon_block_root: Root
    requests_hash: Hash32
```

The two groups are nested rather than flattened so that each keeps a private
index space. Under [EIP-7495](./eip-7495.md) field positions are permanent and
new fields append at the end, so a flat container would permanently interleave
payload-derived and request-level inputs the first time either gained a field.
Both containers merkleize with the progressive scheme of
[EIP-7916](./eip-7916.md).

These are commitments, not headers. Their roots are **not** equal to
`hash_tree_root(ExecutionPayload)` or `hash_tree_root(NewPayloadRequest)`, and
implementations MUST NOT substitute one for the other. Equal roots would require
equal field counts, since `hash_tree_root` of a progressive container mixes in
its `active_fields` bitvector.

### Why `block_hash` stands in for the rest of the payload

The commitment does not enumerate the remaining `ExecutionPayload` fields. The
execution block hash already commits to every one of them: `state_root`,
`receipts_root`, `logs_bloom`, `block_number`, `gas_used`, `extra_data`,
`base_fee_per_gas`, `blob_gas_used`, `excess_blob_gas`, `fee_recipient` (as
`coinbase`), `transactions` (as `transactions_root`) and `block_access_list`
(as `block_access_list_hash`) are all header fields that `block_hash` is the
keccak of, and the execution layer enforces that correspondence.

A future fork that adds an `ExecutionPayload` field not covered by the execution
block hash MUST also add it to `ExecutionPayloadCommitment`, or that field will
not be bound.

`versioned_hashes` and `requests_hash` are carried explicitly even though the
block hash commits to the same data, because it does so under forms the
consensus layer cannot invert: blob hashes inside `transactions_root`, and
requests as the [EIP-7685](./eip-7685.md) `requests_hash`.

### Guarantee classes

| Class | Fields | What equality proves |
| - | - | - |
| Consensus-authoritative | `parent_hash`, `prev_randao`, `timestamp`, `slot_number`, `withdrawals`, `parent_beacon_block_root` | the execution layer used the **correct** value, derived by the consensus layer from its own state |
| Bid-asserted | `gas_limit`, `block_hash`, `requests_hash` | both layers used the **same** value; correctness rests on execution-layer rules |
| Opaque | every other payload field, via `block_hash` | consistency only; the execution layer's own state transition makes them correct |

### Computable without execution

Every input is drawn from the execution header or the block body:

| Input | Source |
| - | - |
| `parent_hash`, `prev_randao`, `gas_limit`, `timestamp`, `slot_number`, `parent_beacon_block_root` ([EIP-4788](./eip-4788.md)) | execution header |
| `block_hash` | the header's own hash |
| `withdrawals`, `versioned_hashes` | block body |
| `requests_hash` | execution header |

No input requires executing the block. This is why `requests_hash` is used in
place of the bid's `execution_requests_root`: execution requests are *produced
by* execution, so their SSZ root is unavailable to a client that has not
executed the block, while `requests_hash` is a header field.

Two inputs require the block **body**, so an execution client extends the chain
where the body is validated against the header rather than during header
validation alone.

### Consensus layer

`BeaconState` gains one field:

```python
payload_request_chain_root: Bytes32
```

`process_parent_execution_payload` is modified to extend the chain once the
parent payload is known to be present:

```python
state.payload_request_chain_root = compute_payload_request_chain_root(
    state.payload_request_chain_root,
    compute_payload_request_root(state, parent_bid, requests),
)
```

```python
def compute_payload_request_chain_root(
    previous_chain_root: Bytes32, payload_request_root: Root
) -> Bytes32:
    return sha256(previous_chain_root + payload_request_root)
```

The chain advances once per **full** payload, never per slot. A slot whose
payload is not revealed produces no execution block, so it contributes nothing.
Extending the chain when the bid is processed would fold in payloads the
execution layer never produced and desynchronise the two chains on an honest
chain.

No other consensus container is modified. In particular `ExecutionPayload` and
`ExecutionPayloadBid` are unchanged, so generalized indices, serialization and
the engine API container layouts are unaffected, and
`verify_execution_payload_envelope` keeps its existing per-field checks for the
case where the payload is in hand.

### Anchoring

`payload_request_chain_root` is part of `BeaconState` and is therefore carried
by a weak subjectivity checkpoint. A consensus client that checkpoint-syncs
trusts the anchor's value exactly as it trusts the rest of the anchor state, and
supplies it to the execution client as the base to fold from. An execution
client with no chain of its own MUST adopt a supplied base rather than starting
from zero, which it could not otherwise reproduce.

The guarantee is anchored at the checkpoint, not at the fork: the chain attests
that the two layers agree over the range since the anchor, and everything before
it rests on weak subjectivity, as it already does.

### Engine API

`engine_newPayload` gains a `payloadRequestChainRoot` parameter carrying the
consensus client's chain root **through this payload**, and `PayloadStatus`
gains a `payloadRequestChainStatus` reporting the comparison. The result is reported separately from `status`; payload validation
is unchanged and does not consult the chain root.

- `MATCH`: the execution client held the block data for the ancestry, folded
  this payload's request root into its chain, and the result equals the supplied
  value.
- `MISMATCH`: it performed that comparison and the roots differ.
- `UNAVAILABLE`: it did not perform the comparison. This is not a disagreement.

A `MISMATCH` means the beacon chain committed to a payload the execution chain
does not contain. The consensus client MUST NOT treat the covered range as
verified. Client software MUST NOT set `status` to `INVALID` on the strength of
a `MISMATCH` alone, because the delivered payload may itself be valid.

### Networking

`ExecutionPayloadEnvelopesByRange v1` is removed. Its purpose is to serve
historical execution payload envelopes for backfill, and this EIP removes the
reason to fetch them.

`ExecutionPayloadEnvelopesByRoot v1` is unaffected. It is bounded to recent
epochs, so every envelope it returns arrived on gossip and is held locally, and
it answers a question this EIP does not address: whether a payload was revealed
at all, which drives payload attestation processing and fork choice. Gossip is
likewise unchanged.

Historical execution payloads remain available from the execution layer, which
holds them as blocks. Consumers needing one obtain it there, rather than from
the beacon network, which retains only the commitments.

## Rationale

### Why a chain rather than per-block comparison

During range sync the consensus layer's chain of execution block hashes is
entirely builder-asserted. `bid.parent_block_hash` is checked against
`state.latest_block_hash`, so the bid chain is internally consistent, but
nothing ties it to the payload's real `parent_hash` without the payload. A
builder can publish a bid whose `parent_block_hash` matches the consensus
client's expectation while revealing a payload built on a different parent.

Carrying `parent_hash` in plaintext closes this: the consensus layer's root
carries the bid's value, the execution layer's carries the payload's, and they
differ. Relying on `block_hash` alone would not, since both sides would hash the
same value.

Chaining compresses the resulting per-block comparisons into one, which is what
makes skipping envelopes worthwhile.

### Why no execution-layer header field

The chain root is derived metadata, not consensus. Placing it in the execution
header would make it part of block validity, require an execution-layer state
transition rule, and introduce a circularity, since a value committed inside a
block cannot depend on that block's hash. Keeping it out means the execution
layer's notion of a valid block is untouched.

The cost is that the comparison is a bilateral check between one consensus
client and its execution client rather than a network-enforced rule. That is
sufficient, because the property being established is precisely that *this
pair* agrees.

### Why the networking method is removed rather than left in place

Removing the reason to fetch historical envelopes without removing the method
would leave the network in the worst of both positions: clients could skip the
download, but would still be expected to serve it, and a client that skipped
could not serve what it never held. The saving would accrue to individual nodes
while the obligation stayed with everyone, which is not a saving so much as a
transfer.

Removing the method resolves that rather than accepting it. What a node can no
longer answer is something no node is any longer asked.

### Why the parameter is required rather than omissible

Making it omissible would buy nothing. The value is 32 bytes over a local
authenticated socket once per slot, and the consensus layer computes it every
block regardless, since it lives in `BeaconState`. It would however permit a
silent downgrade, in which a consensus client that never supplies the parameter
is never verified and nothing reports that.

Whether the execution client is *able* to compare is a separate question,
answered in the response, because it is a property of that client's state
rather than a choice available to the consensus client.

### Why localisation is unnecessary

A chained commitment reports *that* two chains diverged, never *where*. No
lookup method is specified to recover the position, because none is needed. An
`UNAVAILABLE` result resolves by continuing to deliver payloads as the head
advances, and a chain that is genuinely invalid is localised by ordinary
per-payload validation, which reports `INVALID` with `latestValidHash` as
payloads arrive.

### Why SSZ

The commitment is merkleized with SSZ so that it is domain-separated by
construction, extensible through `active_fields` without invalidating existing
roots, and structurally comparable to the consensus-layer containers it mirrors.
A hand-rolled byte concatenation would need explicit framing to avoid ambiguity
between adjacent variable-length fields.

## Backwards Compatibility

`payloadRequestChainRoot` is a required parameter of a new `engine_newPayload`
version, following `parentBeaconBlockRoot` and `executionRequests`.
Compatibility comes from versioning: consensus clients that do not implement
this EIP continue to call the previous version.

Adding `payload_request_chain_root` to `BeaconState` is a consensus-breaking
change requiring activation as part of a hard fork. No other container changes.

The execution layer gains no new block validity rule, so blocks valid before
this EIP remain valid after it.

Removing `ExecutionPayloadEnvelopesByRange v1` is a networking change. The
beacon API's `getSignedExecutionPayloadEnvelope` accepts any `block_id` and so
becomes best-effort for historical blocks: a node answers from what it holds
locally and returns not-found otherwise.

## Security Considerations

This EIP introduces no new trust assumption. The consensus layer still verifies
the correspondence of every payload; it verifies a range in aggregate rather
than block by block, and a single comparison failing means the range is not
verified.

The guarantee is anchored at the weak subjectivity checkpoint rather than at the
fork, since an execution client that acquired its state by snap sync has
executed no history and must be supplied a base to fold from. This does not
weaken the node's overall assumptions, which already rest on that checkpoint,
but it does mean the chain attests to nothing before the anchor.

A consensus client that skips execution payload envelopes during sync cannot
subsequently serve them to peers, and they cannot be reconstructed from the
execution layer. Whether such a node should be considered fully synced, and how
the network's payload-serving capacity is affected if many nodes elect to skip
them, needs discussion.

The execution layer must merkleize the commitment with SSZ, which it does not
otherwise implement. The requirement is deliberately bounded to the leaves
listed above, and in particular does not extend to the transaction list or the
block access list.
