## Abstract

This EIP adds a frame mode to [EIP-8141](./eip-8141.md) frame transactions: the dependency verification frame. It executes no code. Its data is a list of `(scheme, data_hash, verification_key_hash)` triples, the transaction's dependencies. The only scheme defined is leanSPHINCS, a stateless hash-based signature scheme: a dependency states that `data_hash` is signed under the leanSPHINCS public key `verification_key_hash`, and a zero `data_hash` stands for the transaction's own signature hash. Signatures are not part of the transaction. They travel beside it in the mempool and in the block, which carries one signature per distinct dependency of its transactions, and every node verifies them. The block header commits to the signatures the block carries. Smart accounts read their dependencies through the existing frame introspection instructions and approve on them. A later upgrade can replace the per-signature witnesses with a single aggregate proof of all dependencies, as [EIP-8288](./eip-8288.md) does, and can add dependencies of other kinds, such as proofs, without changing transactions or accounts.

## Motivation

Post-quantum accounts need a signature scheme whose security does not rest on the hardness of discrete logarithms. leanSPHINCS is one. It is stateless, so a key can sign from several devices and be restored from a backup without tracking which one-time keys it has used, and its only primitive is Keccak-256, which every client already implements. Its cost is size: a signature is 7,740 bytes, more than a hundred times a secp256k1 signature, and a block of such transactions carries hundreds of kilobytes of signatures that every node downloads, verifies and keeps.

The lasting fix is aggregation: a block carries one recursive proof that all of its signatures are valid, and nodes verify that proof in place of each signature. The proof systems that would do this are still changing, and building every block would require running a prover. Post-quantum accounts should not wait for them, but they do need, from the start, the interface that aggregation will keep. Accounts are long-lived, and their validation code fixes where a signature is looked for. An account that looks in one place cannot use an aggregate that answers in another without changing its code.

Signatures are also not the only thing that will be verified outside the EVM. Proofs follow, and a proof's witness is hundreds of kilobytes, too large for a transaction to carry. A transaction will then declare what it depends on, and the witness will travel beside it until a block's aggregate proof answers for it. This EIP puts signatures on that model from the start: a transaction declares, the witness travels beside it, and the block answers for it.

This EIP therefore fixes what aggregation keeps, and leaves for later only what it replaces:

- A transaction declares the signatures it depends on in a dependency verification frame. The frame is covered by the transaction's signature hash, and accounts read it with `FRAMEPARAM` and `FRAMEDATACOPY`. Aggregation changes neither.
- The frame is the only declaration. A signature carried inside the transaction would need an entry of its own, naming the same scheme, key and message a second time, and a rule to keep the two consistent.
- Signatures travel beside the transaction, in the mempool and in the block. Nodes, wallets and tools handle a transaction together with its witnesses from the start, so when an aggregate proof takes the place of the signatures, only what accompanies the block changes.
- The block header commits only to the signatures a block carries. A block's dependencies are derived from its transactions, so an aggregate proof can later commit to them in whatever form it needs.
- The scheme is the leanSPHINCS definition an aggregate proof verifies, so keys created under this EIP stay usable once signatures are aggregated.
- Signatures are checked outside the EVM and before execution. A node verifies a block's signatures in parallel with executing it, and a mempool node rejects a transaction with a missing or invalid signature before simulating it.

Allowing only leanSPHINCS keeps this upgrade to one scheme, with one parameter set and a fixed verification cost. Other dependency kinds, such as proofs, can arrive with aggregation: the frame format already names the scheme of each dependency.

### Constants

| Name | Value |
| --- | --- |
| `DEP_VERIFY_FRAME_MODE` | `4` |
| `LEANSPHINCS_SCHEME` | `0x10` |
| `MAX_DEPENDENCIES_PER_FRAME` | `256` (provisional) |
| `LEANSPHINCS_VERIFICATION_GAS` | `3000` (provisional) |

Values marked provisional are placeholders. They will be set based on measurements before this EIP is scheduled for a network upgrade.

`ATOMIC_BATCH_FLAG`, `compute_sig_hash`, `FRAMEPARAM` and `FRAMEDATACOPY` are defined in [EIP-8141](./eip-8141.md).

### Dependency Verification Frame

This EIP adds `DEP_VERIFY_FRAME_MODE` to the set of mode values accepted by EIP-8141's static constraint on `frame.mode`. No other mode value becomes valid.

A frame with this mode is a dependency verification frame. It declares dependencies and executes no code.

#### Encoding

The frame's `data` is the concatenation of `k` triples, each 96 bytes long. Each triple consists of:

- `scheme`: 31 zero bytes followed by one byte identifying the scheme. The only scheme is `LEANSPHINCS_SCHEME`.
- `data_hash`: 32 bytes containing the message to be signed. A value of 32 zero bytes stands for the signature hash of the containing transaction, as specified in [Dependencies](#dependencies).
- `verification_key_hash`: 32 bytes containing the leanSPHINCS public key. Since the key is already 32 bytes, it is used directly without hashing.

#### Constraints

A transaction is invalid if any of its dependency verification frames fails any of the checks below. `chunks(b, n)` splits `b` into consecutive pieces of `n` bytes.

```python
for i, frame in enumerate(tx.frames):
    if frame.mode != DEP_VERIFY_FRAME_MODE:
        continue

    assert len(frame.data) % 96 == 0
    k = len(frame.data) // 96
    assert 1 <= k <= MAX_DEPENDENCIES_PER_FRAME

    for triple in chunks(frame.data, 96):
        assert triple[:31] == bytes(31)
        assert triple[31] == LEANSPHINCS_SCHEME

    assert frame.target is None
    assert frame.value == 0
    assert frame.flags == 0

    # The frame must not belong to an atomic batch. Its own flags are zero,
    # so only the preceding frame's batch flag needs to be checked.
    assert i == 0 or tx.frames[i - 1].flags & ATOMIC_BATCH_FLAG == 0

    assert frame.limits.execution == k * LEANSPHINCS_VERIFICATION_GAS
    assert frame.limits.state == 0
```

`None` denotes EIP-8141's absent target, not the zero address. The frame's `resolved_target` is therefore `tx.sender`, and `FRAMEPARAM(0x00, i)` returns the sender's address. Contracts identify a dependency verification frame by its `mode`, not its target.

These checks apply in addition to EIP-8141's static constraints, which also apply to dependency verification frames.

#### Execution and Receipt

Executing a dependency verification frame performs no call, accesses no account and changes no state. The frame consumes its entire `limits.execution`.

Like any other frame, it produces an EIP-8141 frame receipt, with `status = 1`, `gas_used.execution` equal to the frame's `limits.execution`, `gas_used.state = 0`, and no logs.

### Dependencies

A dependency is a triple `(scheme, data_hash, verification_key_hash)`. The dependency `(LEANSPHINCS_SCHEME, m, pk)` states that the 32-byte message `m` is signed under the leanSPHINCS public key `pk`.

A transaction's dependencies are derived from the triples in all of its dependency verification frames. Each zero `data_hash` is replaced with the transaction's signature hash, and the resulting triples are sorted and deduplicated. A block's dependencies are the combined dependencies of all its transactions, also sorted and deduplicated.

```python
def data_triples(frame):
    return [(t[31], t[32:64], t[64:96]) for t in chunks(frame.data, 96)]

def dependencies(tx):
    return deduplicate_and_sort([
        (scheme, compute_sig_hash(tx) if data_hash == bytes(32) else data_hash, verification_key_hash)
        for frame in tx.frames if frame.mode == DEP_VERIFY_FRAME_MODE
        for (scheme, data_hash, verification_key_hash) in data_triples(frame)
    ])

def block_dependencies(block):
    return deduplicate_and_sort([
        dependency
        for tx in block.transactions
        for dependency in dependencies(tx)
    ])

def deduplicate_and_sort(deps):
    out = []
    for dep in sorted(deps):
        if len(out) == 0 or dep != out[-1]:
            out.append(dep)
    return out
```

Triples are ordered first by `scheme` as an integer, then by `data_hash`, and finally by `verification_key_hash`. The two 32-byte fields are compared byte by byte.

A `data_hash` of 32 zero bytes serves as a placeholder for `compute_sig_hash(tx)`. A transaction cannot include its own signature hash directly in a frame, because that hash covers the frame's `data`. The substitution occurs only in `dependencies(tx)`: the frame's encoded `data` remains unchanged, so `compute_sig_hash` covers the zero bytes and `FRAMEDATACOPY` returns them.

Any nonzero `data_hash` is an explicit message, signed as encoded. Transactions that declare the same scheme, explicit message and public key therefore share the same dependency.

A transaction MAY declare the same triple more than once, either within a frame or across several frames. These repeated declarations contribute only one dependency.

The requirements for satisfying dependencies are specified in [Signatures in the Mempool](#signatures-in-the-mempool) and [Signatures in the Block](#signatures-in-the-block).

### Reading Dependencies During Execution

This EIP introduces no new instruction. Contracts read dependency verification frames using EIP-8141's existing frame introspection instructions:

- `FRAMEPARAM(0x02, i)` returns the `mode` of frame `i`. A dependency verification frame has mode `DEP_VERIFY_FRAME_MODE`.
- `FRAMEPARAM(0x04, i)` returns `len(data)` for frame `i`.
- `FRAMEDATACOPY(memOffset, dataOffset, length, i)` copies the `data` of frame `i` into memory.

The data is read as encoded, so a zero `data_hash` remains 32 zero bytes. An account with public key `pk` typically approves a transaction when one of its dependency verification frames contains the triple `(LEANSPHINCS_SCHEME, bytes(32), pk)`.

Validation code can read a dependency verification frame's data even when that frame appears later in the transaction.
