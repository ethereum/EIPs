## Abstract

This EIP defines `eth/76`, extending [EIP-8437](./eip-8437.md) with transport for multi-transaction proof wrappers. It defines wrapper announcements and retrieval, coverage hints, transaction-hash manifests and compact responses. Direct-witness and recursive-proof wrappers support the dependency schemes enabled by the active fork.

## Motivation

Relaying reusable aggregates can replace many individual witnesses with one proof and reduce the proving work left to builders during block construction. Aggregators can produce overlapping proofs for the same transactions. Wrapper hashes alone do not identify equivalent coverage when proof bytes differ, and repeatedly transmitting transaction encodings wastes bandwidth. Aggregate propagation needs coverage-aware discovery and retrieval.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/76` extends `eth/75` and uses its message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md). The *mempool fork* is selected as in EIP-8437.

In the Recursive Length Prefix (RLP) encodings below, `P` is a nonnegative integer (zero encodes as the empty byte string), `B` is a byte string, and `B_n` is a byte string of exactly `n` bytes.

### Wrapper encoding

The canonical wrapper is the [EIP-8288 wrapper](./eip-8288.md#mempool-wrapper-object) encoded as `[transactions, mode, content]`, with:

- `transactions`: a nonempty list of [EIP-8141](./eip-8141.md) pooled transaction encodings as byte strings, in strictly ascending consensus transaction-hash order. These contain the payload and any elided blob sidecar, without [EIP-8504](./eip-8504.md)'s appended witness list; witnesses are in `content`.
- `mode`: `0` for direct witnesses or `1` for a recursive proof.
- `content`: `[deps, proofs]` for mode `0`, or `[deps, recursive_stark]` for mode `1`.
- `deps`: the sorted, deduplicated union of the transactions' resolved dependencies, encoded as strictly byte-lexicographically ordered 96-byte entries under EIP-8288.
- `proofs`: one witness byte string per dependency, in dependency order.
- `recursive_stark`: one nonempty proof byte string.

Both modes support the schemes enabled by the mempool fork's EIP-8288 rules. The complete canonical RLP encoding MUST be at most `MAX_WRAPPER_BYTES = 2**21` (2 MiB); EIP-8288's applicable dependency limits also apply. Wrapper identity is Keccak-256 of this complete encoding. Hash references are transport-only and MUST be resolved before applying the byte bound or computing the hash.

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes. Before EIP-8288 is enabled, clients MUST NOT send wrapper messages and MUST ignore received ones without penalties; underlying transport size limits still apply.

#### NewProofWrapperHashes (0x18)

`[[mode₀: P, length₀: P, hash₀: B_32, deps-hash₀: B_32, txs-hash₀: B_32, txs-meta₀], ...]`

Announce 1–64 held, validated wrappers in strictly ascending hash order, with canonical length 1–`MAX_WRAPPER_BYTES`. Peers SHOULD announce newly validated wrappers to every connected `eth/76` peer, subject to suppression below, and on connection up to 64 offered wrappers covering pending transactions, most recent first.

The complete RLP announcement payload MUST NOT exceed `2**18` bytes (256 KiB), including metadata. Senders MUST split larger sets; receivers MUST check the bound before decoding. Clients MUST ignore unsupported modes without penalties after checking encoding, count, length and ordering.

- `deps-hash`: Keccak-256 of the concatenated 96-byte entries in `deps`.
- `txs-hash`: Keccak-256 of the concatenated, ascending consensus transaction hashes.
- `txs-meta`: inline metadata for mode `0` wrappers with at most 17 transactions; otherwise the empty list.

Metadata follows wrapper transaction order:

`[[txsize₀: P, ...], [txhash₀: B_32, ...], [txsource₀: B_20, ...], [txfees₀: [P, ...], ...], [txgas₀: P, ...]]`

- `txsize`: the length of the pooled transaction encoding in the complete wrapper.
- `txhash`: the consensus transaction hash.
- `txsource`: the frame transaction's explicit `sender` field, not a recovered signer.
- `txfees`: a copy of its [EIP-8141](./eip-8141.md) `fees` list.
- `txgas`: the sum of its frames' execution and state gas limits.

On the wire, gas is an unsigned 64-bit integer, and each fee is an unsigned 256-bit integer; the fee-list length is not fixed. These encoding bounds do not establish transaction validity. Requesters MAY use metadata to choose and order fetches; it establishes no coverage or validity.

The 17-entry inline budget accommodates the 16 native and one generic witness limits without making those core limits transport constants. Transactions can share dependencies; larger mode 0 wrappers remain fetchable without inline metadata.

Clients SHOULD relay mode 0 wrappers unchanged rather than regroup their transactions and witnesses, preserving wrapper hashes across hops. Under the same verification rules, peers SHOULD suppress hashes already exchanged on the connection; they MAY re-announce after a local interval or eviction from the connection's bounded record.

Requesters MAY skip a fetch when both digests match a held wrapper validated under the current rules, subject to [Mixed-version peers](#mixed-version-peers). Hints alone establish no coverage or validity; matching only `deps-hash` does not identify the transactions.

Peers SHOULD announce a wrapper only if it adds transaction coverage, supplies mode 1 coverage where only mode 0 coverage is known, or reduces proof bytes or locally estimated verification work for the recipient. Compare against held, validated wrappers whose hashes either peer has announced on the connection or whose bodies have been exchanged, under the same verification rules. Different proof bytes alone do not justify another announcement. For mode 0 offers, compare only against mode 0 coverage. Verification-work estimates use local verification-only measurements, not gas charges.

#### GetProofWrappers (0x19)

`[request-id: P, compact: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1–32 distinct wrapper hashes previously announced by the responder on this connection under the same verification rules. Responders MUST treat other hashes as unavailable without penalizing the request, since announcement records may be bounded. `compact` is `0` or `1`: with `0`, returned wrappers MUST contain complete transaction encodings; with `1`, responders MAY use [hash-based omission](#hash-based-omission).

#### ProofWrappers (0x1a)

`[request-id: P, [[hash₀: B_32, wrapper₀], [hash₁: B_32, wrapper₁], ...]]`

Return available validated wrappers as embedded RLP items in the [wrapper encoding](#wrapper-encoding), paired with their canonical hashes, in request order with omissions allowed and no repeats. The recommended soft response limit is 2 MiB. Responders SHOULD stop after reaching it, returning complete wrappers only. Empty responses are permitted.

Requesters MUST match distinct requested hashes in order and check canonical hashes, modes and full lengths against the responder's announcements. They re-request hashes after the last returned wrapper; earlier omissions are unavailable from that peer. Requesters SHOULD fetch each wrapper from one announcer at a time and try another after an empty response or timeout.

Responders whose serving budget is spent SHOULD return an empty response rather than omit wrappers or stay silent. Requesters SHOULD NOT penalize an empty response or count it toward a limit on sources tried for a wrapper. They MAY score earlier omissions in a nonempty response in proportion to the requested wrappers withheld, and SHOULD count an unanswered request against the peer.

#### GetProofWrapperManifests (0x1b)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request the manifests of 1 to 32 distinct wrappers, each previously announced by the responder on that connection under the same verification rules; responders treat other hashes as GetProofWrappers does. A wrapper's manifest is the strictly ascending list of all its consensus transaction hashes, whatever its mode and transaction count. Requesters SHOULD fetch a manifest only when comparing its hashes with held coverage may avoid a wrapper fetch; otherwise they SHOULD request the wrapper directly.

#### ProofWrapperManifests (0x1c)

`[request-id: P, [[hash₀: B_32, [txhash₀: B_32, ...]], ...]]`

Return the manifests of available validated wrappers, paired with their hashes. ProofWrappers' response matching, omission and retry rules, soft response limit, empty responses and scoring apply, with complete manifests in place of wrappers, and served manifests count toward the serving budget. Responders SHOULD keep each validated wrapper's manifest rather than derive it per request. Requesters MUST check a manifest on arrival as specified under [Validation](#validation), and against the wrapper if they fetch it.

### Hash-based omission

Compact responses reconstruct the same canonical wrapper using locally cached transaction encodings.

- With `compact = 1`, responders MAY replace transaction bytes with `[encoding-hash: B_32]`, if smaller. They SHOULD do so when prior wrapper exchanges or announcements indicate the requester holds the encoding. The hash is Keccak-256 of the pooled transaction bytes, excluding the enclosing Recursive Length Prefix (RLP) string prefix. References are RLP lists; transactions are byte strings.
- Requesters MUST resolve references by encoding hash from any locally cached, validated encoding, regardless of which peer supplied it, and check their hashes. The complete wrapper determines identity and byte limits; reconstruction MUST stay within the announced length.
- On a missing encoding, requesters MUST discard the compact item and SHOULD retry with `compact = 0` and a fresh request ID. Cache misses MUST NOT incur penalties.

### Transaction and blob propagation

On an `eth/76` connection with EIP-8288 enabled, dependency-bearing transactions MUST travel in wrappers, not Transactions (`0x02`) or PooledTransactions (`0x0a`); GetPooledTransactions (`0x09`) treats them as unavailable. NewPooledTransactionHashes (`0x08`) announces them only for blob availability. Before EIP-8288 activation, EIP-8437's pooled transaction rules apply.

Wrappers use [EIP-8141's blob network form](./eip-8141.md#networking) with data elided under [EIP-8070](./eip-8070.md). After wrapper validation and EIP-8070's checks, clients SHOULD advertise cells through NewPooledTransactionHashes. Unknown frame hashes may elicit empty GetPooledTransactions responses. GetCells/Cells use consensus hashes and [EIP-8408](./eip-8408.md)'s forms. Clients MUST validate covering wrappers before cell retrieval and complete availability checks before pool admission. Wrapper announcements do not count as cell providers; valid wrappers may circulate before availability is established.

### Mixed-version peers

On `eth/75` connections, dependency transactions use EIP-8437's pooled form. Clients MUST NOT send wrapper messages. To convert a validated mode 0 wrapper, select each transaction's witnesses from `proofs` in that transaction's dependency order and construct EIP-8437's pooled form, retaining any blob sidecar fields. Conversely, a complete pooled transaction supplies a single-transaction mode 0 wrapper by deriving `deps` and moving its witness list to `content`. Neither conversion changes consensus bytes or requires signing or proving.

While connected to `eth/75` peers, clients SHOULD fetch and retain direct witnesses for pending transactions and announce their pooled forms, even when aggregates cover those transactions. Aggregate coverage MUST NOT by itself suppress a fetch needed to serve such a peer. Fetching and retention remain subject to local byte budgets and current verification rules; an aggregate cannot reconstruct missing direct witnesses. Clients MAY release data retained solely for older peers when none remain connected.

A wrapper discarded as unsupported on one connection is not thereby invalid. Clients MUST NOT let that discard suppress fetching the same hash from peers whose negotiated version supports it.

### Validation

Clients MUST check transport and metadata before witness or proof verification, then apply EIP-8288 validation before announcement, serving, reaggregation or transaction admission. Decoders MUST accept structurally valid dependencies with unknown scheme identifiers; active core rules determine validity.

- Clients MUST check the reconstructed wrapper's encoding, length and hash and validate under EIP-8288 before announcement, serving or transaction admission. Until validation completes, received wrapper data MUST remain in bounded request-scoped storage and be discarded on cancellation or timeout.

- Clients MUST validate using the mempool fork's EIP-8288 rules. If those rules change, for example through a new proof verifier or dependency limits, wrappers validated only under the previous rules MUST NOT be served, announced or used to suppress announcements.

- Before decoding or hashing wrapper bodies, requesters SHOULD check that the response's request ID is outstanding and its connection open; responders SHOULD skip requests from closed connections.

- Transport item-count, hard byte-length and response-order violations SHOULD cause disconnection. Malformed transport encodings, unmatched or excess responses, hash, mode or length mismatches, and hash references in a `compact = 0` response MUST be discarded and MAY cause penalties or disconnection. Crossing the soft response limit alone MUST NOT cause penalties. A complete wrapper that violates the wrapper encoding above is likewise malformed.

- Metadata is malformed, and the message carrying it MUST be discarded on arrival, if its five fields do not describe the same, nonzero number of transactions; if its hashes are not strictly ascending; if a size is zero or the sizes do not sum to less than the announced length; or if a `txfees` entry is not a list of integers, or a fee or gas value exceeds the wire bounds above. Metadata is also malformed if it describes more than 17 transactions or accompanies a mode 1 wrapper. An empty `txs-meta` carries no metadata and is checked once the wrapper arrives.

- Once the complete wrapper arrives, clients MUST check its hash and the serving peer's announcement metadata before witness verification. Metadata MUST be exactly what the wrapper's transactions give, and inline metadata empty where the rules above require it. A mismatch MUST cause discard and SHOULD cause disconnection of the serving peer, independently of proof validity. Another peer's metadata MUST NOT affect this check.

- Pool rejection of an individual transaction does not invalidate its covering wrapper and MUST NOT incur peer penalties. Clients SHOULD relay such a wrapper unchanged only if it newly admitted at least one transaction and no fewer than it rejected; already-pending transactions count as neither.

- Witness or dependency-rule failures, including exceeding `MAX_SIGS_PER_TX` or another EIP-8288 dependency limit, MUST cause the wrapper to be discarded. Clients MAY deprioritize or rate-limit further fetches, but MUST NOT penalize or disconnect a peer solely for these failures, even when repeated. Such wrappers are invalid, not malformed.

- Clients MAY deprioritize, rate-limit or disconnect peers that repeatedly fail to answer requests. Fetch limits SHOULD be retained by node identity across reconnections.

- Clients SHOULD bound served ProofWrappers bytes globally and divide the budget fairly between peers, for example 32 MiB/s in total and at most 8 MiB/s per peer.

- Before decoding or hashing manifests, requesters SHOULD check that the response's request ID is outstanding and its connection open.
- A manifest MUST contain a nonempty, strictly ascending list of 32-byte hashes and its RLP encoding MUST be smaller than the announced wrapper length. On arrival, the concatenated hashes in inline metadata or a manifest MUST hash to the sender's announced `txs-hash`. Manifests have no 17-transaction limit.
- Before proof verification, clients MUST check the serving peer's announcement digests and any manifest against the reconstructed wrapper. A manifest MUST list exactly the wrapper's transaction hashes. The metadata-mismatch rules above apply to these checks.
- Metadata and manifests are kept per peer. Fetch decisions based only on unverified hints or manifests MUST remain scoped to their sender: they MUST NOT suppress fetching the same wrapper from another announcer or mark its coverage as validated. One peer's claims MUST NOT cause discard of a wrapper served by another; mismatches are attributed only to their sender.

## Rationale

Wrappers carry transactions alongside covering proofs so receivers can validate them together. This permits multi-transaction coverage without a pool of envelopes awaiting proofs.

Mode distinguishes direct-witness verification from recursive-proof verification; length gives the complete wrapper's encoded size. Dependency and transaction digests identify equivalent coverage despite different proof bytes, avoiding redundant downloads. Compared with a dependency hint alone, `txs-hash` adds 33 encoded bytes per announcement to distinguish different transactions sharing dependencies. Keeping `txs-hash` in every announcement gives both modes the same coverage lookup, even when inline hashes make it derivable. The wire dependency digest uses a fixed hash of encoded triples rather than the circuit digest, allowing checks independent of fork verification rules.

Aggregates can overlap. Hashes-only manifests identify partial overlap without repeating per-transaction metadata; fee-based ranking uses transactions already held. Small mode 0 wrappers retain inline metadata. When the hash list would not change the fetch decision, requesting the wrapper directly avoids a round trip. Compact retrieval can reuse encodings obtained from any peer. A full-wrapper retry after a cache miss avoids a separate missing-transaction request protocol. Encoding hashes also bind blob metadata.

Cell announcements retain EIP-8070's provider and sampler behavior. Cell masks are not part of wrapper identity because peer holdings change independently of the proof.

## Backwards Compatibility

`eth/75` exchanges individual transactions with direct witnesses. `eth/76` exchanges wrappers after EIP-8288 activation; its message shapes do not depend on the enabled dependency schemes. Retaining direct witnesses allows translation for older peers, while aggregate-only coverage cannot supply their pooled form. Consensus validity and block-proof exchange are unaffected.

Client integration cases require peer and fork state not modeled by the checker:

- Discard a wrapper received on an unsupported connection, then receive its hash from an `eth/76` peer. The earlier discard neither marks it invalid nor suppresses fetching it from the compatible peer.
- Hold an aggregate without direct witnesses while connected to an `eth/75` peer. Fetch a mode 0 offer or pooled witnesses within local budgets; validate, retain and serve witnessed pooled transactions to the older peer. All schemes enabled by the core rules are eligible. Release compatibility-only data when no older peers remain.
- A peer knows only mode 0 coverage: announce the first mode 1 aggregate even if it is larger or more expensive to verify. After either peer announces that aggregate, suppress another held, validated aggregate with the same coverage and no reduction in proof bytes or locally estimated verification work.
- Peer A supplies a manifest suggesting no useful coverage; peer B announces the same wrapper with different hints. A fetch decision based only on A's manifest does not suppress fetching from B; validate B's response against B's hints and manifest.
- Without held coverage to compare, fetch the wrapper directly rather than requesting its manifest.
- Hints never establish coverage before validation. A correct hint remains consistent across verifier changes; an incorrect hint is penalizable independently of proof failure.
- Before EIP-8288 activation, exchange pooled transactions and ignore all five wrapper messages. After activation, use wrappers on eth/76; invalidate cached verdicts and coverage suppression when verification rules change.
- A valid wrapper covers A with dependencies `{a, shared}` and B with `{b, shared}`. Admit A and reject B: the original wrapper remains valid and relayable unchanged. Reaggregate A alone with `{a, shared}`; discard only `b`, not `shared`.
- Resolve a compact reference using a validated encoding received from a different peer; if absent or evicted, retry in full. An equal consensus hash with different blob metadata does not resolve the reference.
- Exhaust the direct-generic verification budget with mode 0 proofs, or the recursive-verification budget with singleton or overlapping mode 1 wrappers. Account for verification cost rather than wrapper count; defer further work without treating budget exhaustion as invalidity or peer misbehavior.
- Apply blob availability checks after aggregate validation. Multiple wrappers covering one transaction neither add providers nor reset sampling.

## Security Considerations

Clients should bound announcements, outstanding requests, buffered and cached bytes, serving traffic and verification work per peer and globally. Global budgets should apply across node identities. Mode 0 budgets should account for each witness's scheme and measured verification cost, with separate limits for expensive generic proofs. Mode 1 budgets should account for recursive verification, including singleton and overlapping wrappers. Clients should prefer mode 1 when it reduces work for the covered transactions. Manifests and reconstruction caches need byte and record limits. Exhaustion permits refusal without making a wrapper invalid or implying peer misbehavior.

Metadata and manifests remain claims until checked against validated contents. Cheap checks and fetch limits should precede verification. An unverified claim can affect fetching from its sender but not coverage or other peers' offers. Fee-list length is variable, so budgets count bytes as well as records.

Request deadlines limit withholding. Validation before relay adds download and verification latency at each hop; propagation within the aggregation interval requires measurement. EIP-8070's blobpool safeguards apply. Retaining direct witnesses for mixed-version peers consumes additional, locally bounded storage.
