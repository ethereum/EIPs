## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) mempool wrappers. Peers announce wrapper descriptors, request whole wrappers by content hash, and request the transactions a wrapper lists through a dedicated envelope request. Transactions with dependency verification frames propagate only through wrapper exchange and in block bodies, never in `eth` transaction announcements or broadcasts. The version number and message IDs are placeholders.

## Motivation

An EIP-8288 transaction declares dependencies whose signatures and proofs it does not carry. A pool admits it only with a wrapper whose witnesses or aggregate proof cover those dependencies, so a peer receiving the bare transaction through `NewPooledTransactionHashes` or `PooledTransactions` cannot validate it. Wrappers are mempool objects exchanged between the same peers as transactions and blob cells, so they belong in the `eth` wire protocol. As for transactions since `eth/65`, peers announce wrappers and receivers request the ones they want.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` as defined by [EIP-8070](./eip-8070.md). Status (`0x00`) and all other existing messages are unchanged except as stated below. The version number and the message IDs `0x16` to `0x1a`, the next free IDs after `eth/72`'s `0x15`, are placeholders, assigned with the fork that activates EIP-8288.

### Constants

| Name | Value | Meaning |
| --- | --- | --- |
| `SOFT_RESPONSE_LIMIT` | `2097152` | The `eth` soft response limit (2 MiB) |
| `MAX_WRAPPER_BYTES` | EIP-8288 `MAX_WRAPPER_BYTES` | At most `SOFT_RESPONSE_LIMIT` |
| `MAX_REQUEST_BYTES` | `16384` | Message-data ceiling for AnnounceProofWrappers, GetProofWrappers and GetWrapperEnvelopes |
| `MAX_ANNOUNCEMENTS` | `64` | Descriptors per AnnounceProofWrappers |
| `MAX_WRAPPERS_PER_REQUEST` | `64` | Content hashes per GetProofWrappers |
| `MAX_ENVELOPES_PER_REQUEST` | `1024` | Indices per GetWrapperEnvelopes |
| `MAX_REQUESTS_PER_PEER` | `4` | Outstanding wrapper and envelope requests per direction |

These are transport ceilings, not consensus limits. A client MAY enforce lower local limits and refuse work without penalizing the peer.

### Encoding

Messages use canonical RLP with exactly the field counts specified: shortest integer encodings, no trailing bytes, and 32-byte hashes. Lists MUST be checked against their count bounds before elements are allocated, and the advertised uncompressed size against `MAX_REQUEST_BYTES`, or for responses the client's own message cap, before decompression. Transaction envelopes and proofs are opaque at this layer and parsed afterward by their own bounded parsers. `H` is Keccak-256.

### Dependency-Bearing Transactions

A dependency-bearing transaction has at least one EIP-8288 dependency verification frame. Dependency-bearing transactions are never exchanged via Transactions (`0x02`), NewPooledTransactionHashes (`0x08`) or PooledTransactions (`0x0a`): clients MUST NOT send them there, MUST answer GetPooledTransactions (`0x09`) for one as for an unavailable transaction, and MUST NOT admit one received there. They propagate only through wrapper exchange and in block bodies.

### Descriptors

```text
descriptor = [byte_length: P, content_hash: B_32]
content_hash = H(wrapper)
```

The object ID of a wrapper is its `content_hash`. `wrapper` is the canonical hash-only EIP-8288 wrapper encoding, and `byte_length` its length, from 1 to `MAX_WRAPPER_BYTES`, which lets requesters budget responses as with [EIP-5793](./eip-5793.md) sizes. The same wrapper has the same identity at every peer; different proof bytes give a different object.

### Messages

Receiving any message below before Status is a protocol violation, as for other `eth` messages. Request IDs follow [EIP-2481](./eip-2481.md). Each endpoint MUST keep at most `MAX_REQUESTS_PER_PEER` outstanding GetProofWrappers and GetWrapperEnvelopes requests to each peer. A responder MAY answer any GetProofWrappers or GetWrapperEnvelopes request with an empty list: when no requested item is available, when the request would exceed that count of outstanding requests, or when it exceeds the responder's serving budget. An empty list means only that the request was not served; it says nothing about the requested objects, and the requester MAY retry later or ask another peer that announced them. A nonempty response follows the rules below. As elsewhere in `eth`, responses have no normative hard ceiling: a responder includes the first available requested item and stops before an item that would take the message data past `SOFT_RESPONSE_LIMIT`, so a ProofWrappers response holds exactly one wrapper of `MAX_WRAPPER_BYTES`.

#### AnnounceProofWrappers (0x16)

```text
[[byte_length: P, content_hash: B_32], ...]
```

The list holds 1 to `MAX_ANNOUNCEMENTS` descriptors in strictly ascending `content_hash` order. A sender MUST announce only wrappers it holds in full and has fully validated under EIP-8288. On connection, peers SHOULD announce the wrappers they offer, within the announcement rate limit. Announcements establish no validity and require no action. Each peer SHOULD keep a bounded per-connection set of object IDs the other side is known to hold, having announced or sent them, and SHOULD NOT announce those again. A receiver at its request limit SHOULD keep wanted descriptors in a bounded pending cache, since announcements are not repeated.

#### GetProofWrappers (0x17) and ProofWrappers (0x18)

```text
GetProofWrappers = [request_id: P, [content_hash: B_32, ...]]
ProofWrappers = [request_id: P, [wrapper, ...]]
```

The request names 1 to `MAX_WRAPPERS_PER_REQUEST` distinct content hashes from held descriptors. The responder returns the requested wrappers it holds and offers, in request order, skipping unavailable ones as in PooledTransactions and following the response rule above. Each `wrapper` is embedded as its RLP item, exactly the bytes `content_hash` covers. The requester re-requests the hashes after the last one returned. The requester matches each wrapper, in order, to a distinct requested descriptor with equal `byte_length` and `content_hash`. A wrapper matching none is invalid peer data.

#### GetWrapperEnvelopes (0x19) and WrapperEnvelopes (0x1a)

```text
GetWrapperEnvelopes = [request_id: P, content_hash: B_32, [index: P, ...]]
WrapperEnvelopes = [request_id: P, [envelope: B, ...]]
```

The requester MUST hold the wrapper and send the request to a peer that announced or served it. `indices` is a strictly ascending list of 1 to `MAX_ENVELOPES_PER_REQUEST` integers below `T`, the length of the wrapper's `transactions` list; index `i` names the envelope whose hash is `transactions[i]`. A responder without the validated wrapper checks only the wire bounds, including indices below EIP-8288 `MAX_TXS_PER_WRAPPER`, and returns an empty list. For a responder with the wrapper, an index not below `T` is a protocol violation.

A peer offering a validated wrapper MUST NOT skip listed envelopes, including ones absent from its admitted pool: a nonempty response includes every requested envelope in order, following the response rule above. Entry `k` of `envelopes` is the canonical [EIP-2718](./eip-2718.md) envelope for `indices[k]`. Requests trigger no historical searches or recursive peer fetches. A peer MUST NOT announce a wrapper with a listed envelope above `SOFT_RESPONSE_LIMIT` bytes. The requester MUST check that the response holds no more entries than requested and that each entry's `H` equals `transactions[indices[k]]`. A violation is invalid peer data attributable to that source and wrapper, so a holder cannot skip a listed envelope undetected. An empty list leaves the wrapper incomplete, as above.

### Validation and Relay

On receiving a wrapper, the receiver MUST check its length, `content_hash` and canonical encoding, then resolve every listed hash from its pool or through GetWrapperEnvelopes, and fully validate the wrapper under EIP-8288 for its target fork. A wrapper's target fork is the one EIP-8288 defines for wrapper validation: the fork active at the next slot's timestamp, predicted from the local head with EIP-8288's local slot-length estimate. Validation uses the receiver's locally configured verifier for that fork: its `AGGREGATED_VK` for a mode-1 proof, and its verification parameters for the scheme of each mode-0 witness. It SHOULD check the dependency union before or alongside proof verification. Clients MUST NOT announce, serve, admit or reaggregate a wrapper before full validation; a proof check alone does not authenticate the transaction list. Failed envelope recovery leaves the wrapper incomplete, not invalid. After validation, admission is evaluated per transaction; local refusal, state changes or pool policy do not establish proof invalidity.

When the local head advances to a target fork whose verifier differs, held wrappers follow EIP-8288's upgrade rule, and a client MUST NOT announce or serve a wrapper validated only under the previous verifier. Clients SHOULD keep the proof-verdict caches EIP-8288 specifies.

### Resource Bounds

Clients MUST configure finite request deadlines, a finite recovery deadline and source-attempt budget per wrapper, a per-peer serving budget, an announcement rate limit and a bounded pending-announcement cache. RECOMMENDED defaults are 30-second requests, 120-second recovery across at most three sources, 8 MiB/s of ProofWrappers and WrapperEnvelopes data served per peer, 4 AnnounceProofWrappers messages per second per peer, and 1,024 pending descriptors kept for 60 seconds. These are local policy; different values are not misbehavior. Received wrappers awaiting recovery or verification and recovered envelopes MUST be charged to finite per-peer and global byte budgets before allocation, and stay charged until validation finishes or the wrapper is abandoned. Verification, admission and proving queues MUST have finite concurrency and backlog. Receivers SHOULD deprioritize sources whose wrappers failed validation and SHOULD prefer wrappers announced by several peers.

### Errors

Malformed encodings, wrappers matching no requested descriptor, envelope hash mismatches, responses with more entries than requested and invalid proofs are invalid peer data: the client MUST discard the contribution and MAY disconnect or penalize the peer. Exceeding a count or size bound and misordered lists are protocol violations, after which the client SHOULD disconnect. Empty responses, unavailability, timeouts, local refusal, and pool rejection of a validly proven transaction MUST NOT by themselves be treated as misbehavior. Around a fork that changes the verifier, a client SHOULD treat proof failures as local refusal rather than invalid peer data for a bounded local window (RECOMMENDED: from when its target fork switches to the new fork, a slot before activation, until its own head is 64 blocks past the fork; the window also avoids penalizing peers whose target-fork estimates differ around a slot-length change, although wrapper propagation may be delayed). The window is local policy: Status and BlockRangeUpdate advertise available block history, not the verifier a peer validated under.

## Rationale

### No verifier negotiation

Status is unchanged and peers negotiate no verifier. `forkid` ([EIP-2124](./eip-2124.md)) summarizes the fork activation points a peer knows and accepts compatible peers at different sync stages. It does not establish that two peers configure the same cryptographic parameters, and two connected peers can disagree about the target fork, for example one slot apart around an activation. Each receiver therefore verifies under its own configured rules for its target fork and scopes its verdict caches to that verifier. A wrapper proven for another verifier fails or is refused like any unverifiable proof. A verifier identifier in descriptors would authenticate nothing, since the receiver verifies under its own rules regardless, so the object ID is simply the content hash.

### Whole objects

`eth` responses carry whole objects under the soft response limit. EIP-8288 sizes `MAX_WRAPPER_BYTES` to that limit, so a wrapper response occupies a connection no longer than a BlockBodies, Receipts or Cells response, and needs no reassembly state, chunk credit or cancellation. Content hashing the whole body attributes corruption to the one peer that sent it. Validation before relay adds a download and proof check at every hop, so batch sizes need latency measurements; large wrappers cannot be assumed to propagate within the aggregation interval.

Whole-object retrieval holds only while a wrapper at EIP-8288's list ceilings with its largest permitted proof fits `SOFT_RESPONSE_LIMIT`. At 4,096 transaction hashes and 4,096 dependencies the lists take 536,584 bytes, leaving 1,560,555 bytes for the proof; EIP-8288 owns that bound. A chunked message set or separate capability is justified only if benchmarks put aggregate proofs above about 1 to 2 MiB. It would need requested fixed-size chunks from one source, checked against the content hash after reassembly, with per-peer and global reassembly buffers, chunk credit, cancellation and assembly lifetimes.

### Envelopes and identity

Dedicated envelope requests are scoped to one wrapper, so a peer that offers it either serves each listed envelope or answers empty, and skipped envelopes are detectable. With PooledTransactions a missing transaction cannot be distinguished from eviction. Descriptors carry no dependency digest, transaction-list or proof-hash hints: the verdict cache already avoids repeated verification, identical wrappers share a `content_hash`, and unauthenticated hints would invite deprioritization games.

## Backwards Compatibility

This EIP requires a new `eth` version. Peers on older versions keep exchanging blocks and other transactions but never receive wrappers or dependency-bearing transactions, which they could not validate. `eth/73` ships with the fork that activates EIP-8288, since excluding dependency-bearing transactions from transaction messages is safe only if wrapper exchange ships with it. Before that fork no dependency-bearing transactions or wrappers exist. It changes no consensus rules.

## Test Cases

[Descriptor vectors](../assets/eip-8437/descriptor-vectors.json) use `wrapper[i] = i % 251`. [Wrapper vectors](../assets/eip-8437/wrapper-vectors.json) give 96-byte dependency encodings and hash-only mode-0 and mode-1 wrappers; Keccak-256 stands in for `DEPS_HASH`. [The executable checks](../assets/eip-8437/check_vectors.py) cover both, plus message encodings, response limits and envelope truncation. They test transport encodings, not EIP-8288 proof validity.

| Case | Expected result |
| --- | --- |
| Dependency-bearing transaction in the pool | Not announced, broadcast or returned by transaction messages |
| Zero-length or oversized wrapper; noncanonical RLP; excessive list count | Reject before large allocation |
| Requested wrappers or envelopes exceed `SOFT_RESPONSE_LIMIT` | Longest fitting prefix in request order, first item always included; requester re-requests the rest |
| Envelope request for an unknown or evicted wrapper | Empty list; no penalty |
| Envelope retained outside the admitted pool is requested | Served while the wrapper is offered |
| Wrapper matching no requested descriptor, more envelopes than requested, or an envelope hash mismatch | Invalid peer data; the wrapper stays incomplete |
| Envelope indices unordered, too many, or not below the transaction count | Protocol violation |
| Proof verifies but recovered envelopes do not validate the wrapper | No admission, reaggregation or relay |
| Held mode-1 wrapper, or a peer's proof failure, at a fork that changes `AGGREGATED_VK` | Wrapper dropped and not announced or served; a proof failure within the client's configured fork grace window is local refusal, and after it invalid peer data |

## Security Considerations

A content hash supplied by a malicious peer can match an invalid proof, so announcements and responses establish no validity and full validation precedes relay. Invalid proofs cost verification work without corresponding sender effort; per-peer and global byte, recovery and work budgets remain necessary against many peer identities, and deadlines bound withholding and slow responses. A 2 MiB response delays other `eth` messages on the connection as other soft-limited responses do. Raising `MAX_WRAPPER_BYTES` without chunking would lengthen that delay for every `eth` message.
