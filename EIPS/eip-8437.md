## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) mempool wrappers. Peers announce wrapper descriptors, request whole wrappers by content hash, and recover missing transaction envelopes through `GetPooledTransactions`. Transactions with dependency verification frames are never independently announced or broadcast. The version number and message IDs are placeholders.

## Motivation

An EIP-8288 transaction declares dependencies whose signatures and proofs it does not carry. Admission therefore requires a validated wrapper covering those dependencies. Wrappers are mempool objects exchanged between the same peers as transactions and blob cells, so they belong in the `eth` wire protocol. As for transactions since `eth/65`, peers announce wrappers and receivers request the ones they want.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` as defined by [EIP-8070](./eip-8070.md). Status (`0x00`) and all other existing messages are unchanged except as stated below. The protocol version and message IDs are provisional.

### Constants

| Name | Value | Meaning |
| --- | --- | --- |
| `SOFT_RESPONSE_LIMIT` | `2097152` | The `eth` soft response limit (2 MiB) |
| `MAX_WRAPPER_BYTES` | EIP-8288 `MAX_WRAPPER_BYTES` | At most `SOFT_RESPONSE_LIMIT` |
| `MAX_REQUEST_BYTES` | `16384` | Message-data ceiling for AnnounceProofWrappers and GetProofWrappers |
| `MAX_ANNOUNCEMENTS` | `64` | Descriptors per AnnounceProofWrappers |
| `MAX_WRAPPERS_PER_REQUEST` | `64` | Content hashes per GetProofWrappers |
| `MAX_REQUESTS_PER_PEER` | `4` | Combined outgoing wrapper and envelope-recovery requests per peer |

These are transport ceilings, not consensus limits. A client MAY enforce lower local limits and refuse work without penalizing the peer.

### Encoding

The new messages use canonical RLP with exactly the field counts specified: shortest integer encodings, no trailing bytes, and 32-byte hashes. Lists MUST be checked against their count bounds before elements are allocated, and the advertised uncompressed size against `MAX_REQUEST_BYTES`, or for responses the client's own message cap, before decompression. Transaction envelopes and proofs are opaque at this layer and parsed afterward by their own bounded parsers. `H` is Keccak-256.

### Dependency-Bearing Transactions

A dependency-bearing transaction has at least one EIP-8288 dependency verification frame. Clients MUST NOT send these transactions through Transactions (`0x02`) or announce them through NewPooledTransactionHashes (`0x08`). Their envelopes are retrieved through GetPooledTransactions / PooledTransactions for wrapper recovery as specified below; receipt alone does not authorize admission or relay. They also appear in block bodies.

### Descriptors

```text
descriptor = [byte_length: P, content_hash: B_32]
content_hash = H(wrapper)
```

The object ID of a wrapper is its `content_hash`. `wrapper` is the canonical hash-only EIP-8288 wrapper encoding, and `byte_length` its length, from 1 to `MAX_WRAPPER_BYTES`, which lets requesters budget responses as with [EIP-5793](./eip-5793.md) sizes. The same wrapper has the same identity at every peer; different proof bytes give a different object.

### Messages

Receiving any message below before Status is a protocol violation, as for other `eth` messages. Request IDs follow [EIP-2481](./eip-2481.md). Each endpoint MUST keep at most `MAX_REQUESTS_PER_PEER` outstanding requests to each peer, counting GetProofWrappers and GetPooledTransactions used for wrapper recovery together. A responder MAY answer GetProofWrappers with an empty list when no requested wrapper is available or a request or serving budget is exhausted. An empty list means only that the request was not served; it says nothing about the requested wrappers, and the requester MAY retry later or ask another peer that announced them. As elsewhere in `eth`, ProofWrappers responses have no normative hard ceiling: a responder includes the first available requested item and stops before an item that would take the message data past `SOFT_RESPONSE_LIMIT`, so a response holds exactly one wrapper of `MAX_WRAPPER_BYTES`.

#### AnnounceProofWrappers (0x16)

```text
[[byte_length: P, content_hash: B_32], ...]
```

The list holds 1 to `MAX_ANNOUNCEMENTS` descriptors in strictly ascending `content_hash` order. A sender MUST announce only wrappers it holds in full and has fully validated under EIP-8288. On connection, peers SHOULD announce the wrappers they offer, within the announcement rate limit. Announcements establish no validity and require no action. Each peer SHOULD keep a bounded per-connection set of object IDs the other side is known to hold, having announced or sent them, and SHOULD NOT announce those again. A receiver at its request limit SHOULD keep wanted descriptors in a bounded pending cache, since announcements are not repeated.

#### GetProofWrappers (0x17) and ProofWrappers (0x18)

```text
GetProofWrappers = [request_id: P, [content_hash: B_32, ...]]
ProofWrappers = [request_id: P, [wrapper, ...]]
```

The request names 1 to `MAX_WRAPPERS_PER_REQUEST` distinct content hashes from held descriptors. The responder returns the requested wrappers it holds and offers, in request order, skipping unavailable ones as in PooledTransactions and following the response rule above. Each `wrapper` is embedded as its RLP item, exactly the bytes `content_hash` covers. The requester re-requests the hashes after the last one returned. The requester matches each wrapper, in order, to a distinct requested descriptor with equal `byte_length` and `content_hash`. A wrapper matching none is invalid peer data.

### Envelope Recovery

Clients MUST recover missing envelopes through GetPooledTransactions (`0x09`), requesting only hashes listed in held wrappers from peers that announced or served those wrappers. The existing request/response encodings, limits, ordering and unavailable-item handling apply. Clients MUST correlate responses with pending recovery through `request_id` and match each returned envelope's `H` to a distinct requested hash in request order; omitted entries remain unresolved. Dependency-bearing envelopes MUST NOT be admitted or relayed until a covering wrapper is fully validated.

A peer offering a validated wrapper MUST retain every listed envelope and make it available through PooledTransactions (`0x0a`), including envelopes absent from its admitted pool. Lookups MUST be limited to the pool and a bounded cache of retained wrapper envelopes, without historical searches or recursive peer fetches. A peer MUST NOT announce a wrapper with a listed envelope above `SOFT_RESPONSE_LIMIT` bytes. Pool rejection or eviction does not remove an envelope while its wrapper is offered.

### Validation and Relay

On receiving a wrapper, the receiver MUST check its length, `content_hash` and canonical encoding, resolve every listed hash from held envelope bytes or through GetPooledTransactions, and fully validate the wrapper under [EIP-8288](./eip-8288.md), which defines its target fork, verifier, verdict caches, verifier-change rule and per-transaction admission. Clients MUST NOT announce, serve, admit or reaggregate a wrapper before full validation; a proof check alone does not authenticate the transaction list. Failed envelope recovery leaves the wrapper incomplete, not invalid. After a verifier change, a client MUST NOT announce or serve a wrapper validated only under the previous verifier.

### Resource Bounds

Clients MUST configure finite request deadlines, a finite recovery deadline and source-attempt budget per wrapper, a per-peer serving budget, an announcement rate limit and a bounded pending-announcement cache. RECOMMENDED defaults are 30-second requests, 120-second recovery across at most three sources, 8 MiB/s of wrappers and dependency-bearing envelopes served per peer, 4 AnnounceProofWrappers messages per second per peer, and 1,024 pending descriptors kept for 60 seconds. These are local policy; different values are not misbehavior. Received wrappers awaiting recovery or verification and recovered envelopes MUST be charged to finite per-peer and global byte budgets before allocation, and stay charged until validation finishes or the wrapper is abandoned. Verification, admission and proving queues MUST have finite concurrency and backlog. Receivers SHOULD deprioritize sources whose wrappers failed validation.

### Errors

Malformed encodings, wrappers matching no requested descriptor, envelope hash mismatches, responses with more entries than requested and invalid proofs are invalid peer data: the client MUST discard the contribution and MAY disconnect or penalize the peer. Exceeding a count or size bound and misordered lists are protocol violations, after which the client SHOULD disconnect. Empty responses, unavailability, timeouts, local refusal, and pool rejection of a validly proven transaction MUST NOT by themselves be treated as misbehavior. Around a fork that changes the verifier, a client SHOULD treat proof failures as local refusal rather than invalid peer data for a bounded local window (RECOMMENDED: from when its target fork switches to the new fork, a slot before activation, until its own head is 64 blocks past the fork; the window also avoids penalizing peers whose target-fork estimates differ around a slot-length change, although wrapper propagation may be delayed). The window is local policy: Status and BlockRangeUpdate advertise available block history, not the verifier a peer validated under.

## Rationale

### Whole objects

`eth` responses carry whole objects under the soft response limit. Whole-object retrieval requires every permitted wrapper, at EIP-8288's list ceilings with its largest permitted proof, to fit `SOFT_RESPONSE_LIMIT`; EIP-8288 sizes `MAX_WRAPPER_BYTES` to that limit, so a wrapper response occupies a connection no longer than a BlockBodies, Receipts or Cells response. Content hashing the whole body attributes corruption to the one peer that sent it. Validation before relay adds a download and proof check at every hop, so batch sizes need latency measurements; large wrappers cannot be assumed to propagate within the aggregation interval.

### Envelopes and identity

Envelope retrieval reuses GetPooledTransactions, as [EIP-8070](./eip-8070.md) does while retrieving cells separately. Wrapper association stays in local request state, and a bounded envelope cache extends serving beyond pool admission without permitting historical lookups. Descriptors carry no hints: identical wrappers already share a `content_hash`, EIP-8288's verdict caches avoid repeat verification, and unauthenticated hints invite deprioritization games.

## Backwards Compatibility

This EIP requires a new `eth` version: wrappers are mempool objects exchanged with the same peers as transactions, so they extend `eth` rather than a separate capability. Peers on older versions keep exchanging blocks and other transactions but MUST NOT receive wrappers or dependency-bearing envelopes through transaction messages; GetPooledTransactions treats those envelopes as unavailable. `eth/73` ships with the fork that activates EIP-8288, since excluding dependency-bearing transactions from independent transaction gossip is safe only if wrapper exchange ships in the same version. Before that fork no dependency-bearing transactions or wrappers exist.

## Test Cases

[Descriptor vectors](../assets/eip-8437/descriptor-vectors.json) use `wrapper[i] = i % 251`. [Wrapper vectors](../assets/eip-8437/wrapper-vectors.json) give 96-byte dependency encodings and hash-only mode-0 and mode-1 wrappers; Keccak-256 stands in for `DEPS_HASH`. [The executable checks](../assets/eip-8437/check_vectors.py) cover both, plus message encodings, response limits and pooled-envelope response matching. They test transport encodings, not EIP-8288 proof validity.

| Case | Expected result |
| --- | --- |
| Dependency-bearing transaction in the pool | No independent announcement or broadcast; envelope served for wrapper recovery on eth/73 only |
| Zero-length or oversized wrapper; noncanonical RLP; excessive list count | Reject before large allocation |
| Requested wrappers exceed `SOFT_RESPONSE_LIMIT` | First available wrapper always included; stop before the next would exceed the limit |
| PooledTransactions omits an unavailable envelope or truncates the response | Existing eth retry rules; unresolved wrappers remain incomplete, not invalid |
| Envelope retained outside the admitted pool is requested | Served through PooledTransactions while the wrapper is offered |
| Wrapper matching no requested descriptor, more envelopes than requested, or an envelope hash mismatch | Invalid peer data; the wrapper stays incomplete |
| PooledTransactions repeats an envelope or returns envelopes out of request order | Invalid peer data; no wrapper admission or relay |
| Proof verifies but recovered envelopes do not validate the wrapper | No admission, reaggregation or relay |
| Held mode-1 wrapper, or a peer's proof failure, at a fork that changes `AGGREGATED_VK` | Wrapper dropped and not announced or served; a proof failure within the client's configured fork grace window is local refusal, and after it invalid peer data |

## Security Considerations

A content hash supplied by a malicious peer can match an invalid proof, so announcements and responses establish no validity and full validation precedes relay. Invalid proofs cost verification work without corresponding sender effort; per-peer and global byte, recovery and work budgets remain necessary against many peer identities, and deadlines bound withholding and slow responses. A 2 MiB response delays other `eth` messages on the connection as other soft-limited responses do. Raising `MAX_WRAPPER_BYTES` would lengthen that delay for every `eth` message.
