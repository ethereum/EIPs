## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) proof wrappers ("wrappers" below). Peers announce wrapper modes, lengths and hashes, then request whole wrappers by hash.

## Motivation

EIP-8288 separates signatures and proofs from transaction envelopes and permits aggregation across transactions. Existing transaction propagation does not identify this shared proof material, so peers need a way to discover and retrieve it.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` ([EIP-8070](./eip-8070.md)), using its notation and message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md).

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes.

The local target fork is the fork at `head.timestamp + L`, where `L = (head.timestamp - parent.timestamp) // (head.slot_number - parent.slot_number)` using [EIP-7843](./eip-7843.md). If the parent or slot numbers are missing, or either difference is nonpositive, use the head's fork.

Before the local target fork enables EIP-8288, clients MUST NOT send wrapper messages and MUST ignore received wrapper messages without penalties; underlying transport size limits still apply.

#### NewProofWrapperHashes (0x16)

`[[mode₀: P, length₀: P, hash₀: B_32], [mode₁: P, length₁: P, hash₁: B_32], ...]`

Announce 1–64 held wrappers in strictly ascending hash order: mode is `0` or `1`, length is 1–`MAX_WRAPPER_BYTES`, and hash is Keccak-256 of the complete canonical RLP wrapper, including pooled transaction encodings. Peers SHOULD announce offered wrappers on connection and newly validated wrappers to every connected `eth/73` peer.

Under the same verification rules, peers SHOULD suppress hashes already exchanged on the connection and wrappers whose transactions are covered by held, validated wrappers exchanged with or announced by the recipient, unless they reduce proof bytes or estimated verification work, or provide an IL-bounded mode-1 proof where existing coverage cannot.

#### GetProofWrappers (0x17)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1 to 32 distinct wrapper hashes per message, each previously announced by the recipient on that connection under the same verification rules. Responders MUST treat hashes they have not announced as unavailable.

#### ProofWrappers (0x18)

`[request-id: P, [wrapper₀, wrapper₁, ...]]`

Return available validated wrappers as complete embedded [EIP-8288 RLP items](./eip-8288.md#mempool-wrapper-object), in request order with omissions allowed and no repeats. `MAX_WRAPPER_BYTES` equals the 2 MiB soft response limit; responders SHOULD stop once the response reaches it, allowing the last wrapper to cross it. Wrappers MUST NOT be truncated to meet the soft limit. Empty responses are permitted.

Requesters match distinct requested hashes in order, check modes and lengths against the recipient's announcements, and re-request hashes after the last returned wrapper. Earlier omissions are unavailable from that peer. Requesters SHOULD fetch each wrapper from one announcer at a time and try another after an empty response or timeout.

### Transaction propagation

Dependency-bearing transactions MUST NOT appear in Transactions (`0x02`) or PooledTransactions (`0x0a`) on any version; GetPooledTransactions (`0x09`) treats them as unavailable. NewPooledTransactionHashes (`0x08`) MUST NOT announce them except for blob availability below.

#### Blob-carrying dependency transactions

On `eth/73`, EIP-8070 applies to blob-carrying frame transactions. ProofWrappers carries [EIP-8141's pooled network form](./eip-8141.md#networking) with blob data elided.

- After wrapper validation and EIP-8070's checks, clients SHOULD advertise cells through NewPooledTransactionHashes, with covering-wrapper announcements subject to suppression. Unknown frame hashes may elicit empty GetPooledTransactions responses.
- GetCells/Cells use consensus transaction hashes. Dependency-bearing transactions require a validated covering wrapper before cell retrieval and EIP-8070's checks before admission. Validated wrappers may circulate before availability is established; their announcements do not count as providers.

### Validation

- Clients MUST check the complete wrapper's encoding, length and hash and validate under EIP-8288 before announcement, serving, reaggregation or transaction admission. Until validation completes, received wrapper data MUST remain in bounded request-scoped storage and be discarded on cancellation or timeout.

- Validate under the local target fork's EIP-8288 rules. A verification-rule change MUST reset announcement suppression; wrappers validated only under old rules MUST NOT be served or announced.

- Count, hard-length and ordering violations SHOULD cause disconnection. Malformed encodings, unmatched or excess responses, hash or metadata mismatches, and EIP-8288-invalid wrappers MUST be discarded and MAY cause penalties or disconnection. Crossing the soft response limit alone MUST NOT cause penalties.

- Clients SHOULD withhold dependency-validation penalties during a bounded grace window around scheduled verification-rule changes, independent of the local head (recommended: one slot before through 64 slots after activation, measured by wall-clock time).

## Rationale

An EIP-8288 transaction declares dependencies but does not contain the signatures or proofs needed to verify them. Propagating its envelope separately could therefore deliver a transaction before the proof of its dependencies. The receiver would have to retain that envelope pending the proof, or discard it and fetch it again later.

Wrappers bundle transactions with their dependency proofs, allowing dependency validation on receipt. An aggregate proof can cover several transactions; existing transaction messages have no field for that shared proof.

Keeping cell availability in NewPooledTransactionHashes preserves EIP-8070's per-transaction provider/sampler behavior. Cell masks inside hashed wrappers would make identity depend on each peer's changing holdings. An occasional empty transaction fetch is preferable to duplicating that availability protocol.

Mode distinguishes direct checks from recursive verification; length estimates download size. Dependency-digest and proof-hash hints are unnecessary: identical wrappers share a hash, and proof-verification results can be cached independently of wrapper identity. Coverage-based suppression limits reaggregation traffic while allowing cheaper or IL-reusable proofs.

Wrappers fit the soft response limit, so partial responses omit whole wrappers without continuation indices. Omitting cached envelopes could save bandwidth, but requires cache tracking and full-wrapper retries. Validation before relay adds per-hop download and verification latency; propagation within the aggregation interval requires measurements.

## Backwards Compatibility

`eth/73` may be negotiated before EIP-8288 activates; wrapper exchange begins when the local target fork enables it. Older versions continue exchanging blocks and other transactions but receive neither wrappers nor dependency-bearing envelopes through transaction messages.

## Test Cases

[Announcement vectors](../assets/eip-8437/announcement-vectors.json), [wrapper vectors](../assets/eip-8437/wrapper-vectors.json) and [the checker](../assets/eip-8437/check_vectors.py) cover the following encoding and matching cases; synthetic envelopes and witnesses do not test transaction or proof validity.

| Checker case | Expected result |
| --- | --- |
| Maximum announcement/request; excess count | 2,499/1,071 encoded bytes for 64 announcements/32 hashes; reject excess |
| Request a received announcement; request an unannounced hash | Requester selects the former; responder omits the latter |
| Changed enclosed envelope, proof bytes or announced mode/length | Reject mismatch |
| Empty envelopes, hash references, duplicate or reordered envelopes | Reject malformed or noncanonical wrapper |
| Blob network wrapper with elided data, commitments and cell proofs | Accept encoding; use the consensus transaction hash for ordering and cell requests |
| Nonempty blob data, mismatched commitments or wrong proof counts | Reject wrapper; metadata changes also change wrapper identity |
| Complete wrapper exactly at 2 MiB; one byte larger | Accept the size boundary, including response overhead; reject the oversized wrapper |
| Response crosses soft limit on final wrapper | Stop packing; receiver accepts overshoot |
| Response omits whole wrappers, repeats or reorders them | Accept omissions; reject repeats/reordering |

Client integration cases require peer and fork state not modeled by the checker:

- Suppress wrappers covering already-covered transactions unless cheaper or newly IL-reusable.
- Before local activation, ignore wrapper messages without penalties and send none.
- A complete wrapper can be validated without envelope requests; cancelled or timed-out validation releases its request buffer without admitting transactions.
- An unknown blob frame hash triggers an empty GetPooledTransactions response; its covering wrapper later arrives. Fetch cells only after validating it; admit only after EIP-8070's checks.
- Multiple wrappers covering A do not add providers or reset sampling. Two peers' full-cell announcements count as two providers; invalid cells do not invalidate the dependency proof or unrelated transactions.

## Security Considerations

Clients should bound per-peer announcements, outstanding requests, buffered bytes, verification/proving work and serving traffic. Request deadlines limit withholding; large responses delay other messages. EIP-8070's blobpool safeguards apply. Permitted empty or partial responses and local budget exhaustion alone should not incur penalties.
