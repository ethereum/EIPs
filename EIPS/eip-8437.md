## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) proof wrappers ("wrappers" below). Peers announce wrapper hashes and lengths, then request whole wrappers by hash.

## Motivation

EIP-8288 separates signatures and proofs from transaction envelopes and permits aggregation across transactions. Existing transaction propagation does not identify this shared proof material, so peers need a way to discover and retrieve it.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` ([EIP-8070](./eip-8070.md)), using its notation and message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md).

### Modifications to existing messages

A dependency-bearing transaction contains an EIP-8288 dependency verification frame.

**Transactions (0x02) and NewPooledTransactionHashes (0x08):** Clients MUST NOT broadcast or announce dependency-bearing transactions through these messages.

**GetPooledTransactions (0x09) and PooledTransactions (0x0a):** Existing encodings and limits apply.

- Below `eth/73`, responders MUST answer requests for dependency-bearing transactions as unavailable. On `eth/73`, they serve them like any pooled transaction.
- On `eth/73`, missing envelopes are recovered through GetPooledTransactions, requesting distinct hashes listed in held wrappers from peers that announced or served those wrappers. [EIP-5793](./eip-5793.md) announcement-based type and size checks do not apply; requesters correlate responses by `request-id` and keep each request within the usual 256-hash soft limit.
- PooledTransactions returns envelopes in request order without repeats, allowing omissions and truncation. Requesters match each returned transaction to a distinct requested hash by its transaction hash: Keccak-256 of its [EIP-2718](./eip-2718.md) envelope, excluding any network wrapper. Repeated, reordered or unrequested entries are unmatched data: the requester discards them and MAY disconnect.
- Responders SHOULD serve every envelope listed in a wrapper they offer, including those rejected or evicted from the pool, looking up only the pool and a bounded wrapper-envelope cache, without historical searches or recursive fetches. Requesters treat envelopes omitted before the last returned one as unavailable from that peer and continue with another announcer; omissions are not misbehavior.

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes. The largest valid NewProofWrapperHashes is 2,435 bytes and GetProofWrappers 2,127 bytes; larger NewProofWrapperHashes or GetProofWrappers messages are invalid.

#### NewProofWrapperHashes (0x16)

`[[length₀: P, hash₀: B_32], [length₁: P, hash₁: B_32], ...]`

- Announce 1 to 64 held wrappers in strictly ascending hash order.
- Each length is the encoded wrapper size, from 1 to EIP-8288's `MAX_WRAPPER_BYTES`, and each hash is Keccak-256 of those exact bytes.
- Peers SHOULD announce offered wrappers on connection.
- On fully validating a new wrapper, peers SHOULD announce it to every connected `eth/73` peer not known to hold it.
- Peers SHOULD NOT announce hashes already announced or sent, in either direction, on that connection.

#### GetProofWrappers (0x17)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1 to 64 distinct wrapper hashes, each announced by the recipient.

#### ProofWrappers (0x18)

`[request-id: P, [wrapper₀, wrapper₁, ...]]`

- Return requested, offered wrappers in request order, omitting unavailable entries; each wrapper is a canonical hash-only EIP-8288 wrapper embedded as an RLP item.
- Include the first available wrapper, then stop before another would take the encoded response past the `eth` soft response limit (2 MiB).
- Responders MAY return an empty list for unavailability or an exhausted serving budget.
- Requesters match wrappers to distinct requested hashes and the responding peer's announced lengths in order, then re-request hashes after the last returned wrapper.

### Validation

- Clients MUST check wrapper encoding, length and hash, resolve all listed envelopes, and fully validate under [EIP-8288](./eip-8288.md) before announcing, serving or reaggregating. Proof checks against the wrapper's declared dependencies MAY run before or alongside envelope recovery.
- Dependency-bearing transactions MUST NOT be admitted or relayed without a fully validated covering wrapper; unresolved envelopes leave a wrapper incomplete, not invalid.
- After a verifier change, clients MUST NOT announce or serve wrappers validated only under the previous verifier.
- Count, size or ordering violations SHOULD cause disconnection.
- Malformed encodings, unmatched or excess responses, and invalid proofs MUST be discarded and MAY cause disconnection or penalties.
- Unavailability or local refusal alone MUST NOT be treated as misbehavior.
- Around a verifier change, clients SHOULD treat proof failures as local refusal for a bounded local window (RECOMMENDED: from one slot before the local target fork changes the verifier until the head is 64 blocks past the fork).

## Rationale

### Transaction propagation

Standalone transaction announcements do not identify the proofs covering their dependencies. Wrapper announcements let receivers retrieve transaction hashes together with their associated proof material. Transaction envelopes remain retrievable through GetPooledTransactions, reusing existing encodings and response handling without introducing a second envelope-retrieval protocol. Recovery starts from wrapper announcements, which provide no transaction type or size metadata for EIP-5793's checks.

### Whole-wrapper retrieval

Whole-wrapper retrieval follows `eth`'s existing whole-object responses, and EIP-8288 bounds wrapper size to fit the 2 MiB soft limit, avoiding separate chunk requests and assembly. Validation before relay adds a download and proof check at each hop, so batch sizes need latency measurements; propagation within the aggregation interval cannot be assumed.

### Recovery and announcements

A bounded envelope cache permits recovery after pool rejection or eviction without historical lookups. Announcements carry no hints: identical wrappers already share a hash, EIP-8288's verdict caches avoid repeat verification, and unauthenticated hints invite deprioritization games.

The verifier-change grace window accommodates differing fork estimates between peers.

## Backwards Compatibility

`eth/73` activates with EIP-8288. Older versions continue exchanging blocks and other transactions but receive neither wrappers nor dependency-bearing envelopes through transaction messages.

## Test Cases

[Announcement vectors](../assets/eip-8437/announcement-vectors.json) use `wrapper[i] = i % 251`. [Wrapper vectors](../assets/eip-8437/wrapper-vectors.json) give 96-byte dependency encodings, BLAKE2s-256 dependency digests and hash-only mode-0 and mode-1 wrappers. [The executable checks](../assets/eip-8437/check_vectors.py) cover these vectors, message encodings, response limits and pooled-envelope matching, not EIP-8288 proof validity.

| Case | Expected result |
| --- | --- |
| Zero-length or oversized wrapper | Reject |
| Maximum-size wrapper response | Include one wrapper plus message overhead |
| Next wrapper would exceed the soft response limit | Truncate before it |
| PooledTransactions omissions, truncation or empty response | Accept |
| Repeated, reordered, unrequested or extra envelopes | Discard as unmatched data; MAY disconnect |

## Security Considerations

Invalid proofs impose verification costs without corresponding sender effort. Clients should bound outstanding requests per peer, bytes awaiting validation, verification and proving work, and serving traffic; recovery deadlines limit withholding. Large responses delay other messages on the same connection. Implementations should bound each peer's share of pending announcements.
