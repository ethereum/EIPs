## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) mempool wrappers. Peers announce wrapper hashes and lengths, then request whole wrappers by hash.

## Motivation

EIP-8288 transactions declare dependencies whose signatures and proofs are carried separately in wrappers. Admission requires a validated covering wrapper, so announcing a transaction independently prompts fetches without identifying the required proof. Wrapper exchange lets existing transaction peers discover and retrieve that proof material.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` ([EIP-8070](./eip-8070.md)), using its notation and message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md).

### Modifications to existing messages

A dependency-bearing transaction contains an EIP-8288 dependency verification frame.

**Transactions (0x02) and NewPooledTransactionHashes (0x08):** Clients MUST NOT broadcast or announce dependency-bearing transactions through these messages.

**GetPooledTransactions (0x09) and PooledTransactions (0x0a):** Existing encodings and limits apply.

- Below `eth/73`, dependency-bearing envelopes MUST be treated as unavailable. On `eth/73`, clients MUST recover missing envelopes through GetPooledTransactions, requesting distinct hashes listed in held wrappers from peers that announced or served those wrappers.
- PooledTransactions returns envelopes in request order without repeats, allowing omissions and truncation. Clients MUST correlate by `request-id` and match each envelope's Keccak-256 hash to a distinct requested hash.
- While offering a wrapper, peers MUST retain and make every listed envelope available, including those rejected or evicted from the pool. Lookups MUST use only the pool and a bounded wrapper-envelope cache, without historical searches or recursive fetches.

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes.

#### NewWrapperHashes (0x16)

`[[length₀: P, hash₀: B_32], [length₁: P, hash₁: B_32], ...]`

Announce 1 to 64 held wrappers in strictly ascending hash order. Each length is the encoded wrapper size, from 1 to EIP-8288's `MAX_WRAPPER_BYTES`, and each hash is Keccak-256 of those exact bytes. Peers SHOULD announce offered wrappers on connection and SHOULD NOT announce hashes the peer has announced or sent. Peers MUST NOT announce wrappers listing transaction envelopes larger than 2 MiB.

#### GetWrappers (0x17)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1 to 64 distinct wrapper hashes from held announcements.

#### Wrappers (0x18)

`[request-id: P, [wrapper₀, wrapper₁, ...]]`

Return requested, offered wrappers in request order, omitting unavailable entries; each wrapper is a canonical hash-only EIP-8288 wrapper embedded as an RLP item. Include the first available wrapper, then stop before another would take the encoded response past the 2 MiB soft limit used by `eth` block-body responses. Responders MAY return an empty list for unavailability or exhausted serving budgets. Requesters match wrappers to distinct requested hashes and announced lengths in order, then re-request hashes after the last returned wrapper.

### Validation

Clients MUST check wrapper encoding, length and hash, resolve all listed envelopes, and fully validate under [EIP-8288](./eip-8288.md) before announcing, serving or reaggregating. Dependency-bearing transactions MUST NOT be admitted or relayed without a fully validated covering wrapper; unresolved envelopes leave a wrapper incomplete, not invalid. After a verifier change, clients MUST NOT announce or serve wrappers validated only under the previous verifier.

Count, size or ordering violations SHOULD cause disconnection. Malformed encodings, unmatched or excess responses, and invalid proofs MUST be discarded and MAY cause disconnection or penalties; unavailability or local refusal alone MUST NOT be treated as misbehavior.

## Rationale

Whole-wrapper retrieval follows `eth`'s existing whole-object responses, and EIP-8288 bounds wrapper size to fit the 2 MiB soft limit. Validation before relay adds a download and proof check at each hop, so batch sizes need latency measurements; propagation within the aggregation interval cannot be assumed.

A bounded envelope cache permits recovery after pool rejection or eviction without historical lookups. Descriptors carry no hints: identical wrappers already share a hash, EIP-8288's verdict caches avoid repeat verification, and unauthenticated hints invite deprioritization games.

## Backwards Compatibility

`eth/73` activates with EIP-8288. Older versions continue exchanging blocks and other transactions but receive neither wrappers nor dependency-bearing envelopes through transaction messages.

## Test Cases

[Descriptor vectors](../assets/eip-8437/descriptor-vectors.json) use `wrapper[i] = i % 251`. [Wrapper vectors](../assets/eip-8437/wrapper-vectors.json) give 96-byte dependency encodings and hash-only mode-0 and mode-1 wrappers; Keccak-256 stands in for `DEPS_HASH`. [The executable checks](../assets/eip-8437/check_vectors.py) cover these vectors, message encodings, response limits and pooled-envelope matching, not EIP-8288 proof validity.

| Case | Expected result |
| --- | --- |
| Zero-length or oversized wrapper | Reject |
| Maximum-size wrapper response | Include one wrapper plus message overhead |
| Next wrapper would exceed the soft response limit | Truncate before it |
| PooledTransactions omissions, truncation or empty response | Accept |
| Repeated, reordered, unrequested or extra envelopes | Reject |

## Security Considerations

Invalid proofs impose verification costs without corresponding sender effort. Clients should bound outstanding requests per peer, bytes awaiting validation, verification and proving work, and serving traffic; recovery deadlines limit withholding. Large responses delay other messages on the same connection.

Clients SHOULD treat proof failures as local refusal during a bounded grace period around verifier changes to accommodate differing fork estimates.
