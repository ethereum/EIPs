## Abstract

This EIP defines `eth/75`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) proof wrappers ("wrappers" below). Peers announce direct-witness wrappers by mode, length and hash, with transaction metadata for small wrappers, then retrieve complete wrappers by hash.

## Motivation

EIP-8288 separates dependency witnesses from transaction envelopes. Existing transaction propagation does not carry these witnesses, so peers need a way to discover and retrieve transactions together with the evidence needed for admission.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/75` extends `eth/74` ([EIP-8512](./eip-8512.md)) and uses its message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md).

In the Recursive Length Prefix (RLP) encodings below, `P` is a nonnegative integer (zero encodes as the empty byte string), `B` is a byte string, and `B_n` is a byte string of exactly `n` bytes.

The *mempool fork* is the fork selected by the chain's configured activation timestamps at the client's current Unix time in seconds, independently of its head block. EIP-8288 is enabled when included in this fork. Clients MAY negotiate `eth/75` before EIP-8288 is enabled.

### Wrapper encoding

The canonical wrapper is the [EIP-8288 wrapper](./eip-8288.md#mempool-wrapper-object) encoded as the RLP list `[transactions, mode, content]`, with:

- `transactions`: a nonempty list of complete pooled [EIP-8141](./eip-8141.md) frame transaction encodings as byte strings, in strictly ascending consensus transaction-hash order. Blob data is elided as specified under [Blob-carrying dependency transactions](#blob-carrying-dependency-transactions).
- `mode`: `0`, for direct witnesses.
- `content`: `[deps, proofs]`.
- `deps`: a nonempty, strictly byte-lexicographically ordered list of 96-byte dependency encodings as defined by EIP-8288.
- `proofs`: one witness byte string per dependency, in dependency order.

This transport defines `MAX_WRAPPER_BYTES = 2**21` (2 MiB) for the complete canonical RLP encoding; EIP-8288's applicable dependency limits and enabled schemes apply in addition. Clients MUST apply this bound and compute the hash over the complete wrapper.

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes.

Before EIP-8288 is enabled, clients MUST NOT send wrapper messages and MUST ignore received ones without penalties; underlying transport size limits still apply.

#### NewProofWrapperHashes (0x18)

`[[mode₀: P, length₀: P, hash₀: B_32, txs-meta₀], ...]`

Announce 1–64 held wrappers in strictly ascending hash order: mode is `0`, length is 1–`MAX_WRAPPER_BYTES`, and hash is Keccak-256 of the complete canonical RLP wrapper, including pooled transaction encodings. Peers SHOULD announce newly validated wrappers to every connected `eth/75` peer and, on connection, up to 64 offered wrappers covering at least one pending transaction, most recent first.

The complete RLP announcement payload MUST NOT exceed `2**21` bytes (2 MiB), including metadata. Senders MUST split larger announcement sets into separate messages; receivers MUST check this bound before decoding.

Clients MUST ignore announcements of unsupported modes without penalties after checking the message's encoding, count, length and ordering.

`txs-meta` lists every transaction of a mode 0 wrapper holding at most 17 transactions. This inline-metadata threshold is fixed for `eth/75`, independently of EIP-8288's validity limits. Transactions may share dependency triples, so witness-count limits do not bound transaction count. Larger wrappers use an empty `txs-meta` and remain fetchable in full. Metadata follows wrapper transaction order:

`[[txsize₀: P, ...], [txhash₀: B_32, ...], [txsource₀: B_20, ...], [txfees₀: [P, ...], ...], [txgas₀: P, ...]]`

- `txsize`: the length of the pooled transaction encoding in the complete wrapper.
- `txhash`: the consensus transaction hash.
- `txsource`: the frame transaction's explicit `sender` field, not a recovered signer.
- `txfees`: a copy of its [EIP-8141](./eip-8141.md) `fees` list.
- `txgas`: the sum of its frames' execution and state gas limits.

On the wire, gas is an unsigned 64-bit integer, and each fee is an unsigned 256-bit integer; the fee-list length is not fixed. These encoding bounds do not establish transaction validity. Requesters MAY use metadata to choose and order fetches; it establishes no coverage or validity.

Clients SHOULD relay mode 0 wrappers unchanged rather than regroup their transactions and witnesses, preserving wrapper hashes across hops.

Under the same verification rules, peers SHOULD suppress wrapper hashes already exchanged on the connection. Peers MAY re-announce a hash once a local interval has passed or it has left their bounded record of the connection.

The announcement tuple is fixed for `eth/75`. Extending it requires a new protocol version; canonical decoding rejects extra fields.

#### GetProofWrappers (0x19)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1 to 32 distinct wrapper hashes per message, each previously announced by the responder on that connection under the same verification rules. Responders MUST treat hashes they have not announced as unavailable and MUST NOT penalize the request, since either side's record of announcements may be bounded.

#### ProofWrappers (0x1a)

`[request-id: P, [[hash₀: B_32, wrapper₀], [hash₁: B_32, wrapper₁], ...]]`

Return available validated wrappers as embedded RLP items in the [wrapper encoding](#wrapper-encoding), paired with their canonical hashes, in request order with omissions allowed and no repeats. The recommended soft response limit is 2 MiB. Responders SHOULD stop after reaching it, returning complete wrappers only. Empty responses are permitted.

Requesters MUST match distinct requested hashes in order and check canonical hashes, modes and full lengths against the responder's announcements. They re-request hashes after the last returned wrapper; earlier omissions are unavailable from that peer. Requesters SHOULD fetch each wrapper from one announcer at a time and try another after an empty response or timeout.

Responders whose serving budget is spent SHOULD return an empty response rather than omit wrappers or stay silent. Requesters SHOULD NOT penalize an empty response or count it toward a limit on sources tried for a wrapper. They MAY score earlier omissions in a nonempty response in proportion to the requested wrappers withheld, and SHOULD count an unanswered request against the peer.

### Transaction propagation

A *dependency-bearing transaction* is an EIP-8141 transaction containing at least one EIP-8288 `DEP_VERIFY_FRAME_MODE` frame. Clients implementing this EIP MUST NOT send these transactions in Transactions (`0x02`) or PooledTransactions (`0x0a`) on any negotiated version; GetPooledTransactions (`0x09`) treats them as unavailable. NewPooledTransactionHashes (`0x08`) MUST NOT announce them except for [blob availability](#blob-carrying-dependency-transactions).

#### Blob-carrying dependency transactions

On `eth/75`, [EIP-8070](./eip-8070.md) applies to blob-carrying frame transactions. ProofWrappers carries [EIP-8141's pooled network form](./eip-8141.md#networking), with blob data elided as specified by [EIP-8070](./eip-8070.md#execution-clients--devp2p-changes).

- After wrapper validation and EIP-8070's checks, clients SHOULD advertise cells through NewPooledTransactionHashes, with covering-wrapper announcements subject to suppression. Unknown frame hashes may elicit empty GetPooledTransactions responses.
- GetCells/Cells use consensus transaction hashes and [EIP-8408](./eip-8408.md)'s shared or indexed forms. Dependency-bearing transactions require a validated covering wrapper before cell retrieval and EIP-8070's checks before admission. Validated wrappers may circulate before availability is established; their announcements do not count as providers.

### Validation

Clients MUST apply the transport and metadata checks before proof verification, then EIP-8288 validation before relay or admission. Transport decoders MUST accept structurally valid dependencies with unknown or disabled scheme identifiers; scheme support is checked under EIP-8288, not as a malformed-encoding check.

- Clients MUST check the complete wrapper's encoding, length and hash and validate under EIP-8288 before announcement, serving or transaction admission. Until validation completes, received wrapper data MUST remain in bounded request-scoped storage and be discarded on cancellation or timeout.

- Clients MUST validate using the mempool fork's EIP-8288 rules. If those rules change, for example through a new proof verifier or dependency limits, wrappers validated only under the previous rules MUST NOT be served, announced or used to suppress announcements.

- Before decoding or hashing wrapper bodies, requesters SHOULD check that the response's request ID is outstanding and its connection open; responders SHOULD skip requests from closed connections.

- Transport item-count, hard byte-length and response-order violations SHOULD cause disconnection. Malformed transport encodings, unmatched or excess responses, hash, mode or length mismatches, and transaction hash references MUST be discarded and MAY cause penalties or disconnection. Crossing the soft response limit alone MUST NOT cause penalties. A complete wrapper that violates the wrapper encoding above is likewise malformed.

- Metadata is malformed, and the message carrying it MUST be discarded on arrival, if its five fields do not describe the same, nonzero number of transactions; if its hashes are not strictly ascending; if a size is zero or the sizes do not sum to less than the announced length; or if a `txfees` entry is not a list of integers, or a fee or gas value exceeds the wire bounds above. Metadata for supported wrappers is also malformed if it describes more than 17 transactions. An empty `txs-meta` carries no metadata and is checked once the wrapper arrives.

- Once the complete wrapper arrives, clients MUST check its hash and the serving peer's announcement metadata before witness verification. Metadata MUST be exactly what the wrapper's transactions give, and inline metadata empty where the rules above require it. A mismatch MUST cause discard and SHOULD cause disconnection, independently of proof validity.

- Metadata is a claim of the peer that sent it. Clients keep it per peer: one peer's metadata MUST NOT cause the discard of a wrapper served by another. Clients MAY cross-check metadata by hash against locally held transactions, whether pooled or retained with wrappers; no pool scan, state lookup or additional fetch is required. If checked, false metadata MUST be discarded and its sender SHOULD be disconnected, independently of proof validity. A held transaction with a verified consensus hash permits checking source, fees and frame gas, but not pooled encoding size. Checks against a fetched wrapper remain mandatory.

- Pool rejection of an individual transaction does not invalidate its covering wrapper and MUST NOT incur peer penalties. Clients SHOULD relay such a wrapper unchanged only if it newly admitted at least one transaction and no fewer than it rejected; already-pending transactions count as neither.

- Proof or dependency-rule failures, including exceeding `MAX_SIGS_PER_TX` or another EIP-8288 dependency limit, MUST cause the wrapper to be discarded without peer penalties or disconnection for that failure. Such wrappers are invalid, not malformed: only failures of the transport, encoding, hash, mode, length and metadata checks above are malformed.

- Clients MAY deprioritize or rate-limit fetching from peers whose wrappers repeatedly fail validation or whose requests go unanswered, MAY disconnect such peers past a local threshold, and SHOULD retain this standing by node identity across reconnections. Around a configured fork activation, clients SHOULD suspend validation-failure scoring for a short, locally configured clock-tolerance interval before and after the timestamp; transport checks and the mempool fork's validity rules still apply.

- Clients SHOULD bound served ProofWrappers bytes globally and divide the budget fairly between peers, for example 32 MiB/s in total and at most 8 MiB/s per peer.

## Rationale

Wrappers carry transactions alongside their dependency proofs so receivers can validate them together. Separate propagation would require additional mempool state for envelopes awaiting coverage, or fetching those envelopes again after the proof arrives.

Reusing EIP-8070's cell announcements preserves its provider and sampler behavior. Putting cell masks in wrappers would make wrapper identity depend on each peer's changing holdings.

Transaction metadata lets peers rank wrappers by useful coverage and priority fee before downloading up to `MAX_WRAPPER_BYTES`. Arrival checks enforce wire bounds; transaction validity is checked separately. `txgas` sums declared limits rather than the fork-dependent intrinsic cost, and the inline count is fixed independently of EIP-8288's constants. Hash-bound fields can be checked against a held transaction before fetching the wrapper; pooled encoding sizes require the wrapper itself.

Small mode 0 wrappers carry metadata inline so peers can schedule their retrieval without another request. The 17-entry budget accommodates one transaction per witness at EIP-8288's limits of 16 leanSPHINCS witnesses and one leanSTARK witness. It is not a transaction-count limit; larger wrappers remain fetchable without metadata.

## Backwards Compatibility

`eth/75` may be negotiated before EIP-8288 is enabled. Older versions continue exchanging blocks and other transactions but receive neither wrappers nor dependency-bearing envelopes through transaction messages.

## Test Cases

[Announcement vectors](../assets/eip-8437/announcement-vectors.json), [wrapper vectors](../assets/eip-8437/wrapper-vectors.json) and [the checker](../assets/eip-8437/check_vectors.py) cover the following encoding and matching cases; synthetic envelopes and witnesses do not test transaction or proof validity.

| Checker case | Expected result |
| --- | --- |
| Maximum announcement/request; excess count | 2,563/1,071 encoded bytes for 64 announcements without metadata/32 hashes; reject excess |
| Unsupported modes, alone or mixed with mode 0 | Ignore unsupported entries; still enforce message encoding, count, length and ordering |
| Announcement payload exactly 2 MiB; one byte larger, including metadata for an unsupported mode | Accept the size boundary; reject the oversized payload before decoding |
| Structurally valid dependencies with unknown scheme identifiers | Decode; leave rejection to dependency validation, without a malformed-message penalty |
| Metadata fixture: 17 transactions per entry, maximum wire integers and three fee fields | 186,436 encoded bytes for 64 entries; other fee-list lengths are permitted |
| Mode 0 wrappers with 17 or fewer transactions; larger wrappers | Require exact inline metadata for the former and empty metadata for the latter; both remain fetchable |
| Uneven metadata lists, unordered hashes, zero or excessive sizes, misshapen fees or out-of-range values | Reject announcement |
| False or missing metadata; another peer serves the same wrapper correctly | Reject the serving peer's mismatch before witness verification; do not transfer blame between peers |
| False hash-bound fields for a held transaction; only its pooled size differs | Identify the metadata sender's mismatch without fetching; defer the size check to the wrapper |
| Request a received announcement; request an unannounced hash | Requester selects the former; responder omits the latter |
| Changed enclosed envelope, witness bytes or announced mode/length | Reject mismatch |
| Empty envelopes, hash references, duplicate or reordered envelopes | Reject malformed or noncanonical wrapper |
| Response omits whole wrappers, repeats or reorders them | Accept omissions; reject repeats/reordering |
| Blob network wrapper with elided data, commitments and cell proofs | Accept encoding; use the consensus transaction hash for ordering and cell requests |
| Nonempty blob data, mismatched commitments or wrong proof counts | Reject wrapper; metadata changes also change wrapper identity |
| Complete wrapper exactly at 2 MiB; one byte larger | Accept the size boundary, including response overhead; reject the oversized wrapper |
| Response crosses soft limit on final wrapper | Stop packing; receiver accepts overshoot |

Client integration cases require peer and fork state not modeled by the checker:

- Choose and order fetches by metadata, kept per peer. Cross-checks may use hash-indexed transactions from either the pool or a retained wrapper, without scanning the pool or fetching missing transactions. False source, fees or frame gas for a held transaction incurs the metadata sender's mismatch penalty without a fetch; it does not invalidate the held transaction or another peer's wrapper.
- A frame transaction's explicit sender differs from its signer: announce the sender. Distinct transactions sharing a source remain distinct offers identified by their hashes.
- Negotiate `eth/75` before EIP-8288's configured timestamp: ignore wrapper messages without penalties and send none until the local clock reaches that timestamp, independently of head-block progress.
- A later fork changes EIP-8288's rules: do not serve, announce or suppress using wrappers validated only under the previous rules. Peers on opposite sides of the timestamp within the local clock-tolerance interval do not accumulate validation-failure scores; malformed messages remain penalizable.
- Discard a wrapper failing proof or dependency validation, including a mode 0 wrapper within the byte cap but exceeding the active dependency limits or using a reserved scheme, without penalizing its sender; malformed transport or mismatched announced hashes remain penalizable.
- Relay a received mode 0 wrapper with its original hash rather than regrouping its witnesses; a peer that has already received it can suppress the repeated offer.
- A valid wrapper newly admits one transaction and rejects another. Relay it unchanged under the admission threshold above, without penalizing the sender.
- A complete wrapper can be validated without envelope requests; cancelled or timed-out validation releases its request buffer without admitting transactions.
- Exhaust per-peer and global verification budgets with direct mode 0 witnesses. Defer or decline further work without declaring unvalidated wrappers invalid or penalizing senders solely for budget exhaustion.
- An unknown blob frame hash triggers an empty GetPooledTransactions response; its covering wrapper later arrives. Fetch cells only after validating it; admit only after EIP-8070's checks.
- Multiple wrappers covering the same blob-carrying transaction do not add providers or reset sampling. Two peers' full-cell announcements count as two providers; invalid cells do not invalidate the dependency proof or unrelated transactions.

## Security Considerations

Clients should bound announcements, outstanding requests, buffered and cached bytes, verification/proving work and serving traffic per peer and globally. Direct mode 0 witness verification should have an explicit rate limit. Budget values are local policy, informed by verification-only measurements. Exhaustion permits local refusal without making a wrapper invalid or implying peer misbehavior.

Request deadlines limit withholding; large responses delay other messages. Validation before relay adds per-hop download and verification latency, which requires measurement. EIP-8070's blobpool safeguards apply. Empty responses and responses cut at the soft limit alone should not incur penalties.

Metadata drives fetching and optional checks against locally held transactions, so cheap peer and rate limits should come first. Fields not checkable against held transactions remain claims until the wrapper arrives. A peer can understate fees to delay fetching from it, or overstate them to draw a fetch it then withholds. Claims are kept per peer, so other announcers' offers are unaffected. Fee-list length is variable, so per-peer bounds should count bytes and records, not only requests.
