## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) proof wrappers ("wrappers" below). Peers announce wrapper modes, lengths and hashes, then request whole wrappers by hash.

## Motivation

EIP-8288 separates signatures and proofs from transaction envelopes and permits aggregation across transactions. Existing transaction propagation does not identify this shared proof material, so peers need a way to discover and retrieve it.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` ([EIP-8070](./eip-8070.md)), using its notation and message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md).

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes.

Before the local target fork enables EIP-8288, clients MUST NOT send wrapper messages and MUST ignore received wrapper messages without penalties; underlying transport size limits still apply.

#### NewProofWrapperHashes (0x16)

`[[mode₀: P, length₀: P, hash₀: B_32], [mode₁: P, length₁: P, hash₁: B_32], ...]`

Announce 1–64 held wrappers in strictly ascending hash order: mode is `0` or `1`, length is 1–`MAX_WRAPPER_BYTES`, and hash is Keccak-256 of the encoded wrapper. Peers SHOULD announce offered wrappers on connection and newly validated wrappers to every connected `eth/73` peer.

Under the same verification rules, peers SHOULD suppress hashes already exchanged on the connection and wrappers whose transactions are covered by held, validated wrappers exchanged with or announced by the recipient, unless they reduce proof bytes or estimated verification work, or provide an IL-bounded mode-1 proof where existing coverage cannot.

#### GetProofWrappers (0x17)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1 to 64 distinct wrapper hashes per message, each announced in either direction on that connection under the same verification rules. Responders MAY treat hashes announced in neither direction as unavailable.

#### ProofWrappers (0x18)

`[request-id: P, [wrapper₀, wrapper₁, ...]]`

Return available validated wrappers as embedded EIP-8288 RLP items, in request order with omissions allowed. `MAX_WRAPPER_BYTES` MUST NOT exceed the `eth` soft response limit; responders SHOULD stop once the response reaches it, allowing the last wrapper to cross it. Empty responses are permitted.

Requesters match distinct requested hashes in order, check modes and lengths against announcements from either direction, and re-request hashes after the last returned wrapper.

### Transaction propagation

Dependency-bearing transactions contain EIP-8288 dependency frames. On `eth/73`, existing transaction encodings and response rules apply. Clients SHOULD propagate pooled transactions alongside covering-wrapper announcements; they MAY announce only wrappers and recover envelopes through GetPooledTransactions. Envelopes may precede wrappers, but transactions remain incomplete until covering-wrapper validation.

GetPooledTransactions may request distinct hashes listed in offered wrappers without transaction announcements. PooledTransactions returns envelopes in request order, allowing omissions but no repeats; check any announced [EIP-5793](./eip-5793.md) type/size metadata. Responders SHOULD serve offered wrappers' envelopes even after pool rejection or eviction.

Below `eth/73`, clients MUST NOT broadcast or announce dependency-bearing transactions and MUST treat them as unavailable for retrieval.

### Validation

Clients MUST check encoding, length and hash, resolve envelopes and validate under EIP-8288 before wrapper announcement, serving or reaggregation, or transaction admission or relay. Proof checks MAY precede or overlap envelope recovery; unresolved hashes mean incomplete, not invalid. Target-fork selection and verdict reuse follow EIP-8288. A verification-rule change MUST reset announcement suppression; wrappers validated only under old rules MUST NOT be served or announced.

Count, hard-length and ordering violations SHOULD cause disconnection. Malformed encodings, unmatched or excess responses, hash or metadata mismatches, and EIP-8288-invalid wrappers MUST be discarded and MAY cause penalties or disconnection. Crossing the soft response limit alone MUST NOT cause penalties.

Clients SHOULD withhold dependency-validation penalties during a bounded grace window around scheduled verification-rule changes, independent of the local head (recommended: one slot before through 64 slots after activation, measured by wall-clock time).

## Rationale

Concurrent envelope and wrapper propagation overlaps recovery with proof verification, avoiding a sequential fetch round trip. Serving envelopes after pool rejection preserves offered wrappers' availability. Mode and length support download selection; digest and proof-hash hints are unnecessary for verdict reuse. Coverage suppression reduces reaggregation churn while permitting cheaper aggregates and IL-reusable proofs.

Whole-object retrieval fits the existing `eth` response model. Chunking adds indexing and assembly, while verification still needs the complete proof; separate proof retrieval adds another path. Validation before relay incurs download and verification latency at every hop, so propagation within the aggregation interval requires measurement.

## Backwards Compatibility

`eth/73` may be negotiated before EIP-8288 activates; wrapper exchange begins when the local target fork enables it. Older versions continue exchanging blocks and other transactions but receive neither wrappers nor dependency-bearing envelopes through transaction messages.

## Test Cases

[Announcement vectors](../assets/eip-8437/announcement-vectors.json), [wrapper vectors](../assets/eip-8437/wrapper-vectors.json) and [the checker](../assets/eip-8437/check_vectors.py) cover the following encoding and matching cases; synthetic witnesses do not test proof validity.

| Checker case | Expected result |
| --- | --- |
| Maximum announcement/request; excess count | 2,499/2,127 encoded bytes; reject excess |
| Request hashes announced in either direction; unannounced hash | Accept either direction; reject unannounced request |
| Changed wrapper bytes or announced mode/length | Reject mismatch |
| Response crosses soft limit on final wrapper | Stop packing; receiver accepts overshoot |
| Pooled response omits entries, repeats or reorders them | Accept omissions; reject repeats/reordering |
| Pooled response contradicts announced EIP-5793 type/size | Reject mismatch |

Client integration cases require peer and fork state not modeled by the checker:

- Suppress wrappers covering already-covered transactions unless cheaper or newly IL-reusable.
- Before local activation, ignore wrapper messages without penalties and send none.

## Security Considerations

Invalid proofs impose verification costs. Clients should bound each peer's pending announcements, outstanding requests, incomplete wrappers and envelopes, verification/proving work and serving traffic; recovery deadlines limit withholding. Serving should use bounded local storage, without historical searches or recursive fetches. Large responses delay other messages.

Scoring may reflect repeated failure to serve recently offered envelopes or repeated envelope pushes without covering announcements before retention expires. A receiver's own announced coverage excuses reciprocal announcements; unresolved announcements do not establish missing coverage. Permitted empty/partial responses, pool rejection and local budget exhaustion alone should not incur penalties.
