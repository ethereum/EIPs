## Abstract

This EIP defines `eth/75`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) proof wrappers ("wrappers" below). Peers announce wrapper modes, lengths and hashes, with the metadata of mode 0 wrappers' transactions, then retrieve wrappers, or the metadata of their transactions, by hash.

## Motivation

EIP-8288 separates signatures and proofs from transaction envelopes and permits aggregation across transactions. Existing transaction propagation does not identify this shared proof material, so peers need a way to discover and retrieve it.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/75` extends `eth/74`, which extends `eth/73` ([EIP-8408](./eip-8408.md)) with block-level dependency proof retrieval (message IDs 0x16 and 0x17). It uses their message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md).

In the Recursive Length Prefix (RLP) encodings below, `P` is a nonnegative integer (zero encodes as the empty byte string), `B` is a byte string, and `B_n` is a byte string of exactly `n` bytes.

The *mempool fork* is the fork selected by the chain's configured activation timestamps at the client's current Unix time in seconds, independently of its head block. EIP-8288 is enabled when included in this fork. Clients MAY negotiate `eth/75` before EIP-8288 is enabled.

### Wrapper encoding

The canonical wrapper is the [EIP-8288 wrapper](./eip-8288.md#mempool-wrapper-object) encoded as the RLP list `[transactions, mode, content]`, with:

- `transactions`: a nonempty list of complete pooled transaction encodings as byte strings, in strictly ascending consensus transaction-hash order. Blob data is elided as specified under [Blob-carrying dependency transactions](#blob-carrying-dependency-transactions).
- `content`: `[deps, proofs]` for mode `0`, or `[deps, recursive_stark]` for mode `1`.
- `deps`: a nonempty, strictly byte-lexicographically ordered list of 96-byte dependency encodings as defined by EIP-8288.
- `proofs`: one witness byte string per dependency, in dependency order; `recursive_stark`: one nonempty proof byte string.

This transport defines `MAX_WRAPPER_BYTES = 2**21` (2 MiB) for the complete canonical RLP encoding; EIP-8288's applicable dependency limits and enabled schemes apply in addition. Hash references are transport-only: clients MUST reconstruct the complete wrapper before applying this bound or computing its hash.

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes.

Before EIP-8288 is enabled, clients MUST NOT send wrapper messages and MUST ignore received ones without penalties; underlying transport size limits still apply.

#### NewProofWrapperHashes (0x18)

`[[mode₀: P, length₀: P, hash₀: B_32, deps-hash₀: B_32, txs-hash₀: B_32, txs-meta₀], ...]`

Announce 1–64 held wrappers in strictly ascending hash order: mode is `0` or `1`, length is 1–`MAX_WRAPPER_BYTES`, and hash is Keccak-256 of the complete canonical RLP wrapper, including pooled transaction encodings. Peers SHOULD announce newly validated wrappers to every connected `eth/75` peer and, on connection, up to 64 offered wrappers covering at least one pending transaction, most recent first.

Clients MUST ignore announcements of unsupported modes without penalties after checking the message's encoding, count, length and ordering.

`deps-hash` is Keccak-256 of the concatenated 96-byte entries in the canonical `deps` list; `txs-hash` is Keccak-256 of the concatenated, ascending consensus transaction hashes. Requesters MAY skip a fetch when both match a held wrapper validated under the current rules. Hints alone establish no coverage or validity; matching only `deps-hash` does not identify the transactions.

`txs-meta` lists every transaction of a mode 0 wrapper holding at most 17 transactions. This inline-metadata threshold is fixed for `eth/75`, independently of EIP-8288's validity limits. For other wrappers it is the empty list. Metadata follows wrapper transaction order:

`[txtypes: B, [txsize₀: P, ...], [txhash₀: B_32, ...], [txsource₀: B_20, ...], [txnonce₀: P, ...], [txfees₀: [P, ...], ...], [txgas₀: P, ...]]`

- `txtypes`: the concatenated [EIP-2718](./eip-2718.md) transaction-type bytes.
- `txsize`: the length of the pooled transaction encoding in the complete wrapper.
- `txhash`: the consensus transaction hash; the listed hashes concatenate to the preimage of `txs-hash`.
- `txsource`: the frame transaction's explicit `sender` field, not a recovered signer.
- `txnonce`: its `nonce` field, or `nonce_seq` when [EIP-8250](./eip-8250.md) applies.
- `txfees`: a copy of its [EIP-8141](./eip-8141.md) `fees` list.
- `txgas`: the sum of its frames' execution and state gas limits.

On the wire, nonce and gas are unsigned 64-bit integers, and each fee is an unsigned 256-bit integer; the fee-list length is not fixed. These encoding bounds do not establish transaction validity. Requesters MAY use metadata to choose and order fetches; it establishes no coverage or validity.

Metadata omits nonce keys. Receivers MUST NOT compare a frame transaction's `txnonce` with `state[txsource].nonce` to discard an announcement as stale or infer a nonce gap, and MUST use the transaction hash, not `<txsource, txnonce>`, as its identity.

Under the same verification rules, peers SHOULD suppress hashes already exchanged on the connection and wrappers whose transactions are covered by held, validated wrappers exchanged with or announced by the recipient, unless they reduce proof bytes or estimated verification work, or supply a recursive proof for an [EIP-8288 inclusion list](./eip-8288.md#extended-focil-data-structure) where the recipient has only direct witnesses. Peers MAY re-announce a hash once a local interval has passed or it has left their bounded record of the connection.

The announcement tuple is fixed for `eth/75`. Extending it requires a new protocol version; canonical decoding rejects extra fields.

#### GetProofWrappers (0x19)

`[request-id: P, compact: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1 to 32 distinct wrapper hashes per message, each previously announced by the responder on that connection under the same verification rules. Responders MUST treat hashes they have not announced as unavailable and MUST NOT penalize the request, since either side's record of announcements may be bounded. `compact` is `0` or `1`: with `0`, returned wrappers MUST contain complete transaction encodings; with `1`, responders MAY use [hash-based omission](#hash-based-omission).

#### ProofWrappers (0x1a)

`[request-id: P, [[hash₀: B_32, wrapper₀], [hash₁: B_32, wrapper₁], ...]]`

Return available validated wrappers as embedded RLP items in the [wrapper encoding](#wrapper-encoding), paired with their canonical hashes, in request order with omissions allowed and no repeats. The recommended soft response limit is 2 MiB. Responders SHOULD stop after reaching it, returning complete wrappers only. Empty responses are permitted.

Requesters MUST match distinct requested hashes in order, reconstruct wrappers as specified under [Hash-based omission](#hash-based-omission), and check canonical hashes, modes and full lengths against the responder's announcements. They re-request hashes after the last returned wrapper; earlier omissions are unavailable from that peer. Requesters SHOULD fetch each wrapper from one announcer at a time and try another after an empty response or timeout.

Responders whose serving budget is spent SHOULD return an empty response rather than omit wrappers or stay silent. Requesters SHOULD NOT penalize an empty response or count it toward a limit on sources tried for a wrapper. They MAY score earlier omissions in a nonempty response in proportion to the requested wrappers withheld, and SHOULD count an unanswered request against the peer.

#### GetProofWrapperManifests (0x1b)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request the manifests of 1 to 32 distinct wrappers, each previously announced by the responder on that connection under the same verification rules; responders treat other hashes as GetProofWrappers does. A wrapper's manifest is the metadata of all its transactions, in the `txs-meta` layout, whatever its mode and transaction count.

#### ProofWrapperManifests (0x1c)

`[request-id: P, [[hash₀: B_32, txs-meta₀], [hash₁: B_32, txs-meta₁], ...]]`

Return the manifests of available validated wrappers, paired with their hashes. ProofWrappers' response matching, omission and retry rules, soft response limit, empty responses and scoring apply, with complete manifests in place of wrappers, and served manifests count toward the serving budget. Responders SHOULD keep each validated wrapper's manifest rather than derive it per request. Requesters MUST check a manifest on arrival as specified under [Validation](#validation), and against the wrapper if they fetch it.

### Hash-based omission

Compact responses reconstruct the same canonical wrapper using encodings previously delivered on the connection.

- With `compact = 1`, responders MAY replace transaction bytes previously sent in full within a validated wrapper on that connection with `[encoding-hash: B_32]`, if smaller. The hash is Keccak-256 of the pooled transaction bytes, excluding the enclosing RLP string prefix. References are RLP lists; transactions are byte strings.
- Requesters MUST resolve references from cached, validated encodings and check their hashes. The complete wrapper determines identity and byte limits; reconstruction MUST stay within the announced length.
- On a missing encoding, requesters MUST discard the compact item and SHOULD retry with `compact = 0` and a fresh request ID. Cache misses MUST NOT incur penalties.

### Transaction propagation

A *dependency-bearing transaction* is an EIP-8141 transaction containing at least one EIP-8288 `DEP_VERIFY_FRAME_MODE` frame. Clients implementing this EIP MUST NOT send these transactions in Transactions (`0x02`) or PooledTransactions (`0x0a`) on any negotiated version; GetPooledTransactions (`0x09`) treats them as unavailable. NewPooledTransactionHashes (`0x08`) MUST NOT announce them except for [blob availability](#blob-carrying-dependency-transactions).

#### Blob-carrying dependency transactions

On `eth/75`, [EIP-8070](./eip-8070.md) applies to blob-carrying frame transactions. ProofWrappers carries [EIP-8141's pooled network form](./eip-8141.md#networking), with blob data elided as specified by [EIP-8070](./eip-8070.md#execution-clients--devp2p-changes).

- After wrapper validation and EIP-8070's checks, clients SHOULD advertise cells through NewPooledTransactionHashes, with covering-wrapper announcements subject to suppression. Unknown frame hashes may elicit empty GetPooledTransactions responses.
- GetCells/Cells use consensus transaction hashes and EIP-8408's shared or indexed forms. Dependency-bearing transactions require a validated covering wrapper before cell retrieval and EIP-8070's checks before admission. Validated wrappers may circulate before availability is established; their announcements do not count as providers.

### Validation

Clients MUST apply the transport and metadata checks before proof verification, then EIP-8288 validation before relay or admission.

- Clients MUST check the complete wrapper's encoding, length and hash and validate under EIP-8288 before announcement, serving, reaggregation or transaction admission. Until validation completes, received wrapper data MUST remain in bounded request-scoped storage and be discarded on cancellation or timeout.

- Clients MUST validate using the mempool fork's EIP-8288 rules. If those rules change, for example through a new proof verifier or dependency limits, wrappers validated only under the previous rules MUST NOT be served, announced or used to suppress announcements.

- Before decoding or hashing wrapper bodies or manifests, requesters SHOULD check that the response's request ID is outstanding and its connection open; responders SHOULD skip requests from closed connections.

- Transport item-count, hard byte-length and response-order violations SHOULD cause disconnection. Malformed transport encodings, unmatched or excess responses, hash, mode or length mismatches, and references in a `compact = 0` response MUST be discarded and MAY cause penalties or disconnection. Crossing the soft response limit alone MUST NOT cause penalties. A complete wrapper that violates the wrapper encoding above is likewise malformed.

- Metadata is malformed, and the message carrying it MUST be discarded on arrival, if its seven fields do not describe the same, nonzero number of transactions; if its hashes are not strictly ascending or do not hash to the announced `txs-hash`; if a size is zero or the sizes do not sum to less than the announced length; or if a `txfees` entry is not a list of integers, or a nonce, fee or gas value exceeds the wire bounds above. Inline metadata is also malformed if it describes a mode 1 wrapper or more than 17 transactions. An empty inline `txs-meta` carries no metadata and is checked once the wrapper arrives; a manifest always describes every transaction.

- Once the canonical wrapper is reconstructed, clients MUST check, alongside its hash and before proof verification, the announcement digests and metadata, inline or from a manifest, of the peer that served it. Metadata MUST be exactly what the wrapper's transactions give, and inline metadata empty where the rules above require it. A mismatch MUST cause discard and SHOULD cause disconnection, independently of proof validity.

- Metadata is a claim of the peer that sent it. Clients keep it per peer: one peer's metadata MUST NOT cause the discard of a wrapper served by another. Clients MUST discard metadata found false against a wrapper with a verified canonical hash or a held transaction with a verified consensus hash, and SHOULD disconnect its sender, independently of proof validity. A held transaction permits checking type, source, nonce, fees and frame gas; its consensus hash does not bind the pooled encoding's size.

- Pool rejection of an individual transaction does not invalidate its covering wrapper and MUST NOT incur peer penalties. Clients SHOULD relay such a wrapper unchanged only if it newly admitted at least one transaction and no fewer than it rejected; already-pending transactions count as neither.

- Proof or dependency-rule failures, including exceeding `MAX_SIGS_PER_TX` or another EIP-8288 dependency limit, MUST cause the wrapper to be discarded without peer penalties or disconnection for that failure. Such wrappers are invalid, not malformed: only failures of the transport, encoding, hash, mode, length, digest and metadata checks above are malformed.

- Clients MAY deprioritize or rate-limit fetching from peers whose wrappers repeatedly fail validation or whose requests go unanswered, MAY disconnect such peers past a local threshold, and SHOULD retain this standing by node identity across reconnections.

- Clients SHOULD bound served ProofWrappers bytes globally and divide the budget fairly between peers, for example 32 MiB/s in total and at most 8 MiB/s per peer.

## Rationale

Wrappers carry transactions alongside their dependency proofs so receivers can validate them together. Separate propagation would require additional mempool state for envelopes awaiting coverage, or fetching those envelopes again after the proof arrives.

Reusing EIP-8070's cell announcements preserves its provider and sampler behavior. Putting cell masks in wrappers would make wrapper identity depend on each peer's changing holdings.

Mode distinguishes direct-witness verification from recursive-proof verification; length gives the complete wrapper's encoded size. Dependency and transaction digests identify equivalent coverage despite different proof bytes, avoiding redundant downloads. Compared with a dependency hint alone, `txs-hash` adds 33 encoded bytes per announcement to distinguish different transactions sharing dependencies. The wire dependency digest uses a fixed hash of encoded triples rather than the circuit digest, allowing checks independent of fork verification rules.

Transaction metadata lets peers rank wrappers by useful coverage and priority fee before downloading up to `MAX_WRAPPER_BYTES`. Arrival checks enforce wire bounds; transaction validity is checked separately. `txgas` sums declared limits rather than the fork-dependent intrinsic cost, and the inline count is fixed independently of EIP-8288's constants. Hash-bound fields can be checked against a held transaction before fetching the wrapper; pooled encoding sizes require the wrapper itself.

Small mode 0 wrappers carry metadata inline so peers can schedule their retrieval without another request. Aggregates can overlap, repeating metadata across wrappers; peers instead request the manifests of the wrappers they consider fetching. The inline threshold limits announcement overhead without assuming a particular dependency count or enabled scheme.

Hash omission saves repeated transaction bytes while preserving canonical identity, at the cost of cache tracking and full retries after eviction. Encoding hashes also bind blob metadata.

## Backwards Compatibility

`eth/75` may be negotiated before EIP-8288 is enabled. Older versions continue exchanging blocks and other transactions but receive neither wrappers nor dependency-bearing envelopes through transaction messages.

| Compact response with cached references; missing reference | Reconstruct the identical canonical wrapper; discard the incomplete item and retry in full |
| Reference when `compact = 0`, wrong cached encoding or false canonical hash | Reject |
| Compact form fits the byte cap but reconstructed wrapper exceeds it | Reject |

| Nonempty blob data, mismatched commitments or wrong proof counts | Reject wrapper; metadata changes also change wrapper identity |

Client integration cases require peer and fork state not modeled by the checker:

- Suppress wrappers covering already-covered transactions unless cheaper or supplying a recursive proof for an inclusion list where the recipient has only direct witnesses.
- Hints never establish coverage before validation. A correct hint remains consistent across verifier changes; an incorrect hint is penalizable independently of proof failure.
- Choose and order fetches by metadata, kept per peer. False type, source, nonce, fees or frame gas for a held transaction incurs the metadata sender's mismatch penalty without a fetch; it does not invalidate the held transaction or another peer's wrapper.
- A frame transaction's explicit sender differs from its signer: announce the sender. With keyed nonces, announce `nonce_seq`; values below or above the account nonce do not establish staleness or a nonce gap. Distinct transaction hashes sharing a source and sequence remain distinct offers.
- Negotiate `eth/75` before EIP-8288's configured timestamp: ignore wrapper messages without penalties and send none until the local clock reaches that timestamp, independently of head-block progress.
- A later fork changes EIP-8288's rules: do not serve, announce or suppress using wrappers validated only under the previous rules.
- Discard a wrapper failing proof or dependency validation, including a mode 1 wrapper within the byte cap but exceeding the active dependency limits or using a reserved scheme, without penalizing its sender; malformed transport or mismatched announced hashes remain penalizable.
- Omit an encoding previously sent in full on the connection; retain its cache entry for reconstruction or retry in full after eviction. Never omit an encoding not previously delivered.
- A valid wrapper remains relayable unchanged when one transaction fails pool admission; that rejection does not penalize the sender.
- A complete wrapper can be validated without envelope requests; cancelled or timed-out validation releases its request buffer without admitting transactions.
- Exhaust per-peer and global verification budgets with direct mode 0 witnesses and singleton or overlapping mode 1 wrappers. Defer or decline further work without declaring unvalidated wrappers invalid or penalizing senders solely for budget exhaustion.
- An unknown blob frame hash triggers an empty GetPooledTransactions response; its covering wrapper later arrives. Fetch cells only after validating it; admit only after EIP-8070's checks.
- Multiple wrappers covering the same blob-carrying transaction do not add providers or reset sampling. Two peers' full-cell announcements count as two providers; invalid cells do not invalidate the dependency proof or unrelated transactions.

## Security Considerations

Clients should bound announcements, outstanding requests, buffered and cached bytes, verification/proving work and serving traffic per peer and globally. Direct mode 0 witness verification should have an explicit rate limit; singleton and overlapping mode 1 wrappers also consume the verification budget. Clients should prefer mode 1 when it reduces verification work for the covered transactions. Budget values are local policy, informed by verification-only measurements. Exhaustion permits local refusal without making a wrapper invalid or implying peer misbehavior.

Request deadlines limit withholding; large responses delay other messages. Validation before relay adds per-hop download and verification latency; propagation within the aggregation interval requires measurements. EIP-8070's blobpool safeguards apply. Empty responses and responses cut at the soft limit alone should not incur penalties.

Metadata drives fetching and possibly state reads for announced sources before the wrapper arrives, so cheap peer and rate limits should come first. Fields not checkable against held transactions remain claims until the wrapper arrives. A peer can understate fees to delay fetching from it, or overstate them to draw a fetch it then withholds. Claims are kept per peer, so other announcers' offers are unaffected. Manifests can list thousands of transactions, and fee-list length is variable, so per-peer bounds should count bytes and records, not only requests.
