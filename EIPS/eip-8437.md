## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) mempool wrappers. Peers announce wrapper descriptors, request whole wrappers by object ID, and request the transactions a wrapper lists through a dedicated envelope request. Transactions with dependency verification frames travel only inside wrappers and are no longer sent in `eth` transaction announcements or broadcasts. The version number and message IDs are placeholders.

## Motivation

An EIP-8288 transaction declares dependencies whose signatures and proofs it does not carry. A pool admits it only with a wrapper whose witnesses or aggregate proof cover those dependencies, so a peer receiving the bare transaction through `NewPooledTransactionHashes` or `PooledTransactions` cannot validate it. Wrappers are mempool objects exchanged between the same peers as transactions and blob cells, so they belong in the `eth` wire protocol. As for transactions since `eth/65`, peers announce wrappers and receivers request the ones they want.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` as defined by [EIP-8070](./eip-8070.md). All existing messages and semantics are unchanged except as stated below. The version number and the message IDs `0x16` to `0x1a` are placeholders, assigned with the fork that activates EIP-8288.

### Constants

| Name | Value | Meaning |
| --- | --- | --- |
| `SOFT_RESPONSE_LIMIT` | `2097152` | The `eth` soft response limit (2 MiB) |
| `MAX_WRAPPER_BYTES` | EIP-8288 `MAX_WRAPPER_BYTES` | At most `SOFT_RESPONSE_LIMIT` |
| `MAX_RESPONSE_BYTES` | `SOFT_RESPONSE_LIMIT + 32` | Message-data ceiling for ProofWrappers and WrapperEnvelopes |
| `MAX_REQUEST_BYTES` | `16384` | Message-data ceiling for the other new messages |
| `MAX_PROFILES` | `16` | Profile IDs in Status |
| `MAX_ANNOUNCEMENTS` | `64` | Descriptors per AnnounceProofWrappers |
| `MAX_WRAPPERS_PER_REQUEST` | `64` | Object IDs per GetProofWrappers |
| `MAX_ENVELOPES_PER_REQUEST` | `1024` | Indices per GetWrapperEnvelopes |
| `MAX_REQUESTS_PER_PEER` | `4` | Outstanding wrapper and envelope requests per direction |

These are transport ceilings, not consensus limits. A client MAY enforce lower local limits and refuse work without penalizing the peer.

### Encoding

Messages use canonical RLP with exactly the field counts specified: shortest integer encodings, no trailing bytes, and 32-byte hashes. Lists MUST be checked against their count bounds before elements are allocated. Implementations MUST check the advertised uncompressed size against `MAX_RESPONSE_BYTES` or `MAX_REQUEST_BYTES` before decompression. Transaction envelopes and proofs are opaque at this layer and parsed afterward by their own bounded parsers. `H` is Keccak-256, and a domain label is its ASCII bytes followed by one zero byte.

### Status (0x00)

```text
[version, networkid, genesis, forkid, earliest, latest, latestHash, profiles]
```

`profiles` is a strictly ascending list of 0 to `MAX_PROFILES` 32-byte profile IDs the node supports. All other fields are as in `eth/69`. A **profile ID** identifies the aggregate verification key that applies to a wrapper:

```text
profile_id = H("ethereum/8437/profile/v1\0" || AGGREGATED_VK)
```

`AGGREGATED_VK` uses the canonical encoding fixed by the activating EIP-8288 fork, which fixes the proof profile and enabled schemes. Clients derive profile IDs from local fork configuration, never from peer-supplied keys. A mode-1 wrapper's profile is that of the key verifying its aggregate proof; a mode-0 wrapper uses the profile of its target fork. A **common profile** appears in both Status messages. Peers without one MUST NOT send messages `0x16` to `0x1a` to each other and use the rest of `eth/73` normally.

The receiver checks a wrapper's profile against the fork of its local target block, the child of its local head. At a fork boundary, wrappers under the old profile become inappropriate once the target block is in the new fork; a receiver MAY retrieve new-profile wrappers shortly in advance. Status MAY list past and future profiles. Status is not updated at activation; peers reconnect to advertise new profiles.

### Dependency-Bearing Transactions

A dependency-bearing transaction has at least one EIP-8288 dependency verification frame. On every `eth` version, clients MUST NOT send dependency-bearing transactions in Transactions (`0x02`), NewPooledTransactionHashes (`0x08`) or PooledTransactions (`0x0a`), MUST answer GetPooledTransactions for one as for an unavailable transaction, and MUST NOT admit one received in those messages. Such transactions propagate only in wrappers. Block bodies are unaffected.

### Descriptors and Identity

```text
descriptor = [profile_id, byte_length, content_hash]
content_hash = H(wrapper)
object_id = H("ethereum/8437/object/v1\0" || RLP(descriptor))
```

`wrapper` is the canonical hash-only EIP-8288 wrapper encoding, and `byte_length` its length, from 1 to `MAX_WRAPPER_BYTES`. The same wrapper has the same identity at every peer; different proof bytes give a different object. A canonical descriptor encodes in at most 72 bytes.

### Messages

| ID | Message |
| --- | --- |
| `0x16` | AnnounceProofWrappers |
| `0x17` | GetProofWrappers |
| `0x18` | ProofWrappers |
| `0x19` | GetWrapperEnvelopes |
| `0x1a` | WrapperEnvelopes |

Request IDs follow [EIP-2481](./eip-2481.md). Each endpoint MUST keep at most `MAX_REQUESTS_PER_PEER` outstanding GetProofWrappers and GetWrapperEnvelopes requests to each peer. A responder MAY answer a request beyond that count, or beyond its serving budget, with an empty list.

#### AnnounceProofWrappers (0x16)

```text
[[profile_id: B_32, byte_length: P, content_hash: B_32], ...]
```

The list holds 1 to `MAX_ANNOUNCEMENTS` descriptors in strictly ascending `object_id` order. A sender MUST announce only wrappers it holds in full and has fully validated under EIP-8288, using a common profile. Receivers MAY ignore other descriptors. On connection, peers SHOULD announce the wrappers they offer, within the announcement rate limit.

Announcements establish no validity and require no action. Each peer SHOULD keep a bounded per-connection set of object IDs the other side is known to hold, having announced or sent them, and SHOULD NOT announce those again. A receiver at its request limit SHOULD keep wanted descriptors in a bounded pending cache, since announcements are not repeated.

#### GetProofWrappers (0x17) and ProofWrappers (0x18)

```text
GetProofWrappers = [request_id: P, [object_id: B_32, ...]]
ProofWrappers = [request_id: P, [wrapper, ...]]
```

The request names 1 to `MAX_WRAPPERS_PER_REQUEST` distinct object IDs, each from a held descriptor with a common profile. The responder returns the requested wrappers it holds and offers, in request order, skipping unavailable ones as in PooledTransactions. Each `wrapper` is embedded as its RLP item, exactly the bytes `content_hash` covers. The responder includes the first available wrapper and stops before a wrapper that would take the message data past `SOFT_RESPONSE_LIMIT`; the requester re-requests the IDs after the last one returned. The list is empty only if no requested wrapper is available.

The requester matches each wrapper, in order, to a distinct requested descriptor with equal `byte_length` and `content_hash`. A wrapper matching none is invalid peer data.

#### GetWrapperEnvelopes (0x19) and WrapperEnvelopes (0x1a)

```text
GetWrapperEnvelopes = [request_id: P, object_id: B_32, [index: P, ...]]
WrapperEnvelopes = [request_id: P, [envelope: B, ...]]
```

The requester MUST hold a wrapper matching the object's descriptor and send the request to a peer that announced or served it. `indices` is a strictly ascending list of 1 to `MAX_ENVELOPES_PER_REQUEST` integers below `T`, the length of the wrapper's `transactions` list; index `i` names the envelope whose hash is `transactions[i]`. A responder without the validated object checks only the wire bounds, including indices below EIP-8288 `MAX_TXS_PER_WRAPPER`, and returns an empty list. For a responder with the object, an index not below `T` is a protocol violation.

A peer offering a validated wrapper MUST serve its listed envelopes, even when they are absent from its admitted pool. Entry `k` of `envelopes` is the canonical [EIP-2718](./eip-2718.md) envelope for `indices[k]`. The responder includes every requested envelope in order, stopping only before one that would take the message data past `SOFT_RESPONSE_LIMIT`, and always includes the first. Requests trigger no historical searches or recursive peer fetches. A peer MUST NOT announce a wrapper with a listed envelope above `SOFT_RESPONSE_LIMIT` bytes.

The requester MUST check that the response holds no more entries than requested and that each entry's `H` equals `transactions[indices[k]]`. A violation is invalid peer data attributable to that source and object, so a holder cannot skip a listed envelope undetected. An empty list means unavailable: the object stays incomplete, and the requester MAY try another peer that announced it.

### Validation and Relay

On receiving a wrapper, the receiver MUST check its length, `content_hash` and canonical encoding, then resolve every listed hash from its pool or through GetWrapperEnvelopes, and fully validate the wrapper under EIP-8288. It SHOULD check the dependency union before or alongside proof verification. Clients MUST NOT announce, serve, admit or reaggregate a wrapper before full validation; a proof check alone does not authenticate the transaction list. Failed envelope recovery leaves the wrapper incomplete, not invalid.

Clients SHOULD keep a bounded cache of proof verdicts keyed by `(H(proof), deps_hash)`, where `deps_hash` is EIP-8288 `get_deps_hash` of the dependencies the proof covers: the mode-1 `deps`, or a mode-0 proof's single dependency. A known proof arriving in a different or unresolvable wrapper is then not verified again. After validation, admission is evaluated per transaction; local refusal, state changes or pool policy do not establish proof invalidity.

### Resource Bounds

Clients MUST configure finite request deadlines, a finite recovery deadline and source-attempt budget per wrapper, a per-peer serving budget, an announcement rate limit and a bounded pending-announcement cache. RECOMMENDED defaults are 30-second requests, 120-second recovery across at most three sources, 8 MiB/s of ProofWrappers and WrapperEnvelopes data served per peer, 4 AnnounceProofWrappers messages per second per peer, and 1,024 pending descriptors kept for 60 seconds. These are local policy; different values are not misbehavior.

Received wrappers awaiting recovery or verification and recovered envelopes MUST be charged to finite per-peer and global byte budgets before allocation, and stay charged until validation finishes or the wrapper is abandoned. Verification, admission and proving queues MUST have finite concurrency and backlog. Receivers SHOULD deprioritize sources whose wrappers failed validation and SHOULD prefer objects announced by several peers.

### Errors

Malformed encodings, wrappers matching no requested descriptor, envelope hash mismatches, responses with more entries than requested and invalid proofs are invalid peer data: the client MUST discard the contribution and MAY disconnect or penalize the peer. Exceeding a count or size bound, misordered lists, and messages `0x16` to `0x1a` without a common profile are protocol violations, after which the client SHOULD disconnect. Empty responses, unavailability, timeouts, local refusal, a profile inappropriate for the target block, and pool rejection of a validly proven transaction MUST NOT by themselves be treated as misbehavior.

## Rationale

### Why an `eth` version

Every change to transaction or block propagation has been an `eth` version: announcements in `eth/65` ([EIP-2464](./eip-2464.md)), request IDs in `eth/66` ([EIP-2481](./eip-2481.md)), types and sizes in `eth/68` ([EIP-5793](./eip-5793.md)), receipts in `eth/69` ([EIP-7642](./eip-7642.md)) and blob cells in `eth/72`, each a short networking change shipped with a fork. Separate capabilities such as `snap` and `les` serve a different kind of peer or data. Wrappers are mempool objects exchanged with the same peers as transactions, and keeping dependency-bearing transactions out of `eth` transaction exchange is safe only if wrapper exchange ships with it. One version bump couples the two.

### Whole objects

`eth` responses carry whole objects under the soft response limit. EIP-8288 sizes `MAX_WRAPPER_BYTES` to that limit, so a wrapper response occupies a connection no longer than a BlockBodies, Receipts or Cells response, and needs no reassembly state, chunk credit or cancellation. Content hashing the whole body attributes corruption to the one peer that sent it.

### If proofs exceed the soft limit

Whole-object retrieval holds only while a wrapper at EIP-8288's list ceilings with its largest permitted proof fits `SOFT_RESPONSE_LIMIT`. At 4,096 transaction hashes and 4,096 dependencies the lists take 536,584 bytes, leaving 1,560,555 bytes for the proof; EIP-8288 owns that bound. A chunked message set or separate capability is justified only if benchmarks put aggregate proofs above about 1 to 2 MiB. It would need requested fixed-size chunks from one source, checked against the content hash after reassembly, with per-peer and global reassembly buffers, chunk credit, cancellation and assembly lifetimes.

### Envelope retrieval

Dedicated envelope requests are scoped to one wrapper, so a peer that offers it either serves each listed envelope or answers empty, and skipped envelopes are detectable. With PooledTransactions a missing transaction cannot be distinguished from eviction. Responses obey the same soft limit as other `eth` responses.

### Identity

Descriptors carry no dependency digest, transaction-list or proof-hash hints: the verdict cache already avoids repeated verification, identical wrappers share a `content_hash`, and unauthenticated hints would invite deprioritization games. Domain labels omit the `eth` version so identities survive renumbering. Deriving profile IDs from locally configured keys avoids a verifier registry.

### Message numbering

`eth/72` assigns IDs up to `0x15`, so `0x16` to `0x1a` are the next free IDs. `eth/73` is a placeholder, since no proposal for it is scheduled for a fork. The fork that activates EIP-8288 assigns the final version and IDs.

### Relay latency

Validation before relay adds a download and proof check at every hop. Batch sizes need latency measurements, since large wrappers cannot be assumed to propagate within the aggregation interval.

## Backwards Compatibility

This EIP requires a new `eth` version. Peers on older versions keep working but never receive wrappers or dependency-bearing transactions, which they could not validate; they see those transactions only in blocks. `eth/73` should ship with the fork that activates EIP-8288. It changes no consensus rules.

## Test Cases

[Commitment vectors](../assets/eip-8437/commitment-vectors.json) use a zero profile ID and `wrapper[i] = i % 251`. [Wrapper vectors](../assets/eip-8437/wrapper-vectors.json) give a profile ID for a dummy key, 96-byte dependency encodings and hash-only mode-0 and mode-1 wrappers; Keccak-256 stands in for `DEPS_HASH`. [The executable checks](../assets/eip-8437/check_vectors.py) cover both, plus message encodings, response limits and envelope truncation. They test transport encodings, not EIP-8288 proof validity.

| Case | Expected result |
| --- | --- |
| Dependency-bearing transaction in the pool | Not announced, broadcast or returned over any `eth` version |
| Peers without a common profile | No messages `0x16` to `0x1a`; the rest of `eth/73` works |
| Same wrapper offered to peers with different envelope caches | Identical wrapper and object ID |
| Zero-length or oversized wrapper; noncanonical RLP; excessive list count | Reject before large allocation |
| Requested wrappers exceed `SOFT_RESPONSE_LIMIT` | Fitting wrappers in request order; first one always included |
| Wrapper matches no requested descriptor | Invalid peer data |
| Envelope request for an unknown or evicted object | Empty list; no penalty |
| Envelope retained outside the admitted pool is requested | Served while the wrapper is offered |
| Requested envelopes exceed `SOFT_RESPONSE_LIMIT` | Longest fitting prefix; requester re-requests the rest |
| More envelopes than requested, or an envelope hash mismatch | Invalid peer data; the object stays incomplete |
| Envelope indices unordered, too many, or not below the transaction count | Protocol violation |
| Proof verifies but recovered envelopes do not validate the wrapper | No admission, reaggregation or relay |
| Known proof arrives with a different or unresolvable transaction list | Reuse a cached verdict |
| Mode-0 wrapper | Checked against the target fork's profile |

## Security Considerations

A content hash supplied by a malicious peer can match an invalid proof, so announcements and responses establish no validity and full validation precedes relay. Invalid proofs cost verification work without corresponding sender effort; per-peer and global byte, recovery and work budgets remain necessary against many peer identities, and deadlines bound withholding and slow responses.

A 2 MiB response delays other `eth` messages on the connection as other soft-limited responses do. Raising `MAX_WRAPPER_BYTES` without chunking would lengthen that delay for every `eth` message.
