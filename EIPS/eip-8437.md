## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) mempool wrappers. Peers announce wrapper descriptors and request whole wrappers by content hash.

## Motivation

An EIP-8288 transaction declares dependencies whose signatures and proofs it does not carry. Admission therefore requires a validated wrapper covering those dependencies.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` as defined by [EIP-8070](./eip-8070.md). Status (`0x00`) and all other existing messages are unchanged except as stated below. The protocol version and message IDs are provisional.

### Constants

| Name | Value | Meaning |
| --- | --- | --- |
| `SOFT_RESPONSE_LIMIT` | `2097152` | Soft response limit (2 MiB) |
| `MAX_WRAPPER_BYTES` | EIP-8288 `MAX_WRAPPER_BYTES` | At most `SOFT_RESPONSE_LIMIT` |
| `MAX_REQUEST_BYTES` | `16384` | Message-data ceiling for AnnounceProofWrappers and GetProofWrappers |
| `MAX_ANNOUNCEMENTS` | `64` | Descriptors per AnnounceProofWrappers |
| `MAX_WRAPPERS_PER_REQUEST` | `64` | Content hashes per GetProofWrappers |
| `MAX_REQUESTS_PER_PEER` | `4` | Outstanding wrapper and envelope-recovery requests per peer |

A client MAY enforce lower local limits without penalizing the peer.

### Encoding

The new messages use canonical RLP with the structures below and no extra fields or trailing bytes.

- `wrapper`: the canonical hash-only EIP-8288 wrapper, embedded as an RLP item.
- `content_hash`: `keccak256(wrapper)`, over its exact encoded bytes.
- `byte_length`: the encoded wrapper length, from 1 to `MAX_WRAPPER_BYTES`.

### New Messages

Request IDs follow [EIP-2481](./eip-2481.md).

#### AnnounceProofWrappers (0x16)

```text
[[byte_length: P, content_hash: B_32], ...]
```

- Announce descriptors for 1 to `MAX_ANNOUNCEMENTS` held wrappers, in strictly ascending `content_hash` order.
- On connection, peers SHOULD announce offered wrappers within the rate limit.
- Peers SHOULD track hashes the other side has announced or sent in a bounded per-connection set, and SHOULD NOT announce them again.
- Receivers at their request limit SHOULD cache wanted descriptors for later retrieval.

#### GetProofWrappers (0x17)

```text
[request_id: P, [content_hash: B_32, ...]]
```

Request 1 to `MAX_WRAPPERS_PER_REQUEST` distinct hashes from held descriptors.

#### ProofWrappers (0x18)

```text
[request_id: P, [wrapper, ...]]
```

- Return requested, offered wrappers in request order, skipping unavailable ones.
- Include the first available wrapper, then stop before adding one would exceed `SOFT_RESPONSE_LIMIT`. A single maximum-size wrapper plus message overhead may exceed this soft limit.
- Responders MAY return an empty list for unavailability or exhausted request or serving budgets. Requesters MAY retry later or use another announcing peer.
- Requesters match each returned wrapper to a distinct requested descriptor, in order, by `byte_length` and `content_hash`, then re-request hashes after the last returned wrapper.

### Transaction Messages

A dependency-bearing transaction contains an EIP-8288 dependency verification frame. Wrappers provide discovery of these transactions and their proof material; ordinary transaction announcements identify no covering wrapper.

- Clients MUST NOT send dependency-bearing transactions through Transactions (`0x02`) or announce them through NewPooledTransactionHashes (`0x08`).
- Below `eth/73`, GetPooledTransactions MUST treat dependency-bearing envelopes as unavailable.
- On `eth/73`, clients MUST recover missing envelopes through GetPooledTransactions (`0x09`). Request distinct hashes listed in held wrappers, from peers that announced or served those wrappers.
- Existing pooled request/response encodings and limits apply. PooledTransactions (`0x0a`) returns envelopes in request order without repeats, allowing omissions and truncation. Clients MUST correlate by `request_id` and match each envelope's Keccak-256 hash to a distinct requested hash.
- While offering a wrapper, peers MUST retain and serve every listed envelope, including those rejected or evicted from the pool. Lookups MUST use only the pool and a bounded wrapper-envelope cache, without historical searches or recursive fetches.
- Peers MUST NOT announce wrappers listing envelopes larger than `SOFT_RESPONSE_LIMIT`.

### Validation and Relay

- Clients MUST check the wrapper's encoding, length and hash, resolve all listed envelopes, and fully validate it under [EIP-8288](./eip-8288.md).
- Clients MUST NOT announce, serve or reaggregate a wrapper before full validation. Dependency-bearing transactions MUST NOT be admitted or relayed without a fully validated covering wrapper.
- Unresolved envelopes leave a wrapper incomplete, not invalid.
- After a verifier change, clients MUST NOT announce or serve wrappers validated only under the previous verifier.

### Resource Bounds

- Requesters MUST cap combined outstanding GetProofWrappers and envelope-recovery GetPooledTransactions requests at `MAX_REQUESTS_PER_PEER` per peer. This is the requester's local cap, not a peer-enforceable limit.
- Clients MUST check list counts before allocating elements and advertised uncompressed sizes before decompression. Apply `MAX_REQUEST_BYTES` to AnnounceProofWrappers and GetProofWrappers; apply the local message cap to responses.
- Pending wrappers and recovered envelopes MUST count against finite per-peer and global byte budgets before allocation, until validation completes or the wrapper is abandoned.
- Verification, admission and proving queues MUST have finite concurrency and backlog.
- Receivers SHOULD deprioritize sources whose wrappers failed validation.

Clients MUST configure the following finite local limits. These defaults are RECOMMENDED; different values are not misbehavior.

| Limit | Default |
| --- | --- |
| Request deadline | 30 seconds |
| Recovery deadline and source-attempt budget per wrapper | 120 seconds, at most three sources |
| Wrappers and dependency-bearing envelopes served per peer | 8 MiB/s |
| AnnounceProofWrappers rate per peer | 4 messages per second |
| Pending-announcement cache | 1,024 descriptors, retained for 60 seconds |

### Errors

| Condition | Handling |
| --- | --- |
| Malformed encoding, unmatched wrapper or envelope, excess response entries, invalid proof | MUST discard; MAY disconnect or penalize |
| Wire count or size violation; misordered list | SHOULD disconnect |
| Empty response, unavailability, timeout, local refusal, pool rejection of a validly proven transaction | MUST NOT alone treat as misbehavior |

For a bounded local window around verifier changes, clients SHOULD treat proof failures as local refusal. The RECOMMENDED window runs from the client's EIP-8288 target-fork switch until its head is 64 blocks past activation. This accommodates differing fork estimates, including around slot-length changes, but may delay propagation.

## Rationale

### Whole objects

`eth` responses carry whole objects under the soft response limit. Whole-object retrieval requires every permitted wrapper, at EIP-8288's list ceilings with its largest permitted proof, to fit `SOFT_RESPONSE_LIMIT`; EIP-8288 sizes `MAX_WRAPPER_BYTES` to that limit, so a wrapper response occupies a connection no longer than a BlockBodies, Receipts or Cells response. Content hashing the whole body attributes corruption to the one peer that sent it. Validation before relay adds a download and proof check at every hop, so batch sizes need latency measurements; large wrappers cannot be assumed to propagate within the aggregation interval.

### Envelopes and identity

A bounded envelope cache keeps wrapper recovery possible after pool rejection or eviction without requiring historical lookups. Descriptors carry no hints: identical wrappers already share a `content_hash`, EIP-8288's verdict caches avoid repeat verification, and unauthenticated hints invite deprioritization games.

## Backwards Compatibility

This EIP requires a new `eth` version. Peers on older versions keep exchanging blocks and other transactions but receive neither wrappers nor dependency-bearing envelopes through transaction messages. `eth/73` ships with the fork that activates EIP-8288 so wrapper exchange is available when dependency-bearing transactions require it.

## Test Cases

[Descriptor vectors](../assets/eip-8437/descriptor-vectors.json) use `wrapper[i] = i % 251`. [Wrapper vectors](../assets/eip-8437/wrapper-vectors.json) give 96-byte dependency encodings and hash-only mode-0 and mode-1 wrappers; Keccak-256 stands in for `DEPS_HASH`. [The executable checks](../assets/eip-8437/check_vectors.py) cover both, plus message encodings, response limits and pooled-envelope response matching. They test transport encodings, not EIP-8288 proof validity.

| Case | Expected result |
| --- | --- |
| Dependency-bearing transaction in the pool | No independent announcement or broadcast; envelope served for wrapper recovery on eth/73 only |
| Zero-length or oversized wrapper; noncanonical RLP; excessive list count | Reject before large allocation |
| Requested wrappers exceed `SOFT_RESPONSE_LIMIT` | First available wrapper always included; stop before the next would exceed the limit |
| PooledTransactions omits an unavailable envelope or truncates the response | Existing eth retry rules; unresolved wrappers remain incomplete, not invalid |
| Envelope retained outside the admitted pool is requested | Served through PooledTransactions while the wrapper is offered |
| Wrapper matching no requested descriptor, more envelopes than requested, or an envelope hash mismatch | Invalid peer data; the wrapper stays incomplete |
| PooledTransactions repeats an envelope or returns envelopes out of request order | Invalid peer data; no wrapper admission or relay |
| Proof verifies but recovered envelopes do not validate the wrapper | No admission, reaggregation or relay |
| Held mode-1 wrapper, or a peer's proof failure, at a fork that changes `AGGREGATED_VK` | Wrapper dropped and not announced or served; a proof failure within the client's configured fork grace window is local refusal, and after it invalid peer data |

## Security Considerations

A content hash supplied by a malicious peer can match an invalid proof, so announcements and responses establish no validity and full validation precedes relay. Invalid proofs cost verification work without corresponding sender effort; per-peer and global byte, recovery and work budgets remain necessary against many peer identities, and deadlines bound withholding and slow responses. A 2 MiB response delays other `eth` messages on the connection as other soft-limited responses do. Raising `MAX_WRAPPER_BYTES` would lengthen that delay for every `eth` message.
