## Abstract

This EIP defines `eth/75`, extending the transaction messages of the `eth` wire protocol to carry dependency-bearing frame transactions together with their witnesses. It uses the pooled form specified for submission by [EIP-8504](./eip-8504.md#submission), without adding messages or changing transaction hashes.

## Motivation

A dependency-bearing transaction needs its witnesses before a node can validate it. Carrying them with the transaction permits immediate validation and reuses transaction announcement, retrieval and relay. Native signatures can be submitted without proving or constructing a multi-transaction wrapper. Builders can aggregate those witnesses for a block without changing mempool transport.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/75` extends `eth/74` ([EIP-8512](./eip-8512.md)); Status (`0x00`), message IDs and request/response semantics are unchanged. The version number is provisional.

The *mempool fork* is selected by the chain's configured activation timestamps at the client's current Unix time in seconds, independently of its head block. Clients MAY negotiate `eth/75` before dependency transactions are enabled. The active core rules determine valid dependency schemes, witness verification and admission limits; this transport adds no scheme allowlist.

### Pooled transactions

A dependency-bearing transaction is an [EIP-8141](./eip-8141.md) frame transaction containing a dependency frame. This EIP replaces EIP-8504's wrapper-only propagation rule on `eth/75` with its submission encoding as the pooled network form. Clients MUST carry these transactions as the transaction payload followed by its witnesses, with one witness per entry of the transaction's sorted, deduplicated dependency list. Blob-carrying transactions retain EIP-8141's network sidecar fields before the witness list.

Transaction hashes and signature hashes are computed from the consensus transaction, excluding witnesses and network sidecar fields. Transactions without dependencies retain their existing encodings.

### Transaction messages

Clients MUST NOT send or announce dependency-bearing transactions to peers below `eth/75`.

- **Transactions (`0x02`)** carries the complete pooled form for dependency-bearing transactions without blobs. Blob-carrying transactions remain excluded under EIP-8141.
- **NewPooledTransactionHashes (`0x08`)** announces the frame transaction type, consensus transaction hash and complete pooled size, including witnesses, under [EIP-5793](./eip-5793.md). The responder MUST retain the announced encoding while offering it; a different valid witness set may have a different size.
- **GetPooledTransactions (`0x09`) / PooledTransactions (`0x0a`)** requests by consensus transaction hash and returns complete pooled forms. Responses remain in request order, with omissions allowed and no repeats. Receivers MUST check the serving peer's announced type and size where available.

### Blob-carrying transactions

[EIP-8070](./eip-8070.md) applies unchanged: blob data is elided from the pooled form, with commitments and cell proofs retained; cells are retrieved separately using [EIP-8408](./eip-8408.md). Cell requests and provider announcements use the consensus transaction hash. Clients MUST validate dependency witnesses before requesting cells and complete EIP-8070's availability checks before pool admission.

### Validation

Clients MUST derive the dependency list from the transaction, check the pooled encoding and witness count before witness verification, then validate witnesses and apply the active fork's transaction admission rules before relay. Witnesses are opaque byte strings to the transport decoder; a structurally valid dependency using an unsupported scheme is discarded without peer penalties.

Witness or dependency-rule failures MUST NOT alone cause penalties or disconnection. Clients MAY throttle further work. A rejected witness set MUST NOT mark the consensus transaction hash invalid or prevent fetching a different witness set from another peer. Malformed encodings and mismatches with the serving peer's announcement remain transport faults.

Before the mempool fork enables dependency transactions, clients MUST NOT relay or serve them. When its verification rules change, clients MUST revalidate witnesses before relaying or serving them under the new rules. Cached verdicts MUST distinguish the verification rules and witness bytes, not just the transaction hash.

## Rationale

The pooled form keeps each transaction independently verifiable on receipt, as the blob network form does. It adds no state for transactions awaiting a separate proof object. Witnesses are outside the signed transaction, so a builder can aggregate them without sender participation.

The protocol version identifies peers that accept the witness-bearing form of the frame transaction type. It does not activate dependency schemes or require builders to aggregate. Block-proof retrieval is defined separately by EIP-8512.

## Backwards Compatibility

Peers negotiating versions below `eth/75` do not receive dependency-bearing transactions through transaction messages. `eth/75` support can precede activation of the core dependency rules; those rules determine when the transactions become admissible. Builder aggregation does not change this pooled form.

## Test Cases

[Pooled-form vectors](../assets/eip-8437/pooled-vectors.json) and [the checker](../assets/eip-8437/check_vectors.py) cover encoding and witness association. Synthetic witnesses do not test cryptographic validity.

| Case | Expected result |
| --- | --- |
| Non-blob dependency transaction with positional witnesses | Decode the original consensus transaction and witness list |
| Blob dependency transaction with elided data | Retain commitments, cell proofs and witnesses; use the consensus hash |
| Missing or excess witnesses, nested witness item, trailing fields | Reject the pooled form |
| Repeated dependency declarations | Carry one witness per distinct resolved dependency |
| Different witnesses for the same transaction | Equal transaction hash; potentially different pooled size |
| Structurally valid unknown scheme | Decode; let active core rules decide validity |
| Convert a witnessed transaction to a single-transaction mode 0 wrapper and back | Preserve transaction, witness and sidecar bytes without signing or proving |

Client integration cases:

- A peer returns invalid witnesses; another serves valid witnesses for the same hash. The first failure does not suppress the second fetch.
- Announced size includes witnesses, while cell requests use the consensus transaction hash. False announced size is attributed only to the announcing peer.
- Builder aggregation is enabled while peers continue exchanging the same pooled forms; block-proof exchange follows EIP-8512.
- Exhaust per-peer and global verification budgets, including by rotating node identities. Defer work without treating an unverified transaction as invalid.

## Security Considerations

Clients should bound incoming bytes, outstanding fetches and verification work per peer and globally, including unsolicited Transactions messages. Witness budgets should reflect each scheme's measured verification cost, with separate limits for expensive direct proofs. Global limits should apply across node identities. Gas paid on inclusion does not prevent unpaid mempool work.

Transaction hashes do not authenticate witnesses. Cheap encoding checks, bounded retries and witness-verdict caches limit repeated work, while allowing recovery from a bad witness supplied by one peer. Blob availability remains subject to EIP-8070.
