## Abstract

This EIP defines the `lean/1` devp2p capability for discovering and retrieving [EIP-8288](./eip-8288.md) mempool wrappers. Receivers request 64 KiB chunks from one source per assembly, fetch the listed transaction envelopes through dedicated requests, and check the complete content hash and object validity before relay.

## Motivation

Dependency witnesses and aggregated proofs can be much larger than ordinary transactions. Whole-object messages occupy the connection while being written and make interrupted retrieval expensive. Unsolicited objects also consume receiver resources before the receiver decides whether it needs them.

Requested chunks bound each transfer and let proof traffic interleave with other messages. Hash-only wrappers keep object identity independent of which transactions each peer already holds.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

### Constants

EIP-8288 defines wrapper encoding, validity and proof limits.

| Name | Value | Meaning |
| --- | --- | --- |
| `CAPABILITY` | `lean/1` | Capability name and version |
| `MESSAGE_COUNT` | `8` | Relative message IDs `0x00` through `0x07` |
| `CHUNK_BYTES` | `65536` | Fixed object chunk size |
| `MAX_OBJECT_BYTES` | EIP-8288 `MAX_WRAPPER_BYTES` | 9 MiB transport ceiling |
| `MAX_CHUNKS` | `ceil(MAX_OBJECT_BYTES / CHUNK_BYTES)` | Chunks per object, 144 at 9 MiB |
| `MAX_MESSAGE_BYTES` | `131072` | Uncompressed message-data ceiling, except WrapperEnvelopes |
| `MAX_ENVELOPE_RESPONSE_BYTES` | `2097152` | Uncompressed WrapperEnvelopes message-data ceiling |
| `MAX_RLP_DEPTH` | `8` | Maximum nesting of transport lists |
| `MAX_PROFILES` | `16` | Profile IDs in Status |
| `MAX_ANNOUNCEMENTS` | `64` | Descriptors per announcement |
| `MAX_CHUNKS_PER_REQUEST` | `32` | Chunk indices per request |
| `MAX_ENVELOPES_PER_REQUEST` | `1024` | Envelope indices per request |
| `MAX_REQUESTS_PER_PEER` | `4` | Outstanding requests per direction |
| `MAX_BUFFERED_BYTES_PER_PEER` | `MAX_BUFFERED_BYTES / 4` | Unvalidated bytes charged to one source |
| `MAX_BUFFERED_BYTES` | `8 * MAX_OBJECT_BYTES` | Global unvalidated-byte ceiling |

These are transport ceilings, not consensus validity limits. A client MAY enforce lower local limits and refuse work without penalizing the peer. A client's per-peer buffer limit MUST NOT exceed one quarter of its global limit, so filling the buffer takes at least four sources. `MAX_BUFFERED_BYTES` (72 MiB) and its per-peer quarter (18 MiB) are deliberately above `MAX_OBJECT_BYTES`, so the per-peer limit never blocks a single maximum-size object, even with `MAX_REQUESTS_PER_PEER` full envelope responses outstanding. Changing `MAX_WRAPPER_BYTES`, and hence `MAX_OBJECT_BYTES` and `MAX_CHUNKS`, requires a new capability version. A transport refusal MUST NOT be treated as an invalid transaction or block. Request limits do not reserve an entire object per request; all requests share the byte budgets above.

### Local Resource Policy

Clients MUST configure finite request and assembly idle and absolute lifetimes, and a finite source-attempt budget. RECOMMENDED defaults are request idle/absolute lifetimes of 30/120 seconds, assembly idle/absolute lifetimes of 30/300 seconds, and three source attempts. These are local policy, not negotiated wire limits. The chosen limits apply for each request or assembly's lifetime; retries and source changes MUST NOT renew them. Different local limits are not peer misbehavior.

Clients MUST also configure a finite per-peer serving budget, announcement rate limit and pending-announcement cache. RECOMMENDED defaults are 8 MiB/s of Chunk and WrapperEnvelopes data served per peer, 4 AnnounceObjects messages per second per peer, and a pending-announcement cache of 1,024 descriptors with a 60-second lifetime. Excess announcements MAY be ignored without penalty. Receivers SHOULD deprioritize sources whose assemblies failed and SHOULD prefer objects announced by several peers.

### Encoding

Message data and object bodies use canonical RLP with exactly the field counts specified. Integers use the shortest unsigned encoding, with zero as the empty string; stated widths are range bounds, not fixed-width fields. Leading zeros, extra fields, trailing bytes, nonminimal length prefixes and wrong list/string types are invalid. Hashes are exactly 32 bytes. Byte strings sort lexicographically. Lists MUST be checked against their count bounds before allocating elements; the outermost RLP list has depth one and nested transport lists MUST NOT exceed `MAX_RLP_DEPTH`. Transaction envelopes and proofs are opaque byte strings at this layer, parsed afterward by their own bounded parsers. A canonical descriptor encodes in at most 77 bytes.

`H` is Keccak-256, not SHA3-256. `RLP(x)` is canonical RLP. In commitment formulas, `||` is byte concatenation and a domain label is its ASCII bytes followed by one zero byte.

[RLPx](https://github.com/ethereum/devp2p/blob/76cf0a141e8aa8616e3305738d51101945387d3c/rlpx.md) compression, encryption, message-ID multiplexing and authentication are unchanged. Implementations MUST check the advertised uncompressed size before decompression and reject messages exceeding `MAX_MESSAGE_BYTES`, or `MAX_ENVELOPE_RESPONSE_BYTES` for WrapperEnvelopes. Body bytes travel only in requested Chunk messages, one chunk per message. Implementations MUST NOT rely on RLPx frame fragmentation to carry an object.

### Capability and Profiles

Peers negotiate capability name `lean`, version `1`, through the RLPx Hello exchange. Status MUST be sent without waiting for the peer's Status. A peer MUST NOT send any other message before accepting the peer's Status.

A **profile ID** identifies the aggregate verification key that applies to an object:

```text
profile_id = H("lean/1/profile\0" || AGGREGATED_VK)
```

`AGGREGATED_VK` uses the canonical byte encoding fixed by the activated EIP-8288 fork, never a client-specific key serialization. It fixes the cryptographic profile, including dependency hashing and encodings, verifier parameters and bounds, and the fork's `ENABLED_SCHEMES` and verification relations. Changing that scheme set requires a new key and therefore a new `profile_id`. Clients derive profile IDs from local fork configuration, never peer-supplied keys. A mode-1 wrapper's profile is that of the key verifying its recursive STARK; a mode-0 wrapper, which has no recursive STARK, uses the profile of its target fork's `AGGREGATED_VK`. A **common profile** appears in both Status messages and is supported locally.

The **local target block** is the child of the receiver's local head, in the fork active at the next slot. The receiver MUST check the profile against that block's fork. At a fork boundary, objects under the previous profile become inappropriate once the target block is in the new fork, and objects under the new profile are not admitted before then; a receiver MAY retrieve them shortly in advance. Forks sharing a key share the cryptographic profile and enabled schemes but may have different transaction or admission rules outside the circuit. Status MAY list known past and future profiles; activation does not update Status, and peers reconnect if new profiles must be advertised. A profile inappropriate for the receiver's target context is not by itself peer misbehavior.

Status is sent exactly once in each direction:

```text
Status (0x00) = [chain_id, genesis_hash, profiles, max_object_bytes]
```

- `chain_id` is an unsigned integer less than `2**256`.
- `genesis_hash` is 32 bytes.
- `profiles` is a nonempty, strictly ascending list of at most `MAX_PROFILES` 32-byte profile IDs.
- `max_object_bytes` is an integer in `[1, MAX_OBJECT_BYTES]`: a local receive ceiling, not a promise to accept every smaller object.

The chain ID and genesis hash MUST match local configuration, and at least one profile MUST be common. An incompatible Status disables this capability; clients SHOULD keep other protocols on the connection. Malformed or repeated Status, or other messages received before Status, are protocol violations.

### Wrapper Encoding

An **object** consists of a descriptor and a body of 1 to `MAX_OBJECT_BYTES` bytes. The body MUST be a valid EIP-8288 wrapper in its canonical hash-only encoding.

After checking body integrity and encoding, receivers SHOULD recover missing envelopes from the announcing source and check the dependency union before or alongside proof verification, reusing cached proof verdicts. Every transaction hash needs resolution and full EIP-8288 wrapper validation before admission, reaggregation or relay; a proof check alone does not authenticate the transaction-hash list. Failed recovery leaves the object incomplete rather than invalid.

Envelope recovery uses GetWrapperEnvelopes. Dependency-bearing transactions are not announced over the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/76cf0a141e8aa8616e3305738d51101945387d3c/caps/eth.md) (for example `eth/68`); they propagate only inside wrappers. Clients MUST NOT send them in `eth` NewPooledTransactionHashes, Transactions or PooledTransactions messages, so peers without `lean/1` never receive transactions they cannot validate. Block bodies are unaffected.

### Descriptors and Identity

```text
descriptor = [profile_id, byte_length, content_hash]
content_hash = H(body)
object_id = H("lean/1/object\0" || RLP(descriptor))
```

`byte_length` is a 64-bit unsigned integer within the object bounds. Receivers MUST check its encoding, profile and size before requesting chunks. The same wrapper body produces the same identity for every peer; different proof bytes still identify different objects.

An **assembly** is a receiver's partial copy of an object, keyed by `object_id`; requests are keyed by `(connection, request_id)`. A repeated descriptor MUST NOT create another assembly. A receiver uses one source peer at a time for an assembly, without mixing unverified body bytes from different peers.

### Chunk Geometry

```text
N = ceil(byte_length / CHUNK_BYTES)
chunk[i] = body[i * CHUNK_BYTES : min((i + 1) * CHUNK_BYTES, byte_length)]
```

Thus `1 <= N <= MAX_CHUNKS`. Every chunk except the last is exactly `CHUNK_BYTES`; the last is `byte_length - (N - 1) * CHUNK_BYTES` bytes. Chunk bytes remain untrusted until the complete body matches `content_hash`. A source switch discards all partial body bytes, while a retry from the same source may request only missing indices.

### Messages and Request Lifecycle

IDs are relative to the capability's negotiated message offset:

| ID | Message | Direction |
| --- | --- | --- |
| `0x00` | Status | Both |
| `0x01` | AnnounceObjects | Both |
| `0x02` | GetChunks | Request |
| `0x03` | Chunk | Response |
| `0x04` | Complete | Terminal response |
| `0x05` | Cancel | Requester to responder |
| `0x06` | GetWrapperEnvelopes | Request |
| `0x07` | WrapperEnvelopes | Response |

Request IDs are 64-bit unsigned integers. On each connection a peer MUST assign positive, strictly increasing IDs to GetChunks and GetWrapperEnvelopes requests in send order, never wrapping or reusing an ID. Gaps are allowed; each direction has its own sequence, and responses echo the request's ID. A new incoming ID no greater than the preceding one is a protocol violation, even if the request is refused. Each endpoint MUST keep at most `MAX_REQUESTS_PER_PEER` locally live requests per direction. Responders return Complete with Busy for requests they cannot accept. Receiving a request while at the local limit MUST NOT by itself incur a penalty, since expiry times can differ.

Each endpoint measures deadlines with its own monotonic clock: the requester starts when sending the request, the responder when receiving it. Request idle time resets only when the requester receives the first valid Chunk for a requested index, or when the responder writes one. A chunk already obtained through another request to the same source can advance a request without advancing the assembly. Each endpoint retires the request at its idle or absolute deadline, whichever comes first; no synchronized expiry is assumed. Disconnection releases request state. Neither requests nor cancellation reset an assembly's absolute age.

#### AnnounceObjects (0x01)

```text
[descriptor, ...]
```

The list holds 1 to `MAX_ANNOUNCEMENTS` descriptors in strictly ascending `object_id` order. A sender MUST announce only objects it holds in full and has fully validated under EIP-8288. Announced objects MUST use a common profile and fit the receiver's advertised ceiling. Receivers MAY ignore other descriptors without allocating assemblies.

Announcements neither require receiver action nor establish validity. Repetition earns no credit or retention. Each peer SHOULD keep a bounded per-connection set of object IDs the other side is known to hold, having announced or sent them, as `eth` does for transaction hashes, and SHOULD NOT announce those objects again. Peers SHOULD rotate bounded selections fairly across useful objects. A receiver that wants an announced object but is at its request or assembly limits SHOULD keep it pending in a bounded cache and retrieve it when capacity frees, since the announcement may not be repeated.

#### GetChunks (0x02), Chunk (0x03), and Complete (0x04)

```text
GetChunks = [request_id, object_id, indices]
Chunk = [request_id, object_id, index, chunk_bytes]
Complete = [request_id, object_id, status]
```

The requester MUST already hold an announced descriptor using a common profile, within its receive ceiling. `indices` is a strictly ascending list of 1 to `MAX_CHUNKS_PER_REQUEST` 32-bit integers less than `N`. The request grants **credit** for exactly those chunks, at most 2 MiB of body data. A responder without the descriptor checks only the wire bounds (including indices below `MAX_CHUNKS`) and returns Unavailable; it cannot check unknown geometry. A responder with the descriptor MUST check its profile and size before serving.

The responder sends at most one Chunk per requested index, in request order, and nothing unrequested. It MAY stop early for unavailability or resource pressure but MUST then send Complete. Complete statuses are `0 = Served`, `1 = Unavailable`, `2 = Busy`, `3 = Unsupported`, `4 = Cancelled` and `5 = TooLarge`. Unsupported means the object's profile is not a common profile; TooLarge means its `byte_length` exceeds the requester's advertised `max_object_bytes`. Served means every requested chunk was written; it does not mean the receiver accepted anything. Complete is terminal and releases unused credit, and a request never expands to further indices.

A Chunk MUST match the outstanding request's object ID, next expected index and required length, and come from the assembly's current source. It remains unverified. An identical chunk obtained through another request consumes this request's credit but MUST NOT allocate another copy or refresh the assembly's idle timer. Conflicting bytes for an already received index invalidate that source's contribution. Repeating an index within one request is a protocol violation. Complete must match the request's object ID; Served before every requested Chunk has arrived is a protocol violation. Locally discarded chunks MAY be requested again.

#### Cancel (0x05)

```text
[request_id]
```

Cancel names a request originated by its sender. The responder stops scheduling responses and sends Complete with Cancelled for a live request; a Chunk already being written MAY finish first. A terminal response already being written MAY finish without replacement. Cancels for unknown or completed requests are ignored.

The requester marks a cancelled request but retains its slot until a terminal response or local expiry. It MUST discard all subsequent response payloads for that request without proof verification, body hashing, retention or further recovery. A structurally valid Complete with the matching object ID releases the slot, including Served crossing Cancel. Responses with no live request and an ID at or below the highest issued ID are discarded, including unused gaps; ID zero or above the highest issued ID is invalid. The highest issued ID and bounded live-request map suffice. Framing, structure, count, size and rate bounds still apply. Cancellation does not invalidate previously retained chunks.

#### GetWrapperEnvelopes (0x06) and WrapperEnvelopes (0x07)

```text
GetWrapperEnvelopes = [request_id, object_id, indices]
WrapperEnvelopes = [request_id, envelopes]
```

The requester MUST already hold a body matching the object's `content_hash`. `indices` is a strictly ascending list of 1 to `MAX_ENVELOPES_PER_REQUEST` integers less than `T`, the length of the wrapper's `transactions` list; index `i` names the envelope whose hash is `transactions[i]`. A responder without the validated object checks only the wire bounds (including indices below EIP-8288 `MAX_TXS_PER_WRAPPER`) and returns Complete with Unavailable. For a responder with the object, an index not below `T` is a protocol violation.

An envelope request ends with one WrapperEnvelopes message or Complete with Unavailable, Busy or Cancelled; other statuses are protocol violations. Only a responder holding the validated object sends WrapperEnvelopes. `envelopes` holds the canonical [EIP-2718](./eip-2718.md) envelopes for the requested indices in request order. The responder MUST include every requested envelope that fits, omitting only a suffix starting at the first envelope that would take the message data past `MAX_ENVELOPE_RESPONSE_BYTES`; the requester re-requests the omitted indices. A peer MUST NOT announce a wrapper with a listed envelope that does not fit alone in a WrapperEnvelopes message, so every response carries at least one envelope. A peer that announced a wrapper MUST serve its listed envelopes this way while offering it, even when they are absent from its admitted transaction pool; requests trigger no historical searches or recursive peer fetches.

The requester MUST check that `envelopes` is nonempty, holds no more entries than requested, and that each envelope's `H` equals the listed hash at the corresponding index. A violation is invalid peer data, so withholding a listed envelope is attributable to that source and object. A GetWrapperEnvelopes request grants credit for one response and shares the request ID sequence, `MAX_REQUESTS_PER_PEER`, deadlines, Cancel handling and serving budget with GetChunks. Received envelopes are charged to the byte budgets below.

### Reassembly and Source Changes

Clients MUST keep at most one assembly per object ID. Requests can interleave, but all body chunks in an assembly come from the same source peer. They MAY resume missing indices from that peer. Before switching to another source, clients MUST cancel or retire outstanding body requests and release all partial body bytes; the assembly retains its original absolute deadline and source-attempt count. The configured source-attempt budget counts restarts from the same peer; resuming missing indices is not a new attempt.

Before allocation or copying, clients MUST charge retained chunks, recovered envelopes and completion copies to the per-peer and global byte budgets. Declared lengths MUST NOT trigger allocation of the whole object. Metadata, announcements, outstanding envelope requests, source lists and verification work also need finite global and per-peer budgets. Completed objects and pending envelope recovery stay charged until validation finishes or the assembly is abandoned; sharing data MUST NOT hide pinned bytes from accounting.

Assembly timers start at first retrieval, not announcement. Idle time resets only on a newly received missing chunk from the selected source or a newly resolved missing envelope. Duplicate messages, source changes and queue moves do not extend the absolute deadline. Expiry releases bytes and metadata and cancels work no longer needed by a live assembly. Source changes after a mismatch or withholding remain subject to finite retry and work budgets.

Peers MAY evict objects and later answer Unavailable or Busy. Disconnection, expiry and insufficient local capacity do not establish object invalidity. A bounded pending-announcement cache can defer retrieval when resources are occupied; completion is not guaranteed.

### Validation and Relay

With all chunks present, the receiver MUST check the length, `content_hash` and canonical body encoding, then validate the wrapper under EIP-8288.

A descriptor is an untrusted claim, so clients MUST NOT announce, serve, admit or reaggregate an object before full validation. A content-hash mismatch discards the entire source contribution; a retry from another peer starts with no retained body bytes.

Clients SHOULD keep a bounded cache of proof verdicts keyed by `(H(proof), deps_hash)`, where `deps_hash` is EIP-8288 `get_deps_hash` of the dependencies the proof covers: the mode-1 `deps` for its `stark_proof`, or the single dependency of each mode-0 proof. A re-batched wrapper carrying a known proof, or a known proof with a different or unresolvable transaction list, then does not trigger verification again.

After full wrapper validation, ordinary admission is evaluated per transaction under EIP-8288. Local refusal, state changes or pool policy do not establish proof invalidity. No Complete status acknowledges admission or retention.

### Scheduling and Errors

Senders MUST apply backpressure before serializing chunks, MUST yield between Chunk messages so that queued messages of other protocols are serviced at the next message boundary, and MUST NOT queue a whole object as serialized messages. Implementations SHOULD use small write windows and schedule fairly across objects, peers and capabilities.

Malformed encodings, content-hash mismatches, inconsistent geometry, mismatched envelope hashes, withheld listed envelopes, unrequested data and invalid proofs are invalid peer data: the client MUST discard the contribution and stop the associated transfer, and MAY disable `lean/1` for, disconnect or penalize the peer. Size violations MUST be rejected before large allocation or decompression. Message IDs outside `0x00` through `0x07` are protocol violations. On a protocol violation the client SHOULD disconnect the peer. Incompatibility, Unavailable, Busy, TooLarge, local queue exhaustion, cancellation, expiry and pool rejection of a validly proven transaction MUST NOT by themselves be treated as misbehavior.

Verification, transaction-admission and proving queues MUST have finite concurrency and backlog, and Busy results MUST NOT create unbounded retries. Clients SHOULD throttle sources that repeatedly send invalid data or consume credit without useful progress, while tolerating isolated stalls, and MAY throttle peers that repeatedly request the same object.

## Rationale

Announcement followed by requested retrieval follows [EIP-2464](./eip-2464.md); size-aware selection follows [EIP-5793](./eip-5793.md). Request IDs follow [EIP-2481](./eip-2481.md), with strictly increasing IDs allowing stale responses to be discarded without retaining every retired ID.

Single-source assembly makes corrupt data attributable to its sender. Since integrity is checked against the complete content hash, switching sources restarts retrieval; requests to the same source can resume missing chunks. Single-source retrieval with one `content_hash` suffices at objects of at most 9 MiB; if objects grow, multi-source retrieval with per-chunk Merkle verification is an option for `lean/2`.

Dedicated envelope requests are scoped to one object, so a peer that announced it either serves each listed envelope that fits or explicitly refuses, and withholding is unambiguous. Under `eth`, a missing pooled transaction cannot be distinguished from ordinary eviction, and announcing dependency-bearing transactions there would deliver them to peers that cannot validate them. The 2 MiB response ceiling matches the `eth` soft response limit, so a response occupies the connection no longer than the `eth` responses it replaces.

Descriptors carry no dependency-digest, transaction-list or proof-hash hints. The verdict cache already avoids repeated verification after download, identical transaction lists with identical proofs already share a `content_hash`, and unauthenticated announcement fields would invite deprioritization games.

Hash-only wrappers keep identity independent of peers' envelope caches and avoid embedding thousands of transactions. The object-size ceiling accommodates EIP-8288 wrappers; it is not a recommended batch size. Deriving profile IDs from locally configured keys avoids a separate verifier registry.

Validation before relay adds a full download and proof check at every hop. Large wrappers cannot be assumed to propagate within the aggregation interval; batch sizes require latency measurements.

## Backwards Compatibility

Peers without `lean/1` can continue using existing protocols but do not receive pending dependency-bearing transactions, which are not announced over `eth`.

## Test Cases

[Commitment vectors](../assets/eip-8437/commitment-vectors.json) use a zero profile ID and `body[i] = i % 251`. [Wrapper vectors](../assets/eip-8437/wrapper-vectors.json) give a profile ID for a dummy key, 96-byte dependency encodings and hash-only mode-0 and mode-1 bodies; Keccak-256 stands in for `DEPS_HASH`. [The executable checks](../assets/eip-8437/check_vectors.py) cover both, plus chunk boundaries, message bounds and envelope-response truncation. They test transport encodings, not EIP-8288 proof validity.

Implementations should also cover:

| Case | Expected result |
| --- | --- |
| Unknown message ID | Protocol violation |
| Zero-length or oversized body; noncanonical RLP; excessive nesting or list count | Reject before large allocation |
| Same wrapper offered to peers with different envelope caches | Identical body and object ID |
| Request IDs have gaps; an ID repeats or decreases | Accept gaps; reject reuse or decrease |
| Unknown object with syntactically valid indices | Complete with Unavailable |
| Wrong live request object, index order or chunk length | Protocol violation |
| Duplicate chunk through another request to the same source | Consume credit, retain one copy, no renewed assembly progress |
| Chunk bytes conflict with an already retained index | Discard the source contribution |
| Complete says Served before all requested chunks arrive | Protocol violation |
| Cancel crosses the last Chunk and Served | Discard post-cancellation payloads; terminal response releases the slot |
| Late response after expiry; requester and responder expire at different times | Discard retired responses; timing alone incurs no penalty |
| A body fails its content hash; another source offers the same descriptor | Discard partial bytes, retry within the original deadline and attempt bound |
| Source changes or reconnects; duplicate announcements or queue moves | No extended absolute lifetime or multiplied budgets |
| Requests across many peers would exceed the global byte ceiling | Refuse or defer before allocation |
| Complete body waits for verification or envelope recovery | Remains charged and expires normally |
| Envelope retained outside the admitted pool is requested | Serve it while offering its validated wrapper |
| Requested envelopes exceed `MAX_ENVELOPE_RESPONSE_BYTES` | Serve the longest fitting prefix; requester re-requests the rest |
| Response is empty, overlong, omits a fitting envelope or has a hash mismatch | Invalid peer data; the object stays incomplete |
| Envelope request for an unknown or evicted object | Complete with Unavailable |
| Envelope indices unordered, too many, or not below the transaction count | Protocol violation |
| Dependency-bearing transaction in the pool | Not announced, broadcast or returned over `eth` |
| Known proof arrives with a different or unresolvable transaction list | Reuse a cached verdict; no second verification |
| One peer's unvalidated bytes would exceed a quarter of the global buffer | Refuse or defer before allocation |
| Mode-0 wrapper | Checked against the target fork's `AGGREGATED_VK` profile |
| Preliminary proof verifies but recovered envelopes do not validate the wrapper | No admission, reaggregation or relay |
| Envelope unavailable, local refusal, or transaction fails pool policy | No penalty solely for that reason |
| Profile is known but inappropriate for the target fork | No admission or timing-independent misbehavior inference |
| Proof parameters or enabled schemes change | Use the profile derived from the corresponding key |

Scheduling tests should cover bounded retry, completion-copy pressure, verification queues and control messages between chunk writes. Proof-verifier interoperability requires EIP-8288 profiles and test vectors.

## Security Considerations

A content hash supplied by a malicious peer can match an invalid proof. Announcements and chunks therefore establish no validity, and full validation precedes relay. Finite per-peer and global byte, recovery and work budgets remain necessary against many peer identities; absolute deadlines bound withholding and slow streams.

Arithmetic on counts, offsets, lengths and credit must be checked before allocation, and proof decoders need their own resource bounds. Invalid proof checks can cost real work without corresponding sender effort.

Chunking permits interleaving but does not remove TCP head-of-line blocking or guarantee completion within a slot.
