## Abstract

This EIP defines `eth/73`, a version of the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md) that propagates [EIP-8288](./eip-8288.md) proof wrappers ("wrappers" below). Peers announce wrapper modes, lengths and hashes, then request whole wrappers by hash.

## Motivation

EIP-8288 separates signatures and proofs from transaction envelopes and permits aggregation across transactions. Existing transaction propagation does not identify this shared proof material, so peers need a way to discover and retrieve it.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/73` extends `eth/72` ([EIP-8070](./eip-8070.md)), using its notation and message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md).

### Transaction propagation

A dependency-bearing transaction contains an EIP-8288 dependency verification frame. Below `eth/73`, clients MUST NOT broadcast or announce these transactions and MUST answer requests for them as unavailable.

On `eth/73`, existing transaction message encodings, limits and response rules apply:

**Propagation: Transactions (0x02) and NewPooledTransactionHashes (0x08)**

- Clients SHOULD propagate pooled dependency-bearing transactions alongside covering-wrapper announcements, using existing transaction fan-out and size policies.
- Clients MAY instead announce only covering wrappers; receivers then fetch missing envelopes through GetPooledTransactions.

**Envelope retrieval: GetPooledTransactions (0x09) and PooledTransactions (0x0a)**

- Requesters MAY fetch envelopes for distinct transaction hashes listed in a held wrapper from peers that announced or served it. Check responses against any type and size metadata announced by the responding peer ([EIP-5793](./eip-5793.md)).
- Responders SHOULD serve every envelope listed in a wrapper they offer, including those rejected or evicted from the pool, using only the pool or other bounded local storage without historical searches or recursive fetches.

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes.

#### NewProofWrapperHashes (0x16)

`[[mode₀: P, length₀: P, hash₀: B_32], [mode₁: P, length₁: P, hash₁: B_32], ...]`

- Announce 1 to 64 held wrappers per message, in either mode, in strictly ascending hash order.
- Each mode is EIP-8288's wrapper mode: `0` for direct dependencies or `1` for a recursive STARK.
- Each length is the encoded wrapper size, from 1 to EIP-8288's `MAX_WRAPPER_BYTES`, and each hash is Keccak-256 of those exact bytes.
- Peers SHOULD announce offered wrappers on connection.
- On fully validating a received or locally generated wrapper, peers SHOULD announce it to every connected `eth/73` peer, subject to the following suppression rules.
- Peers SHOULD NOT announce hashes already announced or sent, in either direction, on that connection.
- Peers SHOULD NOT announce a wrapper whose transaction hashes are already covered, under the same verification rules, by wrappers they have sent to or received from the recipient, or whose hashes the recipient has announced, unless it reduces proof bytes or verification work.

#### GetProofWrappers (0x17)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1 to 64 distinct wrapper hashes per message, each announced by the recipient.

#### ProofWrappers (0x18)

`[request-id: P, [wrapper₀, wrapper₁, ...]]`

- Return requested, offered wrappers in request order, omitting unavailable entries; each wrapper uses [EIP-8288's mempool wrapper format](./eip-8288.md#mempool-wrapper-object), embedded as an RLP item.
- EIP-8288's `MAX_WRAPPER_BYTES` MUST NOT exceed the `eth` soft response limit (2 MiB). Include the first available wrapper, then stop before another would take the encoded response past that limit.
- Responders MAY return an empty list for unavailability or an exhausted serving budget.
- Requesters match wrappers to distinct requested hashes and the responding peer's announced modes and lengths in order, then re-request hashes after the last returned wrapper.

### Validation

- Clients MUST check wrapper encoding, length and hash, resolve all listed envelopes, and fully validate under [EIP-8288](./eip-8288.md) before announcing, serving or reaggregating. Proof checks against the wrapper's declared dependencies MAY run before or alongside envelope recovery.
- Clients MAY retain envelopes pending a covering wrapper within finite local byte and time limits, but MUST NOT admit or relay their transactions until that wrapper is fully validated. Unresolved envelopes leave a wrapper incomplete, not invalid.
- After EIP-8288's local target fork changes `AGGREGATED_VK` or a scheme's verification parameters, clients MUST NOT announce or serve wrappers validated only under the previous rules.
- Count, size or ordering violations SHOULD cause disconnection.
- Malformed encodings, unmatched or excess responses, and invalid proofs MUST be discarded and MAY cause disconnection or penalties.
- Permitted empty or partial responses, rejection under the receiver's pool policy, or exhaustion of its recovery or verification budgets MUST NOT alone cause peer penalties.
- Clients SHOULD lower a peer's score for repeatedly pushing dependency-bearing envelopes without announcing a covering wrapper on that connection before their retention windows expire. Unresolved announcements do not establish absence of coverage.
- Clients SHOULD withhold peer penalties for proof failures during a bounded local window around a verifier change (RECOMMENDED: from one slot before the local target fork changes the verifier until the head is 64 blocks past the fork).

## Rationale

### Propagation and recovery

Transaction announcements identify envelopes; wrapper announcements identify their proof material. Propagating both concurrently lets receivers obtain envelopes while fetching and checking proofs, avoiding a sequential envelope-fetch round trip. GetPooledTransactions also recovers envelopes discovered through wrappers, which provide hashes but no per-transaction type or size metadata.

Serving envelopes independently of pool admission lets peers validate offered wrappers after individual transactions are rejected or evicted.

### Wrapper retrieval

Whole-wrapper retrieval uses `eth`'s existing response model within the 2 MiB wrapper bound. The 64-hash request limit permits batching small wrappers; large wrappers can reduce a response to one item. Chunk requests would permit resuming or distributing downloads, but require additional indexing and assembly; aggregate verification still requires the full proof. Separately retrieving proofs could reuse proof bytes across wrappers at the cost of another retrieval path. Validation before relay adds download and proof-check latency at each hop, so batch sizes need measurements; propagation within the aggregation interval cannot be assumed.

Mode distinguishes individual dependency checks from a single recursive STARK verification; length estimates transfer cost. Both are checked against the returned wrapper. Announcements omit dependency-digest and proof-hash hints: identical wrappers already share a hash, and EIP-8288's verdict caches avoid repeat verification. Suppressing redundant coverage limits reaggregation churn while allowing more compact or cheaper-to-verify aggregates.

## Backwards Compatibility

`eth/73` activates with EIP-8288. Older versions continue exchanging blocks and other transactions but receive neither wrappers nor dependency-bearing envelopes through transaction messages.

## Test Cases

[Announcement vectors](../assets/eip-8437/announcement-vectors.json) and [wrapper encoding vectors](../assets/eip-8437/wrapper-vectors.json) provide fixed RLP encodings and content hashes. [The checker](../assets/eip-8437/check_vectors.py) exercises encoding, message counts, ordering, metadata matching and response packing. Its synthetic witnesses do not establish EIP-8288 proof validity.

The following client cases use valid dependency-bearing transactions A and B and a covering wrapper W under a fixed target verifier, with sufficient local budgets. They are not executed by the checker; ordinary transaction and pool checks still apply.

| Input sequence | Expected result |
| --- | --- |
| Retain A and B received through Transactions, then announce, request and receive W | No admission or relay before full wrapper validation; afterward the proof requirement is satisfied |
| Receive W first; recover A, then B through GetPooledTransactions | W remains incomplete after A; after B, full validation reaches the same result as the previous case |
| Receive A, B and a wrapper with an invalid proof but correctly announced mode, length and hash | Transport matching passes; proof validation fails, preventing admission, relay or reaggregation based on that wrapper |
| Validate W, evict A from the pool while retaining its envelope, continue offering W, then receive a GetPooledTransactions request for A | Return A under the serving recommendation |
| Fetch A using W's hash list without a transaction announcement; repeat after the responding peer announces an incorrect type or size | Missing announcement metadata alone does not reject A; supplied metadata must match |
| Exchange mode-1 W1 for A and W2 for B with a peer. Generate mode-1 W3 for A and B; after sending W3, generate W4 with W3's coverage, mode and size | W3 can replace two proof verifications with one and be announced; W4 need not be announced merely because its hash differs |
| Repeatedly push envelopes without announcing covering wrappers before their retention windows expire, with no unresolved announcements; repeat with a covering wrapper announced but not fetched | Lower the sender's peer score only in the first case; unresolved announcements or local resource exhaustion alone establish no failure |

## Security Considerations

Invalid proofs impose verification costs without corresponding sender effort. Clients should bound outstanding requests per peer, bytes awaiting validation, verification and proving work, and serving traffic; recovery deadlines limit withholding. Large responses delay other messages on the same connection. Implementations should bound each peer's share of pending announcements.

Near fork transitions, peers may select different target verifiers; the grace window avoids penalizing honest peers for those differences.
