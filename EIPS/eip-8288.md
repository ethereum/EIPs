## Abstract

This EIP extends [EIP-8141](./eip-8141.md) with a new frame mode that enables EVM-level aggregation of cryptographic signatures and STARK (Scalable Transparent ARguments of Knowledge) proofs. The scheme allows transactions to carry lightweight **dependencies** — `(scheme, data_hash, verification_key_hash)` triples — which are aggregated off-chain into a single recursive STARK. Block validity requires this recursive STARK, enabling efficient post-quantum (PQ) and scalable signature aggregation using Lean Ethereum tooling.

## Motivation

Quantum-resistant signatures and zero-knowledge proofs both have a very high calldata requirement and gas cost. Current proposals for hash-based signatures are in the range of ~2-3 kB and ~150,000 to 200,000 gas to verify. Lattice-based signatures have a similar cost. Meanwhile, hash-based zero-knowledge proofs (STARKs) all take over 128 kB, or as much as 512 kB if fast generation is a goal (which it is client-side), which implies a STARK will take many millions of gas to verify. This on its own would mean that privacy protocols will have an impractically high cost, and be completely incompatible with FOCIL ([EIP-7805](./eip-7805.md)) and Frame Transactions ([EIP-8141](./eip-8141.md)).

This EIP solves this problem by adding **STARK-based aggregation**. Instead of a block directly containing these user-submitted signatures and STARKs, the block contains one single recursive STARK that proves their existence. More specifically, it:

- Introduces **dependency frames** that declare `(scheme, data_hash, verification_key_hash)` triples as transaction-level dependencies.
- Requires a **recursive STARK** at the block level that proves the validity of all dependencies in all transactions.
- Reuses **Lean Ethereum** tooling (for signatures and STARKs), to maximize shared codebase.
- Provides a **mempool wrapper** format that bundles transactions with their dependencies and proofs.
- Supports **recursive aggregation** at the mempool layer, allowing mempool nodes to combine proofs and reduce bandwidth overhead.
- Is **compatible with FOCIL** ([EIP-7805](./eip-7805.md)), ensuring that the aggregation scheme works with fork-choice enforced inclusion lists.

### New Frame Mode

This EIP introduces a new frame mode for [EIP-8141](./eip-8141.md) frame transactions:

#### Dependency Verification Frame (`DEP_VERIFY_FRAME_MODE`)

We modify EIP-8141 to also allow frames with mode `DEP_VERIFY_FRAME_MODE`, in addition to all previously allowed modes. `DEP_VERIFY_FRAME_MODE` is added to the set of mode values accepted by EIP-8141's static constraint on `frame.mode`; no other mode value becomes valid. A frame with mode `DEP_VERIFY_FRAME_MODE` is a **dependency verification frame**. It declares a set of **dependencies** as `(scheme, data_hash, verification_key_hash)` triples. These triples are not executed as EVM code; instead, they are recorded as dependencies that must be proven valid by the recursive STARK in the block.

The **payload encoding** is a simple `96*k` byte concatenation of `k` triples, each consisting of:

- `scheme`: 31 zero bytes padding, then 1 byte identifying the verification scheme (`LEANSPHINCS_SCHEME` or `LEANSTARK_SCHEME`).
- `data_hash`: 32 bytes. For `LEANSPHINCS_SCHEME`, this is the message hash (`msghash`). For `LEANSTARK_SCHEME`, this is the public inputs hash (`pub_input_hash`).
- `verification_key_hash`: 32 bytes. For `LEANSPHINCS_SCHEME`, this is the leanSPHINCS public key itself, laid out as `root (16 bytes) || public parameter (16 bytes)`, the order the aggregation circuit hashes it in; a key that already fits in 32 bytes needs no hash. For `LEANSTARK_SCHEME`, this is a hash of the STARK verification key (`vk_hash`).

This data is stored in the frame's `data` field.

**Receipt**:

A dependency verification frame produces an [EIP-8141](./eip-8141.md) frame receipt like any other frame, with `status = 1`, `gas_used.execution` equal to the frame's `limits.execution`, `gas_used.state = 0`, and no logs.

**Validity constraints**:

- The frame's `data` must be exactly `96*k` bytes, and the first 31 bytes of each set of 96 must be zero.
- For each set of 96 bytes, `scheme` (byte 31) must be `LEANSPHINCS_SCHEME`. `LEANSTARK_SCHEME` is reserved: a frame that uses it is invalid until `get_deps_hash` is defined for it.
- Number of triples must be `>= 1` and `<= MAX_DEPENDENCIES_PER_FRAME`.
- The frame's `target` must be `None`. This is EIP-8141's absent target, not the zero address: `resolved_target` is then `tx.sender`, and `FRAMEPARAM(0x00, i)` returns the sender's address. Contracts identify dependency verification frames by `mode`, not by target.
- The frame's `value` must be `0`.
- The frame's `flags` must be `0`.
- The frame must not be part of an [EIP-8141](./eip-8141.md) atomic batch. Its `flags` are `0`, so this means the preceding frame, if any, must not carry `ATOMIC_BATCH_FLAG`.
- The frame's `limits.execution` must be `sum(LEANSPHINCS_VERIFICATION_GAS if triple.scheme == LEANSPHINCS_SCHEME else LEANSTARK_VERIFICATION_GAS for triple in frame.data_triples)`.
- The frame's `limits.state` must be `0`. The frame executes no code, so it can consume no state gas.

### Transaction Dependencies

A frame transaction may contain frames with mode `DEP_VERIFY_FRAME_MODE`. These frames declare **dependencies** that must be satisfied by the block's recursive STARK.

The complete list of dependencies for a transaction is the concatenation of all dependency triples from all dependency verification frames. The `data_triples` property of a frame is the list of `(scheme, data_hash, verification_key_hash)` triples parsed from the frame's `data` field:

```
frame.data_triples = [
    (data[31], data[32:64], data[64:96])
    for data in chunks(frame.data, 96)
]

dependencies(tx) = deduplicate_and_sort([
    (scheme, compute_sig_hash(tx) if data_hash == bytes(32) else data_hash, verification_key_hash)
    for frame in tx.frames if frame.mode == DEP_VERIFY_FRAME_MODE
    for (scheme, data_hash, verification_key_hash) in frame.data_triples
])

dependencies(block) = deduplicate_and_sort([
    triple
    for tx in block.txs
    for triple in dependencies(tx)
])
```

Where `deduplicate_and_sort` deduplicates and sorts:

```python
def deduplicate_and_sort(deps):
    o = []
    for dep in sorted(deps):
      if len(o) == 0 or dep != o[-1]:
        o.append(dep)
    return o
```

A `data_hash` of 32 zero bytes stands for the signature hash of the containing transaction, `compute_sig_hash(tx)` as defined in EIP-8141. A transaction cannot carry its own signature hash in a frame, because that hash covers the frame's `data`. `dependencies(tx)` holds the signature hash in place of the zero bytes, so the mempool wrapper, the FOCIL and the block prove a statement about that hash. The frame's `data` is unchanged: `compute_sig_hash` covers the zero bytes and `FRAMEDATACOPY` returns them.

### Transaction Execution Visibility

During EVM execution, the transaction's dependencies are made available through the existing [EIP-8141](./eip-8141.md) `FRAMEPARAM` and `FRAMEDATACOPY` instructions.

Contracts can iterate over all frames in the transaction using `FRAMEPARAM` to identify `DEP_VERIFY_FRAME_MODE` frames, then use `FRAMEPARAM(0x04, i)` and `FRAMEDATACOPY` to read the dependency data from each frame's `data` field.

Specifically:

- `FRAMEPARAM(0x02, i)` returns the `mode` of frame `i`. Frames with mode `DEP_VERIFY_FRAME_MODE` are dependency frames.
- `FRAMEPARAM(0x04, i)` returns `len(data)` for frame `i`.
- `FRAMEDATACOPY(memOffset, dataOffset, length, i)` copies the dependency data from frame `i` into memory.

The data format for each dependency frame is a concatenation of 96-byte triples: `scheme || data_hash || verification_key_hash`.

This allows smart contracts to introspect the declared dependencies during execution using the existing EIP-8141 frame introspection mechanism.

### Block Validity: Recursive STARK

A block is valid only if it contains a **recursive STARK** that proves the validity of all dependencies in all transactions. The block header commits to the proof and the block body carries it. This is formalized as follows.

#### Recursive STARK Header Entry

Two new 32-byte fields are appended to the block header, in this order: `stark_proof_hash`, which commits to the aggregated STARK proof for the block, and `block_deps_hash`. The proof itself, `stark_proof`, is a new field of the block body, encoded after the existing fields, and the `starkProof` field of the execution payload.

**Header encoding**:

```
stark_proof_hash: Hash32 = keccak256(stark_proof)
block_deps_hash: Hash32 = get_deps_hash(dependencies(block))
```

- `stark_proof`: The serialized recursive STARK proof, carried in the block body. It does not carry the dependencies or their keys; a verifier takes them from the block through `block_deps_hash`. If `dependencies(block)` is empty, `stark_proof` is empty.
- `stark_proof_hash`: `keccak256(stark_proof)`. A body whose `stark_proof` does not hash to this value is not the body of this block: it is discarded and requested again, and the block is not marked invalid.
- `block_deps_hash`: `get_deps_hash(dependencies(block))`, the digest the recursive STARK commits to in its public statement:

```
  get_deps_hash(deps) = DEPS_HASH(concat([
      t.data_hash + t.verification_key_hash
      for t in deps
  ]))
```

`get_deps_hash` is defined for lists of `LEANSPHINCS_SCHEME` dependencies. `DEPS_HASH` is the hash the aggregation circuit uses for its dependency digest; header and circuit use the one function, so a client computes the digest the proof is verified against directly from the block.

#### Recursive STARK Proof Structure

The recursive STARK is generated using Lean Ethereum tooling. It proves the following statement:

```python
public inputs = [deps_hash, AGGREGATED_VK]

private inputs = [deps, witnesses, recursive_proofs, recursive_deps_list, discards]

# get_deps_hash as defined for block_deps_hash

# Verify direct dependencies
assert len(deps) == len(witnesses)
for i in range(len(witnesses)):
    scheme, data_hash, verification_key_hash = deps[i]
    if scheme == LEANSPHINCS_SCHEME:
        assert verify_leanSPHINCS(data_hash, verification_key_hash, witnesses[i])
    else if scheme == LEANSTARK_SCHEME:
        assert verify_leanSTARK((data_hash,), verification_key_hash, witnesses[i])
    else:
        assert False

# Verify recursive proofs and collect their deps
all_deps = list(deps)
for i in range(len(recursive_proofs)):
    proof = recursive_proofs[i]
    inner_deps = recursive_deps_list[i]
    # Verify the recursive proof's public input matches its claimed deps hash
    assert verify_leanSTARK((get_deps_hash(inner_deps), AGGREGATED_VK), AGGREGATED_VK, proof)
    # Add the inner deps to the union
    all_deps.extend(inner_deps)

# Remove discards and duplicates
discard_hashes = set(get_deps_hash([d]) for d in discards)
filtered_deps = deduplicate_and_sort([
    dep for dep in all_deps if get_deps_hash([dep]) not in discard_hashes
])

# Verify final deps hash matches public input
assert get_deps_hash(filtered_deps) == deps_hash
```

The recursive STARK circuit follows a "verify inputs, merge and discard" logic. It verifies:

- All leanSPHINCS signatures using the Lean Ethereum leanSPHINCS verifier
- All leanSTARKs using the Lean Ethereum leanSTARK verifier
- Recursive STARKs using the Lean Ethereum leanSTARK verifier.

We assume that the `leanSPHINCS` and `leanSTARK` verifiers are structured in such a way that they take as input a 32-byte pubkey hash or verification key hash, and the relevant parts of the full public key or verification key are included as part of the signature or proof as a witness. This is a generic transformation that can be made to any signature scheme or STARK scheme: `verify_sig(msg, pub, sig)` becomes `verify(msg, hash(pub), (pub, sig))` and `verify_stark(data_hash, vk, proof)` becomes `verify_stark(data_hash, hash(vk), (vk, proof))`. For `LEANSPHINCS_SCHEME` the public key is already 32 bytes, so it is used directly in place of `hash(pub)`.

The recursive STARK circuit does not understand the structure of transactions or blocks beyond iterating over a flat list of `(scheme, data_hash, verification_key_hash)` triples, their corresponding witnesses, and nested recursive STARKs.

The recursive STARK is verified using a fixed protocol-level `AGGREGATED_VK`.

To enable unlimited-depth recursion, we need to pass the `AGGREGATED_VK` in as an input to the proof itself.

#### Block Validity Rules

A block is valid if and only if:

1. The `block_deps_hash` in the block header equals `get_deps_hash(dependencies(block))`.
2. If `dependencies(block)` is empty, `stark_proof` is empty. Otherwise the recursive STARK proof verifies successfully against `block_deps_hash` and the fixed protocol-level `AGGREGATED_VK`.
3. All transactions satisfy the normal (EIP-8141 or other) validity rules.

### Mempool Wrapper Object

At the mempool level, transactions with dependency verification frames are wrapped in **wrapper objects**. Each wrapper contains a **list of transactions** and either their direct dependencies or a single recursive STARK proving all dependencies.

These proof wrappers are distinct from the blob-transaction network wrappers served by `PooledTransactions`.

**Wrapper encoding** (canonical RLP):

```
[transactions, mode, content]
transactions = list of full EIP-8141 frame transactions
mode = 0 (direct dependencies) or 1 (recursive STARK)
content = if mode == 0: [deps, proofs]
          if mode == 1: [deps, recursive_stark]
```

Where:

- `transactions` = nonempty list of full frame transactions in [EIP-8141's network form](./eip-8141.md#networking), with the pooled-encoding changes of the applicable `eth` version. Each is embedded as an RLP byte string, in strictly ascending transaction-hash order.
- `deps` = sorted, deduplicated union of `dependencies(tx)` for all transactions in the wrapper, each entry as its 96-byte payload encoding from [New Frame Mode](#new-frame-mode)
- `proofs` = list of individual proof byte strings corresponding to each dependency in `deps`, in order
- `recursive_stark` = a single proof byte string proving validity of all deps, with public input `get_deps_hash(deps)`

Transaction hashes and dependency extraction use the [EIP-2718](./eip-2718.md) consensus envelope, excluding any network wrapper.

Every listed transaction must declare at least one dependency.

**Mode 0 (Direct dependencies)**: When a mempool node receives a wrapper with `mode == 0`, they must verify that:

1. The `deps` list is the sorted, deduplicated union of all dependencies from each transaction in `transactions`
2. The total number of leanSPHINCS deps is `<= MAX_LEANSIG_DEPS_PER_WRAPPER`
3. The total number of leanSTARK deps is `<= MAX_LEANSTARK_DEPS_PER_WRAPPER`
4. There is exactly one proof per dependency, in order, and each verifies its dependency individually

**Mode 1 (Recursive STARK)**: When a mempool node receives a wrapper with `mode == 1`, they must verify that:

1. The recursive STARK's public input `deps_hash` equals `get_deps_hash(deps)`
2. The recursive STARK is valid (proves all deps are valid)
3. The `deps` list is the sorted, deduplicated union of all dependencies from each transaction in `transactions`

Validate the wrapper before evaluating admission per transaction, including applicable availability checks. Pool rejection does not invalidate the dependency proof or other transactions.

Validate against the intended inclusion fork's `AGGREGATED_VK` and direct-verification parameters. A verifier change requires revalidation; mode-1 proofs under a different key must be replaced. The [eth/73 proposal](https://github.com/ethereum/EIPs/pull/12423) specifies target-fork selection for its mempool transport.

Each wrapper contains exactly one STARK in mode 1, and one STARK per leanSTARK dependency in mode 0.

Mode 0 is intended to be used primarily by clients broadcasting their transactions. If desired, mempool nodes whose local transaction pool contains ONLY leanSPHINCS signatures and no STARKs may choose to rebroadcast a mode 0 aggregation that naively concatenates the leanSPHINCS instead of proving them, within the mode-0 dependency limits.

The wrapper object is not a valid transaction on its own. Mempool nodes, FOCIL creators and builders use the **same recursive STARK format** to aggregate proofs. The only difference is the scope: mempool nodes aggregate over their current view of valid and includable transactions, while builders aggregate over the transactions they decide to include in the block.

### Recursive Mempool Aggregation

This EIP introduces **recursive aggregation** at the mempool layer. This allows mempool nodes to combine proofs and reduce bandwidth overhead to builders.

Mempool nodes follow the following algorithm:

- They passively wait and receive wrapper objects from users, validating them as above.
- When a transaction becomes unincludable (either because some other transaction from the same sender is included onchain, or because of any other mempool expiry rule), they keep note that its dependencies need to be pruned
- They may generate multiple mode-0 or mode-1 wrappers over still-valid transactions, using `AGGREGATION_INTERVAL` as a recommended cadence.

Splitting or pruning must preserve dependencies shared with retained transactions and prove their exact union. Validated wrappers may be forwarded without reaggregation.

For inclusion-list reuse, aggregators should retain a bounded selection of mode-1 intermediate wrappers whose proofs meet the IL byte and dependency bounds through the next view freeze. A list spanning wrappers may still require a new proof.

If a node anticipates that it will not have enough proving time to aggregate in _all_ aggregates that it saw, it should prioritize in the following order:

1. Its own aggregate from the previous round
2. Removing anything that needs to be removed
3. Other nodes' aggregates, in descending order of how many new transactions they will add to the aggregate
4. Users' transactions, in descending order of priority fee

Nodes may also alternate between adding one object at a time from (3) and (4).

#### Mempool-Level Limits

Wrappers encode in at most `MAX_WRAPPER_BYTES` bytes, including transactions, dependencies, proofs and RLP overhead. Block proofs count toward the [EIP-7934](./eip-7934.md) block-size limit.

Additionally, two mempool-level limits apply to each transaction: a transaction can have `<= MAX_SIGS_PER_TX` leanSPHINCS dependencies and `<= MAX_STARKS_PER_TX` leanSTARK dependencies, added up across all frames.

The wrapper and per-transaction limits are mempool rules, not consensus bounds on blocks or inclusion lists.

Dependency-count limits apply to the length of the sorted, deduplicated dependency list. The list in a wrapper is required to be deduplicated in any case. For transactions, however, it does mean that it is legal to have a transaction with eg. `> MAX_SIGS_PER_TX` leanSPHINCS dependency _declarations_, if some of them are pointing to the same object so the deduplicated list is within limits. This behavior is wasteful but harmless; it is charged for and limited through the gas mechanism.

### Inclusion list interaction

EIP-8288 activates after [EIP-7805](./eip-7805.md), modifying its inclusion obligations and proof transport below. A slot-`N` list constrains slot `N + 1`; that block's fork determines validity, verification and formats, including early publication.

| Parameter | Provisional value |
| --- | --- |
| `MAX_DEPS_PER_IL_PROOF` | `128` |
| `MAX_IL_PROOF_BYTES` | `1310720` (1.25 MiB) |
| `IL_PROOF_CUTOFF_MARGIN_MS` | `1000` |
| `MAX_IL_PROOF_RETENTION_MS` | `48000` |
| `DOMAIN_IL_PROOF` | Assigned by the activating fork |

#### Inclusion obligations

For each counted list, apply EIP-7805's inclusion conditions:

- Dependency-free transactions remain obligatory regardless of proofs. They must decode and contain no dependency frame; an invalid or empty dependency frame does not qualify.
- Dependency-bearing entries require an authenticated list whose commitment check returns `VALID` by view freeze; only covered entries are obligatory. Otherwise treat the commitment as null.
- Mempool limits, proving time, retention and scheduling introduce no omission grounds.

Hypothetical inclusion checks validity and gas fit with proven dependencies satisfied, without requiring coverage by, or regeneration of, the existing block proof. Actual blocks prove exactly `dependencies(block)`, discarding only input dependencies absent from that union; wrapper limits do not constrain blocks.

The proof is part of the RLP-encoded block and counts toward the [EIP-7934](./eip-7934.md) limit. Builders packing transactions before proving must leave room for the final proof and RLP overhead.

#### Commitment

Append `recursive_stark: List[InclusionListProofCommitment, 1]` to EIP-7805's signed `InclusionList`: empty means null, singleton means commitment. Transaction-byte limits are unchanged.

```python
class InclusionListProofCommitment(Container):
    stark_proof_hash: Bytes32
    deps_hash: Bytes32

class InclusionListProof(Container):
    stark_proof: ByteList[MAX_IL_PROOF_BYTES]
    proof_deps: List[ByteVector[96], MAX_DEPS_PER_IL_PROOF]
```

An `il_proof` is an `InclusionListProof` with:

- Nonempty, canonical, sorted, deduplicated `proof_deps` using only schemes permitted in dependency frames.
- Nonempty `stark_proof` verifying against `deps_hash = get_deps_hash(proof_deps)` under `AGGREGATED_VK`.
- `stark_proof_hash = keccak256(stark_proof)`.

`is_static_dependency_tx(tx)` means an envelope decodes as EIP-8141, contains a dependency frame, and satisfies EIP-8141's Constraints as extended here, including dependency-frame constraints; no state or mempool checks apply. An entry is covered independently when this predicate holds and `set(dependencies(tx)) <= set(proof_deps)`.

A valid committed proof matches both hashes, covers at least one entry, and remains held as verified bytes and dependencies. Wrapper proofs may supply it within IL bounds; surplus dependencies are allowed. Commit null when none are covered; unknown, invalid or non-covering proofs count as null. Uncommitted proofs create no obligations. Commitment changes follow EIP-7805's equivocation rule.

#### Proof availability

Add this CL gossip object:

```python
class InclusionListProofMessage(Container):
    slot: Slot
    committee_index: uint64
    stark_proof_hash: Bytes32
    deps_hash: Bytes32

class SignedInclusionListProof(Container):
    message: InclusionListProofMessage
    il_proof: InclusionListProof
    signature: BLSSignature
```

The indexed committee member signs `compute_signing_root(message, get_domain(state, DOMAIN_IL_PROOF, compute_epoch_at_slot(message.slot)))`; the domain differs from list signing.

- The CL accepts proofs only for the previous, current or next slot, with valid committee signatures, matching hashes and encodings within bounds.
- The CL admits at most two distinct proof hashes per member and slot. The second is accepted only once that slot begins. Repeated hashes, third proofs and early second proofs are dropped without treating the member as an IL equivocator.
- The CL forwards a proof only after EL submission returns `VALID`. The member's eventual list may commit to a different proof or null.
- The CL authenticates the first list per member before fetching its proof. Equivocation excludes that member's lists and cancels pending list-proof work.
- Retrieval is limited to the committed proof, allowing one additional distinct proof beyond topic publications.
- Attesters retry `PROOF_UNKNOWN` until the proof deadline; `INVALID` or `PROOF_LATE` ends retrieval. Builders may retrieve until the next slot's proposal deadline.

CL req/resp `(slot, stark_proof_hash)` returns unsigned `il_proof` via the Engine getter, or none.

CL deadlines are `uint64` Unix milliseconds: `proof_deadline_ms` is slot-`N` view freeze minus `IL_PROOF_CUTOFF_MARGIN_MS`; `view_freeze_deadline_ms` is that freeze; `attestation_deadline_ms` is slot-`N + 1`'s attestation deadline. Retain verified bytes and dependencies through the latest required deadline, independently of wrapper eviction; expired deadlines impose nothing. Reject retention beyond either `1000 * timestamp + MAX_IL_PROOF_RETENTION_MS` or current time plus that bound with `-32602`, without clamping; storage exhaustion is an API error, not `INVALID`.

#### Engine API

All methods select the target fork by `timestamp`. Aggregate verdicts are keyed by `(stark_proof_hash, deps_hash, AGGREGATED_VK)`; IL bounds and coverage are checked separately. `available_since_ms` records when uninterrupted retention of verified proof bytes and dependencies began, including those obtained from wrappers. Eviction clears this timestamp.

`engine_verifyInclusionListProofV1(timestamp, transactions, recursive_stark, il_proof, proof_deadline_ms, attestation_deadline_ms)` takes a non-null commitment and an optional proof. The EL ignores a supplied proof that does not match both committed hashes and rejects `proof_deadline_ms > attestation_deadline_ms` with `-32602`. It returns:

- `INVALID`: no statically valid dependency entry, known dependencies cover no entry, a cached invalid aggregate (even without bytes), or a matching malformed/invalid proof.
- `VALID`: held valid committed proof available since the cutoff or earlier.
- `PROOF_LATE`: the same, available later.
- `PROOF_UNKNOWN`: otherwise, including a valid verdict without bytes.

For both `VALID` and `PROOF_LATE`, the EL retains the proof bytes and dependencies through `attestation_deadline_ms`.

`engine_getInclusionListProofV1(timestamp, stark_proof_hash)` returns a held, verified, IL-bounded proof or null.

`engine_submitInclusionListProofV1(timestamp, il_proof, view_freeze_deadline_ms)` rejects invalid shape or bounds with `INVALID`; otherwise verify against `get_deps_hash(proof_deps)`, record and return the aggregate verdict (`VALID` or `INVALID`), retaining valid proofs through `view_freeze_deadline_ms`.

Construction returns transactions, commitment and proof for signing/publication; new building and `engine_newPayload` methods carry separate `(transactions, recursive_stark or null)` lists in committee-position order. Builders accept `VALID` or `PROOF_LATE`, even after view freeze; frozen attester inputs require their own EL's `VALID` by view freeze, otherwise null, and later arrivals do not change that view.

#### Activation requirements

Fix encodings, bounds, SSZ types, signing domain, req/resp, new Engine versions and deadlines together; existing Engine versions remain unchanged. The verifier must support every gas-valid block dependency set. Benchmark cold builder retrieval and construction after the latest list arrival, proof verification by cutoff and coverage by view freeze under background load; repeat before gas-limit increases. `IL_COMMITTEE_SIZE × MAX_IL_PROOF_BYTES`, plus dependency metadata and transport overhead, must fit the dissemination window with margin.

### Lean Ethereum Integration

This EIP assumes the use of Lean Ethereum tooling for generating and verifying the recursive STARKs. This tooling can be found at the leanEthereum GitHub organization.

The recursive STARK is generated by:

1. Defining a Lean function that takes a flat list of `(scheme, data_hash, verification_key_hash)` triples and their corresponding witnesses.
2. Iterating over the list, and for each triple with `scheme == LEANSPHINCS_SCHEME`, calling `leanSPHINCS.verify(data_hash, verification_key_hash, witness)`.
3. For each triple with `scheme == LEANSTARK_SCHEME`, calling `leanSTARK.verify(data_hash, verification_key_hash, witness)`.
4. Proving that all verifications return `true`.
5. Generating a STARK proof of this execution using the Lean Ethereum STARK backend.

The circuit is a relatively simple recursive "union and remove" construction, very similar to that which is planned to be used for consensus-layer signatures. It does not understand transactions or blocks; it only sees a flat list of dependencies and witnesses.

The verification key `AGGREGATED_VK` used to verify the recursive STARK is a fixed protocol-level value derived from the Lean Ethereum STARK circuit definition.

### Gas Accounting

The frame's `limits.execution` for a dependency verification frame is:

```
verification_gas(dep_verify_frame) = sum(
    LEANSPHINCS_VERIFICATION_GAS if triple.scheme == LEANSPHINCS_SCHEME else LEANSTARK_VERIFICATION_GAS
    for triple in dep_verify_frame.data_triples
)
```

The actual STARK verification is performed off-chain by the builder, so the gas cost represents the _expected_ cost of verifying the recursive STARK, not the actual cost. It is much cheaper than the onchain costs for similar operations because the cost is only paid by the builder and the mempool, not by all validating nodes.

Each transaction also pays for its share of the block's recursive STARK:

```
recursive_stark_gas(tx) = LEANSTARK_VERIFICATION_GAS * len(dependency_triples(tx))
```

where `dependency_triples(tx)` is every triple in every dependency verification frame of `tx`, duplicates included. `recursive_stark_gas(tx)` is added to the transaction's intrinsic gas (`frame_tx_intrinsic_gas` in EIP-8141). It is execution gas, counts toward the transaction's `gas_used` and the block's `gas_used`, and is paid by the transaction's payer like the rest of the intrinsic gas. The block's `gas_used` includes no other charge for the recursive STARK.

Because these dependencies are at the transaction body level and are not created inside the EVM, they are not affected by transaction execution reverting, and the gas is still fully charged even if the transaction reverts. This is similar to eg. intrinsic gas for calldata.

As a special case, notice that if a frame or a transaction has the same dependency multiple times, gas is charged for each declaration. So duplicate dependencies in a transaction are legal, but are wasteful.

## Rationale

### Mempool wrapper design

Enclosing transactions with their dependency proofs permits validation without separate envelope retrieval. Bounding the complete object allows whole-wrapper retrieval within the `eth` soft response limit.

### Inclusion-list proofs

Reusing wrapper proofs avoids proving on the list's critical path; early publication permits advance verification. `MAX_IL_PROOF_BYTES` bounds proof bytes; the dependency cap bounds metadata to `96 × MAX_DEPS_PER_IL_PROOF` bytes (currently 12 KiB). Neither bounds prior proving work. Small intermediate wrappers improve reuse, but arbitrary selections may require proving.

Unavailable proofs affect only covered dependency-bearing entries, preserving other obligations. Arrival timing can still produce different attester views; accepting late proofs for building helps satisfy stronger views without changing frozen views. A late list may require cold retrieval and aggregation, which activation benchmarks must cover.

### Why a new frame mode instead of an EVM opcode?

If an EVM opcode were chosen instead, the core question is how to handle missing or invalid proofs. From a mempool node's point of view, if it sees a dependency appear during transaction execution, and it has no valid proof for it, then it must be able to reject that transaction. And if a mempool accepts a transaction, it must be confident that EVM execution in later frames will not create _other_ dependencies that are unfulfilled.

The most realistic alternative would be for an opcode that creates a `(scheme, data_hash, verification_key_hash)` dependency to only be callable during an EIP-8141 validation frame. This would be viable. However, it would still make the mempool and builder's job relatively harder, because the EVM execution and dependency validation would have to be done sequentially rather than in parallel. It would also add more need to reason about special cases where EVM execution might add a dependency but then revert.

### Why recursive STARKs?

Recursive STARKs allow the aggregation of many individual proofs into a single proof. This is essential to avoid the size blowup of one STARK per transaction (that uses a STARK).

Each block carries a recursive STARK. This does increase the block size, a cost that has to be paid if blocks are to be verified without the individual signatures. The header holds a hash of the proof and not the proof: the block hash fixes the proof bytes either way, and checking `block_deps_hash` needs the block's transactions, so a header with the proof inside it proves nothing about the block that a header with the hash does not. Keeping the proof in the body leaves headers at their present size for every reader that handles headers alone.

**This EIP proposes recursive aggregation at the mempool layer.** Mempool nodes generate recursive STARKs over bounded batches of valid wrapper objects they know about. This reduces bandwidth to the builder, as the builder receives pre-aggregated proofs from mempool nodes. The STARK-related overhead depends on batch count, proof size and update frequency.

The builder uses the exact same recursive STARK format to aggregate all included transactions' dependencies into the block-level recursive STARK.

### Why Lean Ethereum?

The Lean Ethereum tooling has already been extensively developed, has full formal verification in progress, and is the expected signature and recursive proof type for the future Ethereum consensus chain.

**This EIP's use case — processing many thousands of signatures and STARKs per slot without extreme data overhead — is almost identical to the consensus layer's use case.** The main differences are:

1. Hashes vs bitfields as identifiers of what objects are being proven
2. Many-time stateless signatures (leanSPHINCS), instead of the counter-based stateful signatures (leanXMSS) that the consensus layer can use because it needs to enforce one-signature-per-slot anyway.

Because the underlying use cases are similar, from a total spec simplification perspective, it is best to reuse the exact same tooling, rather than create a totally different set of tools for the execution layer.

Users who want to use quantum-resistant signature schemes other than leanSPHINCS signatures will have to either use them in the clear, and accept the onchain gas costs of doing so, or wrap them client-side in a STARK, and then reuse the leanSTARK route.

### Gas costs

As written, the EIP enforces fixed gas costs for both signatures and STARKs. This is assuming one parametrization of leanSPHINCS is used, and one parametrization of STARKs (or at least a small ratio between the average case and the upper bound).

An upper bound does need to be enforced. We make sure to add appropriate trace width limits and execution cycle count limits to STARK verification. In the current design (KoalaBear field, fixed trace width), this is enforced by the `2**24` trace length limit inherent to KoalaBear, and the trace width is fixed. If leanVM is redesigned, limits need to be kept in mind, so that the maximum possible proof size is a small multiple of the average case.

There may be two valid reasons to adjust the current fixed-cost approach and switch to variable cost:

- **Mixed k-time and unlimited-time usage of leanSPHINCS**: k-time signatures are significantly smaller than unlimited-time signatures, and SPHINCS could expose a parametrization that supports both. In this case, the former would need to have appropriately lower gas costs.
- **Different STARK sizes based on client-side proving time tradeoffs** Smaller proofs take longer to generate. We want larger proofs (cheaper to generate) to be possible, while still encouraging smaller proofs that put less load on the mempool nodes. This can be achieved by making gas cost proportional to proof size (or a related metric, like query count, and even polynomial degree).

### Why dependency frames may not sit in an atomic batch

Requiring `flags == 0` keeps a dependency verification frame from being a flagged batch member, but leaves it a valid terminator. [EIP-8141](./eip-8141.md) defines an atomic batch as a maximal run `[i, j]` where frames `i` through `j-1` carry `ATOMIC_BATCH_FLAG` and frame `j` does not, and its successor rule excludes only `VERIFY` frames.

The terminator is the frame at which the batch commits. When a batch fails its remaining frames are skipped and take receipt status `0x2`, but a dependency is declared at the transaction body level and, as [Gas Accounting](#gas-accounting) states, is unaffected by execution reverting and charged regardless. A dependency verification frame in that position would be skipped and binding on the block at once. EIP-8141 already restricts the batch flag by mode, so a mode rule here is consistent with it.

### Why the dependency frame still gets a receipt

[EIP-8141](./eip-8141.md) requires a frame receipt per frame, builds the transaction's logs by concatenating them in frame order, and exposes per-frame results through `FRAMEPARAM` `0x05`, `0x0A` and `0x0B`, which read by frame index. Omitting the entry for a frame that does not execute would renumber every later frame's results, on exactly the transactions [Transaction Execution Visibility](#transaction-execution-visibility) invites contracts to walk. EIP-8141's own rationale prices its per-frame cost as covering the receipt sub-entry that each frame adds.

## Backwards Compatibility

This EIP introduces new transaction types and frame modes. It does not modify the behavior of existing transactions. Transactions without signature or STARK verification frames are unaffected.

Nodes that do not implement this EIP will:

- Reject transactions containing `DEP_VERIFY_FRAME_MODE` frames as invalid (unknown frame mode).
- Reject blocks whose header carries the `stark_proof_hash` and `block_deps_hash` fields as invalid.

This is a consensus-breaking change. Activation requires a network upgrade.

## Test Cases

### Test Case 1: Simple leanSPHINCS Verification

A transaction with a single `DEP_VERIFY_FRAME_MODE` frame containing one `(LEANSPHINCS_SCHEME, 0, pubkey_hash)` triple, followed by a `VERIFY` frame that checks the existence of a dependency with a `pubkey_hash` pulled from its storage and a zero `data_hash`, which stands for the transaction's signature hash.

### Test Case 2: Reserved leanSTARK Scheme

A dependency frame using `LEANSTARK_SCHEME` is rejected while the scheme is reserved.

### Test Case 3: Block with Mixed Transactions

A block containing:

- A normal EIP-8141 transaction.
- A transaction with dependency verification frames.
- A block header with `stark_proof_hash` and `block_deps_hash` fields, and a body with a `stark_proof` field.

### Test Case 4: Invalid Recursive STARK

A block with an invalid recursive STARK (e.g., wrong `block_deps_hash` or invalid proof) should be rejected. A body whose `stark_proof` does not match `stark_proof_hash` should be discarded without marking the block invalid.

### Test Case 5: Mode 0 Mempool Wrapper

A mode 0 mempool wrapper containing multiple transactions (including the transaction from Test Case 1). Verify that the wrapper's `deps` and `proofs` match the transactions' dependencies, and that each proof can be verified individually.

### Test Case 6: Mode 1 Mempool Wrapper

A mode 1 mempool wrapper containing multiple transactions (including the transaction from Test Case 1). Verify that the wrapper's recursive STARK proves all dependencies are valid, and that the `deps_hash` matches `get_deps_hash(deps)`.

### Test Case 7: Recursive Mempool Aggregation

A scenario where a mempool node receives multiple transactions and generates a mode 1 wrapper with a recursive STARK. Verify that the recursive STARK covers all dependencies of all transactions in the wrapper, and that the wrapper can be verified by other mempool nodes and builders.

### Test Case 8: Wrapper with Recursive STARK (Mode 1)

A mempool wrapper containing a transaction with dependencies, where the wrapper uses `mode == 1` and contains a pre-computed recursive STARK. Verify that the recursive STARK's public input `deps_hash` matches `get_deps_hash(deps)` and that the proof is valid.

### Test Case 9: FOCIL with Recursive STARK

A FOCIL containing transactions with dependencies, where the FOCIL includes a `recursive_stark` commitment. Verify that the committed proof, received separately, proves the covered list entries' dependencies, and that a builder can incorporate this FOCIL into a block-level recursive STARK.

Also verify these interactions:

- Evicting proof bytes while retaining a valid verdict returns `PROOF_UNKNOWN`; resupply resets availability and may return `PROOF_LATE`.
- A builder uses a late valid proof to satisfy a timely attester's obligations without changing its own frozen view.
- Check an otherwise valid IL proof at `MAX_IL_PROOF_BYTES` and one byte above; reject only the latter for size.
- A proof's failure to cover one list, or to meet IL bounds, does not invalidate its aggregate verdict for another use. Malformed or uncovered entries do not suppress covered entries.
- Two topic publications do not prevent retrieval of a third, list-committed proof; list equivocation cancels pending list-proof work.
- Early proofs use the target block's fork even when mempool validation still uses the preceding fork.

### Test Case 10: Discard Set

A scenario where a mempool node generates a recursive STARK that includes a discard set, excluding expired or invalid objects from the validity claim. Verify that the resulting `deps_hash` reflects only the non-discarded dependencies.

### Test Case 11: FOCIL Compatibility

Verify that:

- Block dependency sets permitted by transaction and gas rules are not rejected by wrapper ceilings or additional dependency-count limits.
- A builder missing a committed proof still satisfies dependency-free obligations; attesters with a timely proof and a list checked by view freeze additionally enforce its covered dependency-bearing entries.
- Superset proofs are merged and pruned to exactly `dependencies(block)`, preserving dependencies shared with retained transactions.
- Mempool limits, proving time, retention and scheduling do not excuse otherwise required transactions, including those evaluated at an earlier index under EIP-7805.

### Test Case 12: Bounded Mempool Aggregation

- Mode 0 accepts 16 signature dependencies and rejects 17; mode 1 can combine two such wrappers, but neither mode admits a transaction with 17 distinct signatures.
- Reject empty transaction or dependency lists, hash references, envelopes not strictly ordered by transaction hash, and mismatched dependency unions.
- Check the complete encoded wrapper at the byte limit and one byte above, including envelope and RLP overhead.
- Ordering and duplicate detection use consensus transaction hashes, excluding network wrappers.
- A wrapper validated under a previous verifier requires revalidation; changing its transactions requires checking their dependency union.

## Security Considerations

### Trust Assumptions

The security of this EIP relies on:

1. **Soundness of Lean Ethereum circuits**: The STARK circuits must correctly implement the verification logic.
2. **Soundness of the hash function used for `deps_hash` and `block_deps_hash`**: `DEPS_HASH` is the hash the aggregation circuit uses for its claim-list digest, BLAKE2s in the current tooling, with BLAKE3 the leading choice to replace it. The header follows the circuit, so the two change together.
3. **Soundness of recursive STARKs**: a STARK of a STARK of ... of a STARK must be sound. This is widely believed to be true and many constructions running live onchain already depend on this. However, this adds difficulty to end-to-end formally proving the scheme and its applications. Note also that the STARK verification keys that users put in to this system are up to users, and may potentially have unlimited recursion depth.

### Denial of Service

Aggregation work depends on proof inputs, overlap and discards, not only on the gas-bounded output. The inclusion-list activation benchmarks therefore cover the complete construction, including dependencies later discarded.

Mempool per-transaction and wrapper limits are not consensus limits on blocks or inclusion lists. Mempool admission and transaction validity add these limits:

- `MAX_SIGS_PER_TX` limits the number of leanSPHINCS dependencies per transaction to 16.
- `MAX_STARKS_PER_TX` limits the number of leanSTARK dependencies per transaction to 1.
- `MAX_DEPENDENCIES_PER_FRAME` limits the number of dependencies per frame.
- `MAX_FRAMES` (from EIP-8141) limits the number of frames per transaction.
- `MAX_LEANSIG_DEPS_PER_WRAPPER` and `MAX_LEANSTARK_DEPS_PER_WRAPPER` limit mode-0 dependencies.
- `MAX_WRAPPER_BYTES` bounds the complete serialized object, including transaction data, in both modes.
- The gas cost for verification frames scales with the number of dependencies, making large dependency sets expensive.

Wrapper bytes and direct-dependency counts bound received data and direct checks; they do not bound recursive proving work, including work on discarded dependencies.

Committee authentication permits two topic proofs and one separately retrieved commitment per member/slot; activation benchmarks include overlapping committees.

These limits are inspired by the mempool policy framework of [ERC-7562](./eip-7562.md) (as used in EIP-8141).
