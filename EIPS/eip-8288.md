## Abstract

This EIP extends [EIP-8141](./eip-8141.md) with a new frame mode that enables EVM-level aggregation of cryptographic signatures and STARK (Scalable Transparent ARguments of Knowledge) proofs. The scheme allows transactions to carry lightweight **dependencies** — `(scheme, data_hash, verification_key_hash)` triples — which are aggregated off-chain into a single recursive STARK. Block validity requires this recursive STARK, enabling efficient post-quantum (PQ) and scalable signature aggregation using Lean Ethereum tooling.

## Motivation

Quantum-resistant signatures and zero-knowledge proofs both have a very high calldata requirement and gas cost. Current proposals for hash-based signatures are in the range of ~2-3 kB and ~150,000 to 200,000 gas to verify. Lattice-based signatures have a similar cost. Meanwhile, hash-based zero-knowledge proofs (STARKs) all take over 128 kB, or as much as 512 kB if fast generation is a goal (which it is client-side), which implies a STARK will take many millions of gas to verify. This on its own would mean that privacy protocols will have an impractically high cost, and be completely incompatible with FOCIL ([EIP-7805](./eip-7805.md)) and Frame Transactions ([EIP-8141](./eip-8141.md)).

This EIP solves this problem by adding **STARK-based aggregation**. Instead of a block directly containing these user-submitted signatures and STARKs, the block contains one single recursive STARK that proves their existence. More specifically, it:

- Introduces **dependency frames** that declare `(scheme, data_hash, verification_key_hash)` triples as transaction-level dependencies.
- Requires a **recursive STARK** at the block level that proves the validity of all dependencies in all transactions.
- Reuses **Lean Ethereum** tooling (for signatures and STARKs), to maximize shared codebase.
- Provides a **mempool wrapper** format that bundles transactions with their dependencies and proofs.
- Supports **recursive aggregation** at the mempool layer, allowing mempool nodes to combine proofs and reduce bandwidth overhead.
- Is **compatible with FOCIL** ([EIP-7805](./eip-7805.md)), ensuring that the aggregation scheme works with fork-choice enforced inclusion lists.

### Cryptographic parameters

`ENABLED_SCHEMES`, verification relations, circuit resource limits (including recursive inputs and discards), and the 32-byte dependency digest and its encoding are fixed by `AGGREGATED_VK`; changing them requires a new key.

Every serialized aggregate proof, including a recursive input, must be at most `MAX_AGGREGATE_PROOF_BYTES` bytes; reject longer proofs before decoding or verification. This bound applies to blocks, wrappers and inclusion lists and is provisional pending proof-size and verifier benchmarks. The activating fork must fix it with the canonical proof encoding and fit a mode-1 wrapper at the list ceilings within `MAX_WRAPPER_BYTES`.

`LEANSTARK_SCHEME` remains reserved until its canonical key and witness encodings, key commitment and verification parameters are specified.

The key-hash rule is `vk_hash = keccak256(domain_tag || canonical_vk)`, where `domain_tag` is the ASCII string `ethereum/8288/leanSTARK/vk/v1` followed by one zero byte. The domain tag prevents reuse of a key commitment across protocols and purposes; scheme separation is already provided by the dependency encoding. Keccak lets contracts and wallets derive `vk_hash` with existing EVM primitives; its in-circuit cost is bounded by the key size limit.

### New Frame Mode

This EIP introduces a new frame mode for [EIP-8141](./eip-8141.md) frame transactions:

#### Dependency Verification Frame (`DEP_VERIFY_FRAME_MODE`)

We modify EIP-8141 to also allow frames with mode `DEP_VERIFY_FRAME_MODE`, in addition to all previously allowed modes. `DEP_VERIFY_FRAME_MODE` is added to the set of mode values accepted by EIP-8141's static constraint on `frame.mode`; no other mode value becomes valid. A frame with mode `DEP_VERIFY_FRAME_MODE` is a **dependency verification frame**. It declares a set of **dependencies** as `(scheme, data_hash, verification_key_hash)` triples. These triples are not executed as EVM code; instead, they are recorded as dependencies that must be proven valid by the recursive STARK in the block.

The **payload encoding** is a simple `96*k` byte concatenation of `k` triples, each consisting of:

- `scheme`: 31 zero bytes padding, then 1 byte identifying the verification scheme (`LEANSPHINCS_SCHEME` or `LEANSTARK_SCHEME`).
- `data_hash`: 32 bytes. For `LEANSPHINCS_SCHEME`, this is the message hash (`msghash`). For `LEANSTARK_SCHEME`, this is the public inputs hash (`pub_input_hash`).
- `verification_key_hash`: 32 bytes. For `LEANSPHINCS_SCHEME`, this is the leanSPHINCS public key itself, laid out as `root (16 bytes) || public parameter (16 bytes)`, the order the aggregation circuit hashes it in; a key that already fits in 32 bytes needs no hash. For `LEANSTARK_SCHEME`, this is a hash of the STARK verification key (`vk_hash`).

This data is stored in the frame's `data` field.

**Receipt**:

A dependency verification frame produces an [EIP-8141](./eip-8141.md) frame receipt like any other frame, with `status = 1`, `gas_used.execution` equal to the frame's `limits.execution`, `gas_used.state = 0`, and no logs.

**Validity constraints**:

- The frame's `data` must be exactly `96*k` bytes, and the first 31 bytes of each set of 96 must be zero.
- For each set of 96 bytes, `scheme` (byte 31) must belong to `ENABLED_SCHEMES`; all other values are invalid.
- Number of triples must be `>= 1` and `<= MAX_DEPENDENCIES_PER_FRAME`.
- The frame's `target` must be `None`. This is EIP-8141's absent target, not the zero address: `resolved_target` is then `tx.sender`, and `FRAMEPARAM(0x00, i)` returns the sender's address. Contracts identify dependency verification frames by `mode`, not by target.
- The frame's `value` must be `0`.
- The frame's `flags` must be `0`.
- The frame must not be part of an [EIP-8141](./eip-8141.md) atomic batch. Its `flags` are `0`, so this means the preceding frame, if any, must not carry `ATOMIC_BATCH_FLAG`.
- The frame's `limits.execution` must be `sum(LEANSPHINCS_VERIFICATION_GAS if triple.scheme == LEANSPHINCS_SCHEME else LEANSTARK_VERIFICATION_GAS for triple in frame.data_triples)`.
- The frame's `limits.state` must be `0`. The frame executes no code, so it can consume no state gas.

### Transaction Dependencies

A frame transaction may contain frames with mode `DEP_VERIFY_FRAME_MODE`. These frames declare **dependencies** that must be satisfied by the block's recursive STARK.

The complete list of dependencies for a transaction is the concatenation of all dependency triples from all dependency verification frames. The `data_triples` property of a frame is the list of `(scheme, data_hash, verification_key_hash)` triples parsed from the frame's `data` field:

```
frame.data_triples = [
    (data[31], data[32:64], data[64:96])
    for data in chunks(frame.data, 96)
]

dependencies(tx) = deduplicate_and_sort([
    (scheme, compute_sig_hash(tx) if data_hash == bytes(32) else data_hash, verification_key_hash)
    for frame in tx.frames if frame.mode == DEP_VERIFY_FRAME_MODE
    for (scheme, data_hash, verification_key_hash) in frame.data_triples
])

dependencies(block) = deduplicate_and_sort([
    triple
    for tx in block.txs
    for triple in dependencies(tx)
])
```

Where `deduplicate_and_sort` deduplicates and sorts:

```python
def deduplicate_and_sort(deps):
    o = []
    for dep in sorted(deps):
      if len(o) == 0 or dep != o[-1]:
        o.append(dep)
    return o
```

A `data_hash` of 32 zero bytes stands for the signature hash of the containing transaction, `compute_sig_hash(tx)` as defined in EIP-8141. A transaction cannot carry its own signature hash in a frame, because that hash covers the frame's `data`. `dependencies(tx)` holds the signature hash in place of the zero bytes, so the mempool wrapper, the FOCIL and the block prove a statement about that hash. The substitution applies to every scheme, so an all-zero `data_hash` is reserved: a leanSPHINCS message or leanSTARK `pub_input_hash` of zero cannot be declared.

The frame's `data` is unchanged: `compute_sig_hash` covers the zero bytes and `FRAMEDATACOPY` returns them, not the signature hash. A contract comparing a dependency with `TXPARAM(0x08)`, the transaction's signature hash, must treat a zero `data_hash` as that hash.

Let `input_deps` be the union of dependencies covered by all input proofs, including mode-0 direct witnesses, and `retained_deps` the dependency union of the selected transactions. The discard set is:

```python
def discard_dependencies(input_deps, retained_deps):
    inputs, retained = set(input_deps), set(retained_deps)
    assert retained <= inputs
    return deduplicate_and_sort(inputs - retained)
```

Wrapper pruning, FOCIL merging and block assembly use this rule. A dependency shared with any retained transaction is retained, even if another transaction declaring it is removed.

### Transaction Execution Visibility

During EVM execution, the transaction's dependencies are made available through the existing [EIP-8141](./eip-8141.md) `FRAMEPARAM` and `FRAMEDATACOPY` instructions.

Contracts can iterate over all frames in the transaction using `FRAMEPARAM` to identify `DEP_VERIFY_FRAME_MODE` frames, then use `FRAMEPARAM(0x04, i)` and `FRAMEDATACOPY` to read the dependency data from each frame's `data` field.

Specifically:

- `FRAMEPARAM(0x02, i)` returns the `mode` of frame `i`. Frames with mode `DEP_VERIFY_FRAME_MODE` are dependency frames.
- `FRAMEPARAM(0x04, i)` returns `len(data)` for frame `i`.
- `FRAMEDATACOPY(memOffset, dataOffset, length, i)` copies the dependency data from frame `i` into memory.

The data format for each dependency frame is a concatenation of 96-byte triples: `scheme || data_hash || verification_key_hash`.

This allows smart contracts to introspect the declared dependencies during execution using the existing EIP-8141 frame introspection mechanism.

### Block Validity: Recursive STARK

A block is valid only if it contains a **recursive STARK** that proves the validity of all dependencies in all transactions. The block header commits to the proof and the block body carries it. This is formalized as follows.

#### Recursive STARK Header Entry

A new top-level field, `recursive_stark`, is added to the block header. This field commits to the aggregated STARK proof for the block. The proof itself, `stark_proof`, is a new field of the block body, encoded after the existing fields, and a field of the execution payload. The `eth` `BlockBodies` encoding carries the new field from the activating fork, as for `withdrawals`.

**Header encoding**:

```
recursive_stark = [stark_proof_hash, block_deps_hash]
```

- `stark_proof`: The serialized recursive STARK proof, carried in the block body. It does not carry the dependencies or their keys; a verifier takes them from the block through `block_deps_hash`. If `dependencies(block)` is empty, `stark_proof` is empty.
- `stark_proof_hash`: `keccak256(stark_proof)`. A block whose `stark_proof` does not hash to this value is invalid.
- `block_deps_hash`: `get_deps_hash(dependencies(block))`, the digest the recursive STARK commits to in its public statement:

```
  get_deps_hash(deps) = DEPS_HASH(concat(encode(t) for t in deps))
```

`encode(t)` is the 96-byte payload encoding from [New Frame Mode](#new-frame-mode): `31 zero bytes || scheme || data_hash || verification_key_hash`, after zero-`data_hash` substitution. Clients and the aggregate circuit use this encoding for every sorted, deduplicated dependency list, including leanSPHINCS-only lists, in blocks, wrappers, inclusion lists and recursive inputs.

#### Recursive STARK Proof Structure

The recursive STARK is generated using Lean Ethereum tooling. It proves the following statement:

```python
public inputs = [deps_hash, AGGREGATED_VK]

private inputs = [deps, witnesses, recursive_proofs, recursive_deps_list, discards]

# get_deps_hash as defined for block_deps_hash
assert len(recursive_proofs) == len(recursive_deps_list)

# Verify direct dependencies
assert len(deps) == len(witnesses)
assert all(dep[0] in ENABLED_SCHEMES for dep in deps)
for i in range(len(witnesses)):
    scheme, data_hash, verification_key_hash = deps[i]
    if scheme == LEANSPHINCS_SCHEME:
        assert verify_leanSPHINCS(data_hash, verification_key_hash, witnesses[i])
    else if scheme == LEANSTARK_SCHEME:
        assert verify_leanSTARK((data_hash,), verification_key_hash, witnesses[i])
    else:
        assert False

# Verify recursive proofs and collect their deps
all_deps = list(deps)
for i in range(len(recursive_proofs)):
    proof = recursive_proofs[i]
    assert len(proof) <= MAX_AGGREGATE_PROOF_BYTES
    inner_deps = recursive_deps_list[i]
    # Verify the recursive proof's public input matches its claimed deps hash
    assert verify_leanSTARK((get_deps_hash(inner_deps), AGGREGATED_VK), AGGREGATED_VK, proof)
    # Add the inner deps to the union
    all_deps.extend(inner_deps)

# Remove discards and duplicates
assert set(discards) <= set(all_deps)
filtered_deps = deduplicate_and_sort(set(all_deps) - set(discards))

# Verify final deps hash matches public input
assert get_deps_hash(filtered_deps) == deps_hash
```

The recursive STARK circuit follows a "verify inputs, merge and discard" logic. It verifies:

- All leanSPHINCS signatures using the Lean Ethereum leanSPHINCS verifier
- All leanSTARKs, only when `LEANSTARK_SCHEME` is in `ENABLED_SCHEMES`, using the Lean Ethereum leanSTARK verifier
- Recursive STARKs using the Lean Ethereum leanSTARK verifier.

We assume that the `leanSPHINCS` and `leanSTARK` verifiers are structured in such a way that they take as input a 32-byte pubkey hash or verification key hash, and the relevant parts of the full public key or verification key are included as part of the signature or proof as a witness. This is a generic transformation that can be made to any signature scheme or STARK scheme: `verify_sig(msg, pub, sig)` becomes `verify(msg, hash(pub), (pub, sig))` and `verify_stark(data_hash, vk, proof)` becomes `verify_stark(data_hash, hash(vk), (vk, proof))`. For `LEANSPHINCS_SCHEME` the public key is already 32 bytes, so it is used directly in place of `hash(pub)`.

The recursive STARK circuit does not understand the structure of transactions or blocks beyond iterating over a flat list of `(scheme, data_hash, verification_key_hash)` triples, their corresponding witnesses, and nested recursive STARKs.

The recursive STARK is verified using a fixed protocol-level `AGGREGATED_VK`.

To enable unlimited-depth recursion, we need to pass the `AGGREGATED_VK` in as an input to the proof itself.

#### Block Validity Rules

The block validity conditions are extended as follows:

1. The `block_deps_hash` in the recursive STARK header entry equals `get_deps_hash(dependencies(block))`.
2. If `dependencies(block)` is empty, `stark_proof` is empty. Otherwise the recursive STARK proof verifies successfully against `block_deps_hash` and the fixed protocol-level `AGGREGATED_VK`.
3. All transactions satisfy the normal (EIP-8141 or other) validity rules.

### Mempool Wrapper Object

At the mempool level, transactions with dependency verification frames are wrapped in **wrapper objects** that are broadcast in bounded batches. Each wrapper contains a **list of transactions** and either their direct dependencies or a single recursive STARK proving all dependencies.

These proof wrappers are distinct from the blob-transaction network wrappers served by `PooledTransactions`.

**Wrapper encoding**:

```
RLP([transactions, mode, [deps, proof_content]])
transactions = [transaction_hash, ...]
mode = 0 (direct dependencies) or 1 (recursive STARK)
deps = [dependency, ...]
proof_content = proofs        if mode == 0
proof_content = stark_proof   if mode == 1
```

Where:

- `transactions` = strictly ascending list of 32-byte `keccak256(transaction_envelope)` hashes, where each envelope is the exact [EIP-2718](./eip-2718.md) encoding of an EIP-8141 frame transaction. Envelopes are recovered through the wrapper transport; wrapper validity below refers to the resolved transactions. Dependency-bearing transactions are not independently announced or broadcast.
- `deps` = sorted, deduplicated union of `dependencies(tx)` for all transactions in the wrapper, with the signature hash in place of each zero `data_hash`, each entry as its 96-byte payload encoding from [New Frame Mode](#new-frame-mode)
- `proofs` = list of individual proof byte strings corresponding to each dependency in `deps`, in order
- `stark_proof` = a single recursive STARK proving validity of all deps, with public input `get_deps_hash(deps)`

Every listed transaction must declare at least one dependency, so `deps` is nonempty in both modes. Dependency-free transactions need no proof wrapper; pruning away every dependency produces no wrapper.

**Mode 0 (Direct dependencies)**: When a mempool node receives a wrapper with `mode == 0`, they must verify that:

1. The `deps` list is the sorted, deduplicated union of all dependencies from each transaction in `transactions`
2. The total number of leanSPHINCS deps is `<= MAX_LEANSIG_DEPS_PER_DIRECT_WRAPPER`
3. The total number of leanSTARK deps is `<= MAX_LEANSTARK_DEPS_PER_DIRECT_WRAPPER`
4. `len(proofs) == len(deps)`, and each proof verifies its dependency individually

**Mode 1 (Recursive STARK)**: When a mempool node receives a wrapper with `mode == 1`, they must verify that:

1. The recursive STARK's public input `deps_hash` equals `get_deps_hash(deps)`
2. The recursive STARK is valid (proves all deps are valid)
3. The `deps` list is the sorted, deduplicated union of all dependencies from each transaction in `transactions`
4. The total number of deps is `<= MAX_DEPS_PER_AGGREGATE_WRAPPER`

Full wrapper validation in either mode requires resolving every transaction hash and checking the exact dependency union. An unresolved hash alone leaves the wrapper incomplete, not invalid. Nodes recover missing envelopes within finite byte and work budgets and a finite deadline, check each envelope against its claimed hash, and check the dependency union. Until all entries are resolved and the wrapper is fully validated, it must not be used for admission, reaggregation or relay. Exhausting those bounds abandons recovery without establishing transaction or proof invalidity.

Wrapper validation uses the node's configured rules for the fork at `head.timestamp + L`, the slot after its local head, even if missed:

- Estimate `L = (head.timestamp - parent.timestamp) // (head.slot_number - parent.slot_number)` in seconds, using [EIP-7843](./eip-7843.md) slot numbers. If no parent exists or the slot difference is nonpositive, use the head's fork. This local estimate sets no proof-retention deadline.
- The target fork determines `AGGREGATED_VK` for mode 1 and each scheme's verification parameters for mode 0.
- On a target-verifier change, drop mode-1 wrappers verified under the old key. Revalidate mode-0 wrappers under the new rules before admission, reaggregation or relay; unchanged verification parameters permit cached direct-witness verdicts.

Transactions covered only by dropped wrappers need new proofs. Nodes should retain their original mode-0 witnesses for a bounded window before scheduled key changes, and senders should rebroadcast mode-0 wrappers afterward.

Nodes should keep two bounded proof-verdict caches, because a mode-0 proof and a mode-1 proof are checked by different verification operations:

- direct-witness verdicts, keyed by `(dep, keccak256(witness), scheme_params)`, where `witness` is a mode-0 proof, `dep` the 96-byte encoding of the dependency it verifies, and `scheme_params` an identifier of the target fork's verification parameters for that dependency's scheme;
- aggregate-proof verdicts, keyed by `(keccak256(stark_proof), get_deps_hash(deps), AGGREGATED_VK)` for a mode-1 proof, with the target fork's `AGGREGATED_VK`.

A lookup consults only the cache for the operation it would run, and an entry applies only under the verifier in its key. A known proof arriving with a different or unresolvable transaction list under the same verifier is not verified again. A direct witness for one dependency placed in a one-dependency mode-1 wrapper, or any proof after the target fork's verifier changes, misses and is verified.

After validation, admission is evaluated per transaction: rejection for current state, fees or local pool policy does not invalidate the proof or require rejecting other transactions.

Each wrapper contains exactly one STARK in mode 1, and one STARK per leanSTARK dependency in mode 0. Nodes may maintain multiple bounded wrappers. `AGGREGATION_INTERVAL` is a recommended scheduling cadence, not a requirement to regenerate or broadcast the entire mempool on every tick.

Mode 0 is intended to be used primarily by clients broadcasting their transactions. If desired, mempool nodes whose local transaction pool contains ONLY leanSPHINCS signatures and no STARKs may choose to rebroadcast a mode 0 aggregation that naively concatenates the leanSPHINCS instead of proving them, as doing so may be more space-efficient within the mode-0 dependency limits.

The wrapper object is not a valid transaction on its own. Mempool nodes, FOCIL creators and builders use the **same recursive STARK format** to aggregate proofs. The only difference is the scope: mempool nodes aggregate over their current view of valid and includable transactions, while builders aggregate over the transactions they decide to include in the block.

### Recursive Mempool Aggregation

This EIP introduces **recursive aggregation** at the mempool layer. This allows mempool nodes to combine proofs and reduce bandwidth overhead to builders.

Mempool nodes follow the following algorithm:

- They passively wait and receive wrapper objects from users. They fully validate each wrapper as above, including transaction recovery, the dependency union and proofs, before evaluating admission per transaction.
- When a transaction becomes unincludable (either because some other transaction from the same sender is included onchain, or because of any other mempool expiry rule), they recompute `discard_dependencies` for the retained transactions
- Every `AGGREGATION_INTERVAL` milliseconds, they may generate new wrapper objects containing bounded subsets of still-valid transactions: using mode 0 or mode 1 for nonempty dependency unions. They forward useful updates with the same hash-only transaction list to every peer.

Splitting or pruning a wrapper uses `discard_dependencies` for each resulting transaction set and requires a proof matching its exact dependency union. Nodes may forward validated wrappers without reaggregation and retain older wrappers within local budgets.

For each batch, if a node anticipates that it will not have enough proving time to aggregate in _all_ aggregates that it saw, it should prioritize in the following order:

1. Its own aggregate from the previous round
2. Removing anything that needs to be removed
3. Other nodes' aggregates, in descending order of how many new transactions they will add to the aggregate
4. Users' transactions, in descending order of priority fee

Nodes may also alternate between adding one object at a time from (3) and (4).

#### Mempool-Level Limits

- Mode 0 uses `MAX_LEANSIG_DEPS_PER_DIRECT_WRAPPER` and `MAX_LEANSTARK_DEPS_PER_DIRECT_WRAPPER`; mode 1 uses `MAX_DEPS_PER_AGGREGATE_WRAPPER`.
- Both modes contain 1 to `MAX_TXS_PER_WRAPPER` transactions and encode in at most `MAX_WRAPPER_BYTES` bytes.
- The selected transaction, dependency and aggregate-proof ceilings must fit together within `MAX_WRAPPER_BYTES`. At the provisional values, a maximal mode-1 wrapper is 1,847,317 bytes.

Mode 1 verifies one aggregate proof, so its dependency-count bound is independent of scheme; the verifier's input and resource bounds apply separately. The activated proof format and `AGGREGATED_VK` must support every valid dependency set composed of enabled schemes within `MAX_DEPS_PER_AGGREGATE_WRAPPER`. A receiver whose verifier cannot verify such a wrapper refuses it locally and does not treat it as invalid.

Additionally, in both modes, two mempool-level limits apply to each transaction: a transaction can have `<= MAX_SIGS_PER_TX` leanSPHINCS dependencies and `<= MAX_STARKS_PER_TX` leanSTARK dependencies, added up across all frames.

These are mempool policy limits, not consensus bounds on blocks or inclusion lists. Dependency-count limits bound the final set, not private proof inputs or proving work, including work on discarded dependencies; the activated verifier's input and resource bounds apply separately. Scheme-specific limits do not enable a scheme. Counts and encoded lengths must be checked before allocation, and retention, recovery, verification and proving must stay within finite local budgets.

These limits in all cases apply to the length of the sorted, deduplicated dependency list. The list in a wrapper is required to be deduplicated in any case. For transactions, however, it does mean that it is legal to have a transaction with eg. `> MAX_SIGS_PER_TX` leanSPHINCS dependency _declarations_, if some of them are pointing to the same object so the deduplicated list is within limits. This behavior is wasteful but harmless; it is charged for and limited through the gas mechanism.

### Inclusion list interaction

EIP-8288 activates after [EIP-7805](./eip-7805.md); this section modifies inclusion-list validity and builder obligations as follows. A list of slot `N` constrains the block of slot `N + 1`; that block's fork determines its static validity rules and verifier.

#### Inclusion obligations

For each list counted by EIP-7805:

- Dependency-free transactions remain obligatory regardless of proof availability. A transaction is dependency-free only if it decodes under the target fork and has no `DEP_VERIFY_FRAME_MODE` frame; an empty or invalid dependency frame does not qualify.
- Dependency-bearing transactions are obligatory only if the attester holds a valid committed proof by slot `N`'s view freeze deadline. Otherwise it treats the commitment as null, without dropping the list. Later proof arrival does not change that view; another list may independently obligate the transaction.
- EIP-7805's inclusion conditions apply. Mempool limits, proving time, retention and aggregation scheduling introduce no additional omission grounds.

The builder may use any proofs covering `dependencies(block)`. It sets `discards = discard_dependencies(input_deps, dependencies(block))`, including direct witnesses in `input_deps`, and proves exactly the block's dependency set. Wrapper limits do not constrain blocks or excuse omissions; inclusion-list proof bounds are specified below.

#### Commitment

Extend the signed inclusion list with `recursive_stark`, covered by its existing signature:

```
recursive_stark = null | [stark_proof_hash, deps_hash]
il_proof = [stark_proof, proof_deps]
```

- `stark_proof_hash = keccak256(stark_proof)`.
- `proof_deps` is sorted and deduplicated, with at most `MAX_DEPS_PER_AGGREGATE_WRAPPER` entries in the 96-byte dependency encoding, using only `ENABLED_SCHEMES`.
- `deps_hash = get_deps_hash(proof_deps)`.
- `stark_proof` is nonempty and at most `MAX_AGGREGATE_PROOF_BYTES` bytes; it verifies against `deps_hash` under the target fork's `AGGREGATED_VK`.

Let `deps` be the sorted, deduplicated union of `dependencies(tx)` over list transactions that decode and pass EIP-8141 and EIP-8288 static validity under the target fork. Other transactions contribute no dependencies. The member commits null when `deps` is empty.

A node holds a valid committed proof when its EL retains a verified `il_proof` matching both hashes, `deps` is nonempty, and `set(deps) <= set(proof_deps)`. A fully validated mode-1 wrapper may supply that proof. A cached verdict without proof bytes does not suffice. Only inclusion-list proofs may cover surplus dependencies; block proofs remain exact.

An unknown, invalid or non-covering proof, or a non-null commitment with empty `deps`, is treated as null. Uncommitted wrapper proofs do not create inclusion obligations. Re-signing a list, including changing its commitment, follows EIP-7805's equivocation rule.

#### Proof availability

**Publication.** Add a consensus-layer gossip object:

```
SignedInclusionListProof = [slot, committee_index, stark_proof_hash, deps_hash, il_proof, signature]
```

The validator at `committee_index` of `slot`'s IL committee signs `[slot, committee_index, stark_proof_hash, deps_hash]` using EIP-7805's signing procedure with a new domain distinct from `DOMAIN_IL_COMMITTEE`. This signature authenticates the proof; the member's eventual list may commit to another proof or null.

Before submitting a topic proof to the EL, the CL checks:

- `slot` is the previous, current or next slot, and the committee signature is valid.
- The proof and dependency list satisfy the size, encoding and hash checks above.
- This is the first or second distinct `stark_proof_hash` from this member for `slot` to pass these checks. A second is admitted only from `slot` onward. Third, repeated or early second proofs are dropped, without marking IL equivocation.

Forward only after `engine_submitInclusionListProofV1` returns `VALID`. Members should publish a selected proof promptly, from slot `N - 1`, and commit to a published proof. Publication is not required for commitment validity.

**Retrieval.** Add a CL req/resp request keyed by the list's slot and `stark_proof_hash`, returning an unsigned `il_proof`. The responding CL calls `engine_getInclusionListProofV1` with the target block's timestamp and returns no proof on null.

- Authenticate lists with EIP-7805's P2P validation before fetching or verifying their proofs. Process only the first list per member. On equivocation, ignore that member's lists and cancel its queued and in-flight list-proof work.
- Request only a proof committed by such a list, independently of topic publications already accepted. Two topic proofs do not prevent fetching a different committed proof; retrieval authorizes at most one further proof per member and slot.
- Attesters call `engine_verifyInclusionListProofV1` as lists arrive and may fetch and retry `PROOF_UNKNOWN` until the view freeze deadline. `INVALID` ends retrieval for that commitment.
- Builders may fetch until the proposal deadline of slot `N + 1`. A builder missing a proof can fail the inclusion check of an attester that holds it.

**Retention.** The CL supplies Unix-millisecond deadlines to the EL: slot `N`'s view freeze deadline for topic submissions, and slot `N + 1`'s attestation deadline for list verification. A `VALID` result requires retaining the proof bytes and `proof_deps` until that deadline, independently of wrapper eviction. Overlapping requirements retain the proof until the latest deadline; expired deadlines impose no retention. Storage may be on disk. A verdict may outlive its bytes, but then the proof is unavailable until resupplied.

#### Engine API

All three methods take the target block's `timestamp` to select the fork. Aggregate-proof verdicts are cached by `(stark_proof_hash, deps_hash, AGGREGATED_VK)`; matching supplied bytes reuse a verdict after hash and shape checks. List coverage is checked separately and must not invalidate an otherwise valid aggregate-proof verdict.

`engine_verifyInclusionListProofV1(timestamp, transactions, recursive_stark, il_proof, attestation_deadline_ms)` accepts a non-null commitment and an optional proof. Ignore a supplied proof not matching both committed hashes. After API parameter decoding, return:

- `INVALID` for empty `deps`, known non-covering `proof_deps`, a cached invalid aggregate verdict, or a matching proof failing the commitment's shape or verification checks. An invalid aggregate verdict applies even without supplied bytes.
- `VALID` when the EL holds a valid committed proof, retaining it through `attestation_deadline_ms`.
- `PROOF_UNKNOWN` otherwise, including a cached valid verdict without proof bytes and no matching supplied proof.

`engine_getInclusionListProofV1(timestamp, stark_proof_hash)` returns a held `il_proof` verified under the target fork, including one from a fully validated mode-1 wrapper, or null.

`engine_submitInclusionListProofV1(timestamp, il_proof, view_freeze_deadline_ms)` checks the proof and dependency-list shape and size rules in [Commitment](#commitment) before verification, returning `INVALID` on failure. Otherwise it verifies the proof against `get_deps_hash(proof_deps)`, records the aggregate verdict and returns `VALID` or `INVALID`. Invalid proofs also produce cached verdicts. On `VALID`, retain the proof through `view_freeze_deadline_ms`.

List construction returns the transactions and commitment for signing, plus any proof to publish. The CL signs and publishes the proof promptly and the list during EIP-7805's construction window. New block-building and `engine_newPayload` versions carry each counted list separately as `(transactions, recursive_stark or null)` in committee-position order. The CL passes a non-null commitment only after its own EL returns `VALID` within its applicable deadline; the EL enforces dependency-bearing obligations only for those commitments.

#### Activation requirements

Activation requires the signed commitment, proof gossip and signing domain, req/resp protocol, and Engine API changes above to be specified together. Existing Engine versions are unchanged.

The proof format and verifier must support every block dependency set permitted by the fork's transaction and gas rules. Before activation, benchmark complete block-proof construction within the last-input-to-proposal budget, and timely attester proof delivery and list checks under the permitted background load. `IL_COMMITTEE_SIZE × MAX_AGGREGATE_PROOF_BYTES`, plus dependency lists and transport overhead, must fit the proof-dissemination window with margin. Repeat the builder benchmark before gas-limit increases. The [benchmark protocol](../assets/eip-8288/benchmarks.md) separates required workloads from measured late and cold cases, and records provisional publication timings and resource accounting.

### Lean Ethereum Integration

This EIP assumes the use of Lean Ethereum tooling for generating and verifying the recursive STARKs. This tooling can be found at the leanEthereum GitHub organization.

The recursive STARK is generated by:

1. Defining a Lean function that takes a flat list of `(scheme, data_hash, verification_key_hash)` triples and their corresponding witnesses.
2. Iterating over the list, and for each triple with `scheme == LEANSPHINCS_SCHEME`, calling `leanSPHINCS.verify(data_hash, verification_key_hash, witness)`.
3. Only when `LEANSTARK_SCHEME` is in `ENABLED_SCHEMES`, for each triple with `scheme == LEANSTARK_SCHEME`, calling `leanSTARK.verify(data_hash, verification_key_hash, witness)`.
4. Proving that all verifications return `true`.
5. Generating a STARK proof of this execution using the Lean Ethereum STARK backend.

The circuit is a relatively simple recursive "union and remove" construction, very similar to that which is planned to be used for consensus-layer signatures. It does not understand transactions or blocks; it only sees a flat list of dependencies and witnesses.

The verification key `AGGREGATED_VK` used to verify the recursive STARK is a fixed protocol-level value derived from the Lean Ethereum STARK circuit definition.

### Gas Accounting

The frame's `limits.execution` for a dependency verification frame is:

```
verification_gas(dep_verify_frame) = sum(
    LEANSPHINCS_VERIFICATION_GAS if triple.scheme == LEANSPHINCS_SCHEME else LEANSTARK_VERIFICATION_GAS
    for triple in dep_verify_frame.data_triples
)
```

Individual dependency verification and aggregation happen outside EVM execution; all validating nodes still verify the final block proof. The gas charges account for the expected verification and aggregation work.

Each transaction also pays for its share of verifying the block's recursive STARK, whose proof is carried in the block body and committed to by the `recursive_stark` header field `[stark_proof_hash, block_deps_hash]`:

```
recursive_stark_gas(tx) = LEANSTARK_VERIFICATION_GAS * len(dependency_triples(tx))
```

where `dependency_triples(tx)` is every triple in every dependency verification frame of `tx`, duplicates included. `recursive_stark_gas(tx)` is added to the transaction's intrinsic gas (`frame_tx_intrinsic_gas` in EIP-8141). It is execution gas, counts toward the transaction's `gas_used` and the block's `gas_used`, and is paid by the transaction's payer like the rest of the intrinsic gas. The block's `gas_used` includes no other charge for the `recursive_stark` field.

Because these dependencies are at the transaction body level and are not created inside the EVM, they are not affected by transaction execution reverting, and the gas is still fully charged even if the transaction reverts. This is similar to eg. intrinsic gas for calldata.

As a special case, notice that if a frame or a transaction has the same dependency multiple times, gas is charged for each declaration. So duplicate dependencies in a transaction are legal, but are wasteful.

## Rationale

### Why hash-only wrappers?

A single hash-only representation preserves wrapper identity across peers and separates envelope recovery from proof transport. The wrapper ceiling fits the `eth` soft response limit; proofs too large to fit with the transaction and dependency lists would require chunked transport. Smaller batches reduce recovery and verification latency. Uniform 96-byte dependency entries bind the scheme without a separate encoding for homogeneous lists.

### Why may inclusion-list proofs cover more than the list?

A committee member can reuse a mempool wrapper's proof without proving afresh on the list's critical path. Publishing it early lets attesters verify before the list arrives. Surplus dependencies create no obligations and are discarded when building the exact block proof.

### Why retain dependency-free obligations without a proof?

Proof availability affects only transactions requiring dependency verification. Keeping dependency-free obligations prevents an unavailable or invalid proof from suppressing the rest of a list. As with EIP-7805's list availability, different views can still disagree on a block; a builder holding all required proofs can satisfy both views.

### Why predict the target fork locally?

Wrapper validation estimates the next-slot fork from the local head. Around fork or slot-length changes, estimates may temporarily differ between peers. The transport's grace window avoids penalizing these differences, although wrapper propagation may be delayed. Inclusion-list proof checks use timestamps and retention deadlines supplied by the consensus layer.

### Why a new frame mode instead of an EVM opcode?

If an EVM opcode were chosen instead, the core question is how to handle missing or invalid proofs. From a mempool node's point of view, if it sees a dependency appear during transaction execution, and it has no valid proof for it, then it must be able to reject that transaction. And if a mempool accepts a transaction, it must be confident that EVM execution in later frames will not create _other_ dependencies that are unfulfilled.

The most realistic alternative would be for an opcode that creates a `(scheme, data_hash, verification_key_hash)` dependency to only be callable during an EIP-8141 validation frame. This would be viable. However, it would still make the mempool and builder's job relatively harder, because the EVM execution and dependency validation would have to be done sequentially rather than in parallel. It would also add more need to reason about special cases where EVM execution might add a dependency but then revert.

### Why recursive STARKs?

Recursive STARKs allow the aggregation of many individual proofs into a single proof. This is essential to avoid the size blowup of one STARK per transaction (that uses a STARK).

Each block carries a recursive STARK. This does increase the block size, a cost that has to be paid if blocks are to be verified without the individual signatures. The header holds a hash of the proof and not the proof: the block hash fixes the proof bytes either way, and checking `block_deps_hash` needs the block's transactions, so a header with the proof inside it proves nothing about the block that a header with the hash does not. Keeping the proof in the body makes header growth independent of proof size for readers that handle headers alone.

**This EIP proposes recursive aggregation at the mempool layer.** Mempool nodes generate recursive STARKs over bounded batches of valid wrapper objects they know about. This reduces bandwidth to the builder, as the builder receives pre-aggregated proofs from mempool nodes. The STARK-related overhead for the builder depends on batch count, proof size and update frequency.

The builder uses the exact same recursive STARK format to aggregate all included transactions' dependencies into the block-level recursive STARK.

### Why Lean Ethereum?

The Lean Ethereum tooling has already been extensively developed, has full formal verification in progress, and is the expected signature and recursive proof type for the future Ethereum consensus chain.

**This EIP's use case — processing many thousands of signatures and STARKs per slot without extreme data overhead — is almost identical to the consensus layer's use case.** The main differences are:

1. Hashes vs bitfields as identifiers of what objects are being proven
2. Many-time stateless signatures (leanSPHINCS), instead of the counter-based stateful signatures (leanXMSS) that the consensus layer can use because it needs to enforce one-signature-per-slot anyway.

Because the underlying use cases are similar, from a total spec simplification perspective, it is best to reuse the exact same tooling, rather than create a totally different set of tools for the execution layer.

Users who want to use quantum-resistant signature schemes other than leanSPHINCS signatures will have to either use them in the clear, and accept the onchain gas costs of doing so, or wrap them client-side in a STARK, and then reuse the leanSTARK route.

### Gas costs

As written, the EIP enforces fixed gas costs for both signatures and STARKs. This is assuming one parametrization of leanSPHINCS is used, and one parametrization of STARKs (or at least a small ratio between the average case and the upper bound).

An upper bound does need to be enforced. We make sure to add appropriate trace width limits and execution cycle count limits to STARK verification. In the current design (KoalaBear field, fixed trace width), this is enforced by the `2**24` trace length limit inherent to KoalaBear, and the trace width is fixed. If leanVM is redesigned, limits need to be kept in mind, so that the maximum possible proof size is a small multiple of the average case.

There may be two valid reasons to adjust the current fixed-cost approach and switch to variable cost:

- **Mixed k-time and unlimited-time usage of leanSPHINCS**: k-time signatures are significantly smaller than unlimited-time signatures, and SPHINCS could expose a parametrization that supports both. In this case, the former would need to have appropriately lower gas costs.
- **Different STARK sizes based on client-side proving time tradeoffs** Smaller proofs take longer to generate. We want larger proofs (cheaper to generate) to be possible, while still encouraging smaller proofs that put less load on the mempool nodes. This can be achieved by making gas cost proportional to proof size (or a related metric, like query count, and even polynomial degree).

### Why dependency frames may not sit in an atomic batch

Requiring `flags == 0` keeps a dependency verification frame from being a flagged batch member, but leaves it a valid terminator. [EIP-8141](./eip-8141.md) defines an atomic batch as a maximal run `[i, j]` where frames `i` through `j-1` carry `ATOMIC_BATCH_FLAG` and frame `j` does not, and its successor rule excludes only `VERIFY` frames.

The terminator is the frame at which the batch commits. When a batch fails its remaining frames are skipped and take receipt status `0x2`, but a dependency is declared at the transaction body level and, as [Gas Accounting](#gas-accounting) states, is unaffected by execution reverting and charged regardless. A dependency verification frame in that position would be skipped and binding on the block at once. EIP-8141 already restricts the batch flag by mode, so a mode rule here is consistent with it.

### Why the dependency frame still gets a receipt

[EIP-8141](./eip-8141.md) requires a frame receipt per frame, builds the transaction's logs by concatenating them in frame order, and exposes per-frame results through `FRAMEPARAM` `0x05`, `0x0A` and `0x0B`, which read by frame index. Omitting the entry for a frame that does not execute would renumber every later frame's results, on exactly the transactions [Transaction Execution Visibility](#transaction-execution-visibility) invites contracts to walk. EIP-8141's own rationale prices its per-frame cost as covering the receipt sub-entry that each frame adds.

## Backwards Compatibility

This EIP introduces a new frame mode, a header commitment and a block-body proof field. It does not modify the behavior of existing transactions. Transactions without signature or STARK verification frames are unaffected.

Nodes that do not implement this EIP will:

- Reject transactions containing `DEP_VERIFY_FRAME_MODE` frames as invalid (unknown frame mode).
- Reject blocks containing a `recursive_stark` header field as invalid.

This is a consensus-breaking change. Activation requires a network upgrade.

## Test Cases

### Test Case 1: Simple leanSPHINCS Verification

A transaction with a single `DEP_VERIFY_FRAME_MODE` frame containing one `(LEANSPHINCS_SCHEME, 0, pubkey_hash)` triple, followed by a `VERIFY` frame that checks the existence of a dependency with a `pubkey_hash` pulled from its storage and a zero `data_hash`, which stands for the transaction's signature hash.

### Test Case 2: Multiple leanSTARK Dependencies

Applies only when `LEANSTARK_SCHEME` is in `ENABLED_SCHEMES`. A transaction with a single `DEP_VERIFY_FRAME_MODE` frame containing multiple `(LEANSTARK_SCHEME, pub_input_hash, vk_hash)` triples, followed by a `VERIFY` frame that checks the existence of the dependencies with `APPROVE_EXECUTION_AND_PAYMENT` flags set.

### Test Case 3: Block with Mixed Transactions

A block containing:

- A normal EIP-8141 transaction.
- A transaction with dependency verification frames.
- A block header with a `recursive_stark` field.

### Test Case 4: Invalid Recursive STARK

A block with a wrong `block_deps_hash`, invalid body proof, or proof bytes that do not match the header commitment is rejected, including a nonempty proof when the dependency set is empty.

### Test Case 5: Mode 0 Mempool Wrapper

A mode 0 mempool wrapper containing multiple transactions (including the transaction from Test Case 1). Verify that the wrapper's `deps` and `proofs` match the transactions' dependencies, and that each proof can be verified individually.

### Test Case 6: Mode 1 Mempool Wrapper

A mode 1 mempool wrapper containing multiple transactions (including, when `LEANSTARK_SCHEME` is enabled, the transaction from Test Case 2). Verify that the wrapper's recursive STARK proves all dependencies are valid, and that the `deps_hash` matches `get_deps_hash(deps)`.

### Test Case 7: Recursive Mempool Aggregation

A scenario where a mempool node receives multiple transactions and generates a mode 1 wrapper with a recursive STARK. Verify that the recursive STARK covers all dependencies of all transactions in the wrapper, and that the wrapper can be verified by other mempool nodes and builders.

### Test Case 8: Wrapper with Recursive STARK (Mode 1)

A mempool wrapper containing a transaction with dependencies, where the wrapper uses `mode == 1` and contains a pre-computed recursive STARK. Verify that the recursive STARK's public input `deps_hash` matches `get_deps_hash(deps)` and that the proof is valid.

### Test Case 9: FOCIL with Recursive STARK

A FOCIL containing transactions with dependencies, where the FOCIL includes a `recursive_stark` commitment. Verify that the committed proof, received separately, proves validity of all dependencies in the FOCIL's transactions, and that a builder can incorporate this FOCIL into a block-level recursive STARK.

The cases for empty dependency sets, unavailable or invalid proofs, the proof topic, retention, equivocation and obligations are listed in the [FOCIL conformance table](../assets/eip-8288/focil-conformance.md).

### Test Case 10: Discard Set

Verify that the circuit:

- Computes `deps_hash` from exactly the retained dependencies.
- Rejects a discard absent from the verified input union.
- Matches full dependency triples, retaining an entry with the same data and key but a different scheme.

### Test Case 11: FOCIL Compatibility

Verify that:

- Block dependency sets permitted by transaction and gas rules are not rejected by wrapper ceilings or additional dependency-count limits.
- A builder missing a committed proof still satisfies dependency-free obligations; proof-holding attesters additionally enforce dependency-bearing entries.
- Superset proofs are merged with `discard_dependencies`, preserving dependencies shared with retained transactions and proving exactly `dependencies(block)`.
- Mempool limits, proving time, retention and scheduling do not excuse otherwise required transactions, including those evaluated at an earlier index under EIP-7805.

Valid-block fixtures and builder and attester workloads are specified in the [benchmark protocol](../assets/eip-8288/benchmarks.md).

### Test Case 12: Bounded Mempool Aggregation

With otherwise valid transactions and proofs, verify that:

- Two mode-0 wrappers with 16 distinct signature dependencies each can combine into a mode-1 wrapper with 32; mode 0 still rejects 32, and either mode rejects a transaction with 17 distinct signature dependencies for mempool admission.
- Mode-1 wrappers at the transaction, dependency and byte ceilings pass the corresponding limit checks; exceeding any ceiling is rejected. 4,096 total dependencies pass; 4,097 fail. Repeated declarations of the same dependency count once.
- For input dependencies `{a, b, c}` and retained dependencies `{b, c}`, `discard_dependencies` returns `{a}` even if a removed transaction also declared `b`. Retained dependencies absent from the inputs are rejected; changing the dependency set requires a matching proof. Dependencies covered only by mode-0 direct witnesses count as inputs.
- Either mode with empty `deps` is rejected. An empty transaction list, duplicate or unsorted hashes, a listed transaction without dependencies, a dependency frame with no triples, or a mode-0 wrapper whose proof count differs from its dependency count is rejected. Full envelopes are not wrapper entries.
- Verdict caches are separate per verification kind and verifier. With a cached valid mode-0 proof `w` for dependency `d`, a mode-1 wrapper over `[d]` whose `stark_proof` is `w` misses the aggregate-proof cache and is verified against `AGGREGATED_VK`; a cached mode-1 verdict likewise does not satisfy a mode-0 lookup for the same bytes. A known proof arriving with a different or unresolvable transaction list under the same verifier reuses its verdict. Once the local head reaches a target fork with a different `AGGREGATED_VK`, every held mode-1 wrapper is dropped and none is relayed after the transition; a mode-0 wrapper whose schemes' verification parameters are unchanged is kept, reusing its direct-witness verdicts.
- An unresolved hash leaves the wrapper incomplete even if its proof verifies. No admission, reaggregation or relay occurs until every envelope is resolved, hash-checked and the wrapper fully validated. Recovery expiry does not establish transaction or proof invalidity; a recovered dependency-union mismatch rejects the wrapper in either mode.

### Test Case 13: Dependency Digests and Proof Size

- Clients and the circuit derive the same digest from the 96-byte encoding, including the scheme and substituted signature hash. Equal data and key fields under different schemes produce different digests; changing the encoding requires a new `AGGREGATED_VK`.
- Aggregate proofs at `MAX_AGGREGATE_PROOF_BYTES` pass the length check but still require verification; proofs one byte longer fail before verification, including private recursive inputs.
- Dependency frames and direct circuit inputs with schemes outside `ENABLED_SCHEMES` are rejected.

## Security Considerations

### Trust Assumptions

The security of this EIP relies on:

1. **Soundness of Lean Ethereum circuits**: The STARK circuits must correctly implement the verification logic.
2. **Soundness of the dependency digest**: clients and the circuit use the same scheme-bound encoding and hash function, fixed by `AGGREGATED_VK`.
3. **Soundness of recursive STARKs**: a STARK of a STARK of ... of a STARK must be sound. This is widely believed to be true and many constructions running live onchain already depend on this. However, this adds difficulty to end-to-end formally proving the scheme and its applications. Note also that the STARK verification keys that users put in to this system are up to users, and may potentially have unlimited recursion depth.

### Denial of Service

Aggregation work depends on proof inputs, overlap and discards, not only on the gas-bounded output. The inclusion-list activation benchmarks therefore cover the complete construction, including dependencies later discarded.

Mempool per-transaction and wrapper limits are not consensus limits on blocks or inclusion lists. Mempool admission and transaction validity add these limits:

- `MAX_SIGS_PER_TX` limits the number of leanSPHINCS dependencies per transaction to 16.
- `MAX_STARKS_PER_TX` limits the number of leanSTARK dependencies per transaction to 1.
- `MAX_DEPENDENCIES_PER_FRAME` limits the number of dependencies per frame.
- `MAX_FRAMES` (from EIP-8141) limits the number of frames per transaction.
- `MAX_LEANSIG_DEPS_PER_DIRECT_WRAPPER` and `MAX_LEANSTARK_DEPS_PER_DIRECT_WRAPPER` limit mode-0 dependencies; `MAX_DEPS_PER_AGGREGATE_WRAPPER` limits mode-1 dependencies.
- `MAX_TXS_PER_WRAPPER` and `MAX_WRAPPER_BYTES` bound transaction count and serialized size in both modes.
- The gas cost for verification frames scales with the number of dependencies, making large dependency sets expensive.

Wrapper limits bound each object, while finite local retention and work budgets bound total mempool resource use. However, an increase in mempool DoS exposure still exists, because quantum-resistant signatures and proofs are much larger and more costly to verify than the present-day elliptic-curve-based versions of these primitives.

Proof availability can weaken censorship resistance for dependency-bearing transactions and cause builders and attesters to disagree. Early publication and retention make proof-holding attesters additional serving sources. Committee authentication bounds proof work; the [benchmark protocol](../assets/eip-8288/benchmarks.md#resource-accounting) accounts for traffic and overlapping retention separately from mempool caching.

These limits are inspired by the mempool policy framework of [ERC-7562](./eip-7562.md) (as used in EIP-8141).

### Verifier Changes

A fork that changes `AGGREGATED_VK` invalidates every mempool aggregate proof at once, a liveness gap for dependency-bearing transactions until they are re-proven (see [Mempool Wrapper Object](#mempool-wrapper-object)).
