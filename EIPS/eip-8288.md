## Abstract

This EIP extends [EIP-8141](./eip-8141.md) with a new frame mode that enables EVM-level aggregation of cryptographic signatures and STARK (Scalable Transparent ARguments of Knowledge) proofs. The scheme allows transactions to carry lightweight **dependencies** — `(scheme, data_hash, verification_key_hash)` triples — which are aggregated off-chain into a single recursive STARK. Block validity requires this recursive STARK, enabling efficient post-quantum (PQ) and scalable signature aggregation using Lean Ethereum tooling.

## Motivation

Quantum-resistant signatures and zero-knowledge proofs both have a very high calldata requirement and gas cost. Current proposals for hash-based signatures are in the range of ~2-3 kB and ~150,000 to 200,000 gas to verify. Lattice-based signatures have a similar cost. Meanwhile, hash-based zero-knowledge proofs (STARKs) all take over 128 kB, or as much as 512 kB if fast generation is a goal (which it is client-side), which implies a STARK will take many millions of gas to verify. This on its own would mean that privacy protocols will have an impractically high cost, and be completely incompatible with FOCIL ([EIP-7805](./eip-7805.md)) and Frame Transactions ([EIP-8141](./eip-8141.md)).

This EIP solves this problem by adding **STARK-based aggregation**. Instead of a block directly containing these user-submitted signatures and STARKs, the block contains one single recursive STARK that proves their existence. More specifically, it:

- Introduces **dependency frames** that declare `(scheme, data_hash, verification_key_hash)` triples as transaction-level dependencies.
- Requires a **recursive STARK** at the block level that proves the validity of all dependencies in all transactions.
- Reuses **Lean Ethereum** tooling (for signatures and STARKs), to maximize shared codebase.
- Provides a **mempool wrapper** format that bundles transactions with their dependencies and proofs.
- Supports **recursive aggregation** at the mempool layer, allowing mempool nodes to combine proofs and reduce bandwidth overhead.
- Is **compatible with FOCIL** ([EIP-7805](./eip-7805.md)), ensuring that the aggregation scheme works with fork-choice enforced inclusion lists.

An account's signature scheme may be constrained by its authenticator or custody system. Future passkeys, hardware wallets and smart cards may use lattice or hybrid schemes rather than leanSPHINCS. Batch-verification programs let these accounts share a proof and reach comparable dependency gas costs without a native verifier or protocol upgrade for each scheme.

### New Frame Mode

This EIP introduces a new frame mode for [EIP-8141](./eip-8141.md) frame transactions:

#### Dependency Verification Frame (`DEP_VERIFY_FRAME_MODE`)

We modify EIP-8141 to also allow frames with mode `DEP_VERIFY_FRAME_MODE`, in addition to all previously allowed modes. `DEP_VERIFY_FRAME_MODE` is added to the set of mode values accepted by EIP-8141's static constraint on `frame.mode`; no other mode value becomes valid. A frame with mode `DEP_VERIFY_FRAME_MODE` is a **dependency verification frame**. It declares a set of **dependencies** as `(scheme, data_hash, verification_key_hash)` triples. These triples are not executed as EVM code; instead, they are recorded as dependencies that must be proven valid by the recursive STARK in the block.

The **payload encoding** is a simple `96*k` byte concatenation of `k` triples, each consisting of:

- `scheme`: 31 zero bytes padding, then 1 byte identifying the verification scheme (`LEANSPHINCS_SCHEME` or `LEANSTARK_SCHEME`).
- `data_hash`: 32 bytes. For `LEANSPHINCS_SCHEME`, this is the message hash (`msghash`). For `LEANSTARK_SCHEME`, it identifies an individual claim established by a batch program.
- `verification_key_hash`: 32 bytes. For `LEANSPHINCS_SCHEME`, this is the leanSPHINCS public key itself, laid out as `root (16 bytes) || public parameter (16 bytes)`, the order the aggregation circuit hashes it in; a key that already fits in 32 bytes needs no hash. For `LEANSTARK_SCHEME`, this is a hash of the STARK verification key (`vk_hash`).

This data is stored in the frame's `data` field.

**Receipt**:

A dependency verification frame produces an [EIP-8141](./eip-8141.md) frame receipt like any other frame, with `status = 1`, `gas_used.execution` equal to the frame's `limits.execution`, `gas_used.state = 0`, and no logs.

**Validity constraints**:

- The frame's `data` must be exactly `96*k` bytes, and the first 31 bytes of each set of 96 must be zero.
- For each set of 96 bytes, `scheme` (byte 31) must be `LEANSPHINCS_SCHEME` or `LEANSTARK_SCHEME`.
- Number of triples must be `>= 1` and `<= MAX_DEPENDENCIES_PER_FRAME`.
- The frame's `target` must be `None`. This is EIP-8141's absent target, not the zero address: `resolved_target` is then `tx.sender`, and `FRAMEPARAM(0x00, i)` returns the sender's address. Contracts identify dependency verification frames by `mode`, not by target.
- The frame's `value` must be `0`.
- The frame's `flags` must be `0`.
- The frame must not be part of an [EIP-8141](./eip-8141.md) atomic batch. Its `flags` are `0`, so this means the preceding frame, if any, must not carry `ATOMIC_BATCH_FLAG`.
- The frame's `limits.execution` must be `sum(LEANSPHINCS_VERIFICATION_GAS if triple.scheme == LEANSPHINCS_SCHEME else LEANSTARK_DEPENDENCY_GAS for triple in frame.data_triples)`.
- The frame's `limits.state` must be `0`. The frame executes no code, so it can consume no state gas.

### Transaction Dependencies

A frame transaction may contain frames with mode `DEP_VERIFY_FRAME_MODE`. These frames declare **dependencies** that must be satisfied by the block's recursive STARK.

The complete list of dependencies for a transaction is the concatenation of all dependency triples from all dependency verification frames. The `data_triples` property of a frame is the list of `(scheme, data_hash, verification_key_hash)` triples parsed from the frame's `data` field:

```
frame.data_triples = [
    (data[31], data[32:64], data[64:96])
    for data in chunks(frame.data, 96)
]

dependencies(tx) = deduplicate_and_sort([
    (scheme, compute_sig_hash(tx) if data_hash == bytes(32) else data_hash, verification_key_hash)
    for frame in tx.frames if frame.mode == DEP_VERIFY_FRAME_MODE
    for (scheme, data_hash, verification_key_hash) in frame.data_triples
])

dependencies(block) = deduplicate_and_sort([
    triple
    for tx in block.txs
    for triple in dependencies(tx)
])
```

Where `deduplicate_and_sort` deduplicates and sorts:

```python
def deduplicate_and_sort(deps):
    o = []
    for dep in sorted(deps):
      if len(o) == 0 or dep != o[-1]:
        o.append(dep)
    return o
```

A `data_hash` of 32 zero bytes stands for the signature hash of the containing transaction, `compute_sig_hash(tx)` as defined in EIP-8141. A transaction cannot carry its own signature hash in a frame, because that hash covers the frame's `data`. `dependencies(tx)` holds the signature hash in place of the zero bytes, so the mempool wrapper, the FOCIL and the block prove a statement about that hash. Zero is reserved for this substitution. The frame's `data` is unchanged: `compute_sig_hash` covers the zero bytes and `FRAMEDATACOPY` returns them.

### Transaction Execution Visibility

During EVM execution, the transaction's dependencies are made available through the existing [EIP-8141](./eip-8141.md) `FRAMEPARAM` and `FRAMEDATACOPY` instructions.

Contracts can iterate over all frames in the transaction using `FRAMEPARAM` to identify `DEP_VERIFY_FRAME_MODE` frames, then use `FRAMEPARAM(0x04, i)` and `FRAMEDATACOPY` to read the dependency data from each frame's `data` field.

Specifically:

- `FRAMEPARAM(0x02, i)` returns the `mode` of frame `i`. Frames with mode `DEP_VERIFY_FRAME_MODE` are dependency frames.
- `FRAMEPARAM(0x04, i)` returns `len(data)` for frame `i`.
- `FRAMEDATACOPY(memOffset, dataOffset, length, i)` copies the dependency data from frame `i` into memory.

The data format for each dependency frame is a concatenation of 96-byte triples: `scheme || data_hash || verification_key_hash`.

This allows smart contracts to introspect the declared dependencies during execution using the existing EIP-8141 frame introspection mechanism.

### Block Validity: Recursive STARK

A block is valid only if it contains a **recursive STARK** in the block header that proves the validity of all dependencies in all transactions. This is formalized as follows.

#### Recursive STARK Header Entry

A new top-level field, `recursive_stark`, is added to the block header. This field contains the aggregated STARK proof for the block.

**Header encoding**:

```
recursive_stark = [stark_proof, block_deps_hash]
```

- `stark_proof`: The serialized recursive STARK proof. It does not carry the dependencies or their keys; a verifier takes them from the block through `block_deps_hash`. If `dependencies(block)` is empty, `stark_proof` is empty.
- `block_deps_hash`: `get_deps_hash(dependencies(block))`, the digest the recursive STARK commits to in its public statement:

```
  get_deps_hash(deps) = DEPS_HASH(concat([
      t.scheme.to_bytes(32, 'big') + t.data_hash + t.verification_key_hash
      for t in deps
  ]))
```

`get_deps_hash` hashes canonical 96-byte triples, including the scheme. `DEPS_HASH` is the hash the aggregation circuit uses for its dependency digest; header and circuit use the one function.

#### Batch Leaf Proofs

A leanSTARK leaf proves a nonempty, strictly increasing list of 32-byte claims `claims` under one user-selected batch program. Each claim yields `(LEANSTARK_SCHEME, claim, vk_hash)`. An authorization program must bind the signer, message and required policy in each claim; it may verify one or several signature schemes. The transaction pins the batch program's key, not a single-signature program or the batch's composition.

```python
vk_hash = keccak256(b'EIP8288:vk:v1' + canonical_verification_key)
batch_hash = DEPS_HASH(b'EIP8288:batch:v1' + concat(claims))
leaf_id = keccak256(b'EIP8288:leaf:v1' + vk_hash + batch_hash)
assert verify_leanSTARK((batch_hash,), vk_hash, proof)
```

The verifier checks the supplied key against `vk_hash` and the program's public commitment against `batch_hash`. A leaf has at most `MAX_AGGREGATED_DEPS` claims. Singleton leaves use this same interface; scalar-input proofs and proofs under another program do not establish these claims. Signature schemes and their witness formats are program choices, not new consensus scheme identifiers.

#### Leaf Accounting

A nonempty aggregate proof is serialized as canonical `rlp([proof, leaf_ids, leaf_indices])`: `proof` is a byte string, `leaf_ids` is a strictly increasing list of 32-byte leaf identifiers, and `leaf_indices` contains one unsigned index per leanSTARK dependency in the output's canonical order. Each index must be in range and selects its supporting leaf. Every listed identifier must be used, and there are at most `MAX_AGGREGATED_LEANSTARK_LEAVES` identifiers. The two lists are empty for a leanSPHINCS-only aggregate.

The STARK public inputs are `(deps_hash, keccak256(rlp([leaf_ids, leaf_indices])), AGGREGATED_VK)`. This serialization is used for block, wrapper and inclusion-list aggregate proofs; metadata counts toward their byte limits. A verifier checks the canonical dependency list, metadata encoding and bounds before verifying the proof.

For each retained leanSTARK dependency the circuit selects a supporting leaf from a verified input. Overlapping inputs may supply different leaves for the same triple; either may be selected. Discarding a triple removes its assignment, and a leaf stops counting only when none of its claims remain. Rewrapping cannot rename a leaf or combine leaf identifiers without verifying a new batch leaf. Different proof bytes for the same leaf statement have the same identifier.

#### Recursive STARK Proof Structure

The recursive STARK is generated using Lean Ethereum tooling. It proves the following statement:

```python
public inputs = [deps_hash, leaf_metadata_hash, AGGREGATED_VK]

private inputs = [deps, witnesses, batch_leaves, recursive_inputs, discards,
                  leaf_ids, leaf_indices]

# get_deps_hash as defined for block_deps_hash
assert len(batch_leaves) + len(recursive_inputs) <= MAX_INNER_PROOFS_PER_STEP

# Direct leanSTARK witnesses are singleton batch leaves.
assert len(deps) == len(witnesses)
assert len(deps) <= MAX_AGGREGATED_DEPS
for (scheme, data_hash, key), witness in zip(deps, witnesses):
    assert scheme == LEANSPHINCS_SCHEME
    assert verify_leanSPHINCS(data_hash, key, witness)

all_deps = list(deps)
support = {}  # triple -> set of authenticated leaf identifiers
for key, claims, proof in batch_leaves:
    # Verify key binding, ordered claims and their bound as specified above.
    leaf_deps, leaf_id = verify_batch_leaf(key, claims, proof)
    all_deps.extend(leaf_deps)
    for dep in leaf_deps:
        support.setdefault(dep, set()).add(leaf_id)

for inner_deps, aggregate_proof in recursive_inputs:
    # Checks the complete inner statement, metadata and output bounds.
    inner_support = verify_aggregate(inner_deps, aggregate_proof, AGGREGATED_VK)
    all_deps.extend(inner_deps)
    for dep, leaf_id in inner_support.items():
        support.setdefault(dep, set()).add(leaf_id)

# Remove discards and duplicates
assert set(discards) <= set(all_deps)
filtered_deps = deduplicate_and_sort(set(all_deps) - set(discards))
assert len(filtered_deps) <= MAX_AGGREGATED_DEPS

# Decode and check Leaf Accounting's canonical metadata and bounds.
assigned = decode_leaf_assignments(filtered_deps, leaf_ids, leaf_indices)
assert all(leaf_id in support[dep] for dep, leaf_id in assigned.items())
assert keccak256(rlp([leaf_ids, leaf_indices])) == leaf_metadata_hash
assert get_deps_hash(filtered_deps) == deps_hash
```

The recursive STARK circuit follows a "verify inputs, merge and discard" logic. It verifies:

- All leanSPHINCS signatures using the Lean Ethereum leanSPHINCS verifier
- Batch leaves using the Lean Ethereum leanSTARK verifier, once per leaf rather than once per output claim
- Recursive STARKs using the Lean Ethereum leanSTARK verifier.

We assume that the `leanSPHINCS` and `leanSTARK` verifiers are structured in such a way that they take as input a 32-byte pubkey hash or verification key hash, and the relevant parts of the full public key or verification key are included as part of the signature or proof as a witness. This is a generic transformation that can be made to any signature scheme or STARK scheme: `verify_sig(msg, pub, sig)` becomes `verify(msg, hash(pub), (pub, sig))` and `verify_stark(data_hash, vk, proof)` becomes `verify_stark(data_hash, hash(vk), (vk, proof))`. For `LEANSPHINCS_SCHEME` the public key is already 32 bytes, so it is used directly in place of `hash(pub)`.

The recursive STARK circuit does not understand the structure of transactions or blocks beyond iterating over a flat list of `(scheme, data_hash, verification_key_hash)` triples, their corresponding witnesses, and nested recursive STARKs.

The recursive STARK is verified using a fixed protocol-level `AGGREGATED_VK`.

`AGGREGATED_VK` changes only at a fork, together with the limits bound to it. Blocks are verified against the key of their fork. When the key changes, nodes drop recursive proofs and mode 1 wrappers made under the previous key, keep direct witnesses that still verify, and reaggregate the transactions they cover; transactions left without a verifying proof leave the pool.

Activation requires a fixed `DEPS_HASH`, canonical leanSTARK key and proof encodings, verifier resource bounds, and a new `AGGREGATED_VK` implementing the batch interface and leaf accounting. The provisional limits and gas rate require benchmarks of singleton leaves, full batches, merges and pruning.

To enable unlimited-depth recursion, we need to pass the `AGGREGATED_VK` in as an input to the proof itself.

#### Block Validity Rules

A block is valid if and only if:

1. The `block_deps_hash` in the recursive STARK header entry equals `get_deps_hash(dependencies(block))`.
2. If `dependencies(block)` is empty, `stark_proof` is empty. Otherwise the aggregate proof and its leaf metadata verify against `block_deps_hash` and the fixed protocol-level `AGGREGATED_VK`.
3. `dependencies(block)` has at most `MAX_AGGREGATED_DEPS` entries, supported by at most `MAX_AGGREGATED_LEANSTARK_LEAVES` distinct leanSTARK leaf statements. A batch emitting multiple retained triples consumes one leaf slot.
4. All transactions satisfy the normal (EIP-8141 or other) validity rules.

### Mempool Wrapper Object

At the mempool level, transactions with dependency verification frames are broadcast in **wrapper objects**. Aggregating nodes emit mode 1 wrappers every `AGGREGATION_INTERVAL`. Each wrapper contains a **list of transactions** and either their direct witnesses or a recursive STARK proving all of the wrapper's dependencies.

**Wrapper encoding** (canonical RLP):

```
[transactions, mode, content]
transactions = list of full EIP-8141 frame transactions
mode = 0 (direct dependencies) or 1 (recursive STARK)
content = if mode == 0: [deps, proofs]
          if mode == 1: [deps, recursive_stark]
```

Where:

- `transactions` = nonempty list of [EIP-8141 frame transactions](./eip-8141.md#networking) in the active `eth` version's pooled form, as RLP byte strings in strictly ascending transaction-hash order. Blob data is elided and excluded from the byte count; commitments and cell proofs are retained.
- `deps` = sorted, deduplicated union of `dependencies(tx)` for all listed transactions, encoded as 96-byte strings per [New Frame Mode](#new-frame-mode)
- `proofs` = list of individual witness byte strings, one per dependency in `deps`, in the same order; a leanSTARK witness proves the singleton claim list `[data_hash]`
- `recursive_stark` = the serialized aggregate proof, including its leaf metadata, proving validity of all `deps`

Transport may replace transaction encodings with hash references, provided the complete canonical wrapper is reconstructed before validation; identity and byte limits use that complete encoding.

Transaction hashes and dependency extraction use the [EIP-2718](./eip-2718.md) consensus envelope, excluding any network wrapper.

Every listed transaction must declare at least one dependency.

**Mode 0 (Direct dependencies)**: When a mempool node receives a wrapper with `mode == 0`, they must verify that:

1. The `deps` list is the sorted, deduplicated union of all dependencies from each transaction in `transactions`
2. The total number of leanSPHINCS deps is `<= MAX_LEANSIG_DEPS_PER_WRAPPER`
3. The total number of leanSTARK deps is `<= MAX_LEANSTARK_DEPS_PER_WRAPPER`
4. Each dependency has a corresponding proof that can be verified individually

**Mode 1 (Recursive STARK)**: When a mempool node receives a wrapper with `mode == 1`, they must verify that:

1. The recursive STARK's public input `deps_hash` equals `get_deps_hash(deps)`
2. The aggregate proof and its leaf metadata are valid (prove all deps are valid)
3. The `deps` list is the sorted, deduplicated union of all dependencies from each transaction in `transactions`

Wrapper validity is independent of pool admission: each transaction is admitted or rejected individually under normal pool rules, as a remote submission without local-transaction privileges, even when submitted locally. Pool rejection does not invalidate the wrapper or prevent its relay unchanged. Reaggregation uses retained pool transactions and their dependency union, discarding dependencies exclusive to omitted transactions.

Each wrapper contains exactly one STARK in mode 1, and one STARK per leanSTARK dependency in mode 0. Active transactions may be split across multiple wrappers.

Mode 0 is intended to be used primarily by clients broadcasting their transactions. If desired, mempool nodes whose local transaction pool contains ONLY leanSPHINCS signatures and no STARKs may choose to rebroadcast a mode 0 aggregation that naively concatenates the leanSPHINCS instead of proving them, as doing so may be more space-efficient up to about a hundred leanSPHINCS signatures.

The wrapper object is not a valid transaction on its own. Mempool nodes, FOCIL creators and builders use the **same recursive STARK format** to aggregate proofs. The only difference is the scope: mempool nodes aggregate over their current view of valid and includable transactions, while builders aggregate over the transactions they decide to include in the block.

### Recursive Mempool Aggregation

This EIP introduces **recursive aggregation** at the mempool layer. This allows mempool nodes to combine proofs and reduce bandwidth overhead to builders.

Mempool nodes follow the following algorithm:

- They passively wait and receive wrapper objects from users. When they see a wrapper, they validate its proof (either direct proofs or a recursive STARK). If valid, they evaluate its transactions individually for pool admission.
- When a transaction becomes unincludable (either because some other transaction from the same sender is included onchain, or because of any other mempool expiry rule), they keep note that its dependencies need to be pruned
- Every `AGGREGATION_INTERVAL` milliseconds, they generate mode 1 wrappers containing bounded subsets of still-valid transactions, each with a recursive STARK proving its dependencies. They forward these wrappers to their peers.

If a node anticipates that it will not have enough proving time to aggregate in _all_ aggregates that it saw, it should prioritize in the following order:

1. Its own aggregate from the previous round
2. Removing anything that needs to be removed
3. Other nodes' aggregates, in descending order of how many new transactions they will add to the aggregate
4. Users' transactions, in descending order of priority fee

Nodes may also alternate between adding one object at a time from (3) and (4). Mode 0 inputs SHOULD be folded directly into an aggregate rather than first wrapped in separate mode 1 proofs; rewrapping a mode 1 proof without adding or removing dependencies is unnecessary.

#### Mempool-Level Limits

The dependency-count limits `MAX_LEANSIG_DEPS_PER_WRAPPER` and `MAX_LEANSTARK_DEPS_PER_WRAPPER`, defined in [Constants](#constants), apply only to mode 0 wrappers. Mode 1 has at most `MAX_AGGREGATED_DEPS` dependencies and `MAX_AGGREGATED_LEANSTARK_LEAVES` supporting leaves. Exceeding either bound is invalid; nodes drop the wrapper without penalizing its sender. Both modes encode in at most `MAX_WRAPPER_BYTES` bytes, including transactions, dependencies, proofs, leaf metadata and RLP overhead.

`MAX_WRAPPER_BYTES` is an upper bound, not a storage or proving requirement. Nodes MAY decline to store or reaggregate wrappers above their local proving capacity without treating them as invalid.

Additionally, two mempool-level limits apply to each transaction: a transaction can have `<= MAX_SIGS_PER_TX` leanSPHINCS dependencies and `<= MAX_STARKS_PER_TX` leanSTARK dependencies, added up across all frames.

These limits ensure that the worst-case mempool DoS vector of this scheme is equivalent to the situation if the same data were sent in the clear. That is, a sender could alternatively submit a transaction containing the raw signatures and STARKs as calldata, and the mempool would have to store and propagate that data anyway.

Dependency-count limits apply to the length of the sorted, deduplicated dependency list. The list in a wrapper is required to be deduplicated in any case. For transactions, however, it does mean that it is legal to have a transaction with eg. `> MAX_SIGS_PER_TX` leanSPHINCS dependency _declarations_, if some of them are pointing to the same object so the deduplicated list is within limits. This behavior is wasteful but harmless; it is charged for and limited through the gas mechanism.

### FOCIL Compatibility

This EIP is designed to be compatible with [EIP-7805 (FOCIL)](./eip-7805.md), which implements fork-choice enforced inclusion lists. The compatibility considerations are as follows.

#### Extended FOCIL Data Structure

The FOCIL data structure is extended to include a `recursive_stark` field, similar to a block. This allows FOCILs to carry pre-aggregated proofs of their transactions' dependencies:

```
[FOCIL]
FOCIL = [transactions, recursive_stark]
recursive_stark = [stark_proof, deps_hash]
```

- `transactions`: The list of transactions in the inclusion list.
- `recursive_stark`: A recursive STARK proving validity of all dependencies in all `transactions`.
- `deps_hash`: The hash of all dependencies in the FOCIL's transactions.

This extension allows FOCILs to be self-contained: they carry not just the transactions but also a proof that all their dependencies are valid. This is analogous to how a block carries both transactions and a recursive STARK.

##### Attesters Validity Verification

To determine which transactions are mandatory to include for FOCIL purposes, attesters must validate all transactions in each FOCIL, and verify their dependencies by verifying the recursive proof in that FOCIL.

##### Builder Workflow with FOCIL

The builder's workflow in a FOCIL-enabled network is:

1. Receive FOCILs from the P2P network. Each FOCIL includes a `recursive_stark` proving validity of its transactions' dependencies.
2. Receive mempool wrapper objects from the mempool. Each wrapper may contain either direct proofs or a recursive STARK.
3. Process FOCILs and mempool wrappers in the same way: extract their dependencies and verify their proofs.
4. Decide which transactions to include in the block (ensuring all FOCIL transactions are included).
5. Perform a recursive wrap over all included transactions' dependencies:
   - Collect all dependencies from all included transactions.
   - Collect all proofs from FOCILs and wrappers that cover included transactions (recursive STARKs from mode 1 wrappers and FOCILs, or direct proofs from mode 0 wrappers).
   - Union all dependencies and remove any from transactions not included.
   - Generate a new recursive STARK proving the final set of dependencies.
6. Set the block header's `recursive_stark` field to the aggregated recursive STARK.
7. Build the execution payload including all included transactions.

Note that the job of a mempool actor aggregating to reforward, a FOCIL creator aggregating to generate a FOCIL, and a builder aggregating to include, are exactly the same task. Both take a set of wrapper objects (from mempool or FOCILs), extract their dependencies and proofs, and produce a recursive STARK covering the union of all valid dependencies.

#### Censorship Resistance

The recursive aggregation scheme preserves FOCIL's censorship resistance properties:

- Mempool nodes can recursively aggregate proofs without understanding transaction semantics.
- The scheme does not introduce new centralization pressures beyond those already present in FOCIL.
- Each mode-1 wrapper carries one recursive proof; total bandwidth depends on the number and size of wrappers.

#### Consensus Layer Integration

The recursive STARK scheme is compatible with the consensus layer's use of Lean Ethereum tooling. The same STARK backend and verification infrastructure can be used for both consensus layer signature aggregation and execution layer dependency verification. Inclusion lists (ILs) are just a different kind of package of transactions (like blocks) and use the same signature schemes as other components; no new signature scheme is required specifically for ILs.

### Lean Ethereum Integration

This EIP assumes the use of Lean Ethereum tooling for generating and verifying the recursive STARKs. This tooling can be found at the leanEthereum GitHub organization.

The recursive STARK is generated by:

1. Defining a Lean function that takes a flat list of `(scheme, data_hash, verification_key_hash)` triples and their corresponding witnesses.
2. Iterating over the list, and for each triple with `scheme == LEANSPHINCS_SCHEME`, calling `leanSPHINCS.verify(data_hash, verification_key_hash, witness)`.
3. Verifying each leanSTARK batch leaf once and assigning its identifier to its output triples.
4. Proving that all verifications return `true`.
5. Generating a STARK proof of this execution using the Lean Ethereum STARK backend.

The circuit is a relatively simple recursive "union and remove" construction, very similar to that which is planned to be used for consensus-layer signatures. It does not understand transactions or blocks; it only sees a flat list of dependencies and witnesses.

The verification key `AGGREGATED_VK` used to verify the recursive STARK is a fixed protocol-level value derived from the Lean Ethereum STARK circuit definition.

### Gas Accounting

The frame's `limits.execution` for a dependency verification frame is:

```
verification_gas(dep_verify_frame) = sum(
    LEANSPHINCS_VERIFICATION_GAS if triple.scheme == LEANSPHINCS_SCHEME else LEANSTARK_DEPENDENCY_GAS
    for triple in dep_verify_frame.data_triples
)
```

Individual dependency verification and aggregation happen outside EVM execution; all validating nodes still verify the final block proof. The gas charges account for verification work.

`LEANSTARK_DEPENDENCY_GAS` applies per declaration, including singleton leaves, independently of batch size or supporting leaf. Gas never depends on proof partitioning. `LEANSTARK_VERIFICATION_GAS` remains the intrinsic proof-share charge below.

Each transaction also pays for its share of the `recursive_stark` header field:

```
recursive_stark_gas(tx) = LEANSTARK_VERIFICATION_GAS * len(dependency_triples(tx))
```

where `dependency_triples(tx)` is every triple in every dependency verification frame of `tx`, duplicates included. `recursive_stark_gas(tx)` is added to the transaction's intrinsic gas (`frame_tx_intrinsic_gas` in EIP-8141). It is execution gas, counts toward the transaction's `gas_used` and the block's `gas_used`, and is paid by the transaction's payer like the rest of the intrinsic gas. The block's `gas_used` includes no other charge for the `recursive_stark` field.

Because these dependencies are at the transaction body level and are not created inside the EVM, they are not affected by transaction execution reverting, and the gas is still fully charged even if the transaction reverts. This is similar to eg. intrinsic gas for calldata.

As a special case, notice that if a frame or a transaction has the same dependency multiple times, gas is charged for each declaration. So duplicate dependencies in a transaction are legal, but are wasteful.

## Rationale

### Why a new frame mode instead of an EVM opcode?

If an EVM opcode were chosen instead, the core question is how to handle missing or invalid proofs. From a mempool node's point of view, if it sees a dependency appear during transaction execution, and it has no valid proof for it, then it must be able to reject that transaction. And if a mempool accepts a transaction, it must be confident that EVM execution in later frames will not create _other_ dependencies that are unfulfilled.

The most realistic alternative would be for an opcode that creates a `(scheme, data_hash, verification_key_hash)` dependency to only be callable during an EIP-8141 validation frame. This would be viable. However, it would still make the mempool and builder's job relatively harder, because the EVM execution and dependency validation would have to be done sequentially rather than in parallel. It would also add more need to reason about special cases where EVM execution might add a dependency but then revert.

### Why recursive STARKs?

Recursive STARKs allow the aggregation of many individual proofs into a single proof. This is essential to avoid the size blowup of one STARK per transaction (that uses a STARK).

Introducing a recursive STARK into each block header does increase the block header size greatly. However, this is ultimately a cost that will have to be paid regardless, if we want light clients to be able to verify the correctness of blocks.

**This EIP proposes recursive aggregation at the mempool layer.** Mempool nodes generate recursive STARKs every tick, combining subsets of valid wrapper objects they know about. This reduces bandwidth to the builder, as the builder receives pre-aggregated proofs from mempool nodes. The STARK-related overhead depends on wrapper count and proof size.

The builder uses the exact same recursive STARK format to aggregate all included transactions' dependencies into the block-level recursive STARK.

Direct witnesses grow with the number of mode 0 dependencies. Applying the same count limit to mode 1 would instead require a separate recursive proof for each small batch. A mode 1 wrapper requires one recursive proof verification, with its transaction bytes, dependency list and proof bounded by `MAX_WRAPPER_BYTES`. Dependency hashing and reaggregation still grow with the input set.

### Why Lean Ethereum?

The Lean Ethereum tooling has already been extensively developed, has full formal verification in progress, and is the expected signature and recursive proof type for the future Ethereum consensus chain.

**This EIP's use case — processing many thousands of signatures and STARKs per slot without extreme data overhead — is almost identical to the consensus layer's use case.** The main differences are:

1. Hashes vs bitfields as identifiers of what objects are being proven
2. Many-time stateless signatures (leanSPHINCS), instead of the counter-based stateful signatures (leanXMSS) that the consensus layer can use because it needs to enforce one-signature-per-slot anyway.

Because the underlying use cases are similar, from a total spec simplification perspective, it is best to reuse the exact same tooling, rather than create a totally different set of tools for the execution layer.

Users of other signature schemes may provide raw witnesses to an aggregator supporting their batch program or produce a leaf proof themselves. One program can combine several schemes, sharing batch capacity without a consensus change for each scheme.

### Batch verification and pricing

Batch proving retains work proportional to the signatures; succinct verification amortizes the proof check while claim hashing remains linear. Aggregators bear proving costs, with any compensation arranged outside this protocol. Proof size and recursive verification cost still depend on the proof system and execution bounds; equal dependency gas rates are provisional, not a claim of equal proving costs.

Gas cannot depend on a builder's later choice of batch. The marginal rate therefore also applies to singleton leaves and to non-signature programs. The leaf cap bounds this fixed-cost subsidy for retained statements; `MAX_INNER_PROOFS_PER_STEP` separately bounds verifications in each aggregation step. Neither bounds total historical proving work or computation inside a user program. Authenticated leaf assignments prevent recursive wrapping or pruning from erasing the cap, without making capacity depend on proof bytes or the aggregation tree.

Lattice verifiers such as ML-DSA (FIPS 204) use SHAKE. Efficient Keccak/SHAKE proving can improve batch economics, but accelerator availability is not a validity rule.

### Example: a future ML-DSA passkey

For an authenticator supporting ML-DSA, a batch program can check a [WebAuthn assertion](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-verifying-assertion) as follows:

1. The transaction commits to hashes of its credential public key and WebAuthn policy in validation-frame data, and declares `(LEANSTARK_SCHEME, 0, batch_program_id)`.
2. The account's validation code checks those commitments against its configuration and requires the declared program and zero placeholder.
3. The batch program checks the supplied key and policy against the commitments, recomputes `compute_sig_hash(tx)`, and checks `clientDataJSON` type, origin and base64url-encoded challenge, plus the authenticator's RP ID hash and required flags. The challenge must encode that signature hash.
4. It verifies ML-DSA over `authenticatorData || SHA-256(clientDataJSON)` with the committed key and emits `compute_sig_hash(tx)` as its claim. Raw assertion bytes are witnesses outside the transaction.

The resulting triple binds both the transaction and its credential through the signature hash. Writing `H(pk, compute_sig_hash(tx))` directly into a dependency frame would instead make the signed hash circular. Adding or removing other signers changes the leaf proof, not the signed transaction or its program identifier.

### Gas costs

As written, the EIP enforces fixed gas costs for both signatures and STARKs. This is assuming one parametrization of leanSPHINCS is used, and one parametrization of STARKs (or at least a small ratio between the average case and the upper bound).

An upper bound does need to be enforced. We make sure to add appropriate trace width limits and execution cycle count limits to STARK verification. In the current design (KoalaBear field, fixed trace width), this is enforced by the `2**24` trace length limit inherent to KoalaBear, and the trace width is fixed. If leanVM is redesigned, limits need to be kept in mind, so that the maximum possible proof size is a small multiple of the average case.

There may be two valid reasons to adjust the current fixed-cost approach and switch to variable cost:

- **Mixed k-time and unlimited-time usage of leanSPHINCS**: k-time signatures are significantly smaller than unlimited-time signatures, and SPHINCS could expose a parametrization that supports both. In this case, the former would need to have appropriately lower gas costs.
- **Different STARK sizes based on client-side proving time tradeoffs** Smaller proofs take longer to generate. We want larger proofs (cheaper to generate) to be possible, while still encouraging smaller proofs that put less load on the mempool nodes. This can be achieved by making gas cost proportional to proof size (or a related metric, like query count, and even polynomial degree).

### Why dependency frames may not sit in an atomic batch

Requiring `flags == 0` keeps a dependency verification frame from being a flagged batch member, but leaves it a valid terminator. [EIP-8141](./eip-8141.md) defines an atomic batch as a maximal run `[i, j]` where frames `i` through `j-1` carry `ATOMIC_BATCH_FLAG` and frame `j` does not, and its successor rule excludes only `VERIFY` frames.

The terminator is the frame at which the batch commits. When a batch fails its remaining frames are skipped and take receipt status `0x2`, but a dependency is declared at the transaction body level and, as [Gas Accounting](#gas-accounting) states, is unaffected by execution reverting and charged regardless. A dependency verification frame in that position would be skipped and binding on the block at once. EIP-8141 already restricts the batch flag by mode, so a mode rule here is consistent with it.

### Why the dependency frame still gets a receipt

[EIP-8141](./eip-8141.md) requires a frame receipt per frame, builds the transaction's logs by concatenating them in frame order, and exposes per-frame results through `FRAMEPARAM` `0x05`, `0x0A` and `0x0B`, which read by frame index. Omitting the entry for a frame that does not execute would renumber every later frame's results, on exactly the transactions [Transaction Execution Visibility](#transaction-execution-visibility) invites contracts to walk. EIP-8141's own rationale prices its per-frame cost as covering the receipt sub-entry that each frame adds.

## Backwards Compatibility

This EIP introduces new transaction types and frame modes. It does not modify the behavior of existing transactions. Transactions without signature or STARK verification frames are unaffected.

Nodes that do not implement this EIP will:

- Reject transactions containing `DEP_VERIFY_FRAME_MODE` frames as invalid (unknown frame mode).
- Reject blocks containing a `recursive_stark` header field as invalid.

This is a consensus-breaking change. Activation requires a network upgrade.

## Test Cases

### Test Case 1: Simple leanSPHINCS Verification

A transaction with a single `DEP_VERIFY_FRAME_MODE` frame containing one `(LEANSPHINCS_SCHEME, 0, pubkey_hash)` triple, followed by a `VERIFY` frame that checks the existence of a dependency with a `pubkey_hash` pulled from its storage and a zero `data_hash`, which stands for the transaction's signature hash.

### Test Case 2: Batched leanSTARK Dependencies

Two transactions each declare one leanSTARK dependency under the same batch program. A leaf proves both claims and consumes one leaf slot. A singleton-input proof or a proof under a different program does not satisfy the batch statement.

### Test Case 3: Block with Mixed Transactions

A block containing:

- A normal EIP-8141 transaction.
- A transaction with dependency verification frames.
- A block header with a `recursive_stark` field.

### Test Case 4: Invalid Recursive STARK

A block with an invalid recursive STARK (e.g., wrong `block_deps_hash` or invalid proof) in the header should be rejected.

The aggregation circuit rejects an inner dependency list without a verifying proof of its full statement, including leaf metadata. These are private circuit inputs, not client-visible validation checks.

### Test Case 5: Mode 0 Mempool Wrapper

A mode 0 mempool wrapper containing multiple transactions (including the transaction from Test Case 1). Verify that the wrapper's `deps` and `proofs` match the transactions' dependencies, and that each proof can be verified individually.

### Test Case 6: Mode 1 Mempool Wrapper

A mode 1 mempool wrapper containing multiple transactions (including the transaction from Test Case 2). Verify that the wrapper's recursive STARK proves all dependencies are valid, and that the `deps_hash` matches `get_deps_hash(deps)`.

### Test Case 7: Recursive Mempool Aggregation

A scenario where a mempool node receives multiple transactions and generates a mode 1 wrapper with a recursive STARK. Verify that the recursive STARK covers all dependencies of all transactions in the wrapper, and that the wrapper can be verified by other mempool nodes and builders.

### Test Case 8: Wrapper with Recursive STARK (Mode 1)

A mempool wrapper containing a transaction with dependencies, where the wrapper uses `mode == 1` and contains a pre-computed recursive STARK. Verify that the recursive STARK's public input `deps_hash` matches `get_deps_hash(deps)` and that the proof is valid.

### Test Case 9: FOCIL with Recursive STARK

A FOCIL containing transactions with dependencies, where the FOCIL includes a `recursive_stark` field. Verify that the recursive STARK proves validity of all dependencies in the FOCIL's transactions, and that a builder can incorporate this FOCIL into a block-level recursive STARK.

### Test Case 10: Discard Set

A scenario where a mempool node generates a recursive STARK that includes a discard set, excluding expired or invalid objects from the validity claim. Verify that the resulting `deps_hash` reflects only the non-discarded dependencies. The circuit rejects a discard absent from the verified input union; overlapping inputs and repeated discards use set semantics.

### Test Case 11: FOCIL Compatibility

A block containing:

- Transactions from FOCIL inclusion lists.
- Transactions with dependency verification frames.
- A block header with a `recursive_stark` field that proves all dependencies are valid.
- Verification that the block satisfies FOCIL inclusion constraints.

### Test Case 12: Wrapper Encoding and Limits

- Reject empty transaction lists, unresolved hash references, duplicate or out-of-order transaction hashes, and dependency unions that do not match `dependencies(tx)`, including zero-hash substitution.
- Transaction hashes exclude blob network wrappers; their elided pooled encoding counts toward the wrapper byte limit.
- Accept an otherwise valid wrapper at `MAX_WRAPPER_BYTES`; reject one byte above.
- Mode 0 accepts 16 signature dependencies. With 17 distinct dependencies across two individually valid transactions, reject mode 0 but accept an otherwise valid mode 1 wrapper within the circuit and byte limits. Per-transaction limits still apply.
- Reject missing or extra direct proofs and transactions without dependencies.
- Accept and permit unchanged relay of a valid wrapper whose transaction fails pool admission; a reaggregated wrapper omits that transaction and its exclusive dependencies.
- Reject a mode 1 proof exceeding the circuit's dependency-list limit; local proving-capacity refusal does not invalidate an otherwise valid wrapper.

### Test Case 13: Batch Statements and Leaf Accounting

- One leaf proves 1,000 distinct claims under one program, using one leaf slot. Accept 4,096 output dependencies and 16 supporting leaves; reject either bound plus one.
- Accept 16 inner proof verifications in a step; reject 17, including redundant inputs whose claims would later be discarded.
- Reject a changed program key, claim, claim order, scheme or leaf assignment. An old digest omitting the scheme does not match the new statement.
- Leaves A and B prove `{a, b}` and `{b, c}`. Merge to `{a, b, c}`, assigning `b` to either leaf; discard `a` and `b`, leaving only B counted. Discarding only `a` keeps A counted if `b` remains assigned to A. Reject a discard absent from the verified union.
- Deduplicate equal triples without dropping their last supporting leaf. Merge two different proofs of the same leaf statement without adding a slot; reject relabeling distinct leaves as one. Changing only valid leaf assignments changes proof metadata, not `block_deps_hash`.
- Charge a declaration identically in a singleton and a shared batch; charge duplicates per declaration. Rebatching must not change transaction signature hashes.
- In the passkey example, reject a wrong key, program, origin, RP ID, challenge or required flags; adding another signer to the batch does not change the accepted transaction.

## Security Considerations

### Trust Assumptions

The security of this EIP relies on:

1. **Soundness of Lean Ethereum circuits**: The STARK circuits must correctly implement the verification logic.
2. **Soundness of the hash function used for `deps_hash` and `block_deps_hash`**: `DEPS_HASH` is the hash the aggregation circuit uses for its claim-list digest, BLAKE2s in the current tooling, with BLAKE3 the leading choice to replace it. The header follows the circuit, so the two change together.
3. **Soundness of recursive STARKs**: a STARK of a STARK of ... of a STARK must be sound. This is widely believed to be true and many constructions running live onchain already depend on this. However, this adds difficulty to end-to-end formally proving the scheme and its applications. Note also that the STARK verification keys that users put in to this system are up to users, and may potentially have unlimited recursion depth.

### Denial of Service

A batch program can establish arbitrary claims, so the marginal gas rate is not restricted to recognizable signature algorithms. Verifier resource bounds and the two leaf/step caps must be benchmarked at their worst cases, including singleton leaves. Native raw-witness validation is local admission policy, not a substitute for the proof required by block validity.

A malicious sender could create transactions with many dependency frames, forcing builders to generate large recursive STARKs. The primary defense is the mempool-level limits:

- `MAX_SIGS_PER_TX` limits the number of leanSPHINCS dependencies per transaction to 16.
- `MAX_STARKS_PER_TX` limits the number of leanSTARK dependencies per transaction to 1.
- `MAX_DEPENDENCIES_PER_FRAME` limits the number of dependencies per frame.
- `MAX_FRAMES` (from EIP-8141) limits the number of frames per transaction.
- `MAX_LEANSIG_DEPS_PER_WRAPPER` and `MAX_LEANSTARK_DEPS_PER_WRAPPER` limit mode 0 dependencies; `MAX_WRAPPER_BYTES` bounds both modes, including the dependency list in a mode 1 wrapper.
- The gas cost for verification frames scales with the number of dependencies, making large dependency sets expensive.

These limits are chosen such that the theoretical worst-case mempool DoS vector of this scheme is equivalent to the situation if the same data were sent in the clear. That is, a sender could alternatively submit a transaction containing the raw signatures and STARKs as calldata, and the mempool would have to store and propagate that data anyway. The limits ensure that the data stored in the dependency frames is bounded by the same order of magnitude as the data that would be stored in a traditional transaction, limiting the increase in mempool DoS exposure. However, an increase in mempool DoS exposure still exists, because quantum-resistant signatures and proofs are much larger and more costly to verify than the present-day elliptic-curve-based versions of these primitives.

These limits are inspired by the mempool policy framework of [ERC-7562](./eip-7562.md) (as used in EIP-8141).
