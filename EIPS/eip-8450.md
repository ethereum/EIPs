## Abstract

This EIP adds a post-quantum public key registry to the beacon state. Each validator registers two hash-based commitments for its existing validator index: a leanXMSS key, used for every message the validator signs once duties switch to it, and the 32-byte root of a VRF tree, which fixes one verifiable random output per index.

Every signature carries its leaf index, and the signer chooses how leaf indices are allocated to messages, provided each leaf index signs at most once.

Registration is a new beacon block operation carrying the keys and a proof of possession that binds the leanXMSS key to the validator's BLS public key. It is authorized by the validator's BLS signing key, which can also replace registered keys, at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs. The keys are dormant: no duty uses them until a later fork switches to them.

## Motivation

Every consensus-layer signature today is a BLS12-381 signature: attestations, block proposals, RANDAO reveals, aggregation selection proofs, sync committee messages, payload attestations, inclusion lists, proposer preferences, voluntary exits, and the deposit proof of possession. BLS relies on the hardness of discrete logarithms in pairing-friendly groups, which Shor's algorithm breaks. A cryptographically relevant quantum computer (CRQC) recovers a validator's secret key from its public key, and every validator's public key is in the beacon state.

BLS therefore has to be replaced, and this EIP splits the replacement into two forks. Generating a post-quantum key involves the validator's secret key material, requires new tooling, and, for staking pools, requires coordination between node operators and stake owners. If this work happens at the fork that switches the signature scheme, the number of ready validators is only known at that fork.

A separate registry fork has the following benefits:

- **Preparation.** Validators generate and register keys, with tooling tested on mainnet, while BLS remains the only scheme used for duties.
- **A readiness signal.** The effective balance of active validators with registered keys can be computed from the state, so the switch can be scheduled against an observed threshold.
- **Early implementation.** Clients run the hash function, the verifier, and the containers on mainnet before any duty depends on them, since every registration carries a proof of possession.

### Cryptographic helpers

This EIP uses two hash-based primitives, a stateful signature scheme and a verifiable random function (VRF), through the interface below. It specifies the interface and the properties it relies on, not the constructions. Key generation, signing, and opening are not consensus-critical.

The signature scheme is leanXMSS and the VRF is a hash-based VRF tree. Their constructions are specified outside this EIP.

| Function | Description |
| - | - |
| `xmss.Verify(public_key: XMSSPublicKey, message: Bytes32, signature: XMSSSignature) -> bool` | Return whether `signature` is a valid signature of `message` under `public_key`, at the leaf index it carries. Return `False`, without raising, for a key or signature that does not decode |
| `vrf.Verify(root: VRFRoot, index: Uint32, opening: bytes) -> Optional[Bytes32]` | Return the output of the VRF tree with root `root` at `index` if `opening` is a valid opening of it, and `None` otherwise. This EIP does not call it |

A signature carries its leaf index in its first 4 bytes, little-endian. The proof-of-possession check reads it with:

```python
def xmss_signature_index(signature: XMSSSignature) -> Uint32:
    """
    Return the leaf index that a signature carries.
    """
    return Uint32(int.from_bytes(signature[0:4], "little"))
```

This EIP relies on the following properties:

- **Stateful signatures.** Signatures are unforgeable as long as each leaf index of a key signs at most once. Signing is not assumed to be deterministic, so signing the same message twice at one leaf index is also a reuse. Every leaf index in `[0, 2**32)` can be used.
- **Unique VRF outputs.** For a given root and index, at most one output verifies, unless a hash collision is known. An output is unpredictable to others until it is opened.

### Helpers

```python
def is_pq_registered(state: BeaconState, index: ValidatorIndex) -> bool:
    """
    Return whether a validator has registered post-quantum keys.
    """
    # A validator that has never registered keys holds FAR_FUTURE_EPOCH.
    return state.pq_key_change_epochs[index] != FAR_FUTURE_EPOCH
```

```python
def is_pq_public_key_in_use(state: BeaconState, public_keys: PQPublicKeys) -> bool:
    """
    Return whether any validator, including the one registering, holds the same leanXMSS key.

    Every registration therefore carries a new leanXMSS key.
    """
    for index, entry in enumerate(state.pq_public_keys):
        # Skip validators without keys.
        if not is_pq_registered(state, ValidatorIndex(index)):
            continue

        # A match means the key is already registered.
        if entry.xmss_public_key == public_keys.xmss_public_key:
            return True
    return False
```

Clients can maintain a map from registered keys to validator indices, as they do for BLS public keys, so that this check does not scan the registry.

```python
def get_pq_possession_signing_root(
    state: BeaconState, validator_pubkey: BLSPubkey, xmss_public_key: XMSSPublicKey
) -> Root:
    """
    Return the message that the proof of possession signs.

    The domain uses the genesis fork version.

    A proof therefore stays valid across forks.
    """
    possession = PQKeyPossession(validator_pubkey=validator_pubkey, xmss_public_key=xmss_public_key)
    domain = compute_domain(
        DOMAIN_PQ_KEY_POSSESSION, genesis_validators_root=state.genesis_validators_root
    )
    return compute_signing_root(possession, domain)
```

```python
def is_valid_pq_possession_proof(
    state: BeaconState,
    validator_pubkey: BLSPubkey,
    xmss_public_key: XMSSPublicKey,
    proof: XMSSSignature,
) -> bool:
    """
    Check that the holder of a leanXMSS key signed it for a validator's BLS public key.

    A copied key cannot be proven for a different validator.
    """
    # Leaf index 0 is reserved for the proof of possession.
    if xmss_signature_index(proof) != PQ_POSSESSION_XMSS_INDEX:
        return False

    # The key signs the validator's BLS public key and itself.
    signing_root = get_pq_possession_signing_root(state, validator_pubkey, xmss_public_key)
    return xmss.Verify(xmss_public_key, signing_root, proof)
```

#### New `process_pq_key_registration`

```python
def process_pq_key_registration(
    state: BeaconState, signed_registration: SignedPQKeyRegistration
) -> None:
    """
    Register or change the post-quantum keys of one validator.

    The validator's BLS signing key authorizes the registration.

    The registration names the validator's last change, so it applies at most once.
    """
    registration = signed_registration.message
    index = registration.validator_index
    public_keys = registration.public_keys

    assert index < len(state.validators)
    validator = state.validators[index]
    # Keys are registered only for validators that have not initiated an exit
    assert validator.exit_epoch == FAR_FUTURE_EPOCH

    # The registration applies to the validator's current entry only.
    # Every change moves the stored epoch, so a replayed registration fails here.
    last_change_epoch = state.pq_key_change_epochs[index]
    assert registration.previous_change_epoch == last_change_epoch

    # Changes of registered keys are rate-limited.
    if is_pq_registered(state, index):
        assert get_current_epoch(state) >= last_change_epoch + MIN_PQ_KEY_CHANGE_DELAY

    # The validator's signing key authorizes the registration.
    domain = compute_domain(
        DOMAIN_PQ_KEY_REGISTRATION, genesis_validators_root=state.genesis_validators_root
    )
    signing_root = compute_signing_root(registration, domain)
    assert bls.Verify(validator.pubkey, signing_root, signed_registration.signature)

    # The key must be unique, and the registrant must prove possession of it.
    assert not is_pq_public_key_in_use(state, public_keys)
    assert is_valid_pq_possession_proof(
        state, validator.pubkey, public_keys.xmss_public_key, signed_registration.possession
    )

    # Write the keys and the epoch of the change into the validator's entry.
    state.pq_public_keys[index] = public_keys
    state.pq_key_change_epochs[index] = get_current_epoch(state)
```

Anyone can submit a registration. Only its BLS signature authorizes it.

Registrations are processed last: after the block's other operations and after `block.body.parent_execution_requests`, which `process_parent_execution_payload` applies before `process_operations`. A registration for a validator whose exit is initiated earlier in the block, by a slashing, a voluntary exit, a withdrawal request, or a consolidation request, therefore invalidates the block, so block producers check registrations against the state after the block's other operations.

### Gossip

A new global topic `pq_key_registration` carries `SignedPQKeyRegistration` messages. The following validations MUST pass before forwarding a `signed_registration` on the network, where `registration = signed_registration.message` and the head state is the node's state at its current head. They are listed in order, cheapest first.

- **[IGNORE]** The current epoch, allowing for `MAXIMUM_GOSSIP_CLOCK_DISPARITY`, is at or after the epoch of the fork that activates this EIP.
- **[IGNORE]** The head state is at or after the fork that activates this EIP, so that it has `pq_public_keys` and `pq_key_change_epochs`.
- **[REJECT]** `registration.validator_index` is a validator in the head state, and its `exit_epoch` is `FAR_FUTURE_EPOCH`.
- **[IGNORE]** `signed_registration` is the first valid registration received for the pair `(registration.validator_index, registration.previous_change_epoch)`.
- **[REJECT]** `registration.previous_change_epoch` is the validator's `pq_key_change_epochs` entry in the head state.
- **[IGNORE]** If the validator has registered keys in the head state, the current epoch, allowing for `MAXIMUM_GOSSIP_CLOCK_DISPARITY`, is at least `registration.previous_change_epoch + MIN_PQ_KEY_CHANGE_DELAY`.
- **[REJECT]** `signed_registration.signature` is a valid BLS signature of `registration` by the validator's public key.
- **[REJECT]** The leanXMSS key in `registration.public_keys` is not registered by any validator in the head state.
- **[REJECT]** `signed_registration.possession` is a valid proof of possession of the leanXMSS key for the validator's BLS public key.

A registration that was valid when first received can become invalid before it is included, for example when another validator registers the same leanXMSS key first. The validator's `pq_key_change_epochs` entry then does not change, so the first-seen record would block every later registration for the pair. Nodes MAY clear the record for a pair once its first-seen registration is no longer valid against the finalized state.

### Key roles

The leanXMSS key is intended to sign every validator message once duties switch to it. This EIP authenticates no duty with it.

A validator's signer MUST NOT sign twice at the same leaf index of a key, and chooses how it allocates leaf indices to messages. Leaf index `PQ_POSSESSION_XMSS_INDEX` is reserved for the proof of possession: a signer MUST NOT sign at it anything other than the `PQKeyPossession` of its key for its validator's BLS public key. A signer MUST use each leanXMSS key in at most one registration, for one validator, and MUST NOT register a key that it has registered before. Its proof is therefore signed once. A registration that is not included stays in the operation pools and is included later with the same bytes. It is never signed again.

The leanXMSS seed and the VRF leaf secrets SHOULD NOT be derived from the validator's BLS key. Keystores and signer state for leanXMSS keys SHOULD follow [EIP-8310](./eip-8310.md), which extends [ERC-2335](./eip-2335.md).

This EIP does not open the VRF root. The fork that uses it defines how its inputs map to indices.

## Rationale

### Registering before switching

Dormant keys cannot cause a missed attestation or a slashing, so the registry can ship before the aggregation and networking changes are ready. For the same reason, a change of keys replaces stored bytes and affects no duty.

### Two keys per validator

A stateful scheme such as leanXMSS signs at most once per leaf index, and several duties produce more than one message per slot. A second, stateless scheme would avoid leaf management at the cost of a second key and verifier and larger signatures. This EIP registers one leanXMSS key for all messages instead: since the signature carries its leaf index, new duties need no new key.

Selection proofs, such as aggregation and sync committee selection proofs, hash unique BLS signatures. leanXMSS signatures are not unique and could be ground, so the VRF root fixes one output per index at registration, before the validator knows its inputs. The root is not checked at registration, which keeps openings out of the registration, so validator clients check their tree before registering it.

### Leaf index 0

Leaf index `0` is reserved for the proof of possession. Under a fixed allocation that gives each slot a range of leaf indices, leaf `0` belongs to the genesis slot, which is never a duty slot after this fork, so the proof never takes a leaf from a duty.

### Proof of possession

The proof detects faulty key generation at registration rather than at the switch. With key uniqueness, it also prevents copying and squatting (see [Key copying and squatting](#key-copying-and-squatting)).

The proof signs `PQKeyPossession` rather than the whole registration, and the BLS signature covers the rest. The validator is named by its BLS public key rather than its index: the public key never changes, no two validators share one, and it is known before the deposit is processed, so the proof can be produced together with the validator's keystore.

Consensus rejects a leanXMSS key that a validator currently holds, including the one registering, so a change never keeps the current key. Changing only the VRF root therefore requires a new leanXMSS key, which is cheap while the keys are dormant. Consensus does not record earlier keys, so returning to an earlier key, or registering a key that another validator has released, is valid on chain. Returning to an earlier key needs either a second proof at leaf `0` or the stored first one, and registering a key that another validator released needs a proof of a different message at leaf `0`. The signer rules forbid both, so a signer never has to keep old proofs.

The proof is 2404 of the 2580 bytes of a registration. It is kept on chain because the signature switch relies on every registered key being a working key for its validator.

### Authorization by the signing key

The operator who holds the BLS signing key also generates and holds the post-quantum key, so it registers each of its validators without a transaction from the stake owner, whatever the validator's withdrawal credentials. The authorization is a consensus-layer operation only, as for `BLSToExecutionChange`, so this EIP needs no execution-layer change.

Allowing changes lets a validator recover from a lost seed, lost signer state, or a faulty key without exiting. The cost is that an adversary able to forge BLS signatures can replace any validator's keys, not only those of unregistered validators (see [Quantum adversaries before the switch](#quantum-adversaries-before-the-switch)). A register-only rule would keep keys registered before a break authentic, at the cost of an exit for every lost or faulty key.

### Changes and replay protection

One stored epoch per validator, named by each registration and set by each change, provides both replay protection and the rate limit. A per-validator counter would prevent replays but not limit changes.

`FAR_FUTURE_EPOCH` marks a validator that has never registered, as it marks unset epochs elsewhere in the consensus specifications. A registration stores the current epoch, and with a delay of at least one epoch every change is applied after the epoch it names, so every applied registration changes the stored epoch and none applies twice. The delay check skips unregistered validators, so it never adds to `FAR_FUTURE_EPOCH`.

`MIN_PQ_KEY_CHANGE_DELAY` bounds each validator to one change per 256 epochs, about 27 hours. Changes and first registrations share `MAX_PQ_KEY_REGISTRATIONS`, and a validator that changes its keys again within the delay wastes no block space, since its registration is invalid.

### Interface instead of construction

This EIP specifies only the interface of the primitives and the properties it relies on, as [EIP-4844](./eip-4844.md) does for KZG. The registry does not depend on how the primitives are constructed, so their specification and test vectors can live with the other consensus cryptography.

Registry entries carry no version: this EIP accepts one set of primitives. A fork that changes the primitives before the switch defines how existing entries are handled, and introduces new `DomainType` constants for registrations and proofs of possession, so that registrations signed for the earlier primitives cannot be applied. Entries registered before that fork can then be told apart only by their change epoch.

### A list parallel to the validator registry

The keys are stored in a list parallel to `validators`. The `Validator` container and its generalized indices do not change, so light clients and proofs against them are not affected until the switch.

### Registration outside the deposit contract

The deposit contract's event layout is fixed, and its events are converted into fixed-size `DepositRequest` records ([EIP-6110](./eip-6110.md)) with no field for post-quantum keys. Existing validators also need a registration path that does not involve a deposit. A new validator registers through the same path once its deposit has been processed and it has an index, which can be before its activation. Setting keys at deposit time requires a new deposit format, which is part of the fork that retires BLS deposits.

### Per-block limits

`MAX_PQ_KEY_REGISTRATIONS = 8` bounds the extra block size at about 20 KiB, and the verification cost at eight BLS verifications and eight leanXMSS verifications per block. At that rate a million validators register in 125,000 full blocks, about 17 days of 12-second slots.

## Backwards Compatibility

This EIP requires a hard fork of the consensus layer. It changes no existing duty: every message is still authenticated with BLS, and a validator that never registers keys is unaffected by this fork.

## Test Cases

The consensus test vectors cover at least:

- A registration for an unregistered validator, and a change of its keys once `MIN_PQ_KEY_CHANGE_DELAY` epochs have passed, including a change that keeps the VRF root.
- Rejection of a change before `MIN_PQ_KEY_CHANGE_DELAY` epochs have passed, and of a replayed registration whose `previous_change_epoch` no longer matches.
- Rejection of a registration for a validator that has initiated an exit, and for a validator whose exit is initiated earlier in the same block by a proposer slashing, an attester slashing, a voluntary exit, a withdrawal request, or a consolidation request in `parent_execution_requests`.
- Rejection of a key already registered by another validator or by the registering validator itself, of an invalid proof of possession, and of a proof of possession at a leaf index other than `PQ_POSSESSION_XMSS_INDEX`.
- An unregistered validator's all-zero entry does not count as holding the all-zero key in `is_pq_public_key_in_use`.
- Rejection of a block with two registrations of the same leanXMSS key for two validators, where the second registration is invalid.
- A registration of a key that another validator held and has released through a change. This is valid on chain, although the signer rules forbid it for honest signers.
- The fork upgrade, and the invariant `len(state.pq_public_keys) == len(state.pq_key_change_epochs) == len(state.validators)` after new validators are added.

## Security Considerations

### Quantum adversaries before the switch

A registration is only as authentic as the BLS signature that authorizes it. Once a CRQC exists, an adversary can register or replace any validator's keys, at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs per validator. The switch therefore has to happen while BLS is believed secure.

### Leaf reuse

Each leaf index signs at most once, whichever allocation the signer uses: slashing protection enforces it under a fixed per-slot allocation, and the signer's state under free allocation. A signer uses each key in one registration, so leaf `0` of each key signs one proof. A registration whose block is orphaned stays in the operation pools and is included again with the same proof bytes. Consensus does not track released keys, so it accepts a key that a validator held before. Returning to an earlier key would need a second proof or the stored first one, and taking another validator's released key would sign a different message at leaf `0`. The signer rules forbid both.

### Key copying and squatting

The registry rejects a key that any validator has already registered. Without that rule, a validator could register another's key and claim its signatures as its own participation, since the signed messages do not name the validator. The proof of possession signs the validator's BLS public key, so a copied key, even one published but not yet registered, cannot be registered for a different validator. This binding relies on BLS public keys never changing: if a later fork made them mutable, a key bound to an outdated public key would need a second proof at leaf `0`, which is a leaf reuse.

### Readiness is not registration

A registered key proves that its holder could sign once, at registration time. It does not prove that the validator will run post-quantum software, keep its seed, or keep its signer state consistent at the switch. The effective balance of active validators with registered keys is therefore an upper bound on readiness, so the switch needs a margin above the two-thirds finality threshold.

### VRF tree

The registry accepts a VRF root that another validator has registered. A validator that copies a root cannot open it before its owner does, but it has the same outputs and can replay the owner's openings once they are published. The fork that uses the tree has to account for this.

### Denial of service and state growth

- **Blocks.** At most `MAX_PQ_KEY_REGISTRATIONS` registrations per block; see [Per-block limits](#per-block-limits).
- **Gossip.** Registrations are first-seen per validator and previous change epoch, and each validator can change its keys at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs.
- **State.** Each validator adds 72 bytes: 64 bytes of keys and an 8-byte change epoch, about 72 MB for a million validators.
