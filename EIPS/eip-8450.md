## Abstract

This EIP adds a post-quantum public key registry to the beacon state. Each validator registers two hash-based commitments for its existing validator index: a leanXMSS key, used for every message the validator signs once duties switch to it, and the 32-byte root of a VRF tree, which fixes one verifiable random output per index. Each builder registers a leanXMSS key for its existing builder index through the same operation.

Every signature carries its leaf index, and the signer chooses how leaf indices are allocated to messages, provided each leaf index signs at most once.

Registration is a new beacon block operation carrying the keys and a proof of possession that binds the leanXMSS key to the BLS public key of the validator or builder. It is authorized by that BLS signing key, which can also replace registered keys, at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs. The keys are dormant: no duty uses them until a later fork switches to them.

## Motivation

Every consensus-layer signature today is a BLS12-381 signature: attestations, block proposals, RANDAO reveals, aggregation selection proofs, sync committee messages, payload attestations, inclusion lists, proposer preferences, voluntary exits, the deposit proof of possession, and the execution payload bids and envelopes of builders. BLS relies on the hardness of discrete logarithms in pairing-friendly groups, which Shor's algorithm breaks. A cryptographically relevant quantum computer (CRQC) recovers a secret key from its public key, and every validator's and builder's public key is in the beacon state.

BLS therefore has to be replaced, and this EIP splits the replacement into two forks. Generating a post-quantum key involves the validator's secret key material, requires new tooling, and, for staking pools, requires coordination between node operators and stake owners. If this work happens at the fork that switches the signature scheme, the number of ready validators is only known at that fork.

A separate registry fork has the following benefits:

- **Preparation.** Validators generate and register keys, with tooling tested on mainnet, while BLS remains the only scheme used for duties.
- **A readiness signal.** The effective balance of active validators with registered keys can be computed from the state, so the switch can be scheduled against an observed threshold.
- **Early implementation.** Clients run the hash function, the verifier, and the containers on mainnet before any duty depends on them, since every registration carries a proof of possession.

### Cryptographic helpers

This EIP uses two hash-based primitives, a stateful signature scheme and a verifiable random function (VRF), through the interface below. It specifies the interface and the properties it relies on, not the constructions. Key generation, signing, and opening are not consensus-critical.

The signature scheme is leanXMSS and the VRF is a hash-based VRF tree. Their constructions are specified outside this EIP. leanXMSS, with 32-byte public keys and 2404-byte signatures, is implemented in the `EthLib/Cryptography/Xmss` module of the `ethereum/EthLib` repository at commit `6390c73ef040311e807b9047d99dca6b1be1c42f`.

| Function | Description |
| - | - |
| `xmss.Verify(public_key: XMSSPublicKey, message: Bytes32, signature: XMSSSignature) -> bool` | Return whether `signature` is a valid signature of `message` under `public_key`, at the leaf index it carries. Return `False`, without raising, for a key or signature that does not decode |
| `vrf.Verify(root: VRFRoot, index: Uint32, opening: bytes) -> Optional[Bytes32]` | Return the output of the VRF tree with root `root` at `index` if `opening` is a valid opening of it, and `None` otherwise. This EIP does not call it |

A signature carries its leaf index in its first 4 bytes, little-endian. The proof-of-possession check reads it with:

```python
def xmss_signature_index(signature: XMSSSignature) -> Uint32:
    """
    Return the leaf index that a signature carries.
    """
    return Uint32(int.from_bytes(signature[0:4], "little"))
```

This EIP relies on the following properties:

- **Stateful signatures.** Signatures are unforgeable as long as each leaf index of a key signs at most once. Signing is not assumed to be deterministic, so signing the same message twice at one leaf index is also a reuse. Every leaf index in `[0, 2**32)` can be used.
- **Unique VRF outputs.** For a given root and index, at most one output verifies, unless a hash collision is known. An output is unpredictable to others until it is opened.

    Serializes to 32 + 32 = 64 bytes.

```python
class PQKeyRegistration(Container):

    """

    index: ValidatorIndex
    # Keys being registered.
    public_keys: PQPublicKeys

    # FAR_FUTURE_EPOCH for a validator, the deposit epoch for a builder.

```

```python
class PQKeyPossession(Container):
    """
    The message of a proof of possession: which validator or builder, and which leanXMSS key.

    The validator or builder is named by its BLS public key, which does not change and is
    known before it has an index.

    It does not depend on the rest of the registration, so a key signs it only once.
    """
    # BLS public key of the validator or builder the key is registered for.
    pubkey: BLSPubkey
    # Key whose possession is proven.
    xmss_public_key: XMSSPublicKey
```

```python
class SignedPQKeyRegistration(Container):
    """
    A registration as it appears in a beacon block.

    It carries the key, a proof that the registrant holds it, and the authorization.
    """
    # Index, keys, and last change being registered.
    # The BLS signature signs it.
    message: PQKeyRegistration
    # Signature of the registrant's BLS public key and the leanXMSS key by that key, at leaf index 0.
    # It proves that the registrant holds the secret key.
    possession: XMSSSignature
    # Signature of the registration by the registrant's BLS signing key.
    # It authorizes the registration.
    signature: BLSSignature
```

### Helpers

An index with `BUILDER_INDEX_FLAG` set names a builder, as for builder withdrawals ([EIP-7732](./eip-7732.md)). The helpers below read and write the entry of a validator or builder index.

```python
def get_pq_unregistered_epoch(state: BeaconState, index: ValidatorIndex) -> Epoch:
    """
    Return the stored change epoch of a validator or builder that has never registered keys.

    Builder indices are reused, so a builder starts from its own deposit epoch.
    """
    if is_builder_index(index):
        return state.builders[convert_validator_index_to_builder_index(index)].deposit_epoch
    return FAR_FUTURE_EPOCH
```

```python
def get_pq_key_change_epoch(state: BeaconState, index: ValidatorIndex) -> Epoch:
    """
    Return the stored change epoch of a validator or builder.
    """
    if is_builder_index(index):
        return state.builder_pq_key_change_epochs[convert_validator_index_to_builder_index(index)]
    return state.pq_key_change_epochs[index]
```

```python
def get_pq_public_keys(state: BeaconState, index: ValidatorIndex) -> PQPublicKeys:
    """
    Return the registered keys of a validator or builder.
    """
    if is_builder_index(index):
        return state.builder_pq_public_keys[convert_validator_index_to_builder_index(index)]
    return state.pq_public_keys[index]
```

```python
def set_pq_public_keys(
    state: BeaconState, index: ValidatorIndex, public_keys: PQPublicKeys, epoch: Epoch
) -> None:
    """
    Write the keys and the change epoch of a validator or builder.
    """
    if is_builder_index(index):
        builder_index = convert_validator_index_to_builder_index(index)
        state.builder_pq_public_keys[builder_index] = public_keys
        state.builder_pq_key_change_epochs[builder_index] = epoch
    else:
        state.pq_public_keys[index] = public_keys
        state.pq_key_change_epochs[index] = epoch
```

```python
def is_pq_registered(state: BeaconState, index: ValidatorIndex) -> bool:
    """
    Return whether a validator or builder has registered post-quantum keys.
    """
    return get_pq_key_change_epoch(state, index) != get_pq_unregistered_epoch(state, index)
```

```python
def get_pq_registry_indices(state: BeaconState) -> Sequence[ValidatorIndex]:
    """
    Return the indices of every validator and builder, with builder indices flagged.
    """
    validator_indices = [ValidatorIndex(index) for index in range(len(state.validators))]
    builder_indices = [
        convert_builder_index_to_validator_index(BuilderIndex(index))
        for index in range(len(state.builders))
    ]
    return validator_indices + builder_indices
```

```python
def is_pq_public_key_in_use(state: BeaconState, public_keys: PQPublicKeys) -> bool:
    """
    Return whether any validator or builder, including the one registering, holds the same leanXMSS key.

    Every registration therefore carries a new leanXMSS key.
    """
    for index in get_pq_registry_indices(state):
        # Skip validators and builders without keys.
        if not is_pq_registered(state, index):
            continue

        # A match means the key is already registered.
        if get_pq_public_keys(state, index).xmss_public_key == public_keys.xmss_public_key:
            return True
    return False
```

Clients can maintain a map from registered keys to indices, as they do for BLS public keys, so that this check does not scan the registries.

```python
def get_pq_possession_signing_root(
    state: BeaconState, pubkey: BLSPubkey, xmss_public_key: XMSSPublicKey
) -> Root:
    """
    Return the message that the proof of possession signs.

    The domain uses the genesis fork version.

    A proof therefore stays valid across forks.
    """
    possession = PQKeyPossession(pubkey=pubkey, xmss_public_key=xmss_public_key)
    domain = compute_domain(
        DOMAIN_PQ_KEY_POSSESSION, genesis_validators_root=state.genesis_validators_root
    )
    return compute_signing_root(possession, domain)
```

```python
def is_valid_pq_possession_proof(
    state: BeaconState,
    pubkey: BLSPubkey,
    xmss_public_key: XMSSPublicKey,
    proof: XMSSSignature,
) -> bool:
    """
    Check that the holder of a leanXMSS key signed it for a BLS public key.

    A copied key cannot be proven for a different validator or builder.
    """
    # Leaf index 0 is reserved for the proof of possession.
    if xmss_signature_index(proof) != PQ_POSSESSION_XMSS_INDEX:
        return False

    # The key signs the BLS public key and itself.
    signing_root = get_pq_possession_signing_root(state, pubkey, xmss_public_key)
    return xmss.Verify(xmss_public_key, signing_root, proof)
```

#### New `process_pq_key_registration`

```python
def process_pq_key_registration(
    state: BeaconState, signed_registration: SignedPQKeyRegistration
) -> None:
    """
    Register or change the post-quantum keys of one validator or builder.

    Its BLS signing key authorizes the registration.

    The registration names the last change, so it applies at most once.
    """
    registration = signed_registration.message
    index = registration.index
    public_keys = registration.public_keys

    if is_builder_index(index):
        builder_index = convert_validator_index_to_builder_index(index)
        assert builder_index < len(state.builders)
        # Keys are registered only for active builders, whose deposit epoch is finalized
        assert is_active_builder(state, builder_index)
        # Builders make no selection proofs, so they register no VRF root
        assert public_keys.vrf_root == VRFRoot()
        pubkey = state.builders[builder_index].pubkey
    else:
        assert index < len(state.validators)
        validator = state.validators[index]
        # Keys are registered only for validators that have not initiated an exit
        assert validator.exit_epoch == FAR_FUTURE_EPOCH
        pubkey = validator.pubkey

    # The registration applies to the current entry only.
    # Every change moves the stored epoch, so a replayed registration fails here.
    last_change_epoch = get_pq_key_change_epoch(state, index)
    assert registration.previous_change_epoch == last_change_epoch

    # Changes of registered keys are rate-limited.
    if is_pq_registered(state, index):
        assert get_current_epoch(state) >= last_change_epoch + MIN_PQ_KEY_CHANGE_DELAY

    # The BLS signing key of the validator or builder authorizes the registration.
    domain = compute_domain(
        DOMAIN_PQ_KEY_REGISTRATION, genesis_validators_root=state.genesis_validators_root
    )
    signing_root = compute_signing_root(registration, domain)
    assert bls.Verify(pubkey, signing_root, signed_registration.signature)

    # The key must be unique, and the registrant must prove possession of it.
    assert not is_pq_public_key_in_use(state, public_keys)
    assert is_valid_pq_possession_proof(
        state, pubkey, public_keys.xmss_public_key, signed_registration.possession
    )

    # Write the keys and the epoch of the change into the entry.
    set_pq_public_keys(state, index, public_keys, get_current_epoch(state))
```

Anyone can submit a registration. Only its BLS signature authorizes it.

Registrations are processed last: after the block's other operations and after `block.body.parent_execution_requests`, which `process_parent_execution_payload` applies before `process_operations`. A registration for a validator whose exit is initiated earlier in the block, by a slashing, a voluntary exit, a withdrawal request, or a consolidation request, or for a builder whose exit is initiated by a builder exit request, therefore invalidates the block, so block producers check registrations against the state after the block's other operations.

### Gossip

A new global topic `pq_key_registration` carries `SignedPQKeyRegistration` messages. The following validations MUST pass before forwarding a `signed_registration` on the network, where `registration = signed_registration.message` and the head state is the node's state at its current head. They are listed in order, cheapest first.

- **[IGNORE]** The current epoch, allowing for `MAXIMUM_GOSSIP_CLOCK_DISPARITY`, is at or after the epoch of the fork that activates this EIP.
- **[IGNORE]** The head state is at or after the fork that activates this EIP, so that it has the registry lists of this EIP.
- **[REJECT]** In the head state, `registration.index` is a validator whose `exit_epoch` is `FAR_FUTURE_EPOCH`, or a builder index, with `BUILDER_INDEX_FLAG` set, of an active builder.
- **[REJECT]** If `registration.index` is a builder index, `registration.public_keys.vrf_root` is zero.
- **[IGNORE]** `signed_registration` is the first valid registration received for the pair `(registration.index, registration.previous_change_epoch)`.
- **[REJECT]** `registration.previous_change_epoch` is the stored change epoch of `registration.index` in the head state.
- **[IGNORE]** If `registration.index` has registered keys in the head state, the current epoch, allowing for `MAXIMUM_GOSSIP_CLOCK_DISPARITY`, is at least `registration.previous_change_epoch + MIN_PQ_KEY_CHANGE_DELAY`.
- **[REJECT]** `signed_registration.signature` is a valid BLS signature of `registration` by the public key of the validator or builder.
- **[REJECT]** The leanXMSS key in `registration.public_keys` is not registered by any validator or builder in the head state.
- **[REJECT]** `signed_registration.possession` is a valid proof of possession of the leanXMSS key for the BLS public key of the validator or builder.

A registration that was valid when first received can become invalid before it is included, for example when another validator or builder registers the same leanXMSS key first. The stored change epoch then does not change, so the first-seen record would block every later registration for the pair. Nodes MAY clear the record for a pair once its first-seen registration is no longer valid against the finalized state.

### Key roles

A validator's leanXMSS key is intended to sign every validator message once duties switch to it, and a builder's to sign its execution payload bids and envelopes. This EIP authenticates no duty with them.

A signer MUST NOT sign twice at the same leaf index of a key, and chooses how it allocates leaf indices to messages. Leaf index `PQ_POSSESSION_XMSS_INDEX` is reserved for the proof of possession: a signer MUST NOT sign at it anything other than the `PQKeyPossession` of its key for the BLS public key of its validator or builder. A signer MUST use each leanXMSS key in at most one registration, for one validator or builder, and MUST NOT register a key that it has registered before. Its proof is therefore signed once. A registration that is not included stays in the operation pools and is included later with the same bytes. It is never signed again.

The leanXMSS seed and the VRF leaf secrets SHOULD NOT be derived from the BLS key of the validator or builder. Keystores and signer state for leanXMSS keys SHOULD follow [EIP-8310](./eip-8310.md), which extends [ERC-2335](./eip-2335.md).

This EIP does not open the VRF root. The fork that uses it defines how its inputs map to indices. Builders register a zero VRF root.

## Rationale

### Registering before switching

Dormant keys cannot cause a missed attestation or a slashing, so the registry can ship before the aggregation and networking changes are ready. For the same reason, a change of keys replaces stored bytes and affects no duty.

### Two keys per validator

A stateful scheme such as leanXMSS signs at most once per leaf index, and several duties produce more than one message per slot. A second, stateless scheme would avoid leaf management at the cost of a second key and verifier and larger signatures. This EIP registers one leanXMSS key for all messages instead: since the signature carries its leaf index, new duties need no new key.

Selection proofs, such as aggregation and sync committee selection proofs, hash unique BLS signatures. leanXMSS signatures are not unique and could be ground, so the VRF root fixes one output per index at registration, before the validator knows its inputs. The root is not checked at registration, which keeps openings out of the registration, so validator clients check their tree before registering it.

### Leaf index 0

Leaf index `0` is reserved for the proof of possession. Under a fixed allocation that gives each slot a range of leaf indices, leaf `0` belongs to the genesis slot, which is never a duty slot after this fork, so the proof never takes a leaf from a duty.

### Proof of possession

The proof detects faulty key generation at registration rather than at the switch. With key uniqueness, it also prevents copying and squatting (see [Key copying and squatting](#key-copying-and-squatting)).

The proof signs `PQKeyPossession` rather than the whole registration, and the BLS signature covers the rest. The validator or builder is named by its BLS public key rather than its index: the public key never changes, and it is known before the deposit is processed, so the proof can be produced together with the keystore.

Consensus rejects a leanXMSS key that a validator or builder currently holds, including the one registering, so a change never keeps the current key. Changing only the VRF root therefore requires a new leanXMSS key, which is cheap while the keys are dormant. Consensus does not record earlier keys, so returning to an earlier key, or registering a key that another validator or builder has released, is valid on chain. Returning to an earlier key needs either a second proof at leaf `0` or the stored first one, and registering a key that another validator or builder released needs a proof of a different message at leaf `0`. The signer rules forbid both, so a signer never has to keep old proofs.

The proof is 2404 of the 2580 bytes of a registration. It is kept on chain because the signature switch relies on every registered key being a working key for its validator or builder.

### Authorization by the signing key

The operator who holds the BLS signing key also generates and holds the post-quantum key, so it registers each of its validators without a transaction from the stake owner, whatever the validator's withdrawal credentials. The authorization is a consensus-layer operation only, as for `BLSToExecutionChange`, so this EIP needs no execution-layer change.

Allowing changes lets a validator recover from a lost seed, lost signer state, or a faulty key without exiting. The cost is that an adversary able to forge BLS signatures can replace any validator's keys, not only those of unregistered validators (see [Quantum adversaries before the switch](#quantum-adversaries-before-the-switch)). A register-only rule would keep keys registered before a break authentic, at the cost of an exit for every lost or faulty key.

### Builders

Builders sign execution payload bids and envelopes with BLS keys from their own registry ([EIP-7732](./eip-7732.md)), so they need post-quantum keys too. Registering them in this fork gives them keys registered while BLS is believed secure, rather than an exit and re-entry at the switch. They use the same operation, message, and proof. The index carries `BUILDER_INDEX_FLAG`, as builder withdrawals do, and the keys are stored in lists parallel to `builders`. Builders make no selection proofs, so their VRF root is zero.

Builder indices are reused once a builder has withdrawn, so `FAR_FUTURE_EPOCH` cannot mark a builder that has never registered: a first registration signed for an earlier builder at the same index would name it too. A builder's entry instead starts at its deposit epoch. A registration requires an active builder, whose deposit epoch is finalized, so it always moves the stored epoch. An index is reassigned only after its earlier builder has exited and withdrawn, so every registration signed for that builder names an epoch before the new builder's deposit epoch.

### Changes and replay protection

One stored epoch per validator or builder, named by each registration and set by each change, provides both replay protection and the rate limit. A per-index counter would prevent replays but not limit changes.

`FAR_FUTURE_EPOCH` marks a validator that has never registered, as it marks unset epochs elsewhere in the consensus specifications. A builder's deposit epoch plays that role for builders (see [Builders](#builders)). A registration stores the current epoch, and with a delay of at least one epoch every change is applied after the epoch it names, so every applied registration changes the stored epoch and none applies twice. The delay check skips unregistered entries, so it never adds to `FAR_FUTURE_EPOCH`.

`MIN_PQ_KEY_CHANGE_DELAY` bounds each validator and builder to one change per 256 epochs, about 27 hours. Changes and first registrations share `MAX_PQ_KEY_REGISTRATIONS`, and a registration that changes keys again within the delay wastes no block space, since it is invalid.

### Interface instead of construction

This EIP specifies only the interface of the primitives and the properties it relies on, as [EIP-4844](./eip-4844.md) does for KZG. The registry does not depend on how the primitives are constructed, so their specification and test vectors can live with the other consensus cryptography.

Registry entries carry no version: this EIP accepts one set of primitives. A fork that changes the primitives before the switch defines how existing entries are handled, and introduces new `DomainType` constants for registrations and proofs of possession, so that registrations signed for the earlier primitives cannot be applied. Entries registered before that fork can then be told apart only by their change epoch.

### Lists parallel to the validator and builder registries

The keys are stored in lists parallel to `validators` and `builders`. The `Validator` and `Builder` containers and their generalized indices do not change, so light clients and proofs against them are not affected until the switch.

### Registration outside the deposit contract

The deposit contract's event layout is fixed, and its events are converted into fixed-size `DepositRequest` records ([EIP-6110](./eip-6110.md)) with no field for post-quantum keys, and builder deposit requests have none either. Existing validators and builders also need a registration path that does not involve a deposit. A new validator registers through the same path once its deposit has been processed and it has an index, which can be before its activation. A new builder registers once it is active. Setting keys at deposit time requires a new deposit format, which is part of the fork that retires BLS deposits.

### Per-block limits

`MAX_PQ_KEY_REGISTRATIONS = 8` bounds the extra block size at about 20 KiB, and the verification cost at eight BLS verifications and eight leanXMSS verifications per block. At that rate a million validators register in 125,000 full blocks, about 17 days of 12-second slots.

## Backwards Compatibility

This EIP requires a hard fork of the consensus layer. It changes no existing duty: every message is still authenticated with BLS, and a validator or builder that never registers keys is unaffected by this fork.

## Test Cases

The consensus test vectors cover at least:

- A registration for an unregistered validator, and a change of its keys once `MIN_PQ_KEY_CHANGE_DELAY` epochs have passed, including a change that keeps the VRF root.
- Rejection of a change before `MIN_PQ_KEY_CHANGE_DELAY` epochs have passed, and of a replayed registration whose `previous_change_epoch` no longer matches.
- Rejection of a registration for a validator that has initiated an exit, and for a validator whose exit is initiated earlier in the same block by a proposer slashing, an attester slashing, a voluntary exit, a withdrawal request, or a consolidation request in `parent_execution_requests`.
- A registration for an active builder with a zero VRF root, and a later change of its keys.
- Rejection of a builder registration with a nonzero VRF root, for a builder that is not yet active, for a builder that has initiated an exit, including by a builder exit request in `parent_execution_requests`, and for a builder index outside the builder registry.
- Rejection of a key already registered by another validator or builder or by the registering validator or builder itself, of an invalid proof of possession, and of a proof of possession at a leaf index other than `PQ_POSSESSION_XMSS_INDEX`.
- An unregistered validator's or builder's all-zero entry does not count as holding the all-zero key in `is_pq_public_key_in_use`.
- Rejection of a block with two registrations of the same leanXMSS key for two validators, or for a validator and a builder, where the second registration is invalid.
- A registration of a key that another validator held and has released through a change. This is valid on chain, although the signer rules forbid it for honest signers.
- After a builder index is reassigned, rejection of a registration signed for the earlier builder at that index, including one signed by the same BLS key after it re-enters at that index.
- The fork upgrade, which sets each builder's change epoch to its deposit epoch, `add_builder_to_registry` on a reused index, and the invariants `len(state.pq_public_keys) == len(state.pq_key_change_epochs) == len(state.validators)` and `len(state.builder_pq_public_keys) == len(state.builder_pq_key_change_epochs) == len(state.builders)`.

## Security Considerations

### Quantum adversaries before the switch

A registration is only as authentic as the BLS signature that authorizes it. Once a CRQC exists, an adversary can register or replace the keys of any validator or builder, at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs per index. The switch therefore has to happen while BLS is believed secure.

### Leaf reuse

Each leaf index signs at most once, whichever allocation the signer uses: slashing protection enforces it under a fixed per-slot allocation, and the signer's state under free allocation. A signer uses each key in one registration, so leaf `0` of each key signs one proof. A registration whose block is orphaned stays in the operation pools and is included again with the same proof bytes. Consensus does not track released keys, so it accepts a key that a validator or builder held before. Returning to an earlier key would need a second proof or the stored first one, and taking another's released key would sign a different message at leaf `0`. The signer rules forbid both.

### Key copying and squatting

The registry rejects a key that any validator or builder has already registered. Without that rule, a validator could register another's key and claim its signatures as its own participation, since the signed messages do not name the validator. The proof of possession signs the BLS public key of the validator or builder, so a copied key, even one published but not yet registered, cannot be registered for another. A validator and a builder may share a BLS public key, since they enter through different deposit paths. Their proofs of possession for a key are then the same message, but uniqueness across both registries keeps one leanXMSS key from serving both. This binding relies on BLS public keys never changing: if a later fork made them mutable, a key bound to an outdated public key would need a second proof at leaf `0`, which is a leaf reuse.

### Readiness is not registration

A registered key proves that its holder could sign once, at registration time. It does not prove that the validator will run post-quantum software, keep its seed, or keep its signer state consistent at the switch. The effective balance of active validators with registered keys is therefore an upper bound on readiness, so the switch needs a margin above the two-thirds finality threshold.

### VRF tree

The registry accepts a VRF root that another validator has registered. A validator that copies a root cannot open it before its owner does, but it has the same outputs and can replay the owner's openings once they are published. The fork that uses the tree has to account for this.

### Builder index reuse

A builder index is reassigned once its builder has exited and withdrawn. `add_builder_to_registry` then resets the entry, releasing the earlier builder's key and starting the change epoch at the new builder's deposit epoch. Every registration signed for an earlier builder at that index names an earlier epoch, so none of them applies, even if the new builder has the same BLS key.

### Denial of service and state growth

- **Blocks.** At most `MAX_PQ_KEY_REGISTRATIONS` registrations per block; see [Per-block limits](#per-block-limits).
- **Gossip.** Registrations are first-seen per index and previous change epoch, and each validator or builder can change its keys at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs.
- **State.** Each validator and builder adds 72 bytes: 64 bytes of keys and an 8-byte change epoch, about 72 MB for a million validators.
