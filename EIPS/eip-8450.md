## Abstract

This EIP adds a post-quantum public key registry to the beacon state. Each validator registers two hash-based commitments, bound to its existing validator index: a leanXMSS key, used for every message the validator signs once duties switch to it, and the 32-byte root of a VRF tree, a Merkle tree of `2**32` leaves that fixes one verifiable random output per index.

Both are defined in [EIP-CRYPTO](./eip-crypto.md). The leanXMSS key has a lifetime of `2**32` leaf indices. Every signature carries its leaf index, and the signer chooses how leaf indices are allocated to messages, provided no leaf index signs two different messages.

Registration is a new beacon block operation carrying the keys and a proof of possession under the leanXMSS key. It is authorized by the validator's BLS signing key, which can also replace registered keys, at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs. The registered keys are dormant: no duty is authenticated with them in this fork. A later fork switches duties to them, and takes over the post-quantum keys of every registered validator.

## Motivation

Every consensus-layer signature today is a BLS12-381 signature: attestations, block proposals, RANDAO reveals, aggregation selection proofs, sync committee messages, payload attestations, inclusion lists, proposer preferences, voluntary exits, and the deposit proof of possession. BLS relies on the hardness of discrete logarithms in pairing-friendly groups, which Shor's algorithm breaks. A cryptographically relevant quantum computer (CRQC) recovers a validator's secret key from its public key, and every validator's public key is in the beacon state.

BLS therefore has to be replaced, and this EIP splits the replacement into two forks. Generating a post-quantum key involves the validator's secret key material, requires new tooling, and, for staking pools, requires coordination between node operators and stake owners. If this work happens at the fork that switches the signature scheme, the number of ready validators is only known at that fork.

A separate registry fork has the following benefits:

- **Preparation.** Validators generate and register keys, with tooling tested on mainnet, while BLS remains the only scheme used for duties.
- **A readiness signal.** The effective balance of active validators with registered keys can be computed from the state, so the switch can be scheduled against an observed threshold.
- **Early implementation.** Consensus clients start manipulating the hash function, the verifier, and the containers of the post-quantum scheme before any duty depends on them, because every registration carries a proof of possession that clients verify.

Each validator registers one leanXMSS key for all of its messages, and one VRF tree for the outputs it must not be able to choose. The [Rationale](#one-key-for-all-duties) explains the first choice and the two ways a signer can allocate leaf indices, and [A VRF tree](#a-vrf-tree) explains the second.

### Helpers

```python
def is_pq_registered(state: BeaconState, index: ValidatorIndex) -> bool:
    """
    Return whether a validator has registered post-quantum keys.
    """
    # A validator without keys holds the all-zero entry, of version 0.
    return state.pq_public_keys[index].version != PQ_KEYS_VERSION_UNSET
```

```python
def is_pq_public_key_in_use(
    state: BeaconState, public_keys: PQPublicKeys, excluded_index: ValidatorIndex
) -> bool:
    """
    Return whether another validator already registered the same leanXMSS key.

    The validator being registered is excluded.

    It can therefore keep its leanXMSS key while changing its VRF root.
    """
    for index, entry in enumerate(state.pq_public_keys):
        # Skip the validator itself and validators without keys.
        if index == excluded_index or entry.version == PQ_KEYS_VERSION_UNSET:
            continue

        # A match means the key belongs to another validator.
        if entry.xmss_public_key == public_keys.xmss_public_key:
            return True
    return False
```

Clients are expected to maintain a map from registered keys to validator indices, as they do for BLS public keys.

```python
def get_pq_possession_signing_root(
    state: BeaconState, validator_pubkey: BLSPubkey, xmss_public_key: XMSSPublicKey
) -> Root:
    """
    Return the message that the proof of possession signs.

    The domain uses the genesis fork version.

    A proof therefore stays valid across forks.
    """
    possession = PQKeyPossession(validator_pubkey=validator_pubkey, xmss_public_key=xmss_public_key)
    domain = compute_domain(
        DOMAIN_PQ_KEY_POSSESSION, genesis_validators_root=state.genesis_validators_root
    )
    return compute_signing_root(possession, domain)
```

```python
def is_valid_pq_possession_proof(
    state: BeaconState,
    validator_pubkey: BLSPubkey,
    xmss_public_key: XMSSPublicKey,
    proof: XMSSSignature,
) -> bool:
    """
    Check that the holder of a leanXMSS key signed it for a validator's BLS public key.

    A copied key cannot be proven for a different validator.
    """
    # Leaf index 0 is reserved for the proof of possession.
    if xmss_signature_index(bytes(proof)) != PQ_POSSESSION_XMSS_INDEX:
        return False

    # The key signs the validator's BLS public key and itself.
    signing_root = get_pq_possession_signing_root(state, validator_pubkey, xmss_public_key)
    return xmss_verify(bytes(xmss_public_key), bytes(signing_root), bytes(proof))
```

#### New `process_pq_key_registration`

```python
def process_pq_key_registration(
    state: BeaconState, signed_registration: SignedPQKeyRegistration
) -> None:
    """
    Register or change the post-quantum keys of one validator.

    The validator's BLS signing key authorizes the registration.

    The registration names the validator's last change, so it applies at most once.
    """
    registration = signed_registration.message
    index = registration.validator_index
    public_keys = registration.public_keys

    assert index < len(state.validators)
    validator = state.validators[index]
    # Keys are registered only for validators that have not initiated an exit
    assert validator.exit_epoch == FAR_FUTURE_EPOCH
    assert public_keys.version == PQ_KEYS_VERSION_1

    # The registration applies to the validator's current entry only.
    # Every change moves the stored epoch, so a replayed registration fails here.
    last_change_epoch = state.pq_key_change_epochs[index]
    assert registration.previous_change_epoch == last_change_epoch

    # Changes of registered keys are rate-limited.
    if is_pq_registered(state, index):
        assert get_current_epoch(state) >= last_change_epoch + MIN_PQ_KEY_CHANGE_DELAY

    # The validator's signing key authorizes the registration.
    domain = compute_domain(
        DOMAIN_PQ_KEY_REGISTRATION, genesis_validators_root=state.genesis_validators_root
    )
    signing_root = compute_signing_root(registration, domain)
    assert bls.Verify(validator.pubkey, signing_root, signed_registration.signature)

    # The key must be unique, and the registrant must prove possession of it.
    assert not is_pq_public_key_in_use(state, public_keys, index)
    assert is_valid_pq_possession_proof(
        state, validator.pubkey, public_keys.xmss_public_key, signed_registration.possession
    )

    # Write the keys and the epoch of the change into the validator's entry.
    state.pq_public_keys[index] = public_keys
    state.pq_key_change_epochs[index] = get_current_epoch(state)
```

The same operation registers keys for a validator that has none and replaces the keys of a registered validator. It is authorized by the validator's BLS signing key, which is held by the validator's operator, and needs no execution-layer transaction. The operation carries the full keys and proof and can be submitted by anyone. Each registration names the epoch of the validator's last change, and every change sets that epoch to the current one, so a registration applies at most once.

Registrations are processed after every other operation of the block, and after the execution requests of the parent payload in `block.body.parent_execution_requests`, which `process_parent_execution_payload` processes before `process_operations`. A registration for a validator whose exit is initiated earlier in the same block, by a slashing, a voluntary exit, a withdrawal request, or a consolidation request, is therefore invalid, and so is the block. Block producers check registrations against the state that results from the other operations of the block.

### Gossip

A new global topic `pq_key_registration` carries `SignedPQKeyRegistration` messages. The following validations MUST pass before forwarding a `signed_registration` on the network, where `registration = signed_registration.message` and the head state is the node's state at its current head. They are listed in order, cheapest first.

- **[REJECT]** `registration.public_keys.version` is `PQ_KEYS_VERSION_1`.
- **[REJECT]** `registration.validator_index` is a validator in the head state, and its `exit_epoch` is `FAR_FUTURE_EPOCH`.
- **[IGNORE]** `signed_registration` is the first valid registration received for the pair `(registration.validator_index, registration.previous_change_epoch)`.
- **[REJECT]** `registration.previous_change_epoch` is the validator's `pq_key_change_epochs` entry in the head state.
- **[IGNORE]** If the validator has registered keys in the head state, the current epoch is at least `registration.previous_change_epoch + MIN_PQ_KEY_CHANGE_DELAY`.
- **[REJECT]** `signed_registration.signature` is a valid BLS signature of `registration` by the validator's public key.
- **[REJECT]** The leanXMSS key in `registration.public_keys` is not registered by another validator in the head state.
- **[REJECT]** `signed_registration.possession` is a valid proof of possession of the leanXMSS key for the validator's BLS public key.

A registration that was valid when first received can become invalid before it is included, for example when another validator registers the same leanXMSS key first. The validator's `pq_key_change_epochs` entry then does not change, so the first-seen record would block every later registration for the pair. Nodes MAY clear the record for a pair once its first-seen registration is no longer valid against the finalized state.

### Key roles

The leanXMSS key registered under `PQ_KEYS_VERSION_1` is registered to sign every validator message once duties switch to it. This EIP does not authenticate any duty with it.

A validator's signer follows the leaf-index rules of [EIP-CRYPTO](./eip-crypto.md). Leaf index `PQ_POSSESSION_XMSS_INDEX` is reserved for the proof of possession: a signer MUST NOT sign at it any message other than the `PQKeyPossession` of its key for its validator's BLS public key, and MUST NOT prove the same key for two validators. The signer chooses how it allocates the other leaf indices to messages, as described in [Leaf allocation](#leaf-allocation).

The VRF root registered under `PQ_KEYS_VERSION_1` commits to one output per index, for duties that need an output the validator cannot choose. This EIP does not open it. The fork that uses it defines how its inputs map to indices. The registry does not require VRF roots to be unique, so two validators can register the same root and have the same outputs.

## Rationale

### Registering before switching

The reasons for separating the registry from the signature switch are given in the [Motivation](#motivation). The registered keys are not used for any duty. They cannot cause a missed attestation or a slashing, so the registry can be deployed before the aggregation and networking changes are ready. The fork that switches duties takes over the registered keys and defines how they are used, including whether and how they can change after the switch.

Because the keys are dormant, a change replaces stored bytes and affects nothing else. The proof of possession catches an incorrectly generated key before it is registered, and a validator that loses its post-quantum seed or its signer state, or finds a fault in its keys, registers new ones without exiting.

### One key for all duties

A stateful signature scheme signs at most one message per leaf index. Attestations fit this rule: one attestation per slot, and two different attestations in the same slot are slashable. Other duties do not: a proposer also attests in its slot, a sync committee member signs a message every slot in addition to its attestation, proposer preferences are re-signed after a reorganization, and voluntary exits are not tied to a slot.

A second, stateless scheme such as leanSPHINCS would sign these messages without leaf management, at the cost of a second key, a second verifier, and larger signatures. This EIP registers one leanXMSS key instead, and leaves leaf allocation to the signer. The signature carries its leaf index, so the verifier needs no schedule, and new duties do not need a new key.

The key is not used for randomness, because hash-based signatures are not unique. The VRF tree provides the outputs that a validator must not be able to choose, as explained in [A VRF tree](#a-vrf-tree).

### Leaf allocation

The signer allocates leaf indices to messages in one of two ways:

- **Free allocation.** The signer gives each message the next unused leaf index and records it in its state. The key signs `2**32 - 1` messages in total, whatever the duties.
- **Fixed allocation.** Each slot owns `k` consecutive leaf indices, `[k * s, k * s + k)` for slot `s`, one per duty the validator may perform in that slot. The schedule needs no state beyond slashing protection, and the lifetime becomes `2**32 / k` slots: with `k = 8`, `2**29` slots, about 204 years at 12-second slots.

Both are compatible with the same registered key and the same verifier. Leaf index `0` falls in slot `0` under fixed allocation, the genesis slot, which is never a duty slot after this fork, so it is reserved for the proof of possession under both. Because signing is deterministic, a proof that is resubmitted, for example after its block was orphaned or when the same key is registered again, is byte-identical and reuses no leaf.

### A VRF tree

BLS signatures are unique, so the consensus layer also uses them as verifiable random outputs: aggregation selection proofs and sync committee selection proofs are BLS signatures whose hash decides the selection. A leanXMSS signature is not unique, since the signer chooses the randomizer and the leaf index, so a validator could grind its selection. The VRF tree of [EIP-CRYPTO](./eip-crypto.md) restores uniqueness: the root fixes one output per index at registration, before the validator knows which inputs it will open.

The registration does not open the tree, so the root is not checked when it is registered. It adds 32 bytes to a registration instead of an opening of 1056 bytes. A root that does not match its secrets is detected only when the tree is first opened, so validator clients are expected to check their tree before registering it.

The registry does not require VRF roots to be unique. Two validators with the same root have the same outputs, so the fork that uses the tree has to bind each selection to the validator, for example by hashing the output with the validator index.

### Proof of possession

Every registration proves possession of the leanXMSS key by signing the validator's BLS public key and the key itself. The proof has three purposes:

- **It detects faulty key generation at registration time.** Without it, a key that does not match its seed would only be detected at the signature switch, when the key is first used.
- **It prevents key copying.** Attestation signatures cover `AttestationData`, and sync committee and payload timeliness signatures cover a block root. None of these signed messages contains the validator index. If two validators could register the same key, one could claim the other's signatures as its own participation. The registry therefore requires keys to be unique.
- **It prevents squatting.** With uniqueness alone, an attacker could register a victim's published key first and block the victim's registration. The proof signs the victim's BLS public key, so a copied key cannot be registered for a different validator without the secret key.

The proof signs `PQKeyPossession`, not the whole registration. Its message is the same in every registration of the key for the validator, including one that changes only the VRF root, so leaf index `0` signs one message and is never reused. The BLS signature covers the rest of the registration.

The proof names the validator by its BLS public key rather than its index. A validator's BLS public key never changes and no two validators share one, so it binds the key to one validator as the index does. Unlike the index, it is known before the deposit is processed, so the proof can be produced in the same offline ceremony that generates the validator's keystore, and a later fork that sets post-quantum keys at deposit time can verify the same proof. The binding relies on BLS public keys staying immutable: if a later fork made them mutable, a key bound to an outdated public key would need a second proof at leaf `0`.

The proof is 2404 of the 2581 bytes of a registration. It is kept on chain because the signature switch relies on every registered key being a working key for its validator.

### Authorization by the signing key

Registration is authorized by the validator's BLS signing key. The operator who holds that key also generates and holds the post-quantum key, so it registers each of its validators without a transaction from the stake owner, whatever the validator's withdrawal credentials. The authorization is a consensus-layer operation only, as for `BLSToExecutionChange`, so this EIP needs no execution-layer change.

The same key can replace registered keys. The keys are dormant until the switch, so a change has no effect on any duty, and it lets a validator recover from a lost seed, a lost signer state, or a faulty key without exiting. The cost is that the registry is only as authentic as BLS until the switch: an adversary that can forge BLS signatures can replace any validator's keys, not only those of validators that have not registered. The switch is therefore scheduled while BLS is believed secure. A register-only rule would keep keys registered before a break authentic, at the cost of an exit for every lost or faulty key.

### Changes and replay protection

A registration names the epoch of the validator's last change, and a change sets that epoch to the current one. One field per validator therefore makes every registration apply to exactly one state of the entry, so a replayed registration is invalid, and also rate-limits changes. A per-validator counter would prevent replays but not limit changes, and a separate rate limit would need a second field.

`GENESIS_EPOCH` marks both a validator that has never registered and a change made in the genesis epoch. This only arises when this EIP is active at genesis. A registration applied in that epoch can then be included once more after `MIN_PQ_KEY_CHANGE_DELAY` epochs. It writes the same keys, which its BLS signature authorized, and restarts the delay once, since the change epoch no longer matches it afterwards.

`MIN_PQ_KEY_CHANGE_DELAY` bounds each validator to one change per 256 epochs, about 27 hours. Changes and first registrations share `MAX_PQ_KEY_REGISTRATIONS`, and a validator that changes its keys again within the delay wastes no block space, since its registration is invalid.

### Registry version

Each registry entry carries a version byte. Version `0` marks a validator with no registered keys, and any other value is the version of [EIP-CRYPTO](./eip-crypto.md) that the keys use, which fixes the hash function, leanXMSS, and the VRF tree together. The version byte identifies the verifier of each entry, independently of the fork that registered it. This EIP accepts only version `1`.

Registering keys under several versions, so that one could be chosen after registration, multiplies the registry size and the key generation work. A later version with the same key sizes can be accepted by a later fork without changing `PQPublicKeys`, while a version with different sizes requires a new container.

### A list parallel to the validator registry

The keys are stored in a list parallel to `validators`. The `Validator` container and its generalized indices do not change, so light clients and proofs against them are not affected until the switch. The fork that switches duties may move the keys into the validator record, since that fork changes the meaning of `Validator.pubkey`.

### Registration outside the deposit contract

The deposit contract's event layout is fixed, and its events are converted into fixed-size `DepositRequest` records ([EIP-6110](./eip-6110.md)) with no field for post-quantum keys. Existing validators also need a registration path that does not involve a deposit. A new validator registers through the same path once its deposit has been processed and it has an index, which can be before its activation. Setting keys at deposit time requires a new deposit format, which is part of the fork that retires BLS deposits.

### Per-block limits

A registration is 2581 bytes, dominated by the proof of possession. `MAX_PQ_KEY_REGISTRATIONS = 8` bounds the extra block size at about 20 KiB, and the verification cost at eight BLS verifications and eight leanXMSS verifications per block. At that rate a million validators register in 125,000 full blocks, about 17 days of 12-second slots.

## Backwards Compatibility

This EIP requires a hard fork of the consensus layer. It changes no existing duty: every message is still authenticated with BLS, and a validator that never registers keys is unaffected by this fork.

## Test Cases

Test vectors for the hash function, leanXMSS, and the VRF tree are specified in [EIP-CRYPTO](./eip-crypto.md). Consensus test vectors are to be provided in the consensus specifications, covering at least:

- A registration for an unregistered validator, and a change of its keys once `MIN_PQ_KEY_CHANGE_DELAY` epochs have passed, including a change of the VRF root alone.
- Rejection of a change before `MIN_PQ_KEY_CHANGE_DELAY` epochs have passed, and of a replayed registration whose `previous_change_epoch` no longer matches.
- Rejection of a registration for a validator that has initiated an exit, and for a validator whose exit is initiated earlier in the same block by a proposer slashing, an attester slashing, a voluntary exit, a withdrawal request, or a consolidation request in `parent_execution_requests`.
- Rejection of a key already registered by another validator, of an invalid proof of possession, and of a proof of possession at a leaf index other than `PQ_POSSESSION_XMSS_INDEX`.
- Rejection of a block with two registrations of the same leanXMSS key for two validators, where the second registration is invalid.
- A registration of a key by another validator once a change of its owner's keys has freed it.
- The fork upgrade, and the invariant `len(state.pq_public_keys) == len(state.pq_key_change_epochs) == len(state.validators)` after new validators are added.

## Reference Implementation

The cryptographic primitives are covered by [EIP-CRYPTO](./eip-crypto.md). The consensus-layer changes are to be provided before this EIP moves beyond Draft.

## Security Considerations

### Quantum adversaries before the switch

A registration is only as authentic as the BLS signature that authorizes it. Before a CRQC exists, it is authentic. After a CRQC exists, an adversary can register or replace the keys of any validator, at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs per validator. The registry is therefore only as authentic as BLS up to the switch, and the switch has to happen while BLS is believed secure.

### Leaf reuse

The leaf-index rules of [EIP-CRYPTO](./eip-crypto.md) apply to every registered leanXMSS key. Under fixed allocation, slashing protection by slot and duty enforces one message per leaf index. Under free allocation, the signer's state does. Keystores and signer state SHOULD follow [EIP-8310](./eip-8310.md).

Leaf index `0` signs only the `PQKeyPossession` of the key for the validator's BLS public key. That message does not change between registrations of the same key, and signing is deterministic, so registering the same key again is safe. Proving the same key for two validators would sign two different messages at leaf `0`, which is why the signer rules forbid it.

### Key copying and squatting

The registry rejects a key that another validator has already registered. Without that rule, a validator could register another's key and claim its signatures as its own participation, since the signed messages do not name the validator. The proof of possession signs the validator's BLS public key, so a copied key and its proof cannot be registered for a different validator. A key that is published but not yet registered cannot be squatted.

### Readiness is not registration

A registered key proves that its holder could sign once, at registration time. It does not prove that the validator will run post-quantum software, keep its seed, or keep its signer state consistent at the switch. The effective balance of active validators with registered keys is therefore an upper bound on readiness, and the switch is scheduled with a margin above the two-thirds threshold that finality needs.

### VRF tree

The registry accepts a VRF root that another validator has registered. A validator that copies a root cannot open it before its owner does, but it has the same outputs and can replay the owner's openings once they are published. The fork that uses the tree has to account for this.

### Denial of service and state growth

- **Blocks.** At most `MAX_PQ_KEY_REGISTRATIONS` registrations per block, about 20 KiB, eight BLS verifications and eight leanXMSS verifications.
- **Gossip.** Registrations are first-seen per validator and previous change epoch, and each validator can change its keys at most once every `MIN_PQ_KEY_CHANGE_DELAY` epochs.
- **State.** Each validator adds 73 bytes: 65 bytes of keys and an 8-byte change epoch, about 73 MB for a million validators.

### Key management

The leanXMSS seed and the VRF leaf secrets SHOULD NOT be derived from the validator's BLS key. A validator that loses its leanXMSS seed, its signer state, or its VRF secrets registers new keys, authorized by its BLS signing key. Keystores for leanXMSS keys SHOULD follow [EIP-8310](./eip-8310.md), which extends [ERC-2335](./eip-2335.md).
