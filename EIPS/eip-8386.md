## Abstract

This proposal extends [EIP-8130](./eip-8130.md) with a new `account_changes` entry, create-ephemeral
(`0x03`). It produces a **stateless** account: one `initial_actor` (the same tuple as an EIP-8130
create actor), a 7702 delegation that exists only for this transaction, and **no Keystore write**.
Config-change entries MAY follow the create-ephemeral entry and are applied to a transaction-scoped
account image, so the full actor map — including a key rotation — is passed in the transaction.
The transaction MUST be nonce-free. Leftover ETH or tokens are recovered by submitting another
create-ephemeral with the same `initial_actor` parameters. No opcodes, statuses, or revert semantics
are added.

## Motivation

EIP-8130 `create` deploys runtime bytecode, writes `initial_actors` into Keystore storage, and leaves a
permanent account. Privacy, one-shot, and fully stateless flows need the opposite: an address that can
originate `calls` without Keystore state, persistent code, or a nonce slot.

Create-ephemeral is create's actor tuple as a single `initial_actor` with those writes removed. During
execution the account is delegated so wallet code can run; at settlement the indicator is cleared.
Replay protection is EIP-8130's existing nonce-free ring buffer. Application-level nullifiers (privacy
pools) live in `calls`, not in this entry.

Chaining EIP-8130 config-change entries after that `initial_actor` is what makes the account *fully*
stateless rather than one-shot-only. The address commits the birth actor; every later actor (a session
key, a rotated authenticator, a `POLICY` manager) is a signed account change carried in the same
transaction. There is no on-chain actor map to update.

## Specification

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" in this document are to be interpreted
as described in RFC 2119 and RFC 8174.

This EIP applies only on chains that implement EIP-8130. An EIP-8130 chain that has not adopted this EIP
MUST reject create-ephemeral entries as an unknown `account_changes` type.

### Constants

| Name                | Value                         | Comment |
| ------------------- | ----------------------------- | ------- |
| `EPHEMERAL_PREFIX`  | ASCII `"EPHEMERAL"` (9 bytes) | Domain separator for address derivation |
| `CREATE_EPHEMERAL_GAS_COST` | TBD                   | Intrinsic cost of applying and clearing the transaction-scoped indicator; no Keystore writes |

### Create-Ephemeral Entry

EIP-8130 `account_changes` gains type `0x03`:

```
rlp([
  0x03,               // type: create ephemeral
  user_salt,          // bytes32: User-chosen uniqueness factor
  delegation,         // address: 7702 target for this transaction only
  initial_actor       // [actorId, authenticator, scope, policyData]
])
```

`initial_actor` uses the same tuple, `policyData`, and `authorizeActor` rules as one element of
EIP-8130 create's `initial_actors`. `expiry` is not expressible. Every `scope` grant is allowed
**except** `NONCE` (`0x04`): reject the entry if `scope & NONCE != 0`. Admin (`scope == 0x00`) and
`SENDER` / `POLICY` / `SELF_PAYER` / `SPONSOR_PAYER` remain expressible. The transaction itself MUST
use `nonce_key == NONCE_KEY_MAX` and `nonce_sequence == 0`; a create-ephemeral entry on a sequenced
`nonce_key` is invalid.

The create-ephemeral entry MUST be first. Combining it with create (`0x00`) or delegation (`0x02`) is
invalid: those persist Keystore or code state. Config-change entries (`0x01`) MAY follow; they do not
persist. See [Stateless Account Image](#stateless-account-image).

Create-ephemeral is authorized by the transaction's `sender_auth`; there is no separate authorization
field on the `0x03` entry. There is no `createEphemeral` Keystore function and no portable EVM
equivalent of transaction-scoped delegation.

### Address Derivation

Addresses are the trailing 20 bytes of a domain-separated hash over the `0x03` entry. Chained
config-changes do **not** participate:

```
actor_commitment = keccak256(actorId || authenticator || scope || policyData)

address = keccak256(EPHEMERAL_PREFIX || user_salt || actor_commitment || delegation)[12:]
```

`user_salt` and `actor_commitment` are 32 bytes each; `delegation` is the 20-byte address. The prefix
domain-separates this space from EIP-8130 CREATE2 create addresses; `delegation` is committed so a
prefunded counterfactual cannot be pointed at a different implementation. Off-chain address prediction
MUST apply the same initial-actor validation as create-ephemeral, including the `NONCE`-bit ban, so a
predicted address always corresponds to an entry the protocol will accept.

The same `(user_salt, initial_actor, delegation)` therefore always produces the same address. That is
the recovery path: leftover ETH or tokens at the address are swept by a later create-ephemeral
transaction with the same parameters. The protocol does not increment the account's EVM nonce and does
not require CREATE2 freshness (`code_size == 0 && nonce == 0`); uniqueness comes from the hash, and
reuse is intentional.

### Stateless Account Image

When a create-ephemeral entry is present, the protocol holds a **transaction-scoped account image**
instead of reading or writing Keystore storage. The image is the actor map, policy slots, lock word,
and local/multichain sequence counters that EIP-8130 create would have written, kept in memory for
this transaction only.

1. **Initialize** from `initial_actor` as EIP-8130 create initializes from a one-element
   `initial_actors` set: that actor is live, `local_sequence = 1`, lock state is the create default,
   `DEFAULT_EOA_REVOKED` is set unless `initial_actor` is the self-actor. No SLOADs, no SSTOREs, no
   `CONTRACT_ESTABLISHED`, no `AccountCreated`.
2. **Apply** each following config-change entry (`0x01`) to the image in order, using EIP-8130's
   `applySignedAccountChanges` rules (batch `auth` MUST be admin against the image *after previous
   entries*, channel/sequence MUST match the image counters, `AuthorizeActor` / `RevokeActor` /
   `IncrementLocalEpoch` mutate the image). `Lock` and `Unlock` MUST be rejected: there is no durable
   lock state. Already-applied skipping does not apply; every tx rehydrates from `initial_actor` and
   MUST replay the chain from the post-create counters.
3. **Authenticate** `sender_auth` against the image **after** all config-change entries. Resolved
   `actorId` and authenticator MUST match a live actor in that image. Scope and `policyData` for the
   rest of the transaction (including the `POLICY` gate's `manager`) are taken from that actor in the
   image.
4. **Discard** the image at settlement, together with the transaction-scoped 7702 indicator.

A transaction with only the `0x03` entry is the empty chain: `sender_auth` is `initial_actor`, as
before. A transaction with `0x03` then one or more `0x01` entries is a **witnessed** account: the
birth actor is in the address, and the rest of the actor map — a rotation, a session key, a policy
manager — is the signed chain.

The next transaction that wants the same live actor set MUST resubmit the same prefix chain. Nothing
about the image survives in Keystore storage.

### Validation

When a create-ephemeral entry is present in `account_changes`:

1. Parse `[0x03, user_salt, delegation, initial_actor]` where `initial_actor` is
   `[actorId, authenticator, scope, policyData]`. Apply EIP-8130 create's `policyData` rule. Reject if
   `delegation` is `address(0)`.
2. Reject if `scope & NONCE != 0`.
3. Require `nonce_key == NONCE_KEY_MAX` and `nonce_sequence == 0`.
4. Require the `0x03` entry is first. Reject if any create (`0x00`) or delegation (`0x02`) entry is
   present. Config-change (`0x01`) entries MAY follow.
5. Compute `actor_commitment` and `expected` per [Address Derivation](#address-derivation).
6. Require `sender == expected` (`sender` MUST be set; this is the configured-actor path).
7. Build the [stateless account image](#stateless-account-image) and apply following `0x01` entries.
   Reject `Lock` / `Unlock`. Reject any `AuthorizeActor` whose `scope & NONCE != 0` (the image MUST
   not gain a `NONCE` actor; the transaction remains nonce-free).
8. Validate `sender_auth` against the resulting image (resolved `actorId` and authenticator MUST
   match a live actor). Scope and `policyData` for the rest of the transaction are taken from that
   actor in the image, not from Keystore storage.

Mempool acceptance uses the image as the effective actor state (no Keystore read). Auto-delegation
to `DEFAULT_ACCOUNT_ADDRESS` is suppressed when a create-ephemeral entry is present.

### Execution

During EIP-8130 block execution, a create-ephemeral entry:

1. Suppresses auto-delegation to `DEFAULT_ACCOUNT_ADDRESS`.
2. Sets `code(sender) = 0xef0100 || delegation` before `calls` (the same indicator as an EIP-8130
   delegation entry).
3. Does **not** write Keystore storage, set `CONTRACT_ESTABLISHED`, initialize lock/channels, or emit
   `AccountCreated` / `DelegationApplied` / `ActorAuthorized`. Config-change entries that follow
   mutate only the image; they MUST NOT SSTORE Keystore slots or emit protocol-injected actor logs.
4. After `calls` settle (every phase succeeded or any phase reverted), discards the image, clears the
   indicator, and resets the account's code hash to the empty code hash.

The temporary code is visible to `EXTCODESIZE` / `EXTCODECOPY` / `CALL` / `DELEGATECALL` / `STATICCALL`
targeting `sender` for the remainder of this transaction only. Subsequent transactions see an empty-code
account unless another create-ephemeral with the same `0x03` parameters is included.

EIP-8130 protocol-injected receipt logs MUST NOT be emitted for a create-ephemeral entry or for
config-changes applied to its image. A failed transaction's earlier phases, nonce-free `replay_id`
insertion, and gas payment still persist; the ephemeral indicator and the image do not.

In-EVM `validateSignature` / Keystore reads during `calls` see empty Keystore storage for `sender`.
Callers that need the in-tx actor map MUST use the transaction's authenticated `actorId` (Transaction
Context) and the calldata chain, not `getActorConfig`.

### Gas

Create-ephemeral does not charge EIP-8130 `bytecode_cost` (no permanent deploy). Its contribution to
`account_changes_cost` is `CREATE_EPHEMERAL_GAS_COST` (TBD) plus, for each chained config-change
entry, that batch's authentication cost (same model as EIP-8130 `sender_auth_cost`) and **no**
Keystore slot-write costs. The indicator is installed and cleared in the same transaction.
Nonce-free `nonce_key_cost` is unchanged from EIP-8130.

## Rationale

**Companion rather than an EIP-8130 patch.** Create-ephemeral is optional. A chain can implement EIP-8130
without privacy or stateless accounts; this EIP can be adopted independently. The wire addition is a
new `account_changes` type, not a change to create, authenticators, or the AA transaction envelope.

**No Keystore write.** Persistent `(address → actor)` state is exactly what one-shot, privacy, and
stateless flows cannot afford. Authentication uses the in-tx image, the same trick EIP-8130 create
already uses before Keystore slots exist.

**Why chain config-changes instead of putting every actor in `initial_actor`.** The address commits
the birth actor. Everything after that — a rotation, a session key, `expiry`, `manager = account` —
is already specified as an EIP-8130 config-change. Replaying those signed batches against an in-memory
image reuses the same `auth`, channels, sequences, and `AuthorizeActor` rules. The entire account is
the `0x03` entry plus the chain; a Keystore-backed account is the same objects with the writes left
on. A second actor-array format would duplicate that.

**Why `sender_auth` is against the post-chain image.** That is what makes a rotation usable on this
transaction: the birth actor signs `AuthorizeActor(new)`, and `sender_auth` is the new actor. EIP-8130
create authenticates against `initial_actors` and then writes the chain to storage for *later*
transactions. Here there is no later storage, so the chain has to take effect before origin.

**Transaction-scoped 7702.** `calls` need wallet code at `sender`. A persistent 7702 indicator or
deployed bytecode would be leftover state. Installing `0xef0100 || delegation` for the transaction and
clearing it at settlement is the minimum that lets the account execute.

**Mandatory nonce-free.** A sequenced `nonce_key` writes a Nonce Manager slot at `(sender, nonce_key)`
forever. Forbidding `NONCE` on `initial_actor` (and on any `AuthorizeActor` in the chain) and
requiring `NONCE_KEY_MAX` keeps the only protocol footprint on EIP-8130's existing capacity-bounded
ring buffer.

**Recovery via recreate.** The address is a pure function of the `0x03` entry. The same parameters
produce the same address, so stranded funds are swept by a later create-ephemeral. CREATE2 freshness
is not required; reuse is the point.

**No logs.** Protocol-injected create/delegation/actor logs would advertise the session. Calldata
already contains the entry and the chain; this EIP adds no further receipt record.

## Backwards Compatibility

No changes to EIP-8130 transactions that do not carry a create-ephemeral entry. An EIP-8130 chain that
has not activated this EIP rejects type `0x03` as unknown. Contracts cannot currently observe
transaction-scoped 7702, so no existing code changes meaning. Chained `0x01` entries after `0x03` are
a new combination; Keystore-backed create+config-change transactions are unchanged.

## Security Considerations

**Address commitment.** The address commits `initial_actor` and `delegation` under `EPHEMERAL_PREFIX`,
so a different authenticator or implementation cannot claim a prefunded counterfactual. Chained
changes are not in the address: they are witnessed by signatures from the image as it evolves.

**Birth actor is a permanent recovery key.** Every transaction rehydrates from `initial_actor`. A
witness that omits later `0x01` entries is valid, so anyone who can authenticate as `initial_actor`
can always originate with the empty chain. `RevokeActor(initial_actor)` in a given witness only
binds *that* transaction. Durable retirement of the birth actor requires Keystore (or some other
stored commitment) and is out of scope. Treat `initial_actor` as a cert root; chained actors are
additional keys, not a replacement root.

**No durable actor map.** Unlinkability across transactions is the wallet's (unique salt / one-shot
actor / how much of the chain is reused), not the protocol's. Calldata is public. Reusing the same
rotation chain across transactions is what a long-lived stateless account looks like on the wire.

**Replay.** `replay_id` only suppresses the same logical transaction inside `NONCE_FREE_EXPIRY_WINDOW`.
A later create-ephemeral with the same `0x03` parameters and different `calls` (or a different chain)
is a new `replay_id` and is the intended recovery and rotation-witness path. Config-change signatures
are meant to be re-submitted; their EIP-8130 sequence counters live only in the image.

**Account storage.** Delegated code that `SSTORE`s to the account leaves storage after the indicator is
cleared; implementations used as `delegation` SHOULD be stateless.

**Ring-buffer capacity.** High-volume ephemeral traffic shares `REPLAY_BUFFER_CAPACITY` with every other
nonce-free transaction.
