## Abstract

This EIP introduces a post-quantum data-availability construction for Peer Data Availability Sampling (PeerDAS). It replaces Kate-Zaverucha-Goldberg (KZG) blob commitments with hash-based Merkle commitments and uses a scalable transparent argument of knowledge (STARK) to prove both the Reed–Solomon encoding relation and the correct derivation of each Merkle commitment. PeerDAS retains its existing column custody and sampling mechanisms, but sampled cells are authenticated using Merkle authentication paths instead of KZG proofs. Blob size and blob-gas pricing remain fixed at the applicable baseline rules. It represents blob-carrying transactions as [EIP-8141](./eip-8141.md) frame transactions and introduces a LeanDA scheme for [EIP-8288](./eip-8288.md) to instantiate data-availability dependency frames. These dependency frames are satisfied using the block-level recursive STARK construction defined in [EIP-8288](./eip-8288.md).

This EIP does not change column custody assignments, sampling, subnet allocation, or recovery thresholds.

## Motivation

PeerDAS currently authenticates blobs and cells using KZG commitments, whose security relies on elliptic-curve assumptions and a trusted setup. A cryptographically relevant quantum computer would break the elliptic-curve assumptions underlying KZG. Hash-based Merkle authentication and transparent STARK proofs provide a path that can be instantiated entirely from post-quantum assumptions. This proposal replaces authentication and encoding at the existing nominal blob capacity, without changing the blob fee market.

### Terminology

This EIP uses the following data-availability terms:

- **Blob.** A byte string representing a rate-1/2 additive Reed–Solomon codeword.

- **Cell.** One of the `NUMBER_OF_COLUMNS` equal-length byte slices a blob is divided into for its Merkle commitment. Cell `i` from every blob belongs to PeerDAS column `i`.

- **Cell byte length.** Every cell is exactly `CELL_BYTES` bytes. Every blob contains exactly `NUMBER_OF_COLUMNS` cells.

- **Blob commitment.** The 32-byte Merkle root that commits to a blob.

- **Ordered blob commitment list.** The list of blob commitments in the order of the corresponding input blobs.

- **Blob binding commitment.** A domain-separated Keccak-256 commitment to the canonical encoding of the ordered blob commitment list. The LeanDA guest derives it from the blobs supplied through private input.

- **Challenge seed.** A domain-separated Keccak-256 hash of the canonical encoding of the ordered blob commitment list. The host uses this seed outside the circuit to derive two Reed–Solomon challenges.

- **Reed–Solomon challenges.** Two field elements `reed_solomon_challenges` obtained by decoding the first and second 16-byte halves of the challenge seed, respectively. The host supplies the ordered pair as public input for the batch. The guest uses each challenge to construct a membership vector for the fixed blob size and requires both membership checks to pass for every blob.

- **Versioned hash.** A 32-byte identifier derived from a blob commitment and returned by the Ethereum Virtual Machine (EVM) `BLOBHASH` opcode.

- **STARK.** A transparent proof system used here to prove execution of the guest program.

- **Guest program.** The computation over host-supplied arguments and private input whose execution and return value a STARK proves.

- **LEANDA_SCHEME.** The protocol-reserved [EIP-8288](./eip-8288.md) verification scheme for proofs of the LeanDA guest program.

### Cryptographic Primitives

- **Hash function.** This EIP uses `keccak256`, the Keccak-256 hash function of the execution layer, for commitments, challenge-seed derivation, and public-input hashing.

- **Lean Ethereum.** The cryptographic libraries reused across the Ethereum protocol to instantiate STARK constructions.

### Blob Binding

A blob commitment is the Merkle root that binds a blob's `CODEWORD_BYTES // 16` field symbols to its cells. The symbol field and encoding are defined below.

```python
class Blob(ByteVector):
    LENGTH = CODEWORD_BYTES


BlobCommitment = Bytes32


def uint64_le(value: uint64) -> Bytes:
    return int(value).to_bytes(8, "little")
```

Deserialization MUST reject a blob unless it contains exactly `CODEWORD_BYTES` bytes, a cell unless it contains exactly `CELL_BYTES` bytes, and a commitment unless it contains exactly `HASH_BYTES` bytes. These fixed-width rules apply to transaction RLP, cell exchange, Engine API responses, consensus SSZ and guest private input before the values are processed. Existing availability markers such as Engine API `null` are not cells. Blob length is implicit in the type and is not transmitted as part of a commitment.

A blob is divided into `NUMBER_OF_COLUMNS` cells of exactly `CELL_BYTES` bytes. The `keccak256` hash of cell `i` is leaf `i` of the binary Merkle tree, whose depth is `MERKLE_DEPTH`. A cell is authenticated against the blob commitment using its Merkle authentication path.

`uint64_le` encodes an unsigned 64-bit integer as exactly eight little-endian bytes. `BLOB_BINDING_DOMAIN_V1`, `LEANDA_CHALLENGE_V1`, and `LEANDA_PUBLIC_INPUT_V1` are four-byte strings, respectively `0x14 0x00 0x00 0x00`, `0x15 0x00 0x00 0x00`, and `0x16 0x00 0x00 0x00`; their hexadecimal constants denote bytes, not integers.

```python
def compute_blob_merkle_root(data: Blob) -> BlobCommitment:
    nodes = [
        keccak256(data[i * CELL_BYTES:(i + 1) * CELL_BYTES])
        for i in range(NUMBER_OF_COLUMNS)
    ]
    while len(nodes) > 1:
        nodes = [
            keccak256(nodes[i] + nodes[i + 1])
            for i in range(0, len(nodes), 2)
        ]
    return nodes[0]
```

### Guest Program

The guest program is used to generate data-availability proofs using the Lean Ethereum stack. At a high level, proof generation follows this flow:

1. The host derives the blob binding commitment and challenge seed from the ordered list of blob commitments.
2. The host decodes the first and second 16-byte halves of the challenge seed as the ordered pair `reed_solomon_challenges`.
3. The blob binding commitment and both Reed–Solomon challenges are supplied as public input to the guest. The ordered batch of blobs is supplied as private input.
4. The guest derives the ordered blob commitment list from the private blobs, recomputes the blob binding commitment, and asserts that it equals the blob binding commitment supplied as public input.
5. For every blob, the guest checks the Reed–Solomon relation separately with each public challenge in `reed_solomon_challenges` and requires both checks to pass.
6. The guest returns `True` if all checks pass. Any failed check makes the guest invocation invalid.

#### Private Input

The private input contains an ordered batch of blobs:

```python
class PrivateInput:
    # A list of input blobs.
    blobs: list[Blob]
```

#### Public Input and Guest Return Value

The public input contains the blob binding commitment and the ordered pair of Reed–Solomon challenges `reed_solomon_challenges`. The guest returns a Boolean, and proof verification requires this return value to be `True`. The proof MUST bind this result to the public input whose encoding, prefixed by `LEANDA_PUBLIC_INPUT_V1`, hashes to the expected `data_hash`. The encoding is `blob_binding_commitment + encode_rs_challenges(reed_solomon_challenges)`: the 32-byte binding commitment followed by the two 16-byte challenge encodings in index order, as defined below.

```python
class FieldElement:
    # The constant coefficient, stored in the low 64 bits.
    low: uint64
    # The coefficient of Y, stored in the high 64 bits.
    high: uint64


class PublicInput:
    # A commitment to the encoded ordered blob commitments.
    blob_binding_commitment: Bytes32
    # The ordered pair of challenges, computed by the host outside the circuit.
    reed_solomon_challenges: tuple[FieldElement, FieldElement]
```

The canonical commitment-list encoding and blob binding commitment are:

```python
def encode_blob_commitments(
    blob_commitments: list[BlobCommitment],
) -> Bytes:
    return (
        uint64_le(len(blob_commitments))
        + b"".join(blob_commitments)
    )


def compute_blob_binding_commitment(
    blob_commitments: list[BlobCommitment],
) -> Bytes32:
    return keccak256(
        BLOB_BINDING_DOMAIN_V1
        + encode_blob_commitments(blob_commitments)
    )

```

#### Reed–Solomon field and challenge derivation

The base field is `K = GF(2)[t] / (t^64 + t^4 + t^3 + t + 1)`. A `K` element is encoded as a little-endian `uint64`, whose bit `i` is the coefficient of `t^i`. The symbol field is `FieldElement = K[Y] / (Y^2 + t*Y + 1)`. A value `value` represents `K(value.low) + K(value.high)*Y`. Its 16-byte encoding is `uint64_le(value.low) + uint64_le(value.high)`: bytes 0–7 contain the constant coefficient and bytes 8–15 contain the coefficient of `Y`, both in little-endian order. Every 16-byte string represents exactly one value of type `FieldElement`. `K(i)` interprets the bits of integer `i` as polynomial coefficients. `FieldElement(K(i), 0)` embeds the resulting base-field element in the symbol field. Field addition is XOR; multiplication and division use these field definitions.

The host computes `reed_solomon_challenges` using `compute_leanda_challenges`, which hashes the encoded ordered blob commitments with the `LEANDA_CHALLENGE_V1` prefix and decodes the first and second 16-byte halves of that seed as challenges 0 and 1, respectively. A batch is accepted only if both membership checks pass independently for every blob. The same ordered pair is used for all blobs in the batch.

The following pseudocode defines the host-side derivation and canonical encoding of the ordered challenge pair. `uint64_from_le` decodes eight bytes.

```python
def encode_field_element(value: FieldElement) -> Bytes:
    return uint64_le(value.low) + uint64_le(value.high)


def decode_field_element(data: Bytes) -> FieldElement:
    assert len(data) == 16
    return FieldElement(
        uint64_from_le(data[:8]),
        uint64_from_le(data[8:]),
    )


def encode_rs_challenges(
    reed_solomon_challenges: tuple[FieldElement, FieldElement],
) -> Bytes32:
    assert len(reed_solomon_challenges) == 2
    return b"".join(encode_field_element(c) for c in reed_solomon_challenges)


def compute_leanda_challenges(
    blob_commitments: list[BlobCommitment],
) -> tuple[FieldElement, FieldElement]:
    seed = keccak256(
        LEANDA_CHALLENGE_V1
        + encode_blob_commitments(blob_commitments)
    )
    return (decode_field_element(seed[:16]), decode_field_element(seed[16:]))
```

The canonical challenge-pair encoding is exactly the 32-byte seed, with no padding. The host MUST independently derive both challenges from the transaction's signed ordered blob commitments when computing the expected public-input digest; it MUST NOT accept prover-selected challenges.

#### Guest Validation

For a blob containing `2*k` field symbols, the additive evaluation domain is `K(i)` for `0 <= i < 2*k`, in byte-string order. The code consists of evaluations of polynomials over `FieldElement` of degree less than `k`. Define `s_j(X)` as the monic polynomial vanishing on the span of `1, t, ..., t^(j-1)`, and `Vhat_j(X) = s_j(X) / s_j(t^j)`. The challenge `reed_solomon_challenge` defines the membership vector with entry `L_challenge(K(i))`, where `L_challenge(X) = product(1 + reed_solomon_challenge^(2^j) * Vhat_j(X) for j in range(log2(k)))`. For one challenge, the check passes exactly when the blob's inner product with this vector is zero. The guest MUST run this check for both challenges and require both results independently; it MUST NOT combine residuals across challenges or blobs. The recurrence below specifies these polynomials without enumerating their roots. Implementations MAY use an equivalent product-tree optimization.

```python
def verify_reed_solomon_relation(data: Blob, reed_solomon_challenge: FieldElement) -> bool:
    symbols = [
        decode_field_element(data[i:i+16])
        for i in range(0, len(data), 16)
    ]
    # The rate-1/2 codeword has twice as many symbols as data symbols.
    k = DATA_BYTES // 16
    log_k = k.bit_length() - 1

    # s_0(X) = X; s_(j+1)(X) = s_j(X) * (s_j(X) + c_j),
    # c_j = s_j(t^j). Then Vhat_j(X) = s_j(X) / c_j.
    constants = []
    for j in range(log_k):
        value = K(1 << j)
        for c in constants:
            value = value * (value + c)
        constants.append(value)

    inner_product = FieldElement(0, 0)
    for i, symbol in enumerate(symbols):
        value = K(i)
        weight = FieldElement(1, 0)
        challenge_power = reed_solomon_challenge
        for c in constants:
            weight = weight * (
                FieldElement(1, 0) + challenge_power * FieldElement(value / c, 0)
            )
            value = value * (value + c)
            challenge_power = challenge_power * challenge_power
        inner_product = inner_product + symbol * weight
    return inner_product == FieldElement(0, 0)


def run_guest(
    public_input: PublicInput,
    private_input: PrivateInput,
) -> bool:
    blob_commitments = [
        compute_blob_merkle_root(blob)
        for blob in private_input.blobs
    ]
    blob_binding_commitment = compute_blob_binding_commitment(
        blob_commitments
    )
    assert blob_binding_commitment == public_input.blob_binding_commitment

    assert len(public_input.reed_solomon_challenges) == 2
    for blob in private_input.blobs:
        for challenge in public_input.reed_solomon_challenges:
            assert verify_reed_solomon_relation(blob, challenge)

    return True
```

Any failed assertion makes the guest invocation invalid. The circuit recomputes the binding commitment from the private blobs and asserts that it equals the binding commitment supplied as public input. It uses both `reed_solomon_challenges` supplied as public input directly, without deriving the seed. The guest returns `True` only after all checks pass. Proof verification binds this successful result to both public input values through the expected `data_hash`, which the host computes outside the circuit as specified below.

### Execution Layer

This EIP modifies [EIP-8141](./eip-8141.md) frame transactions to replace `blob_versioned_hashes` with `blob_commitments` and leverages [EIP-8288](./eip-8288.md) to instantiate data-availability dependency frames. It does not introduce a new transaction type or blob-specific frame mode.

Blob-carrying frame transactions follow this flow:

- A user constructs and signs a blob-carrying frame transaction with a data-availability dependency frame.
- The user submits the signed transaction and blob data to the transaction pool.
- A proof producer generates the LeanDA proof required by the transaction's dependency frame.
- Blob data may be disseminated before payload inclusion, with Merkle authentication paths authenticating individual cells.
- [EIP-8288](./eip-8288.md) folds the required LeanDA proof into its block-level recursive aggregate.
- The execution payload contains the blob-carrying frame transaction, and the execution payload bid ([EIP-7732](./eip-7732.md)) carries its blob commitments.

#### Frame Transaction Blob Commitments

The [EIP-8141](./eip-8141.md) frame transaction `blob_versioned_hashes` field is replaced with an ordered `blob_commitments` list:

```python
class FrameTransaction:
    chain_id: uint256
    nonce: uint64
    sender: Address
    frames: list[Frame]
    signatures: list[FrameSignature]
    fees: TransactionFees
    blob_commitments: list[BlobCommitment]
```

`Frame`, `FrameSignature`, and `TransactionFees` above are local pseudocode names for EIP-8141's frame (`[mode, flags, target, limits, value, data]`), signature (`[scheme, signer, msg, signature]`), and fees (`[max_fee, max_priority_fee_per_gas]`) structures. Their existing field constraints apply, including `nonce < 2**64 - 1`.

The Recursive Length Prefix (RLP) payload encodes these fields in the order shown, with `blob_commitments` occupying the final field position previously occupied by `blob_versioned_hashes`. Each `BlobCommitment` is an RLP byte string of exactly 32 bytes. The list MUST preserve blob order. EIP-8141's existing transaction signature hash therefore commits to the ordered Merkle roots. An empty `blob_commitments` list denotes a frame transaction that carries no blobs. A blob-carrying frame transaction is valid only if:

```python
assert 0 < len(tx.blob_commitments) <= MAX_BLOBS_PER_TX
```

Blob-gas accounting uses `len(tx.blob_commitments)` wherever the baseline counts `tx.blob_versioned_hashes`. Blob pricing and block limits are inherited unchanged from [EIP-4844](./eip-4844.md) and its applicable successors, including [EIP-7892](./eip-7892.md) and [EIP-7918](./eip-7918.md).

#### Versioned Hash

The versioned hash of a commitment is:

```python
def blob_commitment_to_versioned_hash(
    commitment: BlobCommitment,
) -> Bytes32:
    digest = keccak256(commitment)
    return Bytes32(bytes([PQ_VERSION]) + digest[1:])
```

#### BLOBHASH Opcode

`BLOBHASH(index)` (opcode `0x49`) returns the versioned hash derived from `tx.blob_commitments[index]`, or zero when the index is out of range. [EIP-8141](./eip-8141.md) `TXPARAM_BLOB_COUNT` returns `len(tx.blob_commitments)`.

#### [EIP-8288](./eip-8288.md) Data-Availability Dependency Frames

This EIP adds `LEANDA_SCHEME` to the scheme identifiers accepted in [EIP-8288](./eip-8288.md) dependency verification frames. `LEANDA_SCHEME` is a protocol-reserved profile of the leanSTARK verifier. Its `verification_key_hash` MUST equal `LEANDA_GUEST_VERIFICATION_KEY_HASH`:

```python
def verify_leanda_dependency(
    data_hash: Bytes32,
    verification_key_hash: Bytes32,
    witness: Bytes,
) -> bool:
    return (
        verification_key_hash == LEANDA_GUEST_VERIFICATION_KEY_HASH
        and verify_leanSTARK(
            (data_hash,),
            verification_key_hash,
            witness,
        )
    )
```

EIP-8288's `get_deps_hash` is extended to dependency lists containing `LEANDA_SCHEME`. LeanDA dependencies use EIP-8288's existing `(data_hash, verification_key_hash)` dependency-digest encoding. For EIP-8288 gas accounting and dependency limits, `LEANDA_SCHEME` is treated as a leanSTARK dependency.

For `LEANDA_SCHEME`, the EIP-8288 `data_hash` is the domain-separated Keccak-256 hash of the encoded public input, `keccak256(LEANDA_PUBLIC_INPUT_V1 + blob_binding_commitment + encode_rs_challenges(reed_solomon_challenges))`. Outside the circuit, the host MUST derive the blob binding commitment and `reed_solomon_challenges` from the transaction's signed ordered `blob_commitments` list using the helpers above, then compute the expected `data_hash`. Proof verification MUST check that the guest returns `True` for public input whose canonical encoding, prefixed by `LEANDA_PUBLIC_INPUT_V1`, hashes to `data_hash`. The `LEANDA_SCHEME` verifier profile MUST reject proofs that do not bind both public input values and the successful Boolean result; proving a return value of `True` alone is insufficient.

The required LeanDA dependency for a blob-carrying frame transaction is:

```python
def required_leanda_dependency(tx: FrameTransaction) -> Dependency:
    return (
        LEANDA_SCHEME,
        keccak256(
            LEANDA_PUBLIC_INPUT_V1
            + compute_blob_binding_commitment(tx.blob_commitments)
            + encode_rs_challenges(compute_leanda_challenges(tx.blob_commitments))
        ),
        LEANDA_GUEST_VERIFICATION_KEY_HASH,
    )
```

Every frame transaction with a non-empty `blob_commitments` list MUST declare `required_leanda_dependency(tx)` in an [EIP-8288](./eip-8288.md) dependency verification frame. It MAY share that frame with other dependencies. The dependency is included in `dependencies(tx)` using EIP-8288's existing parsing, deduplication, and sorting rules.

An execution block containing a blob-carrying frame transaction is validated under [EIP-8288](./eip-8288.md)'s block-validity rules. Its `block_deps_hash` MUST equal `get_deps_hash(dependencies(block))`, and its recursive STARK MUST verify against that digest and EIP-8288's fixed protocol-level `AGGREGATED_VK`. This verification covers every required data-availability dependency frame.

#### Sparse Blobpool

This EIP provisionally introduces `eth/76`, extending the proposed `eth/75` proof-wrapper transport. That baseline includes [EIP-8408](./eip-8408.md)'s `eth/73` indexed cell requests and [EIP-8512](./eip-8512.md)'s `eth/74` block dependency-proof exchange. The `eth/75` transport is still proposed; its formal proposal reference will be added once it is available in the EIPs repository. This transport integration, its version and message identifiers, and this EIP's `eth/76` version remain provisional pending coordination. Except for the post-quantum transaction and cell formats specified here, the inherited message identifiers, proof-wrapper transport, validation, resource limits, and block dependency-proof exchange are unchanged. This EIP introduces no separate proof-propagation message.

The 128-bit `cell_mask` continues to identify available or requested column indices. In `NewPooledTransactionHashes`, it applies to every blob of every announced blob-carrying frame transaction. For dependency-bearing transactions, these announcements advertise cell availability under the proposed wrapper-transport rules; they do not replace covering-wrapper propagation or establish proof validity.

For post-quantum blob-carrying dependency transactions, the proposed `ProofWrappers` transport carries the ordinary signed [EIP-8141](./eip-8141.md) frame-transaction encoding with `blob_commitments` as defined here. The signed list supplies the Merkle roots. Blob data and cell authentication paths are retrieved separately; the [EIP-7594](./eip-7594.md) type-3 transaction wrapper and its `blobs`, `commitments`, and `cell_proofs` fields are not used, including inside proof wrappers. Wrapper hashes, transaction-encoding hashes, lengths, and metadata MUST be computed from this post-quantum transaction encoding. Wrapper dependency witnesses and recursive proofs retain EIP-8288's encoding.

For dependency-bearing transaction propagation, clients MUST NOT send these transactions in `Transactions` or `PooledTransactions`, and `GetPooledTransactions` MUST treat them as unavailable. Clients MUST validate a covering wrapper before retrieving its transactions' cells and MUST perform the inherited availability checks before pool admission. A validated wrapper alone does not establish data availability.

The `GetCells` request uses the shared-mask schema in [EIP-8070](./eip-8070.md) and the [`eth` wire protocol](https://github.com/ethereum/devp2p/blob/277ceb399c15df86efb17d51eb58200c26879784/caps/eth.md#getcells-0x14), including its request ID:

```text
[request_id: P, [transaction_hash_0: B_32, ...], cell_mask: B_16]
```

`eth/76` replaces fixed-size KZG cells and proofs with the following per-transaction RLP structures. `GetCells` retains both EIP-8408 request forms and their message identifier `0x14`; `Cells` retains message identifier `0x15`. The shared response is:

```text
BlobCells = [
    cells: [B, ...],
    authentication_paths: [[B_32, ...], ...],
]

TransactionCells = [BlobCells, ...]

Cells = [
    request_id: P,
    [transaction_hash_0: B_32, ...],
    transaction_cells: [TransactionCells, ...],
    cell_mask: B_16,
]
```

The indexed forms are:

```text
GetCellsIndexed = [
    request_id: P,
    [transaction_hash_0: B_32, ...],
    masks: [B_16, ...],
    mask_ids: B,
]

CellsIndexed = [
    request_id: P,
    [transaction_hash_0: B_32, ...],
    transaction_cells: [TransactionCells, ...],
    masks: [B_16, ...],
    mask_ids: B,
]
```

The RLP list length distinguishes shared and indexed requests (three versus four fields) and responses (four versus five fields). A response MUST use the same form as its request. EIP-8408's mask-table validity, canonical ordering, request-form selection, indexed transaction limits, resource limits, and response-subset rules continue to apply. An indexed response MUST NOT contain an unrequested transaction hash. For indexed forms, each transaction's mask is `masks[mask_ids[i]]`; it applies to every blob in that transaction. The shared cell-ordering, length, authentication, and reconstruction rules below MUST be applied separately to each indexed transaction with its selected response mask. Different transactions MAY select different masks and therefore different path-omission cases.

An indexed request MUST NOT be empty. An empty indexed response MUST be `[request_id, [], [], [], b""]`, using an RLP empty byte string for `mask_ids`, and has EIP-8408's empty-response exemption from the non-empty transaction and mask counts. In a non-empty indexed response, every selected response mask MUST be nonzero. Shared responses retain the canonical empty and nonzero-mask rules below. Both forms complete the corresponding request when empty.

In the following cell-validation rules, `cell_mask` denotes the shared response mask or, for an indexed response, the selected mask of the transaction being checked.

The `request_id` is a 64-bit integer chosen by the requester. The `Cells` response MUST echo the `request_id` of the corresponding `GetCells` request.

The transaction hashes and `TransactionCells` values MUST have equal lengths and matching order. For each transaction, its `BlobCells` values MUST have the same length and order as its signed `blob_commitments` list. Within each `BlobCells`, the cell list MUST contain exactly one cell for each set bit in the response `cell_mask`, ordered by ascending set-bit index. Each response mask MUST be a subset of the mask requested for its transaction. In the shared form it applies uniformly to every returned `BlobCells` value; in the indexed form the selected mask applies uniformly to that transaction's blobs.

A peer MAY omit unavailable transactions, including transactions evicted after announcement. For a shared response, if no requested cells are returned, both the transaction hash list and the `transaction_cells` list MUST be empty, and `cell_mask` MUST be the all-zero 16-byte value. Otherwise, `cell_mask` MUST be nonzero. An empty response completes the corresponding request.

If fewer than `NUMBER_OF_COLUMNS // 2` cells per blob are returned in a non-empty response, each `authentication_paths` list MUST contain one path per returned cell in the same order. Every path MUST contain exactly `MERKLE_DEPTH` ordered `Bytes32` sibling hashes, and the receiver MUST verify each cell against the corresponding blob commitment.

If at least `NUMBER_OF_COLUMNS // 2` cells per blob are returned, each `authentication_paths` list MUST be empty. When fewer than `NUMBER_OF_COLUMNS` cells are returned, the receiver MUST reconstruct the complete rate-1/2 Reed–Solomon codeword using the returned cells and their column indices. Reconstruction MUST use the same encoding and cell layout as the LeanDA guest. The receiver MUST reject the response if reconstruction fails or if any returned cell differs from the reconstructed cell at its column index. With all `NUMBER_OF_COLUMNS` cells returned, no Reed–Solomon reconstruction is needed. In either case, the receiver MUST compute the complete blob Merkle tree and reject the response unless its root equals the corresponding blob commitment.

#### Engine API

This EIP adds `engine_getBlobsV5`, which retains the `engine_getBlobsV4` request parameters:

- `versioned_blob_hashes`: an ordered list of blob versioned hashes;
- `indices_bitarray`: a 128-bit mask selecting cell indices; and
- timeout: 1 second, matching `engine_getBlobsV4`.

The response is an ordered list containing one `BlobCellsAndPathsV1` value or `null` for each requested versioned hash. A `null` value indicates that the execution client does not hold the requested blob.

```python
class BlobCellsAndPathsV1:
    # Exactly NUMBER_OF_COLUMNS entries. An unrequested or unavailable cell
    # is represented by None.
    blob_cells: list[Bytes | None]

    # Empty when every cell is returned. Otherwise, exactly
    # NUMBER_OF_COLUMNS entries parallel to blob_cells.
    authentication_paths: list[list[Bytes32] | None]
```

Every non-null returned cell MUST be deserialized using the fixed-width rules in Blob Binding, including when all cells are returned.

If all `NUMBER_OF_COLUMNS` cells are returned, `authentication_paths` MUST be empty. The consensus client MUST reconstruct the complete blob Merkle tree and verify its root against the `BlobCommitment` corresponding to the requested versioned hash.

Otherwise, `authentication_paths` MUST contain exactly `NUMBER_OF_COLUMNS` entries. Entry `i` MUST contain exactly `MERKLE_DEPTH` ordered sibling hashes when `blob_cells[i]` is present and MUST be `null` when `blob_cells[i]` is `null`. The consensus client MUST verify every returned cell against the corresponding `BlobCommitment`.

The `engine_forkchoiceUpdatedV4` `custodyColumns` parameter introduced by EIP-8070 is unchanged.

### Consensus Layer

The consensus layer replaces KZG commitments in the execution payload bid with `BlobCommitment` values and replaces KZG proofs in data-column sidecars with Merkle authentication paths.

#### Types and Containers

The consensus-layer `BlobCommitment` is the same `Bytes32` Merkle root as the execution-layer value. `Cell` retains the [Fulu fixed-size byte-vector definition](https://github.com/ethereum/consensus-specs/blob/d2021d2719235f0df4726a1d330502cb15aa8ea3/specs/fulu/das-core.md#cell); it is not redefined by this EIP.

```python
class BlobCommitments(ProgressiveList[BlobCommitment]):
    pass


class MerklePath(Vector[Bytes32]):
    LENGTH = MERKLE_DEPTH


class AuthenticationPaths(ProgressiveList[MerklePath]):
    pass
```

This modifies the [Heze `ExecutionPayloadBid`](https://github.com/ethereum/consensus-specs/blob/d2021d2719235f0df4726a1d330502cb15aa8ea3/specs/heze/beacon-chain.md#executionpayloadbid), incorporating [EIP-7732](./eip-7732.md), [EIP-7805](./eip-7805.md), and [EIP-7688](./eip-7688.md). Its `blob_kzg_commitments` field is replaced with `blob_commitments`:

```python
class ExecutionPayloadBid(ProgressiveContainer):
    ACTIVE_FIELDS = active_fields(width=13)

    parent_block_hash: Hash32
    parent_block_root: Root
    block_hash: Hash32
    prev_randao: Bytes32
    fee_recipient: ExecutionAddress
    gas_limit: Uint64
    builder_index: BuilderIndex
    slot: Slot
    value: Gwei
    execution_payment: Gwei
    blob_commitments: BlobCommitments
    execution_requests_root: Root
    inclusion_list_bits: InclusionListBits
```

`DataColumnSidecar` replaces its KZG proofs with authentication paths ordered by blob commitment:

```python
class DataColumnSidecar(Container):
    index: ColumnIndex
    column: DataColumn
    authentication_paths: AuthenticationPaths
    slot: Slot
    beacon_block_root: Root
```

#### Payload Binding

The builder MUST set `bid.blob_commitments` to the commitments returned with the execution payload, preserving transaction and blob order. The commitment count MUST NOT exceed the active baseline maximum blobs per block, and that count multiplied by `GAS_PER_BLOB` MUST NOT exceed the active maximum blob gas.

Consensus-layer Simple Serialize (SSZ) containers and networking limits retain the baseline scheduled maximum commitment count. Each commitment still represents one fixed-size blob; replacing authentication does not increase the permitted number of commitments. Existing schedule selection, custody and fork-digest rules remain unchanged.

When validating the execution payload, the consensus client MUST derive the Engine API `versionedHashes` list from `bid.blob_commitments` in order:

```python
versioned_hashes = [
    blob_commitment_to_versioned_hash(commitment)
    for commitment in bid.blob_commitments
]
```

The consensus client supplies this list in the `NewPayload` request. The execution client MUST validate it against the ordered blob commitments in the payload's signed transactions.

#### Data-Column Sidecars

For each commitment in `bid.blob_commitments`, a data-column sidecar contains the cell at `sidecar.index` and its `MerklePath` at the same list position. A sidecar therefore satisfies:

```python
def compute_root_from_path(
    cell: Cell,
    column_index: ColumnIndex,
    path: MerklePath,
) -> Bytes32:
    value = keccak256(cell)
    position = int(column_index)
    for sibling in path:
        if position % 2 == 0:
            value = keccak256(value + sibling)
        else:
            value = keccak256(sibling + value)
        position //= 2
    return value


def verify_data_column_sidecar(
    sidecar: DataColumnSidecar,
    blob_commitments: BlobCommitments,
) -> bool:
    if sidecar.index >= NUMBER_OF_COLUMNS:
        return False
    if len(sidecar.column) == 0:
        return False
    if len(sidecar.column) != len(blob_commitments):
        return False
    if len(sidecar.authentication_paths) != len(blob_commitments):
        return False

    for cell, path, commitment in zip(
        sidecar.column,
        sidecar.authentication_paths,
        blob_commitments,
    ):
        if (
            compute_root_from_path(cell, sidecar.index, path)
            != commitment
        ):
            return False

    return True
```

The `MerklePath` type enforces exactly `MERKLE_DEPTH` sibling hashes. The reconstruction-based path omission used by the execution-layer blobpool does not apply to `DataColumnSidecar`, because each sidecar contains only one cell from each blob.

Builders MUST construct one sidecar for each column index. Within every sidecar, cells and authentication paths MUST follow `bid.blob_commitments` order. Existing PeerDAS custody-group mapping, column-subnet mapping, sampling count, recovery threshold, gossip timing, retention, and request/response rules continue to apply.


#### Cell-Level Deltas

The [Gloas partial-column specification](https://github.com/ethereum/consensus-specs/blob/d2021d2719235f0df4726a1d330502cb15aa8ea3/specs/gloas/partial-columns/p2p-interface.md), referenced by [EIP-8136](./eip-8136.md), defines `CellsBitList`, `PartialDataColumnSidecar`, parts metadata, and group IDs. `CellsBitList` continues to contain one bit for each blob commitment in a column. `PartialDataColumnSidecar.kzg_proofs` is replaced with `authentication_paths`:

```python
class PartialDataColumnSidecar(Container):
    cells_present_bitmap: CellsBitList
    partial_column: DataColumn
    authentication_paths: AuthenticationPaths
```

The bitmap length MUST equal `len(bid.blob_commitments)`. Set bits select commitments in ascending blob index. The partial column and authentication-path list MUST both contain exactly one entry per set bit in that order.

```python
def verify_partial_data_column_sidecar(
    sidecar: PartialDataColumnSidecar,
    column_index: ColumnIndex,
    blob_commitments: BlobCommitments,
) -> bool:
    if column_index >= NUMBER_OF_COLUMNS:
        return False
    if len(sidecar.cells_present_bitmap) != len(blob_commitments):
        return False

    blob_indices = [
        blob_index
        for blob_index, present in enumerate(sidecar.cells_present_bitmap)
        if present
    ]
    if len(blob_indices) == 0:
        return False
    if len(sidecar.partial_column) != len(blob_indices):
        return False
    if len(sidecar.authentication_paths) != len(blob_indices):
        return False

    for blob_index, cell, path in zip(
        blob_indices,
        sidecar.partial_column,
        sidecar.authentication_paths,
    ):
        commitment = blob_commitments[blob_index]
        if (
            compute_root_from_path(cell, column_index, path)
            != commitment
        ):
            return False

    return True
```

Authentication paths remain required when every bitmap bit is set because the message contains one column, not every cell of each blob. The commitments are obtained from the execution payload bid associated with the partial-message group; they are not duplicated in a partial sidecar or header. EIP-8136's parts metadata, group ID, topic, partial-message negotiation, eager and pull behavior, and peer-scoring rules are unchanged.

### Fork Transition

At and after activation:

- [EIP-4844](./eip-4844.md) type-3 KZG transactions and legacy KZG blob-carrying frame transactions are invalid for inclusion;
- transaction pools MUST remove those ineligible transactions;
- blob-carrying [EIP-8141](./eip-8141.md) frame transactions MUST carry signed `BlobCommitment` values and declare `required_leanda_dependency(tx)`;
- a block MUST NOT mix KZG and post-quantum blobs; and
- data-column sidecars MUST use the Merkle authentication-path format defined by this EIP. KZG sidecars MUST be rejected for post-fork blocks.

The inherited `eth/72` through proposed `eth/75` protocols retain their KZG-era cell formats. Post-fork post-quantum blob announcements, blob-carrying dependency wrappers, and cell exchange require provisional `eth/76`. Clients MUST NOT send these announcements, wrappers, or cells on an older negotiated version. A peer negotiated on an older version may remain connected and exchange unaffected data. Negotiating `eth/76` does not activate post-quantum transaction validity before the fork; historical KZG data retains its original decoding rules.

`engine_getBlobsV4` retains its KZG response semantics. Consensus clients MUST use `engine_getBlobsV5` for post-quantum blobs. Fork-aware Engine API and consensus-layer decoding MUST NOT interpret one response or sidecar format as the other.

The [EIP-8136](./eip-8136.md) partial-message extension retains its bitmap and negotiation semantics, but it MUST NOT fall back to KZG authentication for post-fork data.


## Rationale

### Post-Quantum Commitments

Merkle commitments replace the elliptic-curve assumptions and trusted setup of KZG with hash-based authentication. The LeanDA guest proves the Reed–Solomon relation and correct commitment derivation, while `LEANDA_SCHEME` allows [EIP-8288](./eip-8288.md) to fold these proofs into its block aggregate.

### Public Input Binding

The LeanDA guest returns a Boolean indicating successful validation. The host derives the blob binding commitment and challenge seed from the transaction's signed commitments using distinct domain-separation prefixes, then decodes the two halves of the seed as `reed_solomon_challenges`. The guest independently derives the binding commitment from the private blobs, checks it against the public input, and returns `True` after validating each blob. Proof verification binds this successful result to the public input through `data_hash = keccak256(LEANDA_PUBLIC_INPUT_V1 + blob_binding_commitment + encode_rs_challenges(reed_solomon_challenges))`, tying the proven computation to the signed blob commitments and their derived challenges `reed_solomon_challenges`. The challenge pair is shared across the batch, while both Reed–Solomon checks must pass separately for each blob.

### Blob-Local Merkle Trees

Each Merkle tree commits to one blob rather than one block column. Anyone holding a blob can derive and seed any of its cells and authentication paths without waiting for the other blobs or their ordering to be finalized. A tree over a block column would make each path depend on that column's final blob set and ordering.

## Backwards Compatibility

Blob-gas pricing and block limits remain unchanged. The blob representation changes to the binary-field codeword specified here; equal nominal data capacity does not preserve EIP-4844 field serialization.

This EIP is a consensus-breaking change activated at a fork. Block, transaction, and sidecar decoding is selected by the fork under which the block was produced. Pre-fork blocks, type-3 transactions, KZG transaction wrappers, and KZG data-column sidecars remain valid under their original rules.

After activation, blob-carrying frame transactions, transaction pools, networking, Engine API calls, and sidecars use the post-quantum formats specified in Fork Transition. Historical KZG formats retain their pre-fork meaning and cannot be substituted for these formats.

Applications that submit blobs must migrate to EIP-8141 blob-carrying frame transactions with signed `BlobCommitment` values and a LeanDA dependency frame. The associated witness is verified through the [EIP-8288](./eip-8288.md) recursive aggregate.

## Test Cases

The following vectors use the fixed profile. Transaction counts are checked independently from the active block schedule.

| Input | Expected result |
| - | - |
| Codeword length `262144` | Valid size; 128 cells of 2048 bytes |
| Codeword lengths `0`, `2048`, `131072`, `262143`, `262145`, `524288` | Invalid size |
| One fixed-size commitment | `131072` blob gas |
| Six fixed-size commitments | `786432` blob gas; valid transaction count |
| Seven fixed-size commitments | Invalid transaction count |
| Cell lengths `2047` or `2049` | Invalid cell |

For any identical parent header and active baseline schedule, the expected blob base fee and excess blob gas are identical before and after substituting post-quantum commitments. This includes the EIP-7918 reserve-price branch and scheduled parameter boundaries. The parent's accumulated excess is preserved.

The proof and commitment test cases cover:

- Canonical ordered root-list encoding, its count prefix and commitment ordering.
- Distinct blob-binding and challenge-seed domains; the two ordered seed halves and their reuse across the batch.
- Guest rejection when private blobs do not match the public binding commitment, or when either membership check fails for any blob.
- Proof rejection when either public input differs from the expected digest, the public-input domain is omitted or changed, the inputs are hashed in the wrong order, or the guest result is not `True`.
- Merkle authentication, fixed-width deserialization and fork boundaries.

The sparse blobpool test cases cover:

- Shared-mask requests, where one `cell_mask` applies to every requested transaction, and indexed requests, where each transaction selects a mask from a canonical table.
- Request-ID and response-form matching, canonical mask tables/identifiers, per-transaction subsets, unrequested transactions and transaction/blob/cell ordering.
- Empty responses, indexed empty responses, zero masks with non-empty lists, mismatched list lengths and proof-wrapper-only propagation.
- Older-version rejection and different per-blob reconstruction thresholds within an indexed response.
- 63, 64, 65, 127 and 128 returned cells, including non-contiguous indices and multiple blobs.
- Missing paths below the recovery threshold, non-empty paths at or above it, failed reconstruction, inconsistent returned cells and reconstructed roots differing from signed commitments.

End-to-end LeanDA/EIP-8288 proof tests and benchmarks for generation, aggregation, validation and PeerDAS network roles remain activation requirements.

## Security Considerations

Challenge derivation relies on the heuristic that `x -> keccak256(LEANDA_CHALLENGE_V1 + x)` behaves as a random oracle, where `x` is the canonical encoding of the ordered blob commitment list. Decoding the first and second 16-byte halves of its output gives two independent uniform elements of `FieldElement` under this heuristic.

The STARK proves correct encoding and commitment derivation, not data availability. Availability continues to depend on PeerDAS custody, sampling, reconstruction, and networking assumptions.

Clients must bind each proof to the signed roots, enforce fixed-width deserialization and list bounds before allocating or hashing, and reject malformed authentication paths. Merkle authentication paths increase bandwidth and denial-of-service exposure relative to KZG proofs. Omitting paths for reconstructable blobpool responses trades authentication bandwidth for reconstruction work before the Merkle-root check can reject invalid data. Clients must bound this work using the fixed blob size and request/response limits.
