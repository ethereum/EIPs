## Abstract

This EIP defines when a builder may omit an [EIP-8141](./eip-8141.md) frame transaction that an inclusion list (IL) lists under [EIP-7805](./eip-7805.md). It builds on the `inclusion_list_bits` field of the execution payload bid. The bid already says which committee members' ILs the builder considered. This EIP adds three things. First, the payload envelope carries the signed ILs that an omission relies on (witnesses), and the bid commits to them. Second, a node counts a witness only if it accepted at least one IL from the same member before a fixed deadline. Third, each omitted transaction is judged at its own check point, which every node derives from the block access list: the state just before the first block transaction that writes its validation state and is not in a counted witness. The builder commits no index or claim. The EIP also adds per-transaction and per-IL gas caps for IL transactions. If `inclusion_list_bits` is removed from the bid, the mechanism keeps working without it.

## Motivation

EIP-7805 checks an omitted transaction at the end of the payload. That check is cheap and complete when validity depends only on nonce and balance. Frame transaction validity can also depend on keyed nonces, payer state, low storage slots of the sender and payer, and the code of accounts that validation reaches. Another transaction in the block can change that state. Two IL transactions that share a payer can make each other invalid, so the end-of-payload check can call an honest block non-compliant or let a builder excuse an omission with a transaction of its choosing.

[EIP-8369](./eip-8369.md) defines a validation surface (Profile 2) and a per-IL `VERIFY` budget for frame transactions. It evaluates an omitted transaction at an index that the builder claims. A claimed index lets any transaction before it, IL-listed or not, excuse the omission, and it needs a claims field, a bound on claims, and a way to carry claims to the execution layer. EIP-8369 is Informational and leaves the binding rules to an enforcing EIP.

The Heze consensus specification already has a per-member commitment in the bid: [`inclusion_list_bits`](https://github.com/ethereum/consensus-specs/blob/e3e2d0128458c2f56092bd459d3c5a85cdf80fcd/specs/heze/inclusion-list.md). A bid is ignored on gossip unless its bits cover every timely, non-equivocating IL that the node has seen (`is_inclusion_list_bits_inclusive`). The bits say which members the builder heard from. They do not carry IL content, so a node cannot tell from the block which transactions were IL-listed in the builder's view. They do not fix a state at which an omitted transaction is judged.

This EIP removes the claimed index and extends the bits with IL content. The evaluation state follows from the block: a write by a transaction in a counted witness can excuse an omission, a write by any other transaction cannot.

### Definitions

- Slot `N` is the slot of the ILs. Slot `N+1` is the slot of the bid and payload.
- An *occurrence* is one transaction entry in one IL.
- `tx_gas(tx)` is `max_gas` as defined in EIP-8141 for a frame transaction, and the signed gas limit otherwise.
- *IL members* are the slot `N` IL committee members that are not known equivocators in the node's frozen EIP-7805 IL view and are not proven equivocators by the envelope (see [Witnesses](#witnesses)). *IL occurrences* are the occurrences in the frozen-view ILs of IL members, in committee order and then IL order.
- An *enforced* transaction is a transaction with at least one *admitted* IL occurrence under the fill below. Transactions are identified by exact [EIP-2718](./eip-2718.md) envelope bytes.
- A *Profile 1* transaction is a legacy, [EIP-2930](./eip-2930.md), [EIP-1559](./eip-1559.md) or [EIP-7702](./eip-7702.md) transaction.
- A *Profile 2 candidate* is an EIP-8141 frame transaction that, from the transaction alone: is statically valid under EIP-8141; has an empty `blob_versioned_hashes` list; ignoring the optional expiry verifier frame and an optional [EIP-8272](./eip-8272.md) recent root verifier frame at the position EIP-8272 allows, matches one of the prefix shapes `self_verify`, `deploy | self_verify`, `only_verify | pay` or `deploy | only_verify | pay` by modes, flags and targets; has no frame in the validation prefix with `ATOMIC_BATCH_FLAG` set; and has no frame after the validation prefix with mode `VERIFY`.
- [EIP-4844](./eip-4844.md) transactions and frame transactions with a non-empty `blob_versioned_hashes` list are neither. Their omission is always justified.

### Fee validity

For a frame transaction, `fee_valid(tx, block)` holds if and only if `tx.fees.max_fee >= required_max_fee`, with `required_max_fee` computed as in EIP-8141 at the block's base fee and blob base fee. For any other transaction, `fee_valid` is the EIP-8369 fee rule.

### Profile 2 eligibility

`is_profile2_eligible(T, S)` holds if and only if, on state `S`, `T` passes every EIP-8141 and [EIP-8250](./eip-8250.md) nonce and keyed nonce check made before the first frame, and a replay of the validation prefix of `T` meets all of the following:

1. The prefix follows the EIP-8141 validation trace rules, except that item 3 replaces the EIP-8141 storage read rule, and the EIP-8272 recent root verifier frame keeps its `SLOTNUM` and `SLOAD` permissions. The EIP-8141 public mempool `MAX_VERIFY_GAS` limit and other mempool-only policies do not apply; replay gas is bounded by `MAX_VERIFY_GAS_PER_TX` as below. The prefix is the frames up to and including the first frame whose `APPROVE` sets the payer.
2. If present, the first non-expiry frame is a deploy frame that installs code or an EIP-7702 delegation indicator at `T.sender`.
3. The prefix reads state only from the Profile 2 surface: `nonce`, `balance` and code of `T.sender` and of the payer; storage slots `0` to `AA_VOPS_SLOT_COUNT - 1` of `T.sender` and of the payer; the EIP-8250 `NONCE_MANAGER` entries for `(T.sender, key)` for every nonzero key in `T.nonce_keys`; the EIP-8272 `RECENT_ROOT_ADDRESS` storage keys derived from the tuples of the recent root verifier frame of `T`; and the code of any other account that the prefix calls or delegates to.
4. The total size of distinct code bodies the prefix loads is at most `MAX_VERIFY_CODE_BYTES`.
5. The recent root verifier frame of `T`, if present, succeeds.
6. The prefix succeeds and sets the payer through `APPROVE_PAYMENT` or `APPROVE_EXECUTION_AND_PAYMENT`, and the payer can pay `max_cost` as defined in EIP-8141.

The payer is `T.sender` for the `self_verify` shapes and the EIP-8141 `resolved_target` of the `pay` frame otherwise.

Replay uses the fork rules, timestamp, base fee and blob base fee of the block, `current_slot` from the block's [EIP-7843](./eip-7843.md) `slotNumber` field, and a warm set holding only the addresses and keys that EIP-8141 warms at transaction start. Gas used by replay counts against `MAX_VERIFY_GAS_PER_TX`. A replay that exceeds it fails.

### Admission fill

Each node runs this fill over IL occurrences, independently per IL, before deduplication. Each IL starts with `MAX_GAS_PER_IL` gas and `MAX_VERIFY_GAS_PER_IL` `VERIFY` gas. For each occurrence, in IL order:

1. If the bytes do not decode to a valid transaction, skip it. Nothing is deducted.
2. If `tx_gas(tx) > MAX_GAS_PER_IL_TX` or `tx_gas(tx)` exceeds the gas left in the IL, skip it. Nothing is deducted.
3. If `tx` is a Profile 2 candidate, run the EIP-8369 static `VERIFY` budget fill step for this occurrence: compute signature and prefix cost, skip with no debit if their sum exceeds `MAX_VERIFY_GAS_PER_TX` or the `VERIFY` gas left, deduct the signature cost, verify signatures, and deduct the prefix cost only if the signatures pass. If the signatures fail, skip it and keep only the `VERIFY` debits made so far.
4. If `tx` is neither a Profile 1 transaction nor a Profile 2 candidate, skip it. Nothing is deducted.
5. Otherwise the occurrence is admitted. Deduct `tx_gas(tx)` from the IL gas.

Includers SHOULD NOT build an IL in which the total `tx_gas` of all listed transactions exceeds `MAX_GAS_PER_IL`, or which lists a transaction with `tx_gas` above `MAX_GAS_PER_IL_TX`.

### Witnesses

The [EIP-7732](./eip-7732.md) `ExecutionPayloadEnvelope` for slot `N+1` gains one field, and `ExecutionPayloadBid` gains its root:

```python
# ExecutionPayloadEnvelope
inclusion_list_witnesses: List[SignedInclusionList, MAX_IL_WITNESSES]
# ExecutionPayloadBid
inclusion_list_witnesses_root: Root
```

An envelope is invalid if `hash_tree_root(envelope.inclusion_list_witnesses)` differs from the bid's `inclusion_list_witnesses_root`.

A carried `SignedInclusionList` `w` is valid if all of the following hold: `w.message.slot == N`; `w.message.dependent_root` is the shuffling dependent root of slot `N` on the chain of the bid's `parent_block_root`; `w.message.validator_index` is in the slot `N` IL committee; `is_valid_inclusion_list_signature` holds for `w`; and `w` meets the size limits of the IL gossip rules. An envelope is invalid if it carries an invalid witness, two witnesses with the same `hash_tree_root`, or more than two witnesses with the same `validator_index`. Equivocation does not make a witness invalid. If the envelope carries two witnesses with the same `validator_index`, that member is a *proven equivocator* for every node: neither witness counts, and the member's ILs create no obligations.

### Relation to inclusion list bits

This section applies while `ExecutionPayloadBid` has the `inclusion_list_bits` field.

1. **Bid binding.** Let `i` be the committee position of `w.message.validator_index`. An envelope is invalid if it carries a witness `w` with `bid.inclusion_list_bits[i] == 0`, unless it carries two witnesses from that validator index with different `hash_tree_root`. The exception covers an equivocating member, whose bit the builder leaves unset because `get_inclusion_list_bits` skips equivocators; the two witnesses are the proof of equivocation.
2. **Counting bits.** Each node computes `witness_bits`, one bit per slot `N` committee member. Bit `i` is set if the node's IL store holds a valid `SignedInclusionList` from committee member `i` for slot `N` and the dependent root, or lists that member as an equivocator. This is `get_inclusion_list_bits` with `only_timely=False` and without the equivocator filter. The node evaluates it on its store as of the slot `N+1` attestation deadline. ILs that arrive after that deadline do not set bits. Acceptance over gossip and over the EIP-7805 by-index request both count. A node MUST validate an IL received over the by-index request with the IL gossip rules, and MUST forward it on the IL gossip topic if it accepts it.
3. **Counted witness.** A carried witness counts for a node if it is valid, its member is not a proven equivocator, and the node's `witness_bits` bit for its validator index is set. Block transaction `i` is *witnessed* for that node if its exact EIP-2718 envelope bytes equal a transaction in a witness that counts.

The existing gossip check `is_inclusion_list_bits_inclusive` makes sure the bid covers every member that the node saw in time. The counting bits make sure, per witnessed member, that the node saw that member at all. The two checks run in opposite directions and do not replace each other.

### If inclusion list bits are removed

If `ExecutionPayloadBid` has no `inclusion_list_bits` field, the bid binding in item 1 above does not apply. Items 2 and 3 apply unchanged: the counting bits are computed from the node's own IL store and do not depend on any bid field. The bid commits to the witnesses only through `inclusion_list_witnesses_root`, and the envelope carries the signed ILs. The gossip filter `is_inclusion_list_bits_inclusive` goes away with the bits, so a bid that ignored timely ILs is no longer dropped on gossip; such a payload is caught only by the omission check after the envelope is revealed. The omission rules of this EIP do not change.

Consensus-specs pull request 5772 (an open draft as of 2026-11-12, not part of the Heze specification; [branch file](https://github.com/ethereum/consensus-specs/blob/c4cf93f1ea5ef1e56a2397b32bf0570106154c87/specs/heze/beacon-chain.md)) passes ILs to the execution layer, keeps `inclusion_list_bits`, and adds an IL exemption list. If that exemption list is adopted, this EIP replaces it. `inclusion_list_witnesses` takes the place of `inclusion_list_exemptions` in the envelope, and `inclusion_list_witnesses_root` takes the place of `inclusion_list_exemptions_root` in the bid.

### State at an index

Let `n` be the number of transactions in the payload. Let `S_k`, for `0 <= k <= n`, be the parent state with the [EIP-7928](./eip-7928.md) block access list changes at indices `0` through `k` applied. Index `0` holds pre-execution system updates.

For a Profile 2 candidate `T`, with the payer as determined by the replay of `T` on `S_0`, `R(T)` is this set of state keys, whether or not that replay reads them:

- `nonce`, `balance` and code of `T.sender` and of the payer;
- storage slots `0` to `AA_VOPS_SLOT_COUNT - 1` of `T.sender` and of the payer;
- the `NONCE_MANAGER` entries for `(T.sender, key)` for every nonzero key in `T.nonce_keys`;
- the `RECENT_ROOT_ADDRESS` storage keys derived from the tuples of the recent root verifier frame of `T`;
- the code of every other account whose code the replay on `S_0` loads, delegated target code included.

Transaction `i` writes `R(T)` if the block access list records, at index `i`, a change to a key in `R(T)`. The *check point* `k*(T)` is the lowest `i` in `[1, n]` such that transaction `i` writes `R(T)` and is not witnessed, or `n+1` if no such `i` exists.

### Omission rule

Omission of a Profile 1 transaction is judged as in EIP-7805, at the end of the payload, with the obligation restricted to enforced transactions.

Omission of an enforced Profile 2 candidate `T` is unjustified if and only if all of the following hold:

1. `fee_valid(T, block)`;
2. `is_profile2_eligible(T, S_0)`;
3. `is_profile2_eligible(T, S_(k*(T)-1))`, and the replay on `S_(k*(T)-1)` reads no state key outside `R(T)`;
4. `T` fits the remaining block capacity after the payload in each gas dimension, per the EIP-8141 inclusion check.

A payload with an unjustified omission does not satisfy the IL conditions of EIP-7805. A node that lacks state or code it needs MUST obtain authenticated data before it decides. Missing local data does not justify an omission.

### Fork choice

The node runs the omission check at the later of envelope verification in `on_execution_payload_envelope` and the slot `N+1` attestation deadline at which `witness_bits` stops. Until then the payload's IL satisfaction is pending and does not affect fork choice. As in EIP-7805, the result does not affect payload validity: the payload is imported and its `FULL` node is added as usual. The node records the result with `record_payload_inclusion_list_satisfaction`. If the result is false, the node MUST NOT apply the `FULL` tiebreak to that node, MUST NOT select it as head for its slot `N+2` duties, and as proposer MUST NOT build on it. Later descendants of it are imported normally.

### Execution layer interface

This EIP adds a new `engine_newPayload` version. It takes the parameters of the version in force at activation plus:

- `inclusionLists`: `Array of Array of DATA`, one entry per IL member in committee order, each holding the transaction bytes of that member's IL in IL order;
- `witnessedTransactions`: `Array of DATA`, the transaction bytes in witnesses that count for this node.

`inclusionLists` has the per-IL shape proposed in execution-apis pull request 960 (an open draft as of 2026-11-12). The consensus layer MAY call the previous `engine_newPayload` version for payload validity as soon as the envelope arrives. It calls the new version, with the same payload, once the envelope is verified and `witness_bits` is frozen. An execution layer that already validated the payload reuses that result. The execution layer first validates the payload as before. If the payload is `VALID`, it runs the admission fill, computes `k*(T)` from the block access list, applies the omission rule, and returns `INCLUSION_LIST_UNSATISFIED` instead of `VALID` if any omission is unjustified. The payload stays valid. The inputs are fixed once the node's IL view and `witness_bits` are frozen, so the result is final for that node and the consensus layer does not retry.

### Honest builder

A builder MUST carry only ILs that it accepted from the IL gossip topic, or from the by-index request and forwarded as required in [Relation to inclusion list bits](#relation-to-inclusion-list-bits), at or before its EIP-7805 builder freeze (slot `N`, `t=11s`). As the only exception, a builder MAY carry a second IL from a member, accepted after the freeze and before the bid, to prove that member's equivocation; the builder then treats that member's transactions as not witnessed when it builds. A builder SHOULD carry only the ILs that an omission relies on. While the bid has `inclusion_list_bits`, a builder MUST set it as in the Heze builder guide; this sets the bit of every non-equivocating member whose IL it carries.

## Rationale

### What this EIP adds to inclusion list bits

| | `inclusion_list_bits` (Heze) | This EIP |
|---|---|---|
| Content in the block | One bit per member | Signed ILs the omission relies on, committed by root in the bid |
| Who sets it | The builder | The builder carries ILs; each node sets its own `witness_bits` |
| Check direction | Bid covers every timely IL the node saw | Node saw every member the block relies on |
| Use in the omission check | None | Defines which writers are witnessed |
| Evaluation state | End of payload | Per-transaction check point `k*(T)` |

EIP-8369 and the exemptions of consensus-specs pull request 5772 already judge an omission at a per-transaction index, but the builder claims that index. The genuinely new parts are a check point `k*(T)` that every node derives from the block access list and the witnessed status of writers, with nothing claimed, and the counting rule (a witness counts only if the node holds any IL from the same member by the slot `N+1` attestation deadline). Carrying signed ILs, gas caps and the `VERIFY` budget come from earlier work, listed below.

### Prior work

- Proposer-carried aggregate IL: the original FOCIL post by Thomas Thiery (soispoke) and co-authors (ethresear.ch topic 19870) had the proposer aggregate the local ILs into its block. EIP-7805 dropped the aggregate; attesters check against their own IL view. This EIP brings back carried ILs only as witnesses, only the ones an omission relies on.
- IL transaction invalidation: Julian Ma, "Transaction Invalidation", FOCIL site, September 2024, describes how a builder can invalidate an IL transaction with an earlier block transaction. This EIP limits which earlier transactions can do so.
- Claims by index and the `VERIFY` budget: Thomas Thiery (soispoke), "FOCIL and Native Account Abstraction", Ethereum Magicians topic 27999, March 2026, proposed the per-IL `VERIFY` budget and index-based validation. EIP-8369 specifies both. This EIP keeps the budget and replaces the claimed index with the check point.
- Per-IL and per-IL-transaction gas caps: proposed by vlad and Thomas Thiery (soispoke) in the consensus-dev channel of the Eth R&D Discord (not publicly archived). This EIP applies them in the admission fill.
- Node-derived evaluation index: chugarchugarr, in the EIP-8369 Ethereum Magicians topic 29298 (September 2026), proposed that nodes evaluate position-stable transactions at the end of the payload and keep the claimed index for the rest, and named the condition that removes the claim: a transaction invalid at an earlier index stays invalid at the end. This EIP derives the index for every Profile 2 transaction from the block access list instead of classifying transactions.
- Passing ILs to the execution layer: Jihoon Song, consensus-specs pull request 5772 and execution-apis pull request 960 (both open drafts), building on execution-apis pull request 911 by Marc Harvey-Hill (Marchhill). The `inclusionLists` parameter follows that shape.

### Witnesses instead of a claimed index

With a claimed index, any transaction before the index can excuse an omission, including a builder transaction that was never public. The exemption list of consensus-specs pull request 5772 names a transaction hash and index, so it is a claimed index. Here only an unwitnessed writer sets the evaluation state, and its writes do not excuse the omission. A witnessed writer was signed by a committee member, and the block carries the signature.

### Why carry the IL in the block

A rule like "a writer counts if its hash is in any IL the node stored" depends on each node's IL view, and the views differ. A node that missed one IL would see a shorter excused set and could reject an honest block. A witness carried in the block makes the evaluation a function of the block. The only node-local input is `witness_bits`. The bid commits to the witnesses, so a builder cannot send different witness sets to different nodes for one bid. `inclusion_list_bits` alone cannot play this role, because it has no transaction content.

### Why the mechanism does not depend on the bits

At FOCIL breakout 45 (2026-10-27), with ILs passed to the execution layer as proposed in consensus-specs pull request 5772, Nico Flaig noted that `inclusion_list_bits` can then be dropped from the payload attributes event. If the bits leave the bid as well, this EIP loses the bid binding, and the network loses the gossip filter `is_inclusion_list_bits_inclusive`. The omission check still works: the counting bits are node-local and the witnesses are committed by their own root. A bid that ignored timely ILs is then caught after the envelope reveal instead of on bid gossip.

### Why "any IL from the member" and not "this IL"

EIP-7805 nodes forward at most two ILs per member. A member can send IL `a` only to the builder's peers and two other ILs to the rest of the network, so part of the network never receives `a`. If the rule required the exact IL, those nodes would reject the honest block. Every node accepts and forwards the first valid IL it receives from a member. So once the builder's node accepted `a`, every connected node ends up holding `a` or two other ILs from that member, and the bit is set either way.

### Per-transaction check point

A single prefix of IL transactions at the top of the block would force the builder to place IL transactions first whenever two of them conflict. A cheap pair of conflicting transactions sent to two includers would then cost the builder the top of the block in every slot. With a per-transaction check point, a top-of-block transaction that does not write `R(T)` does not change the state at which `T` is judged.

### Validity at the parent state

Condition 2 excuses a transaction that becomes valid only through writes inside the block. Without it, each included IL transaction could make an earlier rejected one valid, and the builder would need a repeated append loop over IL transactions. With it, a builder rechecks only candidates whose `R(T)` keys a new transaction writes. The cost of this builder loop is UNMEASURED. A node runs at most two replays per omitted transaction.

### Static surface and reads outside R(T)

`R(T)` holds the whole sender and payer surface, not only the keys the `S_0` replay reads. Otherwise an unwitnessed writer could set a slot that the replay does not read at `S_0`, and a witnessed writer could then turn on a branch that reads it. A witnessed writer can also redirect validation to an account whose code the `S_0` replay did not load. Condition 3 treats a replay that reads outside `R(T)` as not eligible, so a write outside `R(T)` can only make the rule more lenient.

### Gas caps

The `VERIFY` budget bounds validation work. It does not bound the execution of an included IL transaction, which only the per-transaction gas cap bounds. An includer can list transactions that are expensive to simulate and slow down builders that must include them. The per-transaction and per-IL gas caps bound that work. The IL byte limit does not bound gas. Gas is deducted only for admitted occurrences, so a rejected occurrence cannot use up the IL's gas.

### Execution layer complexity

The closest client data point is a draft Nethermind pull request (13590, head `0db03f67`) that implements EIP-8369 with a claimed index and the per-IL `VERIFY` budget. It is not an implementation of this EIP. Its diff is 4,776 added and 3,061 removed lines in 116 files; outside test projects, 2,056 added and 965 removed lines in 75 files. The largest new parts are the eligibility replay over block access list state (239 lines), the inclusion check (168 lines), the `VERIFY` budget fill and Profile 2 rules (162 and 144 lines), and validation tracing (102 lines). Line counts are from the pull request diff on 2026-11-12.

Against that implementation, this EIP removes the claim field and its plumbing, and adds: witness bytes as an `engine_newPayload` input, the `k*(T)` scan over block access list indices, a second replay per omitted transaction, and the gas caps in the fill. Replay time, fill time and the added cost to the payload validation deadline are UNMEASURED.

### Witness encoding

This EIP carries full `SignedInclusionList` objects. A compact form (IL header, signature, transaction count and an SSZ branch per witnessed transaction) is smaller when the builder relies on few transactions from an IL. Which encoding to use is open.

## Backwards Compatibility

This EIP changes consensus rules and requires a network upgrade. It adds a field to the execution payload envelope and to the bid, extends `engine_newPayload`, and changes the EIP-7805 omission check. For Profile 1 transactions, the only change is that omission of a transaction with no admitted occurrence under the gas caps is justified. Blob-carrying transactions are not enforced.

## Test Cases

Required vectors:

- two IL transactions sharing a payer, where the builder includes one and omits the other;
- an unlisted top-of-block transaction that does not write the omitted transaction's state;
- an unlisted transaction that drains a payer before an omitted transaction;
- an unlisted relayer transaction that carries an EIP-7702 authorization writing the sender's code;
- an unlisted transaction that changes the delegation of a verifier account that the sender's code calls;
- a funding chain where each IL transaction funds the payer of the previous one;
- a member that sends one IL to the builder's peers and two other ILs to the rest of the network;
- an IL where an occurrence above `MAX_GAS_PER_IL_TX` precedes an occurrence that fits;
- an envelope whose witnesses do not match `inclusion_list_witnesses_root`;
- a witness from a member whose bit in `inclusion_list_bits` is unset, with and without a second witness proving equivocation;
- the same block judged by a node whose `witness_bits` lacks the witnessed member;
- a bid without `inclusion_list_bits`.

## Security Considerations

### Colluding committee member

A builder colluding with one of the 16 committee members can get an arbitrary transaction `X` into a signed IL. `X` then excuses omissions of every transaction that shares state with it, for example through a key rotation or a payer drain. This holds for claimed-index designs as well. Here `X` must be signed and carried in the block. The honest-builder rule cannot be checked by other nodes, so a colluding pair can choose `X` until the bid is signed, around slot `N+1` `t=0`, about 3 seconds after the EIP-7805 view freeze. `X` need not have been seen by other nodes before their view freeze. If the member also published a different IL, a builder that carries both makes the member a proven equivocator, and neither witness counts. A builder that carries only `X` leaves the block and the other IL as proof of equivocation. Includers SHOULD limit the number of transactions per sender and per payer in one IL. Closing this window fully needs an IL commitment duty before the freeze, or slashing on equivocation proof, both outside EIP-7805.

### Nodes cut off from the IL topic

A node that accepted no IL from a member before the slot `N+1` attestation deadline does not count that member's witnesses. It can then reject a payload from an honest builder. Under EIP-7805, missing an IL only makes a node more lenient. Here it can make it stricter. Between the builder freeze (slot `N`, `t=11s`) and that deadline (`t=3s` under EIP-7732) there are about 4 seconds; the node must receive no IL gossip and no by-index response for that member in the whole IL window, which needs an outage or an eclipse. How often this happens is not measured.

### Enshrined proposer-builder separation

Under EIP-7732, the payload is revealed after slot `N+1` attestations, and the check runs on envelope verification. A payload that fails the check stays valid but gets no `FULL` tiebreak and is not built on by honest nodes. Because the check uses node-local inputs, it never makes a payload invalid. Otherwise a node with a missed bit could reject a chain that freshly synced nodes accept. The next proposer and the slot `N+2` attesters need to finish the check, replay included, before their deadlines. The time for this is not measured.

### Execution cost

`MAX_GAS_PER_IL_TX` and `MAX_GAS_PER_IL` are not set. Until they are, an includer can list transactions that are expensive to simulate. Node replay is at most two replays per omitted transaction, at most `2 * INCLUSION_LIST_COMMITTEE_SIZE * MAX_VERIFY_GAS_PER_IL` `VERIFY` gas per slot, excluding state reconstruction and code loading. The wall time of one replay is not measured.

### Witness size

The Heze IL gossip rules, which every witness must meet, reject an IL whose transactions exceed `MAX_TRANSACTIONS_BYTES_PER_INCLUSION_LIST` = 8,192 bytes or contain an empty transaction (consensus-specs Heze p2p interface). `MAX_IL_WITNESSES` witnesses therefore carry at most `MAX_IL_WITNESSES * 8,192` = 262,144 bytes of transaction bytes, and one witness per member, for 16 members, at most 131,072 bytes. The SSZ overhead of one witness with `n` transactions is 152 bytes of fixed fields and signature, plus 4 bytes of offset per transaction, plus 4 bytes for its offset in `inclusion_list_witnesses`. Because each transaction is at least 1 byte, `n` is at most 8,192, and one witness is at most `MAX_SIGNED_INCLUSION_LIST_SIZE` = 41,112 bytes. The loose ceiling for the list is `MAX_IL_WITNESSES * (41,112 + 4)` = 1,315,712 bytes, which a witness reaches only with 1-byte transactions. If every transaction is at least 100 bytes, `n` is at most 81 and the overhead is at most 480 bytes per witness. The typical witness size is UNMEASURED. The builder pays for the extra bytes.

### Node-local bits

`witness_bits` is local. A syncing node cannot recheck it, in the same way as the EIP-7805 frozen IL view.

### Profile 1 transactions with delegation

Profile 1 omissions are still judged at the end of the payload. An unlisted builder transaction can drain the balance of an EIP-7702 delegated sender through its code and so excuse the omission, the invalidation case of the Motivation. This EIP does not close that case for Profile 1. Applying `k*(T)` to Profile 1 senders with a delegation indicator at `S_0` would close it and is left open.

### Fee bumps

A transaction that replaces an IL transaction with the same keyed nonce after the view freeze is not listed. It does not excuse the listed transaction, so the builder includes the listed version.
