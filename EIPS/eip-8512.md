## Abstract

This EIP modifies the 'eth' peer-to-peer (p2p) protocol to support the block-level dependency proofs of [EIP-8288](./eip-8288.md). It adds two new messages, `GetDependencyProofs` (0x16) and `DependencyProofs` (0x17), enabling peers to request and serve proofs for synchronization.

## Motivation

[EIP-8288](./eip-8288.md) requires every block to carry a dependency proof, currently a recursive Scalable Transparent ARgument of Knowledge (STARK), that proves the validity of all dependencies declared by its transactions. The proof is not part of the block header or the block body. The header carries only a 32-byte commitment to it, `dependency_proof_hash`, and the proof itself travels in the `ExecutionPayload`.

Because the proof is in neither the header nor the body, `GetBlockBodies` cannot serve it, and the Engine API payload body methods reach only the local consensus layer. A node that validates a block by re-execution must verify its proof, so a syncing node needs a way to obtain proofs from peers. This EIP adds that wire protocol support.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

### Protocol Version

This EIP defines `eth/74`, which extends `eth/73` as defined in [EIP-8408](./eip-8408.md) with two new messages. All earlier messages and their semantics are unchanged. Messages are written in the notation of the [`eth` wire protocol specification](https://github.com/ethereum/devp2p/blob/2c19a28b25c29487773ad6b07243e290fa8d65ec/caps/eth.md), where `P` is a positive integer, `B` a byte string and `B_32` a 32-byte byte string.

This EIP uses message IDs 0x16 and 0x17, the next free IDs after `Cells` (0x15).

### Block Header

`BlockHeaders` messages carry the two header fields added by [EIP-8288](./eip-8288.md), at the position EIP-8288 defines. In wire notation, `dependency-proof-hash` is EIP-8288's `dependency_proof_hash` and `block-deps-hash` is its `block_deps_hash`:

```
block-header = [
    ...
    dependency-proof-hash: B_32,
    block-deps-hash: B_32,
]
```

The `dependency-proof-hash` field contains `keccak256(dependency-proof)` and the `block-deps-hash` field contains `get_deps_hash(dependencies(block))`. These fields MUST be present in headers after EIP-8288 activation and absent for earlier blocks.

### Dependency Proof Encoding

A dependency proof is transmitted as the serialized proof byte string defined in [EIP-8288](./eip-8288.md):

```
dependency-proof: B
```

A block without dependencies has an empty `dependency-proof`.

### New Protocol Messages

#### GetDependencyProofs (0x16)

```
[request-id: P, [blockhash₁: B_32, blockhash₂: B_32, ...]]
```

Request dependency proofs for the given block hashes. The number of proofs that can be requested in a single message is subject to implementation-defined limits.

A peer serves the proofs it holds. Proofs exist only for blocks after [EIP-8288](./eip-8288.md) activation, and EIP-8288 sets the minimum period for which they are retained. For a requested block whose proof the peer does not hold, it returns an empty entry.

#### DependencyProofs (0x17)

```
[request-id: P, [dependency-proof₁, dependency-proof₂, ...]]
```

Response to `GetDependencyProofs`. The *i*-th element corresponds to the *i*-th block hash of the request. The Recursive Length Prefix (RLP) empty string (`0x80`) is returned for blocks where the proof is unavailable.

A response MAY contain fewer elements than the request had hashes. It then covers a prefix of the request, and the requester treats the remaining hashes as not served, not as unavailable, and MAY request them again.

A block without dependencies has an empty proof, which also encodes as `0x80`. The receiver tells the two cases apart by the block header: `dependency-proof-hash` equals `keccak256` of the empty byte string only for a block without dependencies.

The RECOMMENDED soft limit for `DependencyProofs` responses is 2 MiB. The soft limit governs when a peer stops appending elements. A response that contains a single proof larger than 2 MiB is valid.

Implementations SHOULD rate limit `GetDependencyProofs` requests per peer.

### Validation

When a dependency proof is received, clients MUST validate it by computing `keccak256(dependency-proof)` and comparing against the `dependency-proof-hash` in the corresponding block header. Verifying the proof against `block-deps-hash` is part of block validation under [EIP-8288](./eip-8288.md) and is not required at the wire protocol level.

An empty entry for a block whose `dependency-proof-hash` is not the hash of the empty byte string does not match, but it signals that the proof is unavailable, not that it is invalid. Clients MUST NOT treat such an entry as an invalid response and SHOULD request the proof from another peer.

A response is invalid if it contains more elements than the request had hashes, or a non-empty entry that is larger than EIP-8288's `MAX_DEPENDENCY_PROOF_BYTES` or does not match the header. Clients MAY check the size before hashing. Clients MUST discard an invalid response and SHOULD disconnect the peer that sent it.

## Rationale

### Separate Messages vs. Block Body Extension

Proofs are transmitted via dedicated messages rather than extending block bodies because:

1. **Size**: A dependency proof is hundreds of kilobytes. Block bodies already grow with the gas limit, and keeping the proof out of them keeps `BlockBodies` responses and the RLP block size independent of proof size.
2. **Optional retrieval**: A node that trusts finality for a block does not need its proof. It can sync headers and bodies for finalized blocks without downloading proofs.
3. **Retention policy**: Proofs may be pruned per [EIP-8288](./eip-8288.md), while block bodies are retained longer.

This follows the same split as block access lists ([EIP-8159](./eip-8159.md)), which are also served by their own messages rather than through block bodies.

### Message IDs

[EIP-8408](./eip-8408.md) keeps the `GetCells` (0x14) and `Cells` (0x15) message IDs in `eth/73`. This EIP takes the next two IDs, 0x16 and 0x17, so message IDs stay sequential across protocol versions.

### Response Size Limit

The 2 MiB soft limit is consistent with other eth protocol responses (blocks, receipts, headers) and accommodates several proofs per response. A single proof over the soft limit is still served, so that no proof becomes unretrievable because of its size.

## Backwards Compatibility

This EIP changes the eth protocol and requires rolling out a new version, `eth/74`. `eth/74` may be negotiated before [EIP-8288](./eip-8288.md) activates. Until then no proofs exist, and peers answer `GetDependencyProofs` with empty entries. Supporting multiple protocol versions is standard practice. Rolling out `eth/74` does not break older clients, as they can continue using earlier versions.

This EIP requires the hard fork that activates [EIP-8288](./eip-8288.md) for the header field extension. The new messages are only meaningful for blocks after that fork.

## Security Considerations

### Validation Cost

Validating a received proof against the header requires one keccak256 over a few hundred kilobytes, which is negligible. EIP-8288's size limit bounds this cost, and clients can reject an oversized entry before hashing it. Verifying the proof against `block-deps-hash` is more expensive and is governed by the block validity rules of [EIP-8288](./eip-8288.md), not by this protocol.

### Amplification

A `GetDependencyProofs` request can trigger responses much larger than the request, since each requested hash can return a proof of hundreds of kilobytes. Rate limiting and the soft response size limit keep this in check.

### Unavailable Data

A peer returning empty entries for available blocks may be misbehaving, but it could also have pruned the data legitimately. For this reason an empty entry is not treated as an invalid response.
