## Abstract

Charge every user-controlled byte in a transaction (calldata, access-list entries, [EIP-7702](./eip-7702.md) auths, [EIP-4844](./eip-4844.md) blob hashes, and [EIP-8141](./eip-8141.md) frames and signatures) at a flat 64 gas at the floor, counting each entry at its encoded size. One rule replaces [EIP-7623](./eip-7623.md)/[EIP-7976](./eip-7976.md) and [EIP-7981](./eip-7981.md) and closes the auth and blob hash floor gaps. Worst-case user-controlled tx content per block is bounded by `block_gas_limit / 64 ≈ 0.94 MB` at a 60M gas limit, a hard cap that shrinks worst-case blocks at an unchanged gas limit. Fewer than 4% of mainnet transactions hit the new floor.

## Motivation

Every node must be able to handle the largest block an attacker can build, not the average one. Lowering that worst case buys headroom, which can either be spent on throughput by raising the gas limit or kept as a buffer. Left unspent, it is a direct gain in robustness. [EIP-7623](./eip-7623.md) introduced a floor cost on calldata bytes to cap worst-case block size. [EIP-7976](./eip-7976.md) raised that floor to a uniform 64 gas per calldata byte, zero and non-zero alike (by treating every byte as 4 floor tokens at 16 gas each). [EIP-7981](./eip-7981.md) extended the same 64 gas/B rate to access-list bytes via a flat data-cost surcharge of 1,280 gas per address and 2,048 gas per storage key. The principle is consistent across both: every user-controlled content byte priced at 64 gas at the floor.

[EIP-7702](./eip-7702.md) authorization tuples (92 B with chain ID 0 or 1 and a small nonce, up to 133 B) and [EIP-4844](./eip-4844.md) blob versioned hashes (32 B each) were added without matching floor terms and still pay nothing at the floor.

| Field | Floor rate | Source |
|---|---|---|
| Calldata byte (zero or non-zero) | 64 gas | EIP-7976 |
| Access-list address (20 B) | 1,280 gas | EIP-7981 |
| Access-list storage key (32 B) | 2,048 gas | EIP-7981 |
| EIP-7702 authorization tuple (up to 133 B) | 0 | uncovered |
| EIP-4844 blob versioned hash (32 B) | 0 | uncovered |

Each per-component extension has needed its own EIP and its own constants. This EIP folds EIP-7976 and EIP-7981 into a single per-byte rule covering every user-controlled tx-content field, and pulls authorization tuples and blob versioned hashes into the same rule. The result is one formula that auto-prices any future variable-length tx field at the same rate, and a worst-case content bound provable from arithmetic.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Constants

```
FLOOR_GAS_PER_BYTE             = 64    # per-byte floor rate established by EIP-7976 (calldata) and EIP-7981 (access lists)
```

### Transaction floor

```
tx_floor = floor_base + FLOOR_GAS_PER_BYTE * (
      len(tx.data)
    + entries_length(tx.access_list)
    + entries_length(tx.authorization_list)
    + entries_length(tx.blob_versioned_hashes)
)

def entries_length(entries):
    return sum(len(rlp(entry)) for entry in entries)
```

`entries_length` counts each entry of a list at its RLP-encoded size, without the list's own header. A field absent from a given transaction type, or an empty list, contributes zero.

`floor_base` is the per-transaction base that [EIP-2780](./eip-2780.md) puts under the [EIP-7623](./eip-7623.md) floor in place of the flat 21,000: `TX_BASE_COST` plus the recipient and value charges, without per-authorization or initcode charges. It is 21,000 for a value transfer to another account.

Blob data carried beside a transaction in the [EIP-4844](./eip-4844.md) network wrapper is not content: it is outside the execution payload and priced by blob gas.

### Frame transactions

For an [EIP-8141](./eip-8141.md) frame transaction, `floor_base` is every term of EIP-8141's `calldata_floor_gas` except `TOTAL_COST_FLOOR_PER_TOKEN * calldata_floor_tokens`, including terms other EIPs add. In place of `calldata_floor_tokens`, the content is:

```
      entries_length(tx.frames)
    + entries_length(tx.signatures)
    + entries_length(tx.blob_versioned_hashes)
```

Data that another EIP adds to `calldata_floor_tokens`, such as the `nonce_calldata` of [EIP-8250](./eip-8250.md), counts at its length.

### Charging

`tx_floor` replaces the calldata floor (`calldata_floor_gas_cost` in [EIP-8037](./eip-8037.md) and [EIP-7778](./eip-7778.md), `calldata_floor_gas` in EIP-8141) in every rule that uses the calldata floor. For transaction types other than frame transactions:

```
require tx.gas >= max(intrinsic, tx_floor)
require max(intrinsic, tx_floor) <= TX_MAX_GAS_LIMIT
tx_gas_used      = max(tx_gas_used_after_refund, tx_floor)
tx_execution_gas = max(tx_gas_used_before_refund - tx_state_gas, tx_floor)
```

`TX_MAX_GAS_LIMIT` is the [EIP-7825](./eip-7825.md) cap. `tx_gas_used` is what the sender pays; `tx_execution_gas` is what the transaction adds to the block's execution gas (`block_execution_gas` in EIP-8141). Frame transactions settle as EIP-8141 defines, with `tx_floor` as their floor.

The [EIP-7981](./eip-7981.md) `access_list_data_cost` is removed from intrinsic gas, so access-list bytes are priced only through `tx_floor`. The rest of intrinsic gas, including the [EIP-2930](./eip-2930.md) per-entry charges, is unchanged. The `max(intrinsic, floor)` shape of [EIP-7623](./eip-7623.md) is preserved.

## Rationale

### One per-byte rate

Pricing every content byte at the same `FLOOR_GAS_PER_BYTE` already used by [EIP-7976](./eip-7976.md) for calldata and by [EIP-7981](./eip-7981.md) for access-list bytes makes the worst case invariant to the attacker's choice of field or byte value: calldata, access-list entries, authorization tuples, and blob versioned hashes all yield `1/64` bytes per gas at the floor. The optimum collapses to `B = block_gas_limit / 64`. The bound holds independent of the network compressor, attacker strategy, or content composition.

### Encoded size, not per-item constants

An entry's encoded size is exactly what it adds to the block; a fixed per-item size is not. An access-list address entry encodes to 23 bytes and a storage key to 33, so counting 20 and 32 lets a block exceed the content bound by about 6%. An authorization tuple encodes to 92 bytes with chain ID 0 or 1 and a nonce below 128, and to up to 133 under EIP-7702's field bounds. Tuples that fail validation still ride in a valid transaction, so any constant either overcharges typical tuples or undercounts the largest.

### Access-list bytes at the floor only

EIP-7981 adds its data cost outside the `max`, so access-list bytes pay it even when execution dominates. Under this EIP they sit inside `tx_floor` like every other content byte, which is all the block-size bound needs. The EIP-2930 per-entry charges stay in intrinsic gas.

### Content-only, not full RLP

Charging every encoded byte (envelope and signature included) would make legacy transactions strictly cheaper than equivalent [EIP-1559](./eip-1559.md) transactions for the same payload, because legacy has a smaller envelope. Content-only is type-symmetric: an entry encodes the same way in every transaction type, and list headers stay with the envelope, so two transactions with identical content pay identical floor regardless of tx type.

### `floor_base` covers envelope

Envelope, signature, type prefix, and list headers total at most ~170 bytes for every transaction type defined to date (a blob transaction with an 8-byte chain ID and the largest fees and value a sender can afford; a frame transaction's envelope is smaller, since its frames and signatures are content). At `FLOOR_GAS_PER_BYTE` that is ~10,900 gas, below the smallest `floor_base` (`TX_BASE_COST = 12,000` for a self-transfer). Charging envelope explicitly would add ~7,700 gas to a typical ETH transfer (about 120 bytes). Treating `floor_base` as covering it avoids the regression.

### Frames are content

A frame's fields (mode, flags, target, limits, value) repeat per frame, so no per-transaction base can cover them. They encode to up to 73 bytes, since `value` is bounded only by `2**256` (a value the sender cannot cover just reverts the frame), while `FRAME_TX_PER_FRAME_COST` (475 gas) pays for about 7. Under EIP-8141's own floor, which counts only frame data and signature bytes, a block of 64-frame transactions (one `VERIFY` frame and 63 `SENDER` frames with zero limits and an unaffordable value) carries five to six times the content bound. Counting whole entries prices these fields like any other content, and blob versioned hashes count as they do in a blob transaction.

### Floor on the execution gas dimension

Under EIP-8037 a block bounds execution gas and state gas separately, so the floor must bind the execution dimension for the block-size bound to hold. That is why `tx_floor` enters `tx_execution_gas` as well as what the sender pays.

### Standard intrinsic unchanged

The standard intrinsic per-byte rate ([EIP-2028](./eip-2028.md): 4 gas per zero, 16 gas per non-zero) is preserved. It prices EVM and state work per byte and is unrelated to the bandwidth-bound floor. Raising it would increase intrinsic cost for every transaction with non-zero data without improving the bandwidth-defense properties this EIP targets.

## Backwards Compatibility

Hard fork.

Floor impact vs current mainnet baseline (EIP-7623 calldata floor, no floor term for access-list bytes, authorization tuples, or blob versioned hashes; mainnet sample 1,500 random blocks, 441,271 transactions, May 2026):

| Type | Share | Avg content (B) | Floor today | Floor under EIP-8131 | Bind rate today | Bind rate under EIP-8131 |
|---|---:|---:|---:|---:|---:|---:|
| 0 Legacy | 10.66% | 164 | 26.3 k | 31.5 k | 0.85% | 1.32% |
| 1 [EIP-2930](./eip-2930.md) | 0.09% | 486 | 33.9 k | 52.1 k | 0.00% | 0.00% |
| 2 EIP-1559 | 87.51% | 421 | 34.9 k | 47.9 k | 1.30% | 2.98% |
| 3 EIP-4844 | 0.44% | 992 | 69 k | 84 k | 60.05% | 60.05% |
| 4 EIP-7702 | 1.29% | 8,768 | 240 k | 587 k | 0.04% | 20.63% |

The "bind rate" is the share of transactions whose `tx_floor` exceeds intrinsic plus execution gas, i.e. transactions whose `tx.gasUsed` is set by the floor rather than by execution. Aggregate bind rate rises from 1.49% to 3.28%, and total network gas rises by 3.56%. These figures appear to use the earlier formula's fixed sizes (108 B per authorization, 20 B per access-list address, 32 B per storage key and blob hash). Encoded entries make a typical authorization 92 B and add a few bytes per access-list entry and blob hash, so the table needs re-measuring.

The repricing concentrates exactly where this EIP intends:

- **Type 4 (SetCode)**: bind rate jumps from 0.04% to 20.63% because authorization tuples (92 B × 64 gas = 5,888 gas for a typical auth) are uncovered today and newly priced. Average type-4 floor rises from 240 k to 587 k.
- **Type 3 (blob carriers, calldata-light)**: already 60% bind rate under today's floor, since blob-carrier transactions execute well below 7976-style calldata cost. This EIP raises the average floor from 69 k to 84 k as the 32-byte blob versioned hashes get priced.
- **Legacy, [EIP-2930](./eip-2930.md), [EIP-1559](./eip-1559.md)** (98.3% of traffic): bind rate moves at most ~1.7 pp, driven by access-list bytes moving into the floor and by [EIP-7623](./eip-7623.md) zero-byte calldata catching up to the [EIP-7976](./eip-7976.md) / EIP-8131 rate.

Relative to a fork with EIP-7981, intrinsic gas drops by `64 × access_list_bytes` (3,328 gas for an address with one storage key), so access-list transactions whose floor does not bind get cheaper.

When does the floor bite? For calldata-only transactions:

```
tx_floor > gas_used  ⇔  calldata_bytes  >  (gas_used − floor_base) / FLOOR_GAS_PER_BYTE
```

A typical token transfer (zero-value call, 68 B calldata) has `tx_floor = 15,000 + 64 × 68 = 19,352`, well under `gas_used`. A zero-value call using 50 k gas needs more than 546 B of calldata before the floor bites.

Wallets and gas estimators need to include the new floor, since a transaction whose gas limit is below `tx_floor` is invalid.

## Test Cases

Unless stated otherwise, each case is a value transfer to another account, so `floor_base = 21,000`.

### Bare ETH transfer

`tx.to = recipient`, `tx.value = 1 ether`, `tx.data = b""`, no access list, no authorizations, no blob hashes.

- `tx_floor = floor_base = 21,000` gas. Unchanged.

### Calldata-only transaction

10,000 calldata bytes, no other variable-length content.

- `tx_floor = 21,000 + 64 × 10,000 = 661,000` gas. Identical across all transaction types carrying the same calldata.

### Access-list entry: address with one storage key

The entry encodes to 56 B.

- `tx_floor = 21,000 + 64 × 56 = 24,584` gas.
- Intrinsic gas excludes the EIP-7981 `access_list_data_cost` of 3,328 gas.

### EIP-7702 with one authorization

`chain_id = 1`, `nonce = 0`, 32-byte `r` and `s`. The tuple encodes to 92 B.

- `tx_floor = 21,000 + 64 × 92 = 26,888` gas.

### EIP-4844 with six blob versioned hashes

Each hash encodes to 33 B.

- `tx_floor = 21,000 + 64 × (6 × 33) = 33,672` gas.

### Other floor bases

10,000 calldata bytes, no other content.

- Zero-value call to another account: `tx_floor = 15,000 + 64 × 10,000 = 655,000` gas.
- Self-transfer: `tx_floor = 12,000 + 64 × 10,000 = 652,000` gas.
- Contract creation: `tx_floor = 24,000 + 64 × 10,000 = 664,000` gas.

### EIP-8141 frame transaction

One `VERIFY` frame `[1, 3, null, [50000, 0], 0, b""]` (11 B) and one `SECP256K1` signature with empty `signer` and `msg` and a 65-byte `signature` (72 B), no blob hashes.

- `floor_base = 12,000 + 475 + 2,800 = 15,275` gas.
- `tx_floor = 15,275 + 64 × (11 + 72) = 20,587` gas.

## Security Considerations

### Block-size bound

Every content byte the transaction contributes is paid at `FLOOR_GAS_PER_BYTE` via `tx_floor`. Implicit per-tx bytes (envelope, signature, type prefix, list headers) are covered by `floor_base`:

```
content_bytes_per_tx * FLOOR_GAS_PER_BYTE  ≤  tx_floor  ≤  tx_execution_gas
```

Summing across user transactions, against the block's execution gas limit:

```
sum(content_bytes) ≤ sum(tx_execution_gas) / 64 ≤ block_gas_limit / 64
```

At a 60M gas limit, the bound is `60,000,000 / 64 ≈ 0.94 MB` of attacker-controlled content per block. It is derived from arithmetic, requires no compression assumption, and survives a change of the network compressor.

Envelope and signature contribute at most `~170 × (block_gas_limit / TX_BASE_COST)` ≈ 850 KB at a 60M gas limit, since a self-transfer has the smallest `floor_base`. This is well below `MAX_RLP_BLOCK_SIZE`.

The bound covers the execution payload. Under [EIP-8142](./eip-8142.md), which publishes the execution payload in blobs, it also limits how much transaction content those payload blobs carry.

### Type symmetry

Two transactions carrying identical content pay identical floor regardless of transaction type. A frame transaction's frames are content in their own right, so calldata inside a frame also pays for the frame around it.

### Gas estimation

Wallets and `eth_estimateGas` need to compute `tx_floor` alongside intrinsic gas. Without it, estimates for floor-bound transactions are too low and submissions will be rejected at validation.
