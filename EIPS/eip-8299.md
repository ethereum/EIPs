## Abstract

Secp256k1 public key recovery fails when the recovered point is the point at infinity, that is when
`s * R == e * G (mod n)` and therefore `Q = r ** -1 * (s * R - e * G)` is the identity. This is the case
for every signature produced with the private key `d = 0`, the address of which is the well known
`keccak256(0x00 * 64)[12:]`.

This EIP defines that such a signature is valid and that the recovered public key is encoded as
`0x04 || 64 zero bytes`, which yields that address, so that transactions signed by `d = 0` can be
included and executed.

## Motivation

The zero private key has a publicly known address and holds real value:

* `10.476116 ETH` and `10,058 USDT` on Ethereum mainnet
* additionally 5000 USDC on Avalanche, ~50 USDT on BSC, plus dust on Polygon, Celo, Base, Arbitrum
* its nonce is `0` and it has not sent a single transaction in about 10 years

Every current client rejects transactions from it. The failure is not in the signature: the signature is
a perfectly valid ECDSA signature, `s * R == e * G (mod n)` holds, and `s` is low. The failure is that
recovery returns the identity, and neither libsecp256k1 nor btcec is willing to serialise it:

* geth (both backends): `recovery failed`, if the result is not cached then `invalid sender`
* reth, erigon, bor, subnet-evm, nitro, op-reth, besu, cronos, aurora, harmony and others: equivalent
  errors (`invalid signature`, `recovered pubkey is the point at infinity`, ...)
* Nethermind: recovery succeeds, the identity is mapped to `null`, then `SenderAddress` is null
* the `ecrecover` precompile (`0x01`) returns empty output for such inputs

Because sender recovery is part of the state transition, this is consensus relevant: a block containing
such a transaction is invalid for an unpatched client, so a single patched block producer would produce
an orphan. Hence a definition and an activation decision are needed.

## Specification

The key words "MUST", "MUST NOT", "SHOULD" and "MAY" are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

For any signature verification that recovers a public key from `(r, s, v)` over secp256k1:

1. Reconstruct the recovery point `R` from `r` and the recovery id as in SEC1 §4.1.6, with the recovery
   id taken as `v - 27` for [EIP-155](./eip-155.md) protected transactions and as `v` for typed transactions.
2. Compute `e` as the signing hash of the object being verified, reduced modulo `n`.
3. Compute `Q = r ** -1 * (s * R - e * G)`, where `G` is the generator of the secp256k1 group.
4. If `Q` is the point at infinity (`s * R == e * G (mod n)`), the recovered public key MUST be encoded
   as the 65 bytes `0x04` followed by 64 zero bytes, and the recovered address MUST be
   `keccak256(0x00 * 64)[12:]`, i.e. `0x3f17f1962B36e491b30A40b2405849e597Ba5FB5`.
5. Otherwise the existing behaviour is unchanged.

This applies to, at least:

* sender recovery of legacy, EIP-155 and typed (`0x01`, `0x02`, `0x03`, `0x04`) transactions
* authority recovery of [EIP-7702](./eip-7702.md) authorisation tuples
The `ecrecover` precompile is deliberately left out of scope for this version (see Rationale): it
returns empty output for such inputs today, and contracts already rely on that, so changing it widens
the blast radius.

Once active, clients MUST accept transactions and blocks relying on this recovery; blocks that were
invalid before activation become valid, which is why an activation mechanism is required.

## Rationale

The encoding is not arbitrary. The address of the zero private key is already defined in practice as the
Keccak-256 digest of 64 zero bytes, which is what a public key with both coordinates zero would hash to,
and `0x04 || 64 zero bytes` is the canonical uncompressed encoding of such a point. Using it keeps the
"address is `keccak256(X || Y)[12:]`" rule intact and needs no special casing anywhere downstream: only
the serialisation step changes.

Alternative considered: rejecting such signatures explicitly and documenting the key as unspendable. This
is simpler, but leaves the address permanently unable to move funds even though the signing operation
itself is trivially available, and it makes any contract relying on `ecrecover` behave inconsistently with
sender recovery.

### Why the precompile is left out

Sender recovery and `ecrecover` are used by very different consumers. Sender recovery is a client side
concern: no contract can observe it, and no application logic depends on it. The precompile is a
contract-visible API: today it returns empty output for a degenerate signature, and existing contracts
treat the empty result as `address(0)` (Solidity's `ecrecover` does exactly this), so switching it to a
real address changes observable behaviour for deployed code. Keeping the first version to sender and
authorisation recovery makes the change testable and cheap to reason about; aligning the precompile can
be a follow-up.

## Backwards Compatibility

* **No past block becomes invalid.** No block in history has ever contained such a transaction, because
  no client has ever accepted one (the address has a nonce of zero after ~10 years). The rule is therefore
  relaxed only towards the future, and a coordinated activation height is not strictly required: clients
  must merely ship support before the first such transaction is mined. A flag that defaults to on, rather
  than a hard fork, is sufficient.
* Transactions and blocks that are rejected today become valid. A block produced by an updated client
  while the rest of the network is still unpatched is rejected by unpatched nodes, which is the only
  reason to coordinate rollout. This does not require unanimity: a node that rejects such a block simply
  stays on its own branch, and the branch backed by the majority of the *stake* wins, with the minority
  re-synchronising. Rollout therefore has to reach staking majorities (block builders and large
  validators), not every node, and a patch-release backport is enough.
* EIP-7702 authorisations are affected as well, and the observable behaviour differs today: an unpatched
  client fails to recover the authority and silently skips that tuple (verified: a type-4 transaction with
  a zero-key authorisation is mined, but no delegation designator is written), while an updated client
  writes the designator. Both variants are valid under their own rules, so a mixed network diverges on the
  block that first contains such a tuple.
* The `ecrecover` precompile changes output from empty to an address. Contracts that today treat the
  empty result as `address(0)` (the usual Solidity `ecrecover` behaviour) will see a real address after
  activation. Contracts comparing against a hard coded `address(0)` for "invalid" are unaffected for all
  other signatures.
* No signing procedure changes. The EIP-155 signing hash (`rlp([nonce, gasPrice, gas, to, value, data,
  chainId, 0, 0])`) stays as specified in EIP-155; note the two trailing zeros, which are a frequent
  source of confusion when reproducing this case.

### Incremental path: EIP-7702 authorisations

The authorisation path can be rolled out on its own, without touching sender recovery, and it is the
cheapest way to make such an address usable:

* the wrapping transaction is signed by an ordinary key, so no client-side crypto on the sender path
  changes;
* before the rule is adopted the transaction is harmless: an unpatched client includes it and silently
  skips the tuple (only the wrapper's gas is spent), so it can be re-broadcast without risk until a
  client that applies it produces the block;
* once the delegation is applied, the delegate code runs in the address's context, so a delegate with a
  hard-coded destination lets *any* caller move the funds - no nonce ordering, no gas reserve, and no
  race between competing sweepers.

A minimal delegate is a handful of lines: `receive`/`fallback` forward the native balance,
`sweepToken`/`sweepTokens` forward [ERC-20](./eip-20.md) balances, `sweepNFT` handles collectibles.

## Test Cases

Signature by the zero private key, low `s` chosen through `k` (never by flipping `s` to `n - s`, which
changes the recovery parity):

* signing hash: `dab7dc9f25247828219ba160c29cfeaa896bd943fb60f5b9308058f064870d2b`
* signature: `dbd5883a2180ae66173ea71181926198e64067fba46c956629409727b5d598e85366cb732b41a51421e448ab7de30eb5b6656a7c5b215b01651bc2a9dda6e51500`
  (`r = dbd5883a...98e8`, `s = 5366cb73...1500`, `v = 27 + 0` for the unprotected case)
* recovered address: `0x3f17f1962B36e491b30A40b2405849e597Ba5FB5`
* recovery point: `s * R == e * G (mod n)` holds, `Q` is the identity

Negative and control cases:

* the same hash signed by `d = 1` must recover normally (unchanged behaviour)
* garbage `(r = 5, s = 1)` must not be treated as the identity
* recovery ids above 3 remain rejected by the pure Go backend

## Security Considerations

* The private key `d = 0` is public knowledge, so the address is claimable by whoever signs first. This
  is true today, but once the EIP activates, the first valid transaction wins. Sending a transaction to
  that address is always possible, so its balance will keep growing.
* Everything else about the signature scheme is unchanged; no new malleability is introduced. The
  predicate is exactly `s * R == e * G (mod n)`, which is checkable in constant time relative to recovery.
* A client may choose to detect the degenerate case either from the recovery error or from the
  predicate; both lead to the same result.
