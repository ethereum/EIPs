## Abstract

This EIP adds a frame mode to [EIP-8141](./eip-8141.md) frame transactions: the proof frame. It executes no code. Its data is a list of `(scheme, data_hash, verification_key_hash)` triples, the transaction's dependencies. Each triple names the scheme of its dependency, and this EIP defines a single scheme, leanSPHINCS, a stateless hash-based signature scheme. A leanSPHINCS dependency states that `data_hash` is signed under the public key `verification_key_hash`, and a `data_hash` of 32 zero bytes stands for the transaction's own signature hash. Signatures are not part of the transaction. They travel beside it in the mempool and in the block, which carries one signature per distinct dependency of its transactions, and every node verifies them. The block header commits to the signatures the block carries. Smart accounts read their dependencies through the existing frame introspection instructions and approve on them. A later upgrade can replace the per-signature witnesses with a single aggregate proof of all dependencies, as [EIP-8288](./eip-8288.md) does, and can add dependencies of other kinds, such as proofs, without changing transactions or accounts.

## Motivation

Post-quantum accounts need a signature scheme whose security does not rest on the hardness of discrete logarithms. leanSPHINCS is one. It is stateless, so a key can sign from several devices and be restored from a backup without tracking which one-time keys it has used, and its only primitive is Keccak-256, which every client already implements. Its cost is size: a signature is 7,740 bytes, more than a hundred times a secp256k1 signature, and a block of such transactions carries hundreds of kilobytes of signatures that every node downloads, verifies and keeps.

The lasting fix is aggregation: a block carries one recursive proof that all of its signatures are valid, and nodes verify that proof in place of each signature. The proof systems that would do this are still changing, and building every block would require running a prover. Post-quantum accounts should not wait for them, but they do need, from the start, the interface that aggregation will keep. Accounts are long-lived, and their validation code fixes where a signature is looked for. An account that looks in one place cannot use an aggregate that answers in another without changing its code.

Signatures are also not the only thing that will be verified outside the EVM. Proofs follow, and a proof's witness is hundreds of kilobytes, too large for a transaction to carry. A transaction will then declare what it depends on, and the witness will travel beside it until a block's aggregate proof answers for it. This EIP puts signatures on that model from the start: a transaction declares, the witness travels beside it, and the block answers for it.

This EIP therefore fixes what aggregation keeps, and leaves for later only what it replaces:

- A transaction declares the signatures it depends on in a proof frame. The frame is covered by the transaction's signature hash, and accounts read it with `FRAMEPARAM` and `FRAMEDATACOPY`. Aggregation changes neither.
- The frame is the only declaration. A signature carried inside the transaction would need an entry of its own, naming the same scheme, key and message a second time, and a rule to keep the two consistent.
- Signatures travel beside the transaction, in the mempool and in the block. Nodes, wallets and tools handle a transaction together with its witnesses from the start, so when an aggregate proof takes the place of the signatures, only what accompanies the block changes.
- The new header field commits only to the signatures a block carries. A block's dependencies are derived from its transactions, so an aggregate proof can later commit to them in whatever form it needs.
- The scheme is the leanSPHINCS definition an aggregate proof verifies, so keys created under this EIP stay usable once signatures are aggregated.
- Signatures are verified outside the EVM. A node may verify a block's signatures before or in parallel with transaction execution. A mempool node rejects a transaction with a missing or invalid signature before simulating it.

Allowing only leanSPHINCS keeps this upgrade to one scheme, with one parameter set and a fixed verification cost. Other dependency kinds, such as proofs, can arrive with aggregation: the frame format already names the scheme of each dependency.

### Proof Frame

This EIP adds `PROOF_FRAME_MODE` to the set of mode values accepted by EIP-8141's static constraint on `frame.mode`. No other mode value becomes valid.

A frame with this mode is a proof frame. A proof frame declares dependencies; the signatures or proofs that satisfy them are carried separately. It executes no code.

#### Encoding

The frame's `data` is the concatenation of `k` triples, each 96 bytes long. Each triple consists of:

- `scheme`: 31 zero bytes followed by one byte identifying the scheme. The only scheme is `LEANSPHINCS_SCHEME`.
- `data_hash`: 32 bytes containing the message to be signed. A value of 32 zero bytes stands for the signature hash of the containing transaction, as specified in [Dependencies](#dependencies).
- `verification_key_hash`: 32 bytes containing the leanSPHINCS public key. Since the key is already 32 bytes, it is used directly without hashing.

#### Constraints

A transaction is invalid if any of its proof frames fails any of the checks below. `chunks(b, n)` splits `b` into consecutive pieces of `n` bytes.

```python
for i, frame in enumerate(tx.frames):
    if frame.mode != PROOF_FRAME_MODE:
        continue

    assert len(frame.data) % 96 == 0
    k = len(frame.data) // 96
    assert 1 <= k <= MAX_DEPENDENCIES_PER_FRAME

    for triple in chunks(frame.data, 96):
        assert triple[:31] == bytes(31)
        assert triple[31] == LEANSPHINCS_SCHEME

    assert frame.target is None
    assert frame.value == 0
    assert frame.flags == 0

    # The frame must not belong to an atomic batch. Its own flags are zero,
    # so only the preceding frame's batch flag needs to be checked.
    assert i == 0 or tx.frames[i - 1].flags & ATOMIC_BATCH_FLAG == 0

    assert frame.limits.execution == k * LEANSPHINCS_VERIFICATION_GAS
    assert frame.limits.state == 0
```

`None` denotes EIP-8141's absent target, not the zero address. The frame's `resolved_target` is therefore `tx.sender`, and `FRAMEPARAM(0x00, i)` returns the sender's address. Contracts identify a proof frame by its `mode`, not its target.

These checks apply in addition to EIP-8141's static constraints, which also apply to proof frames.

#### Execution and Receipt

Executing a proof frame performs no call, accesses no account and changes no state. The frame consumes its entire `limits.execution`.

Like any other frame, it produces an EIP-8141 frame receipt, with `status = 1`, `gas_used.execution` equal to the frame's `limits.execution`, `gas_used.state = 0`, and no logs.

### Dependencies

A dependency is a triple `(scheme, data_hash, verification_key_hash)`. The dependency `(LEANSPHINCS_SCHEME, m, pk)` states that the 32-byte message `m` is signed under the leanSPHINCS public key `pk`.

A transaction's dependencies are derived from the triples in all of its proof frames. Each zero `data_hash` is replaced with the transaction's signature hash, and the resulting triples are sorted and deduplicated. A block's dependencies are the combined dependencies of all its transactions, also sorted and deduplicated.

```python
def data_triples(frame):
    return [(t[31], t[32:64], t[64:96]) for t in chunks(frame.data, 96)]

def dependencies(tx):
    return deduplicate_and_sort([
        (scheme, compute_sig_hash(tx) if data_hash == bytes(32) else data_hash, verification_key_hash)
        for frame in tx.frames if frame.mode == PROOF_FRAME_MODE
        for (scheme, data_hash, verification_key_hash) in data_triples(frame)
    ])

def block_dependencies(block):
    return deduplicate_and_sort([
        dependency
        for tx in block.transactions
        for dependency in dependencies(tx)
    ])

def deduplicate_and_sort(deps):
    out = []
    for dep in sorted(deps):
        if len(out) == 0 or dep != out[-1]:
            out.append(dep)
    return out
```

Triples are ordered first by `scheme` as an integer, then by `data_hash`, and finally by `verification_key_hash`. The two 32-byte fields are compared byte by byte.

A `data_hash` of 32 zero bytes serves as a placeholder for `compute_sig_hash(tx)`. A transaction cannot include its own signature hash directly in a frame, because that hash covers the frame's `data`. The substitution occurs only in `dependencies(tx)`: the frame's encoded `data` remains unchanged, so `compute_sig_hash` covers the zero bytes and `FRAMEDATACOPY` returns them.

Any nonzero `data_hash` is an explicit message, signed as encoded. Transactions that declare the same scheme, explicit message and public key therefore share the same dependency.

A transaction MAY declare the same triple more than once, either within a frame or across several frames. These repeated declarations contribute only one dependency.

The requirements for satisfying dependencies are specified in [Signatures in the Mempool](#signatures-in-the-mempool) and [Signatures in the Block](#signatures-in-the-block).

### Reading Dependencies During Execution

This EIP introduces no new instruction. Contracts read proof frames using EIP-8141's existing frame introspection instructions:

- `FRAMEPARAM(0x02, i)` returns the `mode` of frame `i`. A proof frame has mode `PROOF_FRAME_MODE`.
- `FRAMEPARAM(0x04, i)` returns `len(data)` for frame `i`.
- `FRAMEDATACOPY(memOffset, dataOffset, length, i)` copies the `data` of frame `i` into memory.

The data is read as encoded, so a zero `data_hash` remains 32 zero bytes. An account with public key `pk` typically approves a transaction when one of its proof frames contains the triple `(LEANSPHINCS_SCHEME, bytes(32), pk)`.

Validation code can read a proof frame's data even when that frame appears later in the transaction.

### leanSPHINCS

leanSPHINCS is a stateless hash-based signature scheme. It is SLH-DSA, as specified in FIPS 205[^1], instantiated with Keccak-256 and with WOTS+C as its one-time signature.

This EIP uses leanSPHINCS as specified by the Cryptography/Sphincs module of the ethereum/EthLib repository at commit `c4474ed422d83b6b735ef802ee43960abe1b788f`. That module defines the parameters, the hash layout, the encodings of keys and signatures, and verification. A Rust implementation is available in the `lean_sphincs` crate of the leanEthereum/leanVM repository at commit `92a97c919b2f2d6fe09853090b6b23f781ecec07`. It reproduces the module's test vectors byte for byte.

`LEANSPHINCS_SCHEME` identifies leanSPHINCS with exactly one parameter set. After this EIP is activated, that parameter set does not change: any other parameter set is a different scheme and takes a new `scheme` value.

The following parts of the scheme are fixed:

- A public key is 32 bytes, the size of a triple's `verification_key_hash`. In a dependency, `verification_key_hash` contains the public key.
- A message is 32 bytes, the size of a triple's `data_hash`.
- This EIP uses the scheme only through `leansphincs_verify`, as specified below.

The following parts are provisional. They will be fixed before this EIP is scheduled for a network upgrade:

- The parameter set. The module currently specifies a single parameter set, under which a public key is the 16-byte `PK.seed` followed by the 16-byte `PK.root`, a key signs at most `2^30` messages, and verification performs a constant 515 Keccak-f[1600] permutations.
- The size of a signature, `LEANSPHINCS_SIGNATURE_SIZE`.
- The gas costs that depend on the scheme: `LEANSPHINCS_VERIFICATION_GAS` and the costs specified in [Gas Accounting](#gas-accounting).
- Both commits. Before this EIP moves to Last Call, the parameter set and the test vectors will be part of this EIP, in place of the references to the commits.

This EIP uses the scheme through the following function:

| Function | Description |
| --- | --- |
| `leansphincs_verify(pk: Bytes32, msg: Bytes32, signature: bytes) -> bool` | Return whether `signature` is a valid signature of `msg` under the public key `pk`. Return `False`, without raising, if `signature` is not `LEANSPHINCS_SIGNATURE_SIZE` bytes long |

`leansphincs_verify` applies the module's `verify` to the public key and the signature, decoded with its `decodePublicKey` and `decodeSignature`.

#### Satisfying a Dependency

A byte string `witness` satisfies a dependency when `satisfies(dependency, witness)` returns `True`:

```python
def satisfies(dependency, witness):
    scheme, data_hash, verification_key_hash = dependency
    if scheme != LEANSPHINCS_SCHEME:
        return False
    return leansphincs_verify(verification_key_hash, data_hash, witness)
```

Here `dependency` is a triple as returned by `dependencies(tx)`, so its `data_hash` is the message itself. A declaration with a zero `data_hash` is therefore satisfied by a signature over the transaction's signature hash.

### Signatures in the Mempool

A dependency transaction is a frame transaction with at least one proof frame. Until inclusion in a block, it is handled together with its witnesses: one signature for each dependency. This section defines the wrapper that carries them, how nodes receive and propagate these transactions, and the conditions for admission to the public mempool.

#### Wrapper

A wrapper carries one dependency transaction and its witnesses. It is the RLP serialization of the following structure:

```
[transactions, mode, content]

transactions = [tx]
content = [deps, witnesses]
```

- `transactions` is a list containing exactly one item, `tx`: a byte string encoding the dependency transaction in its pooled network form. This is the form used to carry frame transactions in `PooledTransactions`, as specified in EIP-8141's [Networking](./eip-8141.md#networking) section.
- `mode` is `0`. No other value is valid.
- `deps` contains the transaction's dependencies in the order returned by `dependencies(tx)`. Each dependency is encoded as a 96-byte string using `encode_dependency`.
- `witnesses` is a list of byte strings with exactly one item for each entry in `deps`. The witness at position `i` corresponds to the dependency at position `i`.

```python
def encode_dependency(dependency):
    scheme, data_hash, verification_key_hash = dependency
    return bytes(31) + bytes([scheme]) + data_hash + verification_key_hash
```

An encoded dependency uses the triple layout specified in [Encoding](#encoding). Because `deps` is derived from `dependencies(tx)`, it contains the transaction's signature hash in place of any zero `data_hash` declared in a frame.

For a transaction with a nonempty `blob_versioned_hashes` list, the pooled network form includes the transaction's blob sidecar. EIP-8141's sidecar rules apply unchanged.

A wrapper is identified by the Keccak-256 hash of its RLP serialization.

#### Submission

A dependency transaction is submitted to a node together with its witnesses. For a transaction without blobs, the submitted form is the transaction's type byte followed by the RLP serialization of its payload and witnesses:

```
FRAME_TX_TYPE || rlp([tx_payload_body, witnesses])
```

Here, `tx_payload_body` is the payload list defined by EIP-8141, and `witnesses` is the list specified in [Wrapper](#wrapper).

For a transaction with a nonempty `blob_versioned_hashes` list, `witnesses` follows the blob sidecar fields in EIP-8141's pooled network form:

```
FRAME_TX_TYPE || rlp([tx_payload_body, wrapper_version, blobs, commitments, cell_proofs, witnesses])
```

A node accepts this form wherever it accepts raw transactions from users, including through `eth_sendRawTransaction`. This EIP introduces no new method.

The node builds the wrapper by deriving `deps` from the transaction and using `witnesses` as submitted. A node MUST reject a dependency transaction submitted without its witnesses.

#### Propagation

A dependency transaction is propagated only inside a wrapper. A node MUST NOT send a dependency transaction in a `Transactions` or `PooledTransactions` message.

A node announces a wrapper to its peers by its hash and sends the wrapper only in response to a peer's request. A node MUST NOT announce or send a wrapper unless it has admitted the wrapper's transaction under the rules in [Admission to the Public Mempool](#admission-to-the-public-mempool).

This EIP does not define the `eth` protocol messages used to announce, request and return wrappers.

#### Admission to the Public Mempool

The following rules supplement EIP-8141's public mempool rules, with the adjustments described in [Validation Prefix](#validation-prefix).

A node admits a dependency transaction to the public mempool only if all of the following checks pass. A node SHOULD perform them in the listed order, beginning with the cheapest checks:

1. The wrapper has the form specified in [Wrapper](#wrapper), with `mode` equal to `0` and exactly one transaction.
2. The transaction satisfies EIP-8141's static constraints and the constraints specified in [Constraints](#constraints).
3. The number of dependencies, `len(dependencies(tx))`, is at least one and at most `MAX_SIGS_PER_TX`.
4. The wrapper's `deps` equals `[encode_dependency(d) for d in dependencies(tx)]`, and `witnesses` contains the same number of items as `deps`.
5. Each witness satisfies its corresponding dependency, as specified in [Satisfying a Dependency](#satisfying-a-dependency).
6. The transaction passes EIP-8141's [acceptance algorithm](./eip-8141.md#acceptance-algorithm).

If any check fails, the node rejects the wrapper and does not admit its transaction.

`MAX_SIGS_PER_TX` limits the number of witnesses a node verifies for one transaction. It applies to the deduplicated list returned by `dependencies(tx)`, so repeated declarations of the same triple count once. This limit governs public mempool admission and does not affect transaction validity.

Whether a witness satisfies a dependency is independent of state. A node therefore verifies a transaction's witnesses once; the revalidation specified in EIP-8141 does not repeat checks 1 through 5.

A key holder can produce multiple valid signatures for the same message, so a transaction may have more than one valid wrapper. A node keeps a single wrapper per transaction. Once it has admitted a transaction, it SHOULD ignore any additional wrapper for that transaction.

#### Validation Prefix

EIP-8141's public mempool rules require a transaction's validation prefix to match one of the recognized prefixes and limit the work of validating that prefix to `MAX_VERIFY_GAS`. Proof frames are exempt from both requirements:

- Proof frames are skipped when matching a transaction's frames against the recognized validation prefixes, as is EIP-8141's expiry verifier frame. With `proof` denoting a proof frame, `[proof, self_verify]` is recognized as `[self_verify]`, and `[only_verify, proof, pay]` is recognized as `[only_verify, pay]`. Proof frames are also skipped when checking that an expiry verifier frame appears first. Thus, `[proof, expiry_verify, self_verify]` is recognized as `[self_verify]`.
- A proof frame's `limits.execution` is excluded from the sum compared against `MAX_VERIFY_GAS`. Witness verification also does not count toward that limit; `MAX_SIGS_PER_TX` bounds this work. This exemption and the value of `MAX_SIGS_PER_TX` are provisional. Both will be finalized based on measurements comparing witness verification with the simulation work allowed by `MAX_VERIFY_GAS`.

These adjustments allow a proof frame to appear at any position in a transaction admitted to the public mempool.

EIP-8141's mempool rules examine only the validation prefix. The checks in [Admission to the Public Mempool](#admission-to-the-public-mempool) cover the entire transaction: `dependencies(tx)` includes dependencies from every proof frame, so a node verifies a witness for every dependency, including those declared in the execution body.

### Signatures in the Block

A block carries one witness for each distinct dependency. The following rules define the witness list, its header commitment and the checks required for block validity.

#### Block Body

The block body is extended with a `dependency_witnesses` field immediately after `withdrawals`:

```
block_rlp = rlp([header, transactions, ommers, withdrawals, dependency_witnesses])
```

`dependency_witnesses` is a list of byte strings with exactly one item for each entry in `block_dependencies(block)`. The witness at position `i` corresponds to the dependency at position `i`. A block without dependencies carries an empty list.

Because `block_dependencies(block)` is deduplicated, a dependency declared by several transactions in a block has a single witness. A key holder can produce multiple valid signatures for the same message, so a dependency may have more than one valid witness. A block builder MAY include any of them.

The witnesses are part of the block, so their size counts toward the block size limit specified in [EIP-7934](./eip-7934.md).

#### Block Header

The block header is extended with one field, `dependency_witnesses_hash`, appended after the existing fields. It contains the Keccak-256 hash of the RLP serialization of the block's `dependency_witnesses`:

```python
class Header:
    # Existing fields
    ...

    dependency_witnesses_hash: Hash32 = keccak256(rlp.encode(dependency_witnesses))
```

For an empty list, this is `keccak256(rlp.encode([])) = 0x1dcc4de8dec75d7aab85b567b6ccd41ad312451b948a7413f0a142fd40d49347`.

The new header field commits to the witness list. The header already commits to the dependencies indirectly through `transactions_root`, since they are derived from the transactions. No separate commitment to the dependency list is added.

#### Block Validity

A block is invalid if it fails any of the checks below:

```python
def validate_dependency_witnesses(block):
    witnesses = block.dependency_witnesses
    assert block.header.dependency_witnesses_hash == keccak256(rlp.encode(witnesses))

    deps = block_dependencies(block)
    assert len(witnesses) == len(deps)
    for dependency, witness in zip(deps, witnesses):
        assert satisfies(dependency, witness)
```

These checks depend only on the block's contents and require neither state access nor transaction execution. A node MAY perform them before executing the block or in parallel with transaction execution.

Executing proof frames does not verify their witnesses. These checks are therefore additional requirements for block validity.

#### Engine API

The execution payload is extended with one field:

- `dependencyWitnesses`: `Array of DATA`, the block's `dependency_witnesses` in the same order.

A new version of `engine_newPayload` accepts the extended payload, and a new version of `engine_getPayload` returns it. The execution layer computes `dependency_witnesses_hash` from the payload's `dependencyWitnesses`, as it computes `transactions_root` from the payload's `transactions`. The payload is invalid if the block hash recomputed using this commitment does not match its `blockHash`.

The payload bodies returned by `engine_getPayloadBodiesByHash` and `engine_getPayloadBodiesByRange` are extended with the same field.

The consensus layer's `ExecutionPayload` container is extended with the corresponding field, `dependency_witnesses`.

### Gas Accounting

A transaction pays separately for witness verification and witness size. Verification is charged through proof-frame execution gas. Witness size is charged through an additional term in both intrinsic gas and the calldata floor.

#### Verification

A proof frame's `limits.execution` equals `k * LEANSPHINCS_VERIFICATION_GAS`, as specified in [Constraints](#constraints), and the frame consumes that limit entirely, as specified in [Execution and Receipt](#execution-and-receipt). A transaction therefore pays `LEANSPHINCS_VERIFICATION_GAS` for each triple it declares, including each repeated declaration of the same triple.

#### Witness Size

Witnesses are not part of the transaction, so EIP-8141's calldata costs do not apply to them. This EIP adds one term, `dependency_witness_cost`, to both EIP-8141's `frame_tx_intrinsic_gas` and its `calldata_floor_gas`:

```python
dependency_witness_cost = len(dependencies(tx)) * LEANSPHINCS_WITNESS_GAS
```

Adding this term to both values ensures that the witness-size charge applies even when the calldata floor determines the transaction's gas charge. The term is included in `standard_gas_limit` and `max_gas`, and counts toward the transaction gas cap, `TX_MAX_GAS_LIMIT`.

The witness-size charge applies to the deduplicated list returned by `dependencies(tx)`, so repeated declarations of the same triple incur this charge only once per transaction. The verification charge still applies to every declaration. If several transactions share a dependency, each pays its witness-size charge, even though the block carries only one witness for it.

`LEANSPHINCS_WITNESS_GAS` equals `LEANSPHINCS_SIGNATURE_SIZE * 4 * TOTAL_COST_FLOOR_PER_TOKEN`, pricing each witness byte at EIP-8141's calldata floor rate. Both the value and the choice of this rate are provisional.

With the provisional values above, `TX_MAX_GAS_LIMIT` permits at most 33 distinct dependencies per transaction. Other transaction costs may reduce that number. Public mempool admission is separately limited to `MAX_SIGS_PER_TX` dependencies.
