## Abstract

This EIP defines optional admission certificates for [EIP-8141](./eip-8141.md) frame transactions. A STARK certifies successful validation-prefix execution conditional on explicit inputs and separately checked protocol obligations. Nodes may verify the certificate instead of simulating the prefix, subject to a higher, bounded validation budget. Recursive batches amortize proof verification and transport across transactions. Certificates are networking metadata: ordinary block execution, gas charges, and inclusion-list eligibility remain unchanged.

## Motivation

Expensive account authorization can exceed the public mempool's validation budget despite satisfying its state-access restrictions. Admission certificates let one party perform that computation for many verifying nodes. Candidate applications include existing accounts with substantial delegation, session-key or recovery-policy processing, and bespoke proof verifiers that cannot conveniently be replaced with [EIP-8288](./eip-8288.md) dependencies. Such applications must still obey EIP-8141's validation rules.

This is a long-term proposal targeting local proof generation on consumer hardware: a wallet proves its transaction's bounded validation prefix and submits the certificate directly to the public mempool. Improvements in proving algorithms, EVM execution circuits and hardware make this a plausible deployment target. Individual proofs may require expensive prefixes to justify their overhead; recursive batches can spread that overhead over multiple transactions. Deployment requires practical local proving and measured network savings against optimized simulation and caching. On-chain execution costs remain unchanged.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

### Proof profile and limits

A proof profile fixes the network and fork rules, canonical encodings, prefix interpreter, execution environment, STARK verifier, and verification keys `PREFIX_VK` and `BATCH_VK`. Its identifier commits to these choices and the following limits:

| Parameter | Bound |
| --- | --- |
| `MAX_PROVEN_VERIFY_GAS` | EIP-8141 signature cost plus declared prefix execution-gas limits |
| `MAX_ASSUMPTION_COUNT` | Assumptions per transaction |
| `MAX_BATCH_STATEMENTS` | Distinct statements per certificate |
| `MAX_ADMISSION_PROOF_SIZE` | Encoded proof bytes |
| `MAX_ADMISSION_MESSAGE_SIZE` | Total encoded certificate and supplied transaction records |

These values, verifier work and memory bounds, and devp2p message assignments MUST be fixed before activation, with benchmarks demonstrating practical local proving on representative consumer hardware for the supported workloads. `MAX_PROVEN_VERIFY_GAS` MUST respect the ordinary transaction execution-gas cap. Recursive circuits MUST also bound their private input counts and verification work independently of their output size. Nodes MUST reject unknown or inactive profiles.

### Certified statement

Let `T` be the exact canonical typed transaction envelope, including all signature bytes, and `A` its assumption vector. A statement commits to:

```text
statement_digest = keccak256(rlp(["eip-8361/statement", profile_id, keccak256(T), A, P]))
```

Here the domain string is encoded as ASCII bytes and `P` is the payer. `sig_hash(T)` remains an execution input, but is insufficient as the certificate's transaction identifier because it omits some signature bytes observable by account code.

The circuit MUST prove the complete recognized validation prefix through successful completion of the first top-level frame that leaves payer `P` set. It enforces the fork's EVM and frame semantics, approval scopes, nonce effects, gas accounting, and EIP-8141 structural and trace rules, replacing only `MAX_VERIFY_GAS` with `MAX_PROVEN_VERIFY_GAS`. The existing state-gas bound remains. An `APPROVE` in a nested call followed by an enclosing revert does not establish successful validation.

`A` is a list of exact `(selector, value)` assumptions, ordered by the canonical encoding of `selector`, with no duplicate selectors. The profile defines typed selectors for account nonce, balance, code hash, existence, storage slots, and permitted execution-context inputs. Every external input affecting the prefix MUST be fixed by `T`, the profile, `A`, or the native checks below, including implicit inputs to account warmth and gas charging. Declaring an input does not permit an otherwise forbidden access.

Supplied code MUST match its recorded code hash. Execution uses normal transaction-local writes and rollback: a read after a deployment write cannot substitute an independent initial-state value. The circuit performs no state-tree lookup; nodes check assumptions against their own state and execution context. Arbitrary threshold assumptions about EVM reads are not supported.

### Native checks

The circuit MAY assume successful EIP-8141 protocol-signature verification and EIP-8288 dependency verification. Nodes MUST derive both lists from `T` and verify them through their respective mechanisms. Verification executed by account bytecode, including checks of `ARBITRARY` signature witnesses, MUST remain inside the proven computation.

The circuit MAY defer the protocol balance check at `APPROVE`. It may omit that payer balance from `A` only if it proves the prefix leaves the balance unchanged before payment and does not otherwise observe it, including through implicit checks. Nodes then check `balance(P) >= max_cost(T)` natively. All other approval effects, account-existence and state-gas checks, and completion of the enclosing frame remain proven. Any other dependence on that balance requires an exact assumption. EIP-8141's reservations, pending withdrawals, and payer-exposure rules always apply separately.

The canonical expiry frame's predicate MAY likewise be checked natively when the circuit establishes the required runtime-code match and frame semantics. The deadline comes from `T`. No unsigned metadata condition changes the transaction's authorization or on-chain validity.

### Recursive batches

A single certificate contains one statement digest and a proof under `PREFIX_VK` with public input `statement_digest`. A batch certificate contains a strictly increasing list `digests`, with `1 <= len(digests) <= MAX_BATCH_STATEMENTS`, and a proof under `BATCH_VK` with public input:

```text
batch_digest = keccak256(rlp(["eip-8361/batch", profile_id, len(digests), digests]))
```

The batch circuit MUST verify single or batch certificates under the same profile's fixed keys and prove that `digests` is exactly the sorted, deduplicated union of their statements. It MUST reject invalid child proofs or mismatched commitments. A batch certifies independent conditional statements; it does not certify their joint executability or shared funding.

Nodes MAY admit or forward any supplied subset of the certified transactions, retaining the complete digest list and unchanged proof. Each supplied `(T, A, P)` MUST match a listed digest, with at most one record per digest. Unprovided members create no pool entries or obligations and need not be retrieved. A stale member does not invalidate another member's certificate or prevent its admission. Removing digests from the certificate requires a new proof; dropping transaction records does not.

### Admission and revalidation

Before admission, a node MUST:

1. Enforce profile, byte and count limits before large allocations; check canonical encodings, transaction structure and intrinsic validity.
2. Match each supplied transaction record to its certified digest and check its current assumptions, protocol nonce, expiry, fee eligibility and available payer funding.
3. Verify the single or batch proof, unless the exact certificate is already verified under the active profile.
4. Verify the transaction's protocol signatures and dependencies separately. Native protocol-signature work remains bounded by EIP-8141's `MAX_VERIFY_GAS`; EIP-8288 limits also remain in force.
5. Apply ordinary pool admission, replacement and reservation accounting to each admitted transaction. Shared funding MUST be reserved sequentially, not tested independently against the same unreserved balance.

Passing these checks permits admission without prefix simulation. A valid certificate is not sufficient if any native check fails. Nodes MAY decline certificates under local resource policy.

Nodes MUST recheck affected assumptions and native obligations on head changes and update reservations on pool changes; they SHOULD index dependencies to avoid scanning unaffected transactions. Verified proofs need not be reverified while the profile remains active. Failed assumptions require a replacement certificate or ordinary simulated admission; nodes MAY retain bounded parked entries but MUST NOT propagate them as currently admissible.

A builder relying on a certificate MUST check its assumptions and native obligations against the state and context at the proposed insertion point. If they fail, the certificate provides no assurance there; any fallback simulation remains subject to the builder's unpaid-work limits. Included transactions execute normally.

### Transport

A negotiated devp2p extension announces certificate identifiers and sizes and retrieves certificates and transaction records on demand. Single and batch kinds MUST be distinguished; identifiers commit to the profile, kind, full digest list, and proof bytes. Proofs for this EIP MUST NOT be interpreted as EIP-8288 aggregation proofs merely because they share a backend.

Nodes MUST verify a certificate before forwarding it and MUST bound verification queues, bandwidth, and cached bytes, including duplicate and overlapping batches. Forwarded transaction records MUST pass admission checks. Cached certificates may support multiple pending members and can be released when no retained member needs them. Certificates are never included in blocks or receipts. Nodes are not required to generate proofs, aggregate, or wait for a full batch.

## Rationale

**Local proving and public admission.** The intended path is wallet proof generation followed by ordinary public gossip. A general zkVM running a fork-specific EVM interpreter is one implementation route; specialized execution circuits are another. Only the bounded validation prefix is proven, without state-tree membership proofs. Receiving nodes verify certificates and need not run a prover. Delegation is optional and outside this protocol. Exact frame, gas and trace semantics still require careful implementation and audit. Reusing EIP-8288's backend requires a compatible profile; another zkVM adds a verifier or requires wrapping.

**Cost and applications.** Exceeding `MAX_VERIFY_GAS` does not establish that a STARK is economical: EVM gas, native execution time and proving work differ. Benchmarks must compare optimized simulation and caching with proof decoding, valid and invalid verification, assumption checks, bandwidth and memory. They must report consumer hardware specifications, prover peak memory and latency, including recursion, against assumption lifetimes and transaction deadlines. The target is useful bounded workloads, without assuming every device can promptly prove every permitted prefix. Stable, expensive authorization and batches of independent validations are candidate workloads. Cryptography expressible as EIP-8288 dependencies can also avoid in-EVM verification at inclusion; this EIP retains that execution cost.

**Amortization.** Peers may recursively combine independently generated certificates during gossip, spreading outer proof and verification costs over usable members. Metadata and state checks remain per transaction. Aggregation before public gossip can save first-hop leaf verification; aggregation after a node verifies every leaf saves subsequent hops only. Batching adds proving work and waiting time, without eliminating prefix proving or on-chain execution. Mostly stale batches, sparse traffic or short deadlines may favor individual certificates or simulation; public admission does not require an aggregator.

**Reusable assumptions.** Exact assumptions survive unrelated state changes. Native payment checks tolerate balance churn when the code has no other balance dependence; reservations still apply. Arbitrary `GEQ` assumptions would require proving success for every satisfying input, which one execution at a threshold cannot establish. Ordinary simulation results can also be cached while their inputs remain valid.

## Backwards Compatibility

This is optional networking policy with no new transaction type, opcode, or consensus gas change. Nodes without support may simulate within their existing limits or decline admission, so propagation depends on participating peers. Public admission grants no additional inclusion-list eligibility; any such extension requires its own consensus rules.

## Test Cases

Profiles MUST cover at least:

- Changed `ARBITRARY` witness bytes; omitted code or storage assumptions; incorrect reads after deployment writes; insufficient state gas; nested approval followed by enclosing revert.
- Balance changes with and without another balance dependence; changed paymaster owner; insufficient shared reservations; expired transactions; different insertion-point context.
- Invalid external signatures or dependencies despite a valid prefix proof; wrong profile or verification key; malformed and oversized objects.
- Invalid recursive children; altered, duplicate or missing digests; subset delivery; overlapping batches; one stale member alongside valid members; private recursion work exceeding its bound despite a small final list.

## Security Considerations

Certificate soundness depends on both the proof system and the prefix interpreter. Fork changes require updated profiles; cached results MUST NOT cross incompatible profiles. Bugs can admit invalid transactions and cause unpaid work even though ordinary execution remains authoritative. Invalid proofs require no honest proving effort to send, so size caps alone are insufficient: verifier work, memory, and queue bounds must cover adversarial inputs. Restricting state access, funding exposure and revalidation remains necessary even when proof verification is succinct.
