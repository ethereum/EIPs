## Abstract

This EIP closes the inflow of the `BLS_WITHDRAWAL_PREFIX` (`0x00`) withdrawal credential type into the active validator set. Deposits with `0x00` credentials are still registered, with their full balance, but a validator with `0x00` credentials is never activated. Once its credentials are changed to `0x01` execution credentials with a `BLSToExecutionChange`, its balance is queued again as a pending deposit, so it becomes active only through the activation churn. Existing active `0x00` validators are unaffected. They continue to validate, earn rewards, and accrue penalties.

This is the first stage of a staged deprecation of `0x00`, and it is intended as the notice step of a documented timeline. With activation gated, the active `0x00` population cannot grow. Later stages of the deprecation are left to separate EIPs.

## Motivation

The `0x00` credential type is the original genesis-era withdrawal format: `0x00 || sha256(withdrawal_bls_pubkey)[1:]`, with withdrawal controlled by a BLS key and no execution address. Since Capella opened one-way conversion to `0x01`, the population has fallen from roughly 600,000 to about 9,200 validators (mainnet, August 2026), but the decline has stalled: conversion inclusions have decayed to double digits per month, and several hundred of the remaining validators have not attested for over six months, which suggests lost keys.

Despite this, deposits can still create new `0x00` validators, and they still do. Mainnet data shows 58 validators created with `0x00` credentials in 2026, including one batch of 50 by a single entity in March. These validators have no execution address, so they cannot use execution-layer triggerable exits ([EIP-7002](./eip-7002.md)), and a lost withdrawal key leaves their balance permanently stranded on the consensus layer. Every `0x00` validator also extends the protocol's dependence on `process_bls_to_execution_change`, its gossip topic, its operation pool, and the `0x00` branch of every credential check, all of which must be carried into and hardened for the post-quantum transition as long as the population exists.

Keeping new `0x00` validators out of the active set prevents the legacy population from growing while the remaining stages of the deprecation are scheduled, and it signals the planned deprecation of `0x00` credentials in consensus code rather than in announcements alone.

This EIP does not exit, penalize, or otherwise change existing `0x00` validators. They continue to validate, and their balances remain unchanged.

## Specification

### Consensus layer

#### Activation

`is_eligible_for_activation` is modified so that validators with `0x00` withdrawal credentials are not activated:

```python
def is_eligible_for_activation(state: BeaconState, validator: Validator) -> bool:
    return (
        # Placement in queue is finalized
        validator.activation_eligibility_epoch <= state.finalized_checkpoint.epoch
        # Has not yet been activated
        and validator.activation_epoch == FAR_FUTURE_EPOCH
        # [New in this EIP] Does not have BLS withdrawal credentials
        and validator.withdrawal_credentials[:1] != BLS_WITHDRAWAL_PREFIX
    )
```

Deposit processing is unchanged. A valid deposit with `0x00` credentials for an unknown public key registers a validator with its full balance, and a top-up to an existing validator, including a `0x00` validator, increases its balance.

#### BLS to execution change

`process_bls_to_execution_change` is modified so that a validator that changes its credentials before it is activated has its balance queued as a pending deposit:

```python
def process_bls_to_execution_change(
    state: BeaconState, signed_address_change: SignedBLSToExecutionChange
) -> None:
    address_change = signed_address_change.message
    assert address_change.validator_index < len(state.validators)
    validator = state.validators[address_change.validator_index]
    assert validator.withdrawal_credentials[:1] == BLS_WITHDRAWAL_PREFIX
    assert validator.withdrawal_credentials[1:] == sha256(address_change.from_bls_pubkey)[1:]
    domain = compute_domain(
        DOMAIN_BLS_TO_EXECUTION_CHANGE, genesis_validators_root=state.genesis_validators_root
    )
    signing_root = compute_signing_root(address_change, domain)
    assert bls.Verify(address_change.from_bls_pubkey, signing_root, signed_address_change.signature)
    validator.withdrawal_credentials = Bytes32(
        ETH1_ADDRESS_WITHDRAWAL_PREFIX + b"\x00" * 11 + address_change.to_execution_address
    )
    # [New in this EIP] Send the balance of a never activated validator back through the churn
    if validator.activation_epoch == FAR_FUTURE_EPOCH:
        balance = state.balances[address_change.validator_index]
        state.balances[address_change.validator_index] = Gwei(0)
        validator.effective_balance = Gwei(0)
        validator.activation_eligibility_epoch = FAR_FUTURE_EPOCH
        state.pending_deposits.append(
            PendingDeposit(
                pubkey=validator.pubkey,
                withdrawal_credentials=validator.withdrawal_credentials,
                amount=balance,
                signature=G2_POINT_AT_INFINITY,
                slot=GENESIS_SLOT,
            )
        )
```

`process_bls_to_execution_change` does not require the validator to be active, so a registered but never activated `0x00` validator can change its credentials to `0x01`. Its balance then re-enters through `process_pending_deposits` as a top-up, which consumes activation churn, after which the validator is placed in the activation queue and activated through the standard flow. The re-queue follows the treatment of not yet active validators in the [EIP-7251](./eip-7251.md) fork upgrade.

The check applies to every validator that has not been assigned an activation epoch when this EIP activates, including validators created from deposits submitted before the fork. Validators that are already active or already assigned an activation epoch are unaffected.

## Rationale

### Gate activation instead of rejecting deposits

The consensus layer has no mechanism to refund a deposit. A `0x00` credential commits only to the hash of a BLS withdrawal public key, and [EIP-6110](./eip-6110.md) deposit requests do not carry the depositor's address. Rejecting a deposit therefore destroys it: the ETH stays in the deposit contract permanently.

Gating activation reaches the same goal, an active `0x00` population that cannot grow, without destroying any ETH. The deposited balance stays in the registry, and the holder of the withdrawal key, which the `0x00` credential already commits to, can recover it at any time by changing credentials and activating.

The amounts at stake are not marginal. Mainnet data cited in the motivation shows 58 validators created with `0x00` credentials in 2026, including a single batch of 50 in March. Under a rejection rule that batch alone would have destroyed 1,600 ETH.

### Long deposit queues

Pending deposits are processed under the activation churn limit, so the time between submitting a deposit and processing it grows with the queue. At the mainnet cap of `MAX_PER_EPOCH_ACTIVATION_EXIT_CHURN_LIMIT` (256 ETH per epoch), the queue drains at most 57,600 ETH per day, and a backlog of 1,000,000 ETH takes about 17 days to clear. With a rejection rule and no grandfathering, a `0x00` deposit that was valid when it was submitted is destroyed if it is still queued at the fork. With the activation gate, the same deposit is registered and remains recoverable.

### Re-queue on credential change

Since [EIP-7251](./eip-7251.md), activation churn is charged when a deposit is processed, and every validator whose queue placement is finalized is activated without a further limit. A parked `0x00` validator is funded and its queue placement is finalized, so without the re-queue a credential change would activate it immediately. `BLSToExecutionChange` operations do not queue: with `MAX_BLS_TO_EXECUTION_CHANGES` of 16 per block, a holder who parks validators over time could activate 512 validators, about 16,384 ETH, in a single epoch, 64 times the 256 ETH per epoch churn limit, and could choose the moment of activation whenever the deposit queue is long. Queuing the balance again as a pending deposit when the credentials change keeps the activation churn as the bound on how fast active stake grows. The parked balance goes through the churn twice, which is acceptable for a deprecated path.

## Backwards Compatibility

This EIP introduces backward-incompatible changes to consensus-layer state transition and must be scheduled with a hard fork. No execution-layer changes are required. Deposit tooling is unaffected. A validator created with `0x00` credentials is registered but is not activated until its credentials are changed.

## Test Cases

The following cases define the required behavior:

- A valid `0x00` pending deposit for an unknown public key registers a validator with its full balance.
- A registered `0x00` validator whose queue placement is finalized is not activated.
- A `BLSToExecutionChange` for a never activated validator queues its full balance as a pending deposit and resets its effective balance and activation eligibility.
- A `BLSToExecutionChange` for an active validator leaves its balance unchanged.
- A pre-fork `0x00` deposit that is still pending when this EIP activates registers a validator that is not activated.
- A `0x00` deposit followed by a `0x01` deposit for the same public key registers one `0x00` validator holding both amounts.
- A top-up to an existing `0x00` validator is applied.
- An active `0x00` validator stays active.
- Valid deposits that create `0x01` or `0x02` validators are applied and activated as before.

## Security Considerations

### Registry growth

Registered but never activated `0x00` validators occupy registry entries. Creating one requires a deposit of at least `MIN_DEPOSIT_AMOUNT`, the same cost as creating an underfunded validator today, so the gate adds no new way to grow the registry.

### Activation churn

Every path to activation for a `0x00` deposit goes through `process_pending_deposits`, so the gate adds no way to grow the active set faster than the activation churn.

### Stranded balances

A `0x00` validator whose withdrawal key is lost cannot change its credentials, so its balance remains in the registry. This is the same outcome as a rejected deposit for that holder, but every holder who still has the withdrawal key can recover their funds.
