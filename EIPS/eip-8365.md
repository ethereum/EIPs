## Abstract

This EIP closes the inflow of the `BLS_WITHDRAWAL_PREFIX` (`0x00`) and `ETH1_ADDRESS_WITHDRAWAL_PREFIX` (`0x01`) withdrawal credential types into the active validator set. Deposits with `0x00` or `0x01` credentials are still registered, with their full balance, but a validator with `0x00` or `0x01` credentials is never activated. Once it switches to `0x02` compounding credentials with a consolidation request, its balance is queued again as a pending deposit, so it becomes active only through the activation churn. A never activated `0x00` or `0x01` validator can also exit at any time, with a voluntary exit or, for `0x01`, a withdrawal request, after which its balance is withdrawn to its execution address, which a `0x00` validator first has to set with a `BLSToExecutionChange`. Existing active `0x00` and `0x01` validators are unaffected. They continue to validate, earn rewards, and accrue penalties.

For `0x00`, this is the first stage of a staged deprecation, and it is intended as the notice step of a documented timeline. With activation gated, the active `0x00` and `0x01` populations cannot grow, and every validator that becomes active after this EIP has `0x02` credentials. Later stages of the deprecation are left to separate EIPs.

## Motivation

The `0x00` credential type is the original genesis-era withdrawal format: `0x00 || sha256(withdrawal_bls_pubkey)[1:]`, with withdrawal controlled by a BLS key and no execution address. Since Capella opened one-way conversion to `0x01`, the population has fallen from roughly 600,000 to about 9,200 validators (mainnet, August 2026), but the decline has stalled: conversion inclusions have decayed to double digits per month, and several hundred of the remaining validators have not attested for over six months, which suggests lost keys.

Despite this, deposits can still create new `0x00` validators, and they still do. Mainnet data shows 58 validators created with `0x00` credentials in 2026, including one batch of 50 by a single entity in March. These validators have no execution address, so they cannot use execution-layer triggerable exits ([EIP-7002](./eip-7002.md)), and a lost withdrawal key leaves their balance permanently stranded on the consensus layer. Every `0x00` validator also extends the protocol's dependence on `process_bls_to_execution_change`, its gossip topic, its operation pool, and the `0x00` branch of every credential check, all of which must be carried into and hardened for the post-quantum transition as long as the population exists.

Keeping new `0x00` validators out of the active set prevents the legacy population from growing while the remaining stages of the deprecation are scheduled, and it signals the planned deprecation of `0x00` credentials in consensus code rather than in announcements alone.

The `0x01` credential type has an execution address but caps the effective balance at `MIN_ACTIVATION_BALANCE` (32 ETH). Stake that enters with `0x01` credentials therefore adds one validator, one registry entry that performs duties, and one attestation per epoch for every 32 ETH. [EIP-7251](./eip-7251.md) introduced `0x02` compounding credentials, with an effective balance of up to `MAX_EFFECTIVE_BALANCE_ELECTRA` (2,048 ETH), so that the same stake can be represented by fewer validators, but it left `0x01` open for new validators. As long as new stake can enter as `0x01`, the active set keeps growing in 32 ETH units while consolidation works to shrink it. Gating `0x01` activation makes `0x02` the only credential type with which a validator can become active.

This EIP does not exit, penalize, or otherwise change existing `0x00` or `0x01` validators. They continue to validate, and their balances remain unchanged.

## Specification

### Consensus layer

#### Activation

`is_eligible_for_activation` is modified so that validators with `0x00` or `0x01` withdrawal credentials are not activated:

```python
def is_eligible_for_activation(state: BeaconState, validator: Validator) -> bool:
    return (
        # Placement in queue is finalized
        validator.activation_eligibility_epoch <= state.finalized_checkpoint.epoch
        # Has not yet been activated
        and validator.activation_epoch == FAR_FUTURE_EPOCH
        # [New in this EIP] Does not have BLS or ETH1 withdrawal credentials
        and validator.withdrawal_credentials[:1]
        not in (BLS_WITHDRAWAL_PREFIX, ETH1_ADDRESS_WITHDRAWAL_PREFIX)
    )
```

Deposit processing is unchanged. A valid deposit with `0x00` or `0x01` credentials for an unknown public key registers a validator with its full balance, and a top-up to an existing validator, including a `0x00` or `0x01` validator, increases its balance.

`process_bls_to_execution_change` is unchanged. It does not require the validator to be active, so a registered but never activated `0x00` validator can change its credentials to `0x01`. It is still not activated until it switches to `0x02`.

#### Switch to compounding

`is_valid_switch_to_compounding_request` is modified so that a validator that has never been activated can switch to compounding credentials:

```python
def is_valid_switch_to_compounding_request(
    state: BeaconState, consolidation_request: ConsolidationRequest
) -> bool:
    # Switch to compounding requires source and target be equal
    if consolidation_request.source_pubkey != consolidation_request.target_pubkey:
        return False

    # Verify pubkey exists
    source_pubkey = consolidation_request.source_pubkey
    validator_pubkeys = [validator.pubkey for validator in state.validators]
    if source_pubkey not in validator_pubkeys:
        return False

    source_validator = state.validators[ValidatorIndex(validator_pubkeys.index(source_pubkey))]

    # Verify request has been authorized
    if source_validator.withdrawal_credentials[12:] != consolidation_request.source_address:
        return False

    # Verify source withdrawal credentials
    if not has_eth1_withdrawal_credential(source_validator):
        return False

    # [Modified in this EIP] Verify the source is active or has never been activated
    current_epoch = get_current_epoch(state)
    if (
        not is_active_validator(source_validator, current_epoch)
        and source_validator.activation_epoch != FAR_FUTURE_EPOCH
    ):
        return False

    # Verify exit for source has not been initiated
    if source_validator.exit_epoch != FAR_FUTURE_EPOCH:
        return False

    return True
```

`switch_to_compounding_validator` is modified so that a validator that switches before it is activated has its balance queued as a pending deposit:

```python
def switch_to_compounding_validator(state: BeaconState, index: ValidatorIndex) -> None:
    validator = state.validators[index]
    validator.withdrawal_credentials = Bytes32(
        COMPOUNDING_WITHDRAWAL_PREFIX + validator.withdrawal_credentials[1:]
    )
    # [New in this EIP] Send the balance of a never activated validator back through the churn
    if validator.activation_epoch == FAR_FUTURE_EPOCH:
        balance = state.balances[index]
        state.balances[index] = Gwei(0)
        validator.effective_balance = Gwei(0)
        validator.activation_eligibility_epoch = FAR_FUTURE_EPOCH
        state.pending_deposits.append(
            PendingDeposit(
                pubkey=validator.pubkey,
                withdrawal_credentials=validator.withdrawal_credentials,
                amount=balance,
                signature=G2_POINT_AT_INFINITY,
                slot=GENESIS_SLOT,
            )
        )
    else:
        queue_excess_active_balance(state, index)
```

A registered but never activated `0x01` validator switches to `0x02` with a consolidation request whose source and target are its own public key, sent from the execution address in its withdrawal credentials. Its balance then re-enters through `process_pending_deposits` as a top-up, which consumes activation churn, after which the validator is placed in the activation queue and activated through the standard flow. The re-queue follows the treatment of not yet active validators in the [EIP-7251](./eip-7251.md) fork upgrade. A never activated `0x00` validator first changes its credentials to `0x01` with a `BLSToExecutionChange` and then switches in the same way.

#### Exit of never activated validators

A validator is gated if it has never been assigned an activation epoch and has `0x00` or `0x01` withdrawal credentials:

```python
def is_activation_gated_validator(validator: Validator) -> bool:
    return (
        validator.activation_epoch == FAR_FUTURE_EPOCH
        and validator.withdrawal_credentials[:1]
        in (BLS_WITHDRAWAL_PREFIX, ETH1_ADDRESS_WITHDRAWAL_PREFIX)
    )
```

A gated validator exits and becomes withdrawable in the current epoch, without consuming exit churn:

```python
def exit_gated_validator(state: BeaconState, index: ValidatorIndex) -> None:
    validator = state.validators[index]
    current_epoch = get_current_epoch(state)
    validator.exit_epoch = current_epoch
    validator.withdrawable_epoch = current_epoch
```

`process_voluntary_exit` is modified so that a gated validator can exit:

```python
def process_voluntary_exit(state: BeaconState, signed_voluntary_exit: SignedVoluntaryExit) -> None:
    voluntary_exit = signed_voluntary_exit.message
    validator = state.validators[voluntary_exit.validator_index]
    # [New in this EIP]
    is_gated = is_activation_gated_validator(validator)
    # [Modified in this EIP] Verify the validator is active or gated
    assert is_gated or is_active_validator(validator, get_current_epoch(state))
    # Verify exit has not been initiated
    assert validator.exit_epoch == FAR_FUTURE_EPOCH
    # Exits must specify an epoch when they become valid; they are not valid before then
    assert get_current_epoch(state) >= voluntary_exit.epoch
    # [Modified in this EIP] Verify the validator has been active long enough, unless it is gated
    assert is_gated or (
        get_current_epoch(state) >= validator.activation_epoch + SHARD_COMMITTEE_PERIOD
    )
    # Only exit validator if it has no pending withdrawals in the queue
    assert get_pending_balance_to_withdraw(state, voluntary_exit.validator_index) == 0
    # Verify signature
    domain = compute_domain(
        DOMAIN_VOLUNTARY_EXIT, CAPELLA_FORK_VERSION, state.genesis_validators_root
    )
    signing_root = compute_signing_root(voluntary_exit, domain)
    assert bls.Verify(validator.pubkey, signing_root, signed_voluntary_exit.signature)
    # [Modified in this EIP] Initiate exit
    if is_gated:
        exit_gated_validator(state, voluntary_exit.validator_index)
    else:
        initiate_validator_exit(state, voluntary_exit.validator_index)
```

`process_withdrawal_request` is modified so that a full exit request exits a gated validator:

```python
def process_withdrawal_request(state: BeaconState, withdrawal_request: WithdrawalRequest) -> None:
    amount = withdrawal_request.amount
    is_full_exit_request = amount == FULL_EXIT_REQUEST_AMOUNT

    # If partial withdrawal queue is full, only full exits are processed
    if (
        len(state.pending_partial_withdrawals) == PENDING_PARTIAL_WITHDRAWALS_LIMIT
        and not is_full_exit_request
    ):
        return

    validator_pubkeys = [validator.pubkey for validator in state.validators]
    # Verify pubkey exists
    request_pubkey = withdrawal_request.validator_pubkey
    if request_pubkey not in validator_pubkeys:
        return
    index = ValidatorIndex(validator_pubkeys.index(request_pubkey))
    validator = state.validators[index]

    # Verify withdrawal credentials
    has_correct_credential = has_execution_withdrawal_credential(validator)
    is_correct_source_address = (
        validator.withdrawal_credentials[12:] == withdrawal_request.source_address
    )
    if not (has_correct_credential and is_correct_source_address):
        return
    # [New in this EIP] Exit a gated validator on a full exit request
    if is_activation_gated_validator(validator):
        if is_full_exit_request and validator.exit_epoch == FAR_FUTURE_EPOCH:
            exit_gated_validator(state, index)
        return
    # Verify the validator is active
    if not is_active_validator(validator, get_current_epoch(state)):
        return
    # Verify exit has not been initiated
    if validator.exit_epoch != FAR_FUTURE_EPOCH:
        return
    # Verify the validator has been active long enough
    if get_current_epoch(state) < validator.activation_epoch + SHARD_COMMITTEE_PERIOD:
        return

    pending_balance_to_withdraw = get_pending_balance_to_withdraw(state, index)

    if is_full_exit_request:
        # Only exit validator if it has no pending withdrawals in the queue
        if pending_balance_to_withdraw == 0:
            initiate_validator_exit(state, index)
        return

    has_sufficient_effective_balance = validator.effective_balance >= MIN_ACTIVATION_BALANCE
    has_excess_balance = (
        state.balances[index] > MIN_ACTIVATION_BALANCE + pending_balance_to_withdraw
    )

    # Only allow partial withdrawals with compounding withdrawal credentials
    if (
        has_compounding_withdrawal_credential(validator)
        and has_sufficient_effective_balance
        and has_excess_balance
    ):
        to_withdraw = min(
            state.balances[index] - MIN_ACTIVATION_BALANCE - pending_balance_to_withdraw, amount
        )
        exit_queue_epoch = compute_exit_epoch_and_update_churn(state, to_withdraw)
        withdrawable_epoch = exit_queue_epoch + MIN_VALIDATOR_WITHDRAWABILITY_DELAY
        state.pending_partial_withdrawals.append(
            PendingPartialWithdrawal(
                validator_index=index,
                amount=to_withdraw,
                withdrawable_epoch=withdrawable_epoch,
            )
        )
```

A gated validator can be exited with a voluntary exit signed by its signing key, whatever its credentials, or, if it has `0x01` credentials, with a full exit withdrawal request from the execution address in its withdrawal credentials. An exited `0x01` validator is fully withdrawable, and the withdrawal sweep pays its whole balance to that address. An exited `0x00` validator has no execution address, so its balance stays in the registry until its credentials are changed to `0x01` with a `BLSToExecutionChange`, after which the sweep pays it out. An exited validator cannot switch to compounding, because `is_valid_switch_to_compounding_request` requires that no exit has been initiated, so it is never activated.

The check applies to every validator that has not been assigned an activation epoch when this EIP activates, including validators created from deposits submitted before the fork. Validators that are already active or already assigned an activation epoch are unaffected.

## Rationale

### Gate activation instead of rejecting deposits

The consensus layer has no mechanism to refund a deposit. A `0x00` credential commits only to the hash of a BLS withdrawal public key, and [EIP-6110](./eip-6110.md) deposit requests do not carry the depositor's address. Rejecting a deposit therefore destroys it: the ETH stays in the deposit contract permanently.

Gating activation reaches the same goal, active `0x00` and `0x01` populations that cannot grow, without destroying any ETH. The deposited balance stays in the registry, and the holder of the withdrawal key or execution address that the credential already commits to can recover it at any time by switching to `0x02` and activating.

The amounts at stake are not marginal. Mainnet data cited in the motivation shows 58 validators created with `0x00` credentials in 2026, including a single batch of 50 in March. Under a rejection rule that batch alone would have destroyed 1,600 ETH. Deposit tooling that still defaults to `0x01` when this EIP activates would lose every deposit under a rejection rule.

### Long deposit queues

Pending deposits are processed under the activation churn limit, so the time between submitting a deposit and processing it grows with the queue. At the mainnet cap of `MAX_PER_EPOCH_ACTIVATION_EXIT_CHURN_LIMIT` (256 ETH per epoch), the queue drains at most 57,600 ETH per day, and a backlog of 1,000,000 ETH takes about 17 days to clear. With a rejection rule and no grandfathering, a `0x00` or `0x01` deposit that was valid when it was submitted is destroyed if it is still queued at the fork. With the activation gate, the same deposit is registered and remains recoverable.

### Switch to compounding as the path to activation

A `0x01` validator that has never been activated needs a way to reach `0x02`. The switch to compounding from [EIP-7251](./eip-7251.md) already performs that credential change for active validators and is authorized by the execution address in the withdrawal credentials. Allowing it for never activated validators reuses the existing request type and contract, and adds no new operation. `BLSToExecutionChange` is left unchanged and still produces `0x01` credentials, so the `0x00` path is the existing credential change followed by the same switch.

### Re-queue on switch

Since [EIP-7251](./eip-7251.md), activation churn is charged when a deposit is processed, and every validator whose queue placement is finalized is activated without a further limit. A parked `0x00` or `0x01` validator is funded and its queue placement is finalized, so without the re-queue a switch to `0x02` would activate it immediately. Top-ups are applied to parked validators, so a parked balance is not limited to 32 ETH. With `MAX_CONSOLIDATION_REQUESTS_PER_PAYLOAD` of 2 per block, a holder who parks validators over time could activate 64 validators in a single epoch, up to 131,072 ETH of effective balance at 2,048 ETH each, 512 times the 256 ETH per epoch churn limit, and could choose the moment of activation whenever the deposit queue is long. Queuing the balance again as a pending deposit when the validator switches keeps the activation churn as the bound on how fast active stake grows. The parked balance goes through the churn twice, which is acceptable for a deprecated path.

### Exit without activation

Before this EIP, a voluntary exit and a withdrawal request both require an active validator, so a validator that is never activated can never leave. A parked `0x01` validator whose withdrawal address is a contract that cannot call the consolidation request contract could then neither switch nor exit, and a holder who does not want a `0x02` validator would have no way to get the deposit back. Allowing a gated validator to exit removes both cases: the signing key is always sufficient to exit, and for `0x01` the withdrawal address is as well.

A gated validator has never been part of the active set. Its exit does not change the active stake, so it does not go through the exit churn, and it has never been slashable, so the `MIN_VALIDATOR_WITHDRAWABILITY_DELAY` that keeps an exited validator's balance available for slashing is not needed. The exit and the withdrawability therefore take effect in the current epoch.

The exit is limited to validators with `0x00` or `0x01` credentials. A never activated `0x02` validator is either waiting for its activation or underfunded, and this EIP does not change either case.

## Backwards Compatibility

This EIP introduces backward-incompatible changes to consensus-layer state transition and must be scheduled with a hard fork. No execution-layer changes are required. Deposit tooling that creates validators with `0x00` or `0x01` credentials must create them with `0x02` credentials instead. A validator created with `0x00` or `0x01` credentials is registered but is not activated until it switches to `0x02`.

## Test Cases

The following cases define the required behavior:

- A valid `0x00` or `0x01` pending deposit for an unknown public key registers a validator with its full balance.
- A registered `0x00` or `0x01` validator whose queue placement is finalized is not activated.
- A `BLSToExecutionChange` for a never activated validator changes its credentials to `0x01`, leaves its balance unchanged, and does not activate it.
- A switch to compounding for a never activated `0x01` validator queues its full balance as a pending deposit and resets its effective balance and activation eligibility.
- A switch to compounding for an active `0x01` validator queues only its balance above `MIN_ACTIVATION_BALANCE`.
- A switch to compounding for a never activated validator from an address other than the one in its withdrawal credentials is ignored.
- Switches for more never activated validators than the activation churn allows in one epoch have their balances applied across several epochs.
- A voluntary exit for a never activated `0x00` or `0x01` validator sets its exit epoch and withdrawable epoch to the current epoch and leaves the exit churn state unchanged.
- A full exit withdrawal request from the withdrawal address of a never activated `0x01` validator has the same effect, and a partial withdrawal request for it is ignored.
- An exited never activated `0x01` validator has its full balance withdrawn by the sweep.
- An exited never activated `0x00` validator keeps its balance until a `BLSToExecutionChange`, after which the sweep withdraws it.
- A switch to compounding for an exited never activated validator is ignored, and the validator is never activated.
- A voluntary exit for a never activated `0x02` validator is rejected.
- A pre-fork `0x00` or `0x01` deposit that is still pending when this EIP activates registers a validator that is not activated.
- A `0x01` validator that has been assigned an activation epoch before this EIP activates is activated.
- A `0x00` deposit followed by a `0x01` deposit for the same public key registers one `0x00` validator holding both amounts.
- A top-up to an existing `0x00` or `0x01` validator is applied.
- An active `0x00` or `0x01` validator stays active.
- Valid deposits that create `0x02` validators are applied and activated as before.

## Security Considerations

### Registry growth

Registered but never activated `0x00` and `0x01` validators occupy registry entries. Creating one requires a deposit of at least `MIN_DEPOSIT_AMOUNT`, the same cost as creating an underfunded validator today, so the gate adds no new way to grow the registry.

### Activation churn

Every path to activation for a `0x00` or `0x01` deposit goes through `process_pending_deposits`, so the gate adds no way to grow the active set faster than the activation churn.

### Stranded balances

A `0x00` validator whose withdrawal key is lost cannot change its credentials, so its balance remains in the registry. This is the same outcome as a rejected deposit for that holder, but every holder who still has the withdrawal key can recover their funds.

A never activated `0x01` validator can only switch through a consolidation request sent from its withdrawal address. If that address is a contract that cannot call the consolidation request contract, the validator cannot switch, but it can exit with a voluntary exit signed by its signing key, and its balance is then withdrawn to the withdrawal address. A balance is stranded only if both the signing key and the withdrawal address are unable to act.
