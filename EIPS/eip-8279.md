## Abstract

Meter the bytes execution adds to the [EIP-7928](./eip-7928.md) Block Access List in an explicit per-transaction counter, and fold that count, at 64 gas/byte, into the transaction's floor accumulator — checked at runtime before the BAL grows. The runtime count admits a transaction on an upper bound of what it could contribute; the final charge settles on the bytes it actually leaves in the BAL. Today an attacker can pack ~1.55 MiB into a 60M-gas block: 75% of gas on cold `SLOAD`s (32 BAL bytes per 2,100 gas) + 25% on calldata at 16 gas/byte. On top of [EIP-8131](./eip-8131.md)'s tx-content floor (same rate), block content is capped at `block_gas_limit / 64 ≈ 0.89 MiB`, a ~42% cut in worst-case block size at an unchanged gas limit. Neither EIP alone closes the bypass: 8131 does not price BAL bytes; 8279 reuses 8131's floor. In the sampled transactions, the runtime BAL component did not bind on its own; it matters mainly when the static floor is already high.

## Motivation

Every node must be able to handle the largest block an attacker can build, not the average one. Lowering that worst case buys headroom, which can either be spent on throughput by raising the gas limit or kept as a buffer. Left unspent, it is a direct gain in robustness. [EIP-7623](./eip-7623.md) caps worst-case block size by charging at least 64 gas per non-zero calldata byte. [EIP-7981](./eip-7981.md) extended that to access-list entries, and [EIP-8131](./eip-8131.md) generalises the floor to a uniform per-byte rule over all tx-content fields, including [EIP-7702](./eip-7702.md) authorization tuples and [EIP-4844](./eip-4844.md) blob versioned hashes. [EIP-7928](./eip-7928.md) introduces a new source of block bytes, the BAL, populated by runtime opcodes. None of those static floors cover it.

The cheapest BAL contributor is a cold `SLOAD`: 32 bytes for 2,100 gas. Combined with all-non-zero calldata, an attacker pushes intrinsic gas above the calldata floor, pays intrinsic, and gets calldata at 16 gas/byte while loading the rest of the block via `SLOAD` keys.

At a 60M gas limit:

| Attack | Worst-case block bytes |
|---|---|
| Pure calldata at floor | 0.894 MiB (target) |
| Auth-tuple bypass under EIP-8131 alone | 1.067 MiB |
| Cold-`SLOAD` bypass under EIP-7928 | **1.548 MiB** |

`SSTORE`, address access, `CREATE`, and successful EIP-7702 delegations give further vectors. This EIP closes them with one uniform mechanism.

### Constants

```
FLOOR_GAS_PER_BYTE          = 64   # per-byte floor rate (EIP-7976)
BAL_BYTES_PER_ADDRESS       = 20
BAL_BYTES_PER_STORAGE_KEY   = 32
BAL_BYTES_PER_STORAGE_VALUE = 32
BAL_BYTES_PER_BALANCE       = 32
BAL_BYTES_PER_NONCE         = 8
DELEGATION_CODE_BYTES       = 23   # EIP-7702 delegation marker length
```

### Data meter and floor accumulator

Clients keep two internal, per-transaction counters and six sets on the execution environment for the duration of the transaction:

- `bal_data_bytes` — an explicit count of the bytes execution could contribute to the BAL,
- `floor_gas_used` — the admitted floor, derived from the static seed plus the metered bytes,
- `metered_addresses` — the addresses whose 20-byte address has been metered,
- `metered_storage_keys` — the `(storage_address, key)` pairs whose 32-byte storage key has been metered,
- `metered_storage_values` — the `(storage_address, key)` pairs whose 32-byte storage value has been metered,
- `metered_balances` — the accounts whose 32-byte post-balance has been metered,
- `metered_nonces` — the accounts whose 8-byte post-nonce has been metered, and
- `metered_code` — the accounts whose deployed code bytes have been metered.

None is part of the signed transaction, RLP-encoded, gossiped, or persisted; no new transaction field or type is introduced. `floor_gas_used` is seeded with the static floor (below), `bal_data_bytes = 0`, and all six sets empty. The counters and sets are extended at runtime and never rewound. No gas is reserved or deducted from the execution budget; the admitted floor is checked against `tx.gas` so that the transaction can pay for every byte it might still leave in the BAL. The [final charge](#final-charge) is settled on the bytes it actually leaves.

```
def meter_bal_data(tx_env, num_bytes):
    new_bal_data_bytes = tx_env.bal_data_bytes + num_bytes
    new_floor = tx_env.static_floor + new_bal_data_bytes * FLOOR_GAS_PER_BYTE
    if new_floor > tx_env.gas_limit:    # tx_env.gas_limit = tx.gas
        raise OutOfGasError
    tx_env.bal_data_bytes = new_bal_data_bytes
    tx_env.floor_gas_used = new_floor

def meter_once(tx_env, metered_set, item, num_bytes):
    if item in metered_set:
        return
    meter_bal_data(tx_env, num_bytes)
    metered_set.add(item)

def meter_bal_address(tx_env, address):
    meter_once(tx_env, tx_env.metered_addresses, address, BAL_BYTES_PER_ADDRESS)

def meter_bal_storage_key(tx_env, storage_address, key):
    meter_once(tx_env, tx_env.metered_storage_keys, (storage_address, key), BAL_BYTES_PER_STORAGE_KEY)

def meter_bal_storage_value(tx_env, storage_address, key):
    meter_once(tx_env, tx_env.metered_storage_values, (storage_address, key), BAL_BYTES_PER_STORAGE_VALUE)

def meter_bal_balance(tx_env, address):
    meter_once(tx_env, tx_env.metered_balances, address, BAL_BYTES_PER_BALANCE)

def meter_bal_nonce(tx_env, address):
    meter_once(tx_env, tx_env.metered_nonces, address, BAL_BYTES_PER_NONCE)

def meter_bal_code(tx_env, address, code):
    meter_bal_data(tx_env, len(code))      # every deploy is metered in full
    tx_env.metered_code.add(address)
```

`meter_bal_data` MUST be called after the opcode's execution-gas charge has succeeded and BEFORE the matching BAL insertion or state mutation. An operation that cannot pay its execution gas meters nothing, and an `OutOfGasError` at the metering step aborts before any unpaid BAL byte exists. Each item is metered once, when it first becomes possible for the transaction to leave it in the BAL, and no charge is ever taken back at runtime (see [Reverts](#reverts) and [Repeated writes to the same slot](#repeated-writes-to-the-same-slot)). The admitted count is therefore an upper bound on the transaction's actual BAL contribution; only deployed code is metered per deploy rather than once per account, because a later deploy to the same address can be longer than an earlier, reverted one.

### Static floor seed

The tx-content portion of the floor (calldata, access-list entries, authorization tuples, blob versioned hashes) is defined by [EIP-8131](./eip-8131.md) as `tx_floor`. This EIP adds the per-auth BAL contribution that arises when an authorization is processed:

```
auth_bal_bytes = BAL_BYTES_PER_ADDRESS     #  20: authority address
               + DELEGATION_CODE_BYTES     #  23: delegation marker
               + BAL_BYTES_PER_NONCE       #   8: authority nonce

static_floor = tx_floor + FLOOR_GAS_PER_BYTE * auth_bal_bytes * num_authorizations
```

`tx_env.static_floor` holds this value and `tx_env.floor_gas_used` is initialised to it (with `bal_data_bytes = 0`) at the start of execution. The per-auth term covers each authorization's worst-case BAL contribution statically, so `set_delegation` (which runs before the EVM's OOG handler) never meters at runtime.

Per-transaction accounting always adds further BAL entries that no opcode places there: sender, coinbase, and top-level target addresses; sender and coinbase balances; sender nonce; recipient balance for a top-level value transfer; top-level creation target nonce; and an optional top-level EIP-7702 delegated target. These total at most 184 bytes, fully covered by the `TX_BASE / FLOOR_GAS_PER_BYTE = 328` bytes of headroom already in `TX_BASE`.

### Runtime data metering

Each trigger meters the byte count below before the corresponding BAL entry is added and after the opcode's execution-gas charge. Address and storage-key touches use `meter_bal_address` and `meter_bal_storage_key`; storage values use `meter_bal_storage_value`; balances and nonces use `meter_bal_balance` and `meter_bal_nonce`; deployed code uses `meter_bal_code`. These first-touch sets are independent of EVM warmness: an address or storage key pre-warmed by an [EIP-2930](./eip-2930.md) access list is still metered when execution first touches it, because EIP-7928 then adds it to the BAL.

| Trigger | Bytes added |
|---|---|
| First account touch in the transaction (`BALANCE`, `EXT*`, `CALL*`, `SELFDESTRUCT` beneficiary, `CREATE`/`CREATE2` deployed address) | 20 |
| First storage-key touch in the transaction (`SLOAD`, `SSTORE`) | 32 |
| `SSTORE` with `current == original` and `new != original`, if the `(storage_address, key)` pair has not been metered | +32 |
| `CALL` with non-zero value to a different account: caller and recipient, each if not yet in `metered_balances` | up to 64 |
| `SELFDESTRUCT` with non-zero balance to a different beneficiary: originator and beneficiary, each if not yet in `metered_balances` | up to 64 |
| `CREATE` / `CREATE2` before incrementing the creator's nonce, if the creator is not yet in `metered_nonces` | 8 |
| `CREATE` / `CREATE2` after the collision check, if the new contract is not yet in `metered_nonces` | 8 |
| `CREATE` / `CREATE2` with non-zero endowment: creator and new contract, each if not yet in `metered_balances` | up to +64 |
| Successful top-level contract creation, `CREATE`, or `CREATE2` deploy, just before `set_code` | `len(deployed_code)` |

EIP-7702 delegations are covered by the static `auth_bytes` term. `CALLCODE`, `DELEGATECALL`, and `STATICCALL` transfer no value out of the executing account and therefore add no balance bytes.

The 32 storage-value bytes are metered at most once per slot per transaction. Before mutating storage, every `SSTORE` with `current == original` and `new != original` MUST call `meter_bal_storage_value(tx_env, storage_address, key)`; the helper returns without charging if the pair was already metered. Here, `storage_address` is the account whose storage the current execution context modifies; for `CALLCODE` and `DELEGATECALL`, it is not the account whose code is executing. Balance and nonce bytes are likewise metered at most once per account. None of the sets is rewound and no charge is taken back at runtime, even if a later `SSTORE` restores the original value or the frame that made the change reverts: if the first changing write reverts, its retained charge covers any later committed change to the same slot; if a restoring write reverts, the charge still covers the earlier change that reappears in the BAL. The over-count is corrected at [settlement](#final-charge), not during execution.

### Final charge

The admitted floor decides only whether execution may continue. The final charge settles on the bytes the transaction actually leaves in the BAL. When execution completes, before gas is settled, clients compute `settled_bal_bytes` from the metered sets and the state at that point, comparing against the same pre-transaction values EIP-7928 uses to build the transaction's BAL entries:

| Metered item | Settled bytes |
|---|---|
| Address in `metered_addresses` | 20 (EIP-7928 keeps accessed addresses across reverts) |
| Storage key in `metered_storage_keys` | 32 (EIP-7928 keeps accessed keys across reverts) |
| Slot in `metered_storage_values` | 32 if its value differs from its pre-transaction value, else 0 |
| Account in `metered_balances` | 32 if its balance differs from its pre-transaction balance, else 0 |
| Account in `metered_nonces` | 8 if its nonce differs from its pre-transaction nonce, else 0 |
| Account in `metered_code` | `len(code)` if its code differs from its pre-transaction code, else 0 |

```
settled_floor = static_floor + settled_bal_bytes * FLOOR_GAS_PER_BYTE
tx.gasUsed    = max(execution_gas_used, settled_floor)
```

Every settled item was metered, and no item settles for more than it was metered, so `settled_floor <= floor_gas_used <= tx.gas` whenever execution completes. Transaction validation continues to require `tx.gas >= max(intrinsic, static_floor)`.

### System transactions and withdrawals

System-contract calls ([EIP-2935](./eip-2935.md), [EIP-4788](./eip-4788.md), [EIP-7002](./eip-7002.md), [EIP-7251](./eip-7251.md)) and withdrawals do NOT consume from a per-transaction floor. Their BAL bytes are absorbed by the existing EIP-7928 block-level buffer `bal_items <= block_gas_limit / ITEM_COST`.

## Rationale

### Floor side, not intrinsic side

Raising execution charges would penalise every user, including ones who never bypass. Charging on the floor only bites when execution is too cheap to cover the floor, which is exactly the bypass case.

A pure intrinsic surcharge also fails to cap the block at `gas_limit / 64`: for any added per-`SLOAD` cost `X`, the optimum bypass still yields `B = gas_limit / 64 + 24 · gas_limit / (2100 + X)` bytes, with the residual only vanishing as `X` grows large. Floor-side charging gives a closed bound directly.

### Runtime extensions can bind

Runtime contributions are checked against `tx.gas` because they can make the floor bind even when execution gas would not. Representative cases are:

| Trigger | Floor extension | Min execution charge |
|---|---:|---:|
| First account touch, cold | 1,280 | 2,600 |
| First account touch, pre-warmed by [EIP-2930](./eip-2930.md) | 1,280 | 100 |
| First storage-key touch, cold `SLOAD` | 2,048 | 2,100 |
| First storage-key touch, pre-warmed `SLOAD` | 2,048 | 100 |
| `SSTORE` (cold, zero → non-zero) | 4,096 | 22,100 |
| `CALL` with non-zero value | 4,096 | 9,000 |
| `SELFDESTRUCT` with non-zero balance, beneficiary already metered | 4,096 | 5,000 |
| `SELFDESTRUCT` with non-zero balance, warm beneficiary first touched | 5,376 | 5,000 |
| Successful `CREATE` / `CREATE2`, no endowment/code (address and two nonces) | 2,304 | 32,000 |
| Deployed code (per byte) | 64 | 200 |

A pre-warmed [EIP-2930](./eip-2930.md) entry is charged once for its bytes in the transaction and again when execution first touches it and EIP-7928 copies it into the BAL. The warm execution charge can be lower than this second floor contribution. A positive-balance `SELFDESTRUCT` to a warm, not-yet-metered beneficiary likewise adds the 20-byte beneficiary address plus two 32-byte balances: `84 × 64 = 5,376` floor gas against a 5,000 execution-gas charge. The pre-mutation runtime check handles these cases directly.

The main high-volume case remains a static seed defined by [EIP-8131](./eip-8131.md) (calldata, access-list entries, auths, blob hashes) that is already close to `tx.gas`; that is the calldata + `SLOAD` bypass this EIP targets.

### One per-byte rate

Pricing every BAL byte at the same `FLOOR_GAS_PER_BYTE` as non-zero calldata makes the worst case invariant to the attacker's choice: calldata, auths, storage keys, addresses, code, and balances all yield `1/64` bytes per gas at the floor. The optimum collapses to `B = gas_limit / 64`.

### Admit on an upper bound, settle on the actual bytes

The meter has two jobs, and they want different rules. The runtime check exists so that a transaction can never commit a BAL byte it cannot pay for, so the admitted count must bound what the transaction could still leave in the BAL at every point, under any later sequence of reverts. The tightest rule with that property counts each item once, at the first moment it becomes possible, and never takes it back: a slot can hold at most one post-value, so a second departure from the original value counts bytes that cannot exist, and a runtime credit for a restoring write is unsafe because that write may itself sit in a frame that later reverts, by which time the freed headroom can have been spent on a key or address that survives the revert. Metering before the insertion guarantees every BAL byte is accounted for, and an out-of-gas at the metering step aborts before the matching insertion.

The final charge asks a different question: what did the transaction actually put in the BAL. That answer is already computed. EIP-7928 builds the transaction's entries by comparing its final state against its pre-transaction state, and the BAL hash is part of the header, so every client holds this diff. Settling on it charges a restored slot no value bytes, a balance change in a reverted frame nothing, and a deployment in a reverted frame nothing, without a single journaled credit in the EVM. The shape matches execution gas exactly: a transaction must hold gas for the gross cost and pays the net at the end. The per-transaction [block-size bound](#block-size-bound) becomes exact rather than a deliberate over-count.

### Per-auth coverage is static

`set_delegation` runs outside the EVM's exception handler. A runtime `meter_bal_data` raising `OutOfGasError` there would propagate uncaught and crash block processing. Folding the worst-case 51 BAL bytes per auth (on top of the 108-byte tuple priced by EIP-8131, for 159 B total) into the static floor lets `set_delegation` mutate state freely: any transaction whose `tx.gas` cannot cover it has already been rejected at validation.

### Counter, not a reservation

The runtime mechanism does not deduct gas from the execution budget or pre-commit any gas. `meter_bal_data` only increments the explicit byte counter (`bal_data_bytes`) and the derived accumulator (`floor_gas_used`), and checks that the admitted floor remains `≤ tx.gas`. Execution gas accounting is untouched. At the end, `tx.gasUsed = max(execution_gas_used, settled_floor)`; the admitted floor never appears in the charge, it only decides whether execution may continue.

### `max(execution, floor)` preserved

The EIP-7623 / EIP-8131 charging shape is unchanged; only the floor side gains a BAL component that is admitted at runtime and charged at settlement. Transactions whose execution exceeds the floor pay exactly as today.

## Backwards Compatibility

Hard fork.

The static floor takes `tx_floor` from EIP-8131 and adds 51 BAL bytes per authorization, plus the settled BAL bytes contributed during execution. The combined floor per auth is `(108 + 51) × 64 = 10,176` gas, still below the `PER_EMPTY_ACCOUNT_COST = 25,000` intrinsic per auth. Static transaction validation changes only when this combined static floor dominates. During execution, a runtime BAL extension can cause `OutOfGasError` when the admitted floor exceeds `tx.gas`, including for pre-warmed first touches, and the settled floor can raise `gasUsed`. A bare ETH transfer stays at 21,000.

Mainnet sample (1,500 random blocks, 441,271 transactions, 20,000 of those traced for BAL bytes, May 2026): EIP-8131 alone makes 3.24% of transactions pay more (+3.29% gas). EIP-8279 adds another 0.54 pp and +0.77 pp, for a combined 3.79% / +4.06%. In the sampled transactions, the BAL piece did not bind on its own: per-tx BAL bytes average 120-200 B after `TX_BASE` absorption, under 13 k floor gas, well below typical execution gas. EIP-8279's main job is to close the calldata + `SLOAD` bypass when paired with EIP-8131, not to add a broadly binding standalone floor.

Wallets and `eth_estimateGas` MUST compute the new static floor (including the per-auth term) and, when tracing execution, meter the runtime BAL bytes for first touches, value-bearing calls, and deployments alongside intrinsic gas. The gas limit must cover the admitted floor; the charge is the settled floor, which can be lower.

## Test Cases

### Bare ETH transfer

`tx.to = recipient`, `tx.value = 1 ether`, `tx.data = b""`.

- `static_floor = TX_BASE = 21,000` gas.
- Minimum `tx.gas = 21,000`, unchanged.

### Cold `SLOAD` bypass attempt

Before this EIP, an idealized worst-case mix at `gas_limit = 60M` uses 937,171 non-zero calldata bytes plus 21,421 cold `SLOAD`s in one transaction, for 1,622,643 logical content bytes.

- Static seed: `21,000 + 64 × 937,171 = 59,999,944`.
- Per cold `SLOAD` floor extension: `32 × 64 = 2,048`.
- With this EIP, the first cold `SLOAD` raises the floor above `gas_limit`; all 21,421 would raise it to `59,999,944 + 21,421 × 2,048 = 103,870,152`.
- The largest feasible metered content is `floor((gas_limit - TX_BASE) / 64) = 937,171` bytes. Including the implicit per-transaction bytes covered by `TX_BASE`, the bound remains `gas_limit / 64 = 937,500` bytes.

### Pre-warmed storage-key touch

The transaction's [EIP-2930](./eip-2930.md) access list contains `(contract, slot)`, and execution then performs `SLOAD(slot)`.

- EIP-8131 meters the 20-byte address and 32-byte key in the transaction's static floor.
- The key is EVM-warm, but its first actual `SLOAD` calls `meter_bal_storage_key`, adding another 32 bytes for the BAL copy. The account address is covered separately when first touched or by the implicit per-transaction accounting above.
- Repeated touches in the transaction add nothing.

### Cold `SSTORE` (zero → non-zero)

Single cold `SSTORE` writing a non-zero value to an empty slot.

- Metered: `32 (key) + 32 (value) = 64` BAL bytes → `4,096` gas folded into `floor_gas_used`.
- The `SSTORE` execution charge is 22,100, larger than the 4,096 floor extension, so this trigger remains execution-dominated.

### Net-zero `SSTORE` round-trip

Slot starts at original value `O`; the transaction writes `X ≠ O` then writes `O` again.

- First `SSTORE` (`O → X`): `32 (cold key) + 32 (value)` metered.
- Second `SSTORE` (`X → O`): slot is back at its pre-transaction value, a no-op write under EIP-7928; the `32` value bytes stay admitted.
- Admitted: `64`. Settled: `32`, the key only, because the slot's final value equals its pre-transaction value. The BAL records the slot in `storage_reads` with no `storage_changes` entry, and the charge matches.

### Repeated distinct writes

Slot starts at `O`; the transaction writes `A`, then `B`, then `C` (all distinct, `C ≠ O`).

- The `32` value bytes are metered once, on the `O → A` transition; `A → B` and `B → C` add nothing.
- Admitted and settled: `32 (key) + 32 (value) = 64`, matching the single post-value `C` the BAL records.

### Repeated departures from the original value

Slot starts at `O`; the transaction writes `A`, restores `O`, then writes `B` (`A != O`, `B != O`).

- `O → A` meters the `32` value bytes and adds the slot to `metered_storage_values`.
- `A → O` takes nothing back; `O → B` sees the slot already in `metered_storage_values` and adds nothing.
- Admitted and settled: `64`, matching the single post-value `B` the BAL records.

### Restoring write inside a reverted frame

The top frame writes `O → X`, then `DELEGATECALL`s into a frame that writes `X → O` and reverts.

- `O → X` meters the key and value; the child's restoring write adds nothing and takes nothing back.
- After the revert the slot holds `X` again. Admitted and settled: `64`. A runtime credit for the child's restoring write would have left the reappearing `X` unpaid.

### Changing write inside a reverted frame, then committed

A child frame writes `O → X` and reverts; the top frame then writes `O → Y`.

- The child's write meters `32 (key) + 32 (value)`; the slot stays in `metered_storage_values` across the revert, so `O → Y` adds nothing.
- Admitted and settled: `64`, matching the single post-value `Y` the BAL records.

### Reverted `CALL` with value

`CALL` with `value > 0` to a recipient that reverts.

- Caller and recipient enter `metered_balances`; `64` balance bytes are admitted before `generic_call`.
- Both balance changes are discarded on revert (per EIP-7928); neither `bal_data_bytes` nor the sets are rewound.
- Admitted: `64` balance bytes. Settled: `0`, since both balances equal their pre-transaction values. The BAL holds no balance entry for either account from this transaction, and the charge matches.

### `CREATE` inside a reverted frame

A child frame performs `CREATE` with no endowment, deploying `code`, and then reverts.

- Admitted: `20` (new address) `+ 8` (creator nonce) `+ 8` (new contract nonce) `+ len(code)`.
- Settled: `20`. The deployed address stays in the BAL as an accessed address; the creator's nonce, the new contract's nonce, and the code are discarded with the revert and settle to zero.

## Security Considerations

### Block-size bound

Per transaction, every byte the tx contributes to the block (tx blob + BAL) is accounted for at the floor rate via either the static seed or a settled runtime contribution, with implicit per-tx bytes covered by `TX_BASE`:

```
block_bytes_per_tx × FLOOR_GAS_PER_BYTE  ≤  settled_floor  ≤  tx.gasUsed
```

The admitted floor bounds the settled floor at every point of execution, `settled_floor ≤ floor_gas_used ≤ tx.gas`, which is what lets the runtime check stop a transaction before it commits a byte it cannot pay for. Summing across user transactions:

```
sum(block_bytes) ≤ sum(tx.gasUsed) / 64 ≤ block_gas_limit / 64
```

System-contract and withdrawal contributions are bounded separately by the EIP-7928 block-level `ITEM_COST` buffer (~1,428 items at a 60M gas limit), sized to absorb existing system contract use.

### Reverts

Accessed addresses and storage keys persist in the BAL across reverts (per EIP-7928); balance, nonce, code, and storage-value changes from reverted frames are discarded. At runtime, neither `bal_data_bytes`, `floor_gas_used`, nor any of the metering sets is rewound for discarded entries, and no charge is taken back: the admitted floor only ever grows, so no revert can free headroom that was already spent on bytes the revert leaves in place. At settlement, every discarded entry settles to zero. The transaction is charged for the bytes it left in the BAL and could never have left more than it admitted.

### Repeated writes to the same slot

The 32 storage-value bytes are admitted at most once per slot per transaction. Repeated distinct writes (`O → A → B → C`) and repeated departures from the original value (`O → X → O → Y`) therefore admit 32 value bytes total, not 32 per write or departure. Since `metered_storage_values` is not rewound, a charge from a reverted frame also covers any later committed change to the same slot. At settlement the slot pays its value bytes exactly when its final value differs from its pre-transaction value, so a net-zero round-trip (`O → X → O`) admits 32 value bytes and settles none.

### Gas estimation

Wallets and `eth_estimateGas` MUST simulate the admitted `floor_gas_used` alongside intrinsic and execution gas, since `tx.gas` must cover it. Without it, estimates for floor-bound transactions are too low; a transaction may pass static validation and then halt with `OutOfGasError` when a runtime extension exceeds `tx.gas`. The settled floor is at most the admitted floor and is what the transaction pays.
